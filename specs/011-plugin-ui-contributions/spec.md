# Feature Specification: Plugin UI Contributions — Panels, Overlays, Shortcuts, Settings, Notifications

**Feature Branch**: `feature/011-plugin-ui-contributions`

**Created**: 2026-09-20

**Status**: Clarified (2026-09-20, specify pass + clarify pass) — no open [NEEDS CLARIFICATION] markers, no human escalations; ready for `/speckit-plan`

**Input**: User description: "Let a plugin show the user something and give them controls — a panel, drawings on the waveform, keyboard shortcuts, a settings page, a notification — while the host stays in charge of rendering, theming, accessibility, and safety. Plugins never inject markup, styles, or scripts into the host; everything is declarative. With `ui.panel` a plugin registers a layout built from host widgets: label, button, toggle, slider, knob, list, text, marker list, meter. The host renders it, applies the active theme tokens, and makes every widget keyboard-operable with an accessible name taken from the plugin's label; a widget without a label is refused at registration with the widget path reported. Panels are always attributed with the plugin's name and icon, can be docked or floated, and can be closed or disabled by the user. Plugins update widget values through the API and receive interaction events back. With `ui.overlay` a plugin draws lines, regions, labels, and glyphs on the waveform in track-time coordinates; the host re-projects them on zoom and scroll. With `ui.shortcuts` a plugin registers actions (trigger or continuous) with default bindings, namespaced by plugin identifier so identifiers cannot collide; the host owns binding and conflict handling, and delivers `action_invoked` with the source (keyboard, UI, later MIDI) and value. Plugin shortcuts appear in the central shortcut map; a conflict with a host or another plugin's binding leaves the plugin's shortcut inactive until the user resolves it, with bundled plugins winning by default over community ones. With `ui.settings` a plugin registers a declarative settings schema the host renders inside Settings and persists, sending `settings_changed`. With `ui.notify` a plugin posts non-blocking notifications, attributed to it and rate-limited to 6 per minute. Acceptance: when a plugin registers a panel with a slider labeled \"Tempo\", a screen-reader user hears \"Tempo, slider\" and can adjust it by keyboard. When a plugin requests the `L` shortcut already used by the host's loop toggle, the map flags the conflict and the plugin's binding stays inactive. When a plugin posts a seventh notification within a minute, it receives `rate_limited`. When the user switches from light to dark theme, plugin panels update without any plugin code running."

**Source**: [ModPlayer-Software-Specification.md](../../docs/ModPlayer-Software-Specification.md) — Part 5 §6.5 UI, Part 5 §7 UI contribution rules (PL-7.1–7.4), Part 5 §4 Permission catalog (`ui.panel`, `ui.overlay`, `ui.shortcuts`, `ui.notify`, `ui.settings`), Part 5 §2 Plugin package (PL-2.1 icons/resources, PL-2.2 `contributions` manifest field), Part 5 §5 Events (`action_invoked`, `settings_changed`), FR-7.4 Conflicts and ordering (FR-7.4.1), FR-11.1 Settings (FR-11.1.3), FR-14.1 Notifications (FR-14.1.1–.3), FR-4.1.3 (waveform plugin overlays), Part 9 §3 User interface layer (AR-19 Plugin Panel Host), EC §6 Plugins (EC-6.8, EC-6.9, EC-6.19), NFR §4 Security (NFR-4.7), NFR §6 Accessibility (NFR-6.3), Part 2 §3 Edge users (screen-reader user, multi-monitor performer). **Prerequisites**: [009-plugin-runtime-and-permissions](../009-plugin-runtime-and-permissions/spec.md) — the plugin runtime, the Capability Gateway, the permission catalog and refusal shape, per-plugin storage (`state.plugin`), and the notification budget default (PL-8.1, 6/min) this slice activates for `ui.notify`; [007-keyboard-actions-and-shortcuts](../007-keyboard-actions-and-shortcuts/spec.md) — the Action & Binding service, the DM-14/DM-15 model (already namespace- and owner-aware per its own FR-016), and the shortcut map this slice extends with plugin-owned rows; [005-now-playing-waveform](../005-now-playing-waveform/spec.md) — the track-time coordinate space (FR-014) `ui.overlay` draws into; [001-walking-skeleton](../001-walking-skeleton/spec.md) — the theme system (System/Light/Dark), the notification area and severities, and the Settings category registry and search this slice renders into.

**Scope boundary**: Does not cover detaching panels to a second display, the developer console, or the permission approval sheet — only the contribution surface itself (`ui.panel`, `ui.overlay`, `ui.shortcuts`, `ui.settings`, `ui.notify`).

## Clarifications

### Session 2026-09-20 (specify pass)

Resolution ladder applied: (D) derived from an authoritative source, (A) assumed conventional default, consistent with 001–010. No item below met the materiality bar for human escalation.

- Q: Part 5 §6.5 says a panel widget interaction is delivered back to the plugin as "interaction events," but the Part 5 §5 events table names no such event (only `action_invoked` and `settings_changed` are new this slice) — what is it called and what does it carry? → A (A, naming convention consistent with the table's other `*_changed`/`*_invoked` events): a new, permission-less-beyond-`ui.panel` event, `panel_interaction`, carrying the panel id, the widget's path, and its new value; delivered only for a widget the user actually changed (button press, toggle flip, slider/knob commit, list selection) — never for a plugin's own `update_widget` call, and never for a `button` that instead names a target action (FR-008, which fires `action_invoked` instead).
- Q: Does `register_panel` take one panel per call, or can a plugin contribute several independent panels, and what happens on re-registration? → A (D, PL-2.2's `contributions` manifest field is plural — "panels, overlays, settings page" — and nothing bounds it to one): a plugin MAY register any number of independently dockable/floatable/closable panels, each identified by a panel id namespaced by the plugin's identifier; calling `register_panel` again with an id the plugin already used atomically replaces that panel's whole layout (never a partial merge).
- Q: PL-7.4 says a panel "can be closed or disabled by the user" — how does that differ from disabling the whole plugin, which 009 FR-012 already handles (it removes all of a plugin's UI)? → A (D, PL-7.4 speaks of the panel, not the plugin; 009's FR-012 teardown remains the only way a plugin's UI disappears because the plugin itself stopped): "close" hides an open panel for the rest of the running session only — it reappears at next launch. "Disable" is a separate, persisted per-panel visibility flag the user sets from that panel's own title-bar control or from its plugin's row in the Plugins list (009 FR-023); a disabled panel stays hidden across restarts until the user re-enables it from the same place. Both act only on the panel's visibility and are independent of, and unaffected by, the plugin's own enabled/disabled/suspended state.
- Q: Source §6.5 says panels "can be docked, floated, or detached," but this feature's own scope boundary excludes "detaching panels to a second display" — is "detach" a fourth placement or the excluded one? → A (D, the scope-boundary sentence names exactly "detaching... to a second display," and the Edge-users table ties "detachable panels" to the "second screen" need): "detach to a second display" is the excluded state; this slice ships exactly the two placements the prompt itself names — **docked** (attached inside the main window's layout, in a per-plugin persisted dock area alongside the Now Playing view) and **floated** (a movable, resizable overlay confined to the main window's own bounds, not a separate OS window). A panel opens docked by default. ~~Docked order among multiple panels is registration order, then plugin name~~ — **realigned by the clarify pass**: by owning plugin name, then that plugin's registration order (see below); manual reordering is not in this slice.
- Q: What does each host widget kind actually do, and what must a screen reader announce? → A (D, the prompt's acceptance text — "Tempo, slider" — fixes the pattern "label, kind"; A for the rest, conventional per-kind behavior): **label** — static text, non-interactive, its own text is both its content and its accessible name. **button** — momentary; activating it (click, or `Space`/`Enter` when focused) either fires `panel_interaction` or, if it names a target action (FR-008), routes through the Action & Binding dispatcher instead. **toggle** — boolean; announces state (on/off) with the label; flipping it (click, or `Space`) fires `panel_interaction`. **slider** and **knob** — numeric within a plugin-declared `[min, max]` and `step`; keyboard arrows move one step, Page Up/Down move ten (mirroring 001's volume slider), and the committed value fires `panel_interaction`; a knob differs from a slider only in on-screen affordance (rotary vs. linear), not in behavior. **list** — single-selection from a plugin-supplied item set; arrow keys move selection, `Enter`/selection fires `panel_interaction` with the chosen item. **marker list** — read-oriented, showing the plugin's own markers (styled like 006's marker list); selecting a row seeks to that marker's position and does not itself fire `panel_interaction`. **text** — a plugin-updatable, read-only text display (distinct from the static `label`); non-interactive but still requires a label describing what it shows (e.g., "Status"). **meter** — a read-only level display the plugin drives via `update_widget`; non-interactive, still requires a label (e.g., "Input level"). Every kind, interactive or not, requires the plugin-supplied label EC-6.19 refuses registration without (NFR-6.3).
- Q: Is there a bound on widgets per panel or panels per plugin, matching the project's convention of a fixed numeric cap on every plugin-facing collection (64 markers, 256 timers, 10 MB storage)? → A (A, same convention, chosen generously above any legitimate panel size): at most 100 widgets per panel; a `register_panel` call whose layout would exceed this is refused whole (`invalid_state`/`panel_widget_limit`), leaving any previously registered panel of that id unchanged. ~~No cap on the number of distinct panels a plugin may register~~ — **realigned by the clarify pass**: 16 panels per plugin (`invalid_state`/`panel_limit`), see below.
- Q: `ui.overlay` needs a numeric bound for the same reason — what is it, and what happens to a plugin's overlays across a track change? → A (A for the cap, D for lifecycle — PL-3.4 "on disable, suspend, or unload the host removes the plugin's UI contributions," and overlays are track-scoped by nature, drawn "in track-time coordinates"): at most 500 overlay primitives (lines, regions, labels, glyphs combined) registered per plugin at once; exceeding it is refused, `invalid_state`/`overlay_limit`, leaving previously registered primitives unchanged. A plugin's overlays are cleared automatically on track change (the plugin re-registers for the new track if it wants overlays there) and on the plugin's own disable/suspend/unload (PL-3.4); none persist across restarts. When multiple plugins overlay the same waveform region, they draw in plugin-registration order, above host markers and the active loop region and below the playhead.
- Q: A plugin's overlay glyph needs some visual asset — can it reference an arbitrary image or inline drawing instructions, which PL-7.1 ("no markup, styles, or scripts") would seem to forbid? → A (D, PL-2.1 already allows a plugin package to declare "optional UI resources (layouts, icons, localized strings)" verified with the rest of the signed package): a glyph MAY reference only an icon declared among the plugin's own package resources (verified and digest-checked at install like the rest of the package, 009-inherited NFR-4.4) or one of a small host-provided glyph set (plan-time detail); it MAY NOT reference an arbitrary URL, inline path data, or any other markup.
- Q: The prompt's acceptance line ("plugin requests the `L` shortcut already used by the host's loop toggle... plugin's binding stays inactive") describes host-beats-plugin, while EC-6.8 separately says two plugins colliding leaves "neither active... (bundled plugins win by default over community ones)" — are these the same rule or two different ones? → A (D, reading both together): ownership carries one of three tiers, **host** > **bundled plugin** > **community plugin** (community is modeled by this mechanism but unreachable until a later slice ships a non-bundled source, per 009's own Assumptions). When two colliding, enabled, currently-reachable bindings (007 FR-009/FR-010) belong to different tiers, the higher tier's binding keeps firing and the lower tier's is flagged inactive in the map automatically, with no user action required — this is the host-vs-plugin case the prompt's acceptance text describes. When both belong to the same tier (two bundled plugins, today's only reachable case), 007's existing symmetric rule applies unchanged: neither fires until the user changes or removes one of the two bindings — this is EC-6.8's "neither active... until resolved," and its "bundled wins over community" parenthetical becomes live only once a community source exists.
- Q: Does a plugin action's `enabled` flag (DM-14) track the owning plugin's health, the way 007 FR-012 already modeled `enabled` for a not-yet-built host feature? → A (D, 007 FR-012's own words: "reflects whether its owning host component currently supports it... This slice ships exactly two actions with `enabled: false` as the concrete instance" — plugin ownership is the mechanism's other half FR-016 named): yes. A plugin action's `enabled` is `false` whenever its owning plugin is disabled, suspended, or invalid — shown greyed in the shortcut map, excluded from conflict evaluation, never dispatched — and returns to `true` the moment the plugin's context becomes Active again (bindings and any user customization intact; conflicts re-evaluated at that moment, exactly as 007 FR-012 already specifies for the flag flipping either way). Uninstalling a plugin (unavailable for bundled, 009 FR-013) removes its actions and bindings entirely rather than merely disabling them.
- Q: `ui.settings` says the host "renders inside Settings and persists" a plugin's schema — persists where, and does the plugin need `state.plugin` too? → A (D, Constitution III "host primitives, plugin behaviors" plus Constitution X YAGNI — 009 already built exactly this per-plugin, atomically-written, 10 MB-capped store): the host persists every settings-page edit into the same per-plugin storage 009 FR-014 already built, subject to its existing 10 MB cap and atomic-write guarantee, without requiring the plugin to separately hold `state.plugin` — the host, not the plugin script, performs the write. A plugin MAY read its current settings values at any time via a read-only `get_settings()` call; there is no plugin-initiated write call in this slice (only the user, through the rendered page, changes a value), and every change delivers `settings_changed` naming the field(s) that changed.
- Q: What field kinds does a declarative settings schema support, and where does the resulting page live? → A (A, the smallest conventional set covering the prompt's own example categories — Section Loop's "snap to beat" toggle, Key & Tempo's numeric shift — plus string for free text): boolean, number (with `min`/`max`/`step`), string, and single-choice (a fixed option list) — matching the host widget vocabulary already defined for panels, so there is exactly one declarative field grammar in this feature, not two. Each schema renders as one page per plugin under **Settings › Plugins**, listed by plugin name, and its fields are reachable from Settings' existing search (001 FR-019) by field title. Settings › Plugins' own plugin-management content (permission summaries, the approval sheet) stays the placeholder 009 left it as; a plugin's settings page is additive to that category, not a replacement for it.
- Q: PL-8.1's notification cap is "6/min" — over what window, and does the 7th call queue or drop? → A (D, PL-8.1 "default"; A for the window shape, consistent with 009 FR-025's rate-limit style for other categories): a rolling 60-second window per plugin; the 7th and any further `notify` call within that window returns `rate_limited` immediately, shows nothing, and is never queued for later delivery (matching the prompt's own acceptance line and 009's "no host-side effect, not queued or retried" convention for every other rate limit).
- Q: PL-7.3 (plugin string localization with host-locale rendering and a fallback to the plugin's own default) is squarely Part 5 §7 and this feature's own Source line — does it need a working locale switch to matter in this slice? → A (D, 001 FR-018 and 007 FR-015 both already record "en-US is the only shipped locale... consistent with 001–00N"): this slice defines the mechanism (a plugin MAY declare per-string localized tables for panel/overlay/action/settings/notification text; the host resolves the active locale and falls back to the plugin's declared default) but, like every prior slice, ships only the en-US host locale, so no plugin string is shown untranslated in practice yet. The mechanism exists so a later localization slice needs no plugin-facing contract change.
- Q: All five `ui.*` refusals need to fit 009's closed six-code shape (`permission_denied`, `no_focus`, `invalid_state`, `not_found`, `rate_limited`, `budget_exceeded`) — how do the new caps and the unlabeled-widget case map onto it? → A (D, 009 FR-008's own precedent — "a host-side capacity limit... MUST return `invalid_state`" — plus its ordering rule, permission checked first): a call made without the relevant `ui.*` permission returns `permission_denied` before anything else is checked. An unlabeled widget, a panel over its widget cap, or an overlay set over its primitive cap each return `invalid_state` with `reason` `unlabeled_widget`, `panel_widget_limit`, or `overlay_limit` respectively, and `message` a user-legible sentence naming the offending widget's path where applicable (EC-6.19). A seventh-in-a-minute `notify` returns `rate_limited`. No `ui.*` call in this slice produces `no_focus`, `not_found`, or `budget_exceeded`.

Same ladder: (D) derived from an authoritative source, (A) assumed conventional default. Every item below is encoded in the Requirements section; none met the materiality bar for human escalation. Two specify-pass decisions are realigned here (panel count cap; docked order) — each is marked.

- Q: What is a panel's layout structure, and what exactly is the "widget path" EC-6.19 reports? → A (A, Constitution X — the source names nine widget kinds and no container): a panel layout is a **flat, ordered list** of widgets the host stacks vertically inside the panel body (vertically scrollable when taller than its placement allows); there are no container or grouping nodes in this slice (a `label` widget serves as a section heading). Every widget carries a plugin-supplied `id` (`[a-z][a-z0-9_]{0,63}`, unique within the panel); the **widget path** is that `id`. A refusal `message` always names the widget positionally as `widgets[<zero-based index>]` and, when an `id` is present, appends it — so an unlabeled, id-less widget is still locatable. A missing, malformed, or duplicate `id` is refused whole, `invalid_state`/`invalid_widget_id`, naming the positional path. `register_panel(panel_id, title, widgets)` also takes a required panel `title` (≤ 64 characters) shown in the header beside the plugin attribution, since a plugin may own several panels.
- Q: Per-kind value grammar for `update_widget` and `panel_interaction` — what is accepted, what is refused, and when does a slider/knob/list "commit"? → A (A, conventional per-kind behavior; refusal shape per 009 FR-008): `toggle` — boolean. `slider`/`knob` — number; registration requires `min < max`, `step > 0`, and an optional initial `value` in range (default `min`); `update_widget` with a value outside `[min, max]` or of the wrong type is refused `invalid_state`/`invalid_value` (never clamped). Pointer drags deliver **one** `panel_interaction` on release (no per-pixel stream); each keyboard step (arrow = one `step`, Page Up/Down = ten) commits immediately and delivers one event; the announced value text is the number. `list` — `items` is a plugin-supplied list of `{ id, label }` (≤ 256 items); selection **follows focus** (arrow key or click changes the selection and delivers `panel_interaction` with the item `id`; `Enter` is a no-op), and `update_widget` accepts either an item `id` (`not_found` if unknown) or `{ items, selected? }` to replace the item set. `text` — string ≤ 1,024 characters. `meter` — number, **clamped** to `[0.0, 1.0]` (a streamed display, so clamping rather than refusal is the convention). `label`, `button`, and `marker list` are not updatable: `update_widget` on them is refused `invalid_state`/`not_updatable`; a label or button text is fixed at registration (re-register the panel to change it). Widget labels are ≤ 256 characters. No widget has a plugin-settable `disabled`/hidden state in this slice (Constitution X).
- Q: Which markers does a `marker list` widget show, and does it need a `markers.*` grant? → A (D, 006 DM-6 `owner` + 009 FR-018 marker ownership): it lists the current track's markers whose `owner` is the plugin's own identifier, sorted by position, updating live as they change; it needs only `ui.panel` (the host already knows ownership — no `markers.read` is required, and a plugin without `markers.write` simply shows an empty list). Selecting a row seeks as a **host user command** (FR-3.3.2 — no plugin permission, no transport-focus check), which is why it never delivers `panel_interaction`. The widget is read-only: renaming, recoloring, and deleting stay on 006's own marker list.
- Q: Is there a cap on panels per plugin? The specify pass said "no cap" — does that hold against the project's every-collection-is-capped convention? → A (A; **realigns** the specify-pass item): at most **16 panels per plugin** (`invalid_state`/`panel_limit`); the plugin's CPU/memory budgets bound render cost, but an uncapped dock column is a user-facing clutter vector the convention exists to prevent. 16 is far above any legitimate need.
- Q: Where do panels live, when are they visible, and how does the dock order work? The specify pass said "registration order, then plugin name," which is not a well-defined sort. → A (A; **realigns** the docked-order item; placement consistent with 008's Effect Chain panel and 010's Transport panel, both Now Playing-scoped): the **dock area** is a fixed-width column at the right edge of the **Now Playing view**, hidden when it holds no visible panel, stacking docked panels vertically (scrolling when they overflow). Docked panels are ordered **by owning plugin name, then by that plugin's registration order** (stable across restarts; not user-reorderable in this slice). Docked and floated plugin panels are visible only while the Now Playing view is shown; they are retained (state intact) while another view is shown. A floated panel opens at its docked size, centered over the Now Playing content; minimum size 200 × 120 px; on restore its persisted position/size is clamped into the current window bounds. Floated panels render above the Now Playing content and below the notification area and any sheet.
- Q: Where are per-panel placement and visibility persisted, and how does a user reopen a panel they closed this session? → A (A, 007 FR-013 convention — user customizations go in `settings.toml`): each panel's placement (`docked` | `floated`), floated position/size, and `disabled` flag persist in `settings.toml` under a `[plugin_panels]` table keyed `"<plugin-identifier>/<panel-id>"`, using that file's existing write/read rules; an entry for a panel that is not currently registered is retained dormant and applied when it registers again. The plugin's row in the Plugins list (009 FR-023) gains, per registered panel, a **Show/Hide** (this session — reopens a closed panel) and **Enable/Disable** (persisted) control, in addition to the panel's own title-bar Close and Disable controls. The plugin receives **no event** for close, disable, float, or dock (Constitution X).
- Q: Source §5.4 step 3 says "Panel Host replaces its panels with a placeholder" when a plugin hangs, but PL-3.4 says the host "removes the plugin's UI contributions" on disable/suspend/unload — which applies? → A (D, both read together — a suspended plugin is restartable, a disabled one is not): on **suspend**, each of the plugin's visible panels keeps its frame and placement and shows a placeholder body — the plugin's name, "suspended," the cause, and **Restart**/**Disable** controls mirroring 009 FR-011's notice — with its widgets removed; on **disable**, unload, or auto-disable, the panels are removed entirely. Overlays are cleared, actions are greyed (FR-013), and the settings page is hidden in both cases. When the same identifier's context calls `ready()` again, placeholders are removed; panels reappear only when the plugin re-registers them.
- Q: 010's auto-on-interaction clarification defers to this slice: "once 011 ships plugin-contributed transport widgets, using one of those becomes an equivalent qualifying interaction (that slice's job to wire)." What qualifies? → A (D, 010 Clarifications; source §5.3 "the request came from a user interaction with X's panel"): a `request_focus()` call the plugin makes **synchronously inside its handler** for a `panel_interaction` event or an `action_invoked` event (either source) is a user-interaction-originated request. Under **auto on interaction** it is granted immediately, revoking any current plugin holder per 010's existing hand-over sequence; under **manual** and **first request wins** 010's rules apply unchanged (recorded, not granted by the interaction). Merely interacting with a plugin's widget never moves focus by itself — the plugin must ask, and must hold `transport.control`, exactly as in 010.
- Q: While a plugin panel widget has keyboard focus, which keys reach it and which fire host shortcuts? How does keyboard focus reach the dock at all? → A (D, 007 FR-019's single-consumer precedence): plugin widgets participate in step (2) exactly like host widgets — a focused widget consumes only the keys its kind handles (`Space`/`Enter` on a button, `Space` on a toggle, arrows and Page Up/Down on a slider/knob, arrows on a list/marker list); every other key falls through to registered actions. No panel widget is a text field, so none swallows keys. The dock column follows the Now Playing view's existing controls in `Tab` order; each panel is one focus group: title-bar controls (float/dock, close, disable) first, then its widgets in layout order.
- Q: A plugin action needs the DM-14 fields 007 requires that the source does not mention — activation `scope` and `repeats_while_held` — and a binding grammar; what are they, and what if a default binding is one 007 would reject? → A (D, 007 FR-001/FR-007/FR-018/FR-019; A for the defaults): every plugin action has scope **`app`** (no plugin-declared scope in this slice; a later API minor may add one); `repeats_while_held` is an optional registration flag, default `false`; `default_binding` is optional (an action may ship unbound, 007 FR-008) and uses the same platform-neutral encoding 007 persists. A default binding 007's capture would reject (lone modifiers, `Tab`/`Shift+Tab`, `Esc`, a macOS `Control` chord) or that cannot be parsed registers the action **unbound** with a console warning — the call is not refused. At most **64 actions per plugin** (`invalid_state`/`action_limit`); re-registering an id replaces its label, kind, flag, and default binding while any user override is kept. For a `continuous` action invoked from the keyboard or a panel button, `value` is the fixed step `1.0` (007 FR-001; MIDI supplies real values later).
- Q: 007 FR-013 drops a persisted `[keybindings]` entry "naming an unknown action id" — a plugin's actions are registered only after its context loads, so its user overrides would be dropped at every launch. → A (D, 007's own intent that customizations survive restarts; A for the mechanism): an entry whose action id is **not** in the `host.` namespace is never treated as unknown — it is retained dormant (not shown, not evaluated) and applied the moment an action with that id registers. Only `host.`-namespaced unknown ids and unparseable combinations trigger 007's `keybindings-invalid-entries` warning. A plugin that is disabled at launch therefore has no rows in the shortcut map until it is enabled; a plugin disabled or suspended mid-session keeps its rows greyed (FR-013) until the session ends.
- Q: What are the overlay calls, the primitive attributes, and the color/placement rules under PL-7.1's "no styles"? → A (A, smallest grammar that serves Chord Chart / Section Loop): `add_overlays(primitives)` is additive, keyed by a plugin-supplied primitive `id` (same grammar as widget ids; re-adding an id replaces that primitive in place), plus `remove_overlays(ids)` (`not_found` for an unknown id) and `clear_overlays()`. The 500 cap is evaluated on the count after the call; an exceeding call is refused whole. Primitives: `line { id, at }`, `region { id, from, to }` (`from < to`), `label { id, at, text ≤ 64 chars }`, `glyph { id, at, icon }`; positions are **track-time milliseconds** (006's marker unit), non-negative integers (negative or non-finite → `invalid_state`/`invalid_value`); a position beyond the current best-known duration is accepted and simply not drawn until the duration allows (005's streaming-duration fallback). Each primitive takes an optional `color` from the closed host token set `accent` (default), `secondary`, `positive`, `warning`, `neutral`, resolved through the active theme; no other style input exists. The host owns vertical placement: lines and regions span the waveform height (regions translucent); glyphs and labels sit in a plugin lane above the waveform. Lines, regions, and glyphs render on **both** the overview and the detail view; labels render on the detail view only. Overlays are non-interactive and not focusable, and are not individually exposed to assistive technology in this slice — a plugin conveys the same information accessibly through a panel (`list`/`marker list`).
- Q: How does a manifest declare the plugin icon (PL-7.4) and the glyph icons (PL-2.1), and what formats are safe under NFR-4.7? → A (D, PL-2.1 "optional UI resources (icons)"; A for format — SVG can carry script, so it is excluded): the manifest gains an optional `icon` (package-relative path to a **PNG**, square, ≤ 128 × 128 px, ≤ 256 KB) and an optional `glyphs` map (≤ 32 entries, key `[a-z][a-z0-9_]{0,31}` → package-relative PNG ≤ 32 × 32 px, ≤ 64 KB). An overlay `glyph.icon` names either a `glyphs` key or one of the host glyph set `dot`, `flag`, `note`, `chord`, `star`, `warning`. An `icon`/`glyphs` entry that is missing, not PNG, or over-limit is **not** a manifest error: the plugin loads, the host shows its generic plugin glyph in place of the bad asset, and a console warning names the file. A manifest's `contributions` field stays descriptive (recorded, per 009 FR-001); runtime `register_*` calls are the sole source of truth and are not cross-checked against it in this slice.
- Q: What is the exact settings-schema grammar, where do values live inside 009's store, and what happens to stale or invalid stored values? → A (A, one field grammar mirroring the panel widget vocabulary; D for storage — 009 FR-014): `register_settings(fields)` takes ≤ 100 fields (`invalid_state`/`settings_field_limit`), each `{ id, kind, label, description?, default, … }` with the same `id` grammar as widgets; `boolean`; `number { min, max, step }` (`min ≤ default ≤ max`, `step > 0`); `string` (≤ 1,024 characters, the host input stops accepting beyond that); `choice { options: [{ id, label }] }` (1–64 options, `default` ∈ options). A malformed schema is refused whole, `invalid_state`/`invalid_schema`, naming the field path as `fields[<index>]`. Values live in a host-owned **`settings` scope** of the plugin's own per-plugin store — counted against its 10 MB cap, written atomically, **not** addressable through `state.plugin` get/set. `get_settings()` returns every field's current value, using the field's `default` where nothing is stored or the stored value is invalid for the kind/range (a console warning is logged; storage is not rewritten until the user next edits). Re-registering a schema replaces the page; values for still-present fields are kept, values for removed fields are retained in storage untouched. Boolean and choice edits apply on change; number and string edits apply on commit (`Enter` or focus leaving the field). `settings_changed` carries `{ changes: { <field-id>: <new value> } }` and is delivered only for user edits — never at startup or on re-registration.
- Q: Does a `notify` call have a text bound, and do refused calls count against the 6/min window? → A (D, 009 FR-025's check order — permission → focus → rate limit → validation — and "counted after the permission and focus checks"): `notify(level, text)` with `level` ∈ `critical` | `warning` | `info` and `text` ≤ 200 characters; a bad level or over-length text is refused `invalid_state`/`invalid_value`. The window is consumed at the rate-limit step, so a call refused at validation still counts, while a `permission_denied` or `rate_limited` call does not. There is no notification key, replace, dismiss, or action parameter for plugins in this slice (§6.5 names only `notify(level, text)`); a plugin's already-shown notifications follow 001's ordinary lifecycle and are unaffected by the plugin's later disable/suspend. Attribution renders as the plugin's icon (or generic glyph) plus its name before the text.
- Q: Do the new `ui.*` calls fall under 009 FR-025's 100 calls/second per-category limit? → A (D, FR-025's per-category design): yes — a new **`ui`** category covers `register_panel`, `update_widget`, `add_overlays`, `remove_overlays`, `clear_overlays`, `register_action`, `register_settings`, and `get_settings` at 100/s on a rolling 1-second window (`rate_limited`, no effect, never queued). `notify` is governed solely by its own 6/60 s window.
- Q: How does a plugin reference a localized string (PL-7.3), and what happens for an unknown key? → A (A, lenient-fallback convention matching PL-7.3's own "falls back"): any user-facing string parameter (labels, titles, item labels, overlay label text, action labels, settings labels/descriptions/option labels, notification text) is either a literal (rendered as-is, treated as default-locale) or a string-table reference `@<key>` resolved against the manifest's string tables for the active locale, then the plugin's declared default locale. A reference with no entry in any locale renders the literal `@<key>` text and logs a console warning; a reference that resolves to an empty string on a widget label is an unlabeled widget (FR-001).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A plugin's panel is fully accessible and themed by the host (Priority: P1)

A plugin registers a panel built from host widgets — say, a slider labeled "Tempo" and a toggle labeled "Snap to beat." The host renders it, attributed with the plugin's name and icon, docked beside the Now Playing view. A screen-reader user tabs to the slider and hears "Tempo, slider," adjusts it with arrow keys, and the plugin receives the new value. When the user switches the app from light to dark theme, the panel's colors update instantly with no plugin code running. A plugin that tries to register a widget with no label is refused, and the reported widget path tells the plugin author exactly which one.

**Why this priority**: This is the prompt's headline acceptance scenario and the feature's core safety property (Constitution II, NFR-4.7, NFR-6.3): plugin UI must be fully accessible and rendered exclusively by trusted host code, never by plugin-supplied markup. Nothing else in this feature is worth building if a plugin panel can be unlabeled, untheme-able, or a code-injection vector.

**Independent Test**: Register a fixture panel with one of every widget kind, including one deliberately unlabeled; verify the unlabeled registration is refused with its widget path, the rest of the panel renders with correct accessible names and roles, every widget is keyboard-operable, changing theme updates it live, and interacting with each widget delivers the correct value to the plugin.

**Acceptance Scenarios**:

1. **Given** a plugin registers a panel with a slider labeled "Tempo," **When** a screen-reader user tabs to it, **Then** the reader announces "Tempo, slider," and the arrow keys change its value, sending the new value to the plugin (prompt acceptance).
2. **Given** a plugin's `register_panel` call includes a widget with no label, **When** the host validates it, **Then** the whole call is refused with `invalid_state`/`unlabeled_widget` naming that widget's path, and none of the panel's other widgets are registered either.
3. **Given** an open plugin panel, **When** the user switches the app's theme from light to dark, **Then** the panel's colors and fonts update to the new theme's tokens within the same frame, and the plugin receives no event and runs no code (prompt acceptance).
4. **Given** a panel with a toggle labeled "Snap to beat," **When** the user clicks it, **Then** its state flips, the host announces the new state, and the plugin receives a `panel_interaction` event naming the widget and its new value.
5. **Given** any docked panel, **When** the user floats it, moves it, and later re-docks it, **Then** its placement persists across an app restart; **When** the user closes it, **Then** it disappears for the rest of the session (re-showable from the plugin's row in the Plugins list) and reappears at next launch; **When** the user disables it from the plugin's row in the Plugins list, **Then** it stays hidden across restarts until re-enabled from the same place.
6. **Given** any panel, **When** it is shown, **Then** its header shows the panel title, the owning plugin's name, and its icon (or the generic plugin glyph when the manifest declares none or an invalid one), regardless of docked or floated state (PL-7.4).
7. **Given** a panel widget's handler throws while processing a `panel_interaction`, **When** the fault occurs, **Then** only that handler aborts (009's existing fault-isolation rules apply), the panel keeps rendering, and every other plugin's and the host's own UI is unaffected.
8. **Given** a plugin with two visible panels is suspended for a hang, **When** the suspension takes effect, **Then** each panel's frame stays in place showing a placeholder ("<plugin>, suspended, <cause>") with Restart and Disable controls and no widgets; **When** the user chooses Restart and the plugin re-registers its panels after `ready()`, **Then** the placeholders are replaced by the live panels in the same placement; **When** the user chooses Disable instead, **Then** the frames are removed entirely.
9. **Given** a panel with a slider, **When** the user drags it with the pointer across many pixels and releases, **Then** exactly one `panel_interaction` is delivered, carrying the released value; **When** the user presses `→` three times, **Then** three events are delivered, each one `step` apart.
10. **Given** a `list` widget, **When** the user presses `↓`, **Then** the selection moves and one `panel_interaction` carrying the new item id is delivered without pressing `Enter`.
11. **Given** a plugin holding `transport.control` whose panel has a "Take over" button, **When** the user activates it under the auto-on-interaction policy and the plugin calls `request_focus()` inside the resulting `panel_interaction` handler, **Then** the plugin is granted focus immediately (010's hand-over sequence); **When** the same plugin calls `request_focus()` from a timer instead, **Then** it is only recorded as a requester, as 010 already specifies.
12. **Given** a plugin registers a 17th panel, or `update_widget` is called with a slider value outside `[min, max]`, or on a `label`, **When** the call is made, **Then** it is refused `invalid_state` with reason `panel_limit`, `invalid_value`, or `not_updatable` respectively, and nothing changes.

### User Story 2 - A plugin's keyboard shortcuts join the central map, with the user always able to resolve a conflict (Priority: P2)

A plugin registers an action with a default key binding. It shows up in the same shortcut map 007 built, grouped under the plugin's name, fully rebindable. When the plugin's requested key is already the host's own binding, the map flags the conflict and the plugin's binding is the one that stays inactive — the host's keeps working exactly as before. Pressing the key it did win invokes the plugin's handler with the actual value and the source (keyboard or a panel button wired to the same action).

**Why this priority**: JTBD-5/FR-9.1.1's promise that shortcuts are a single, coherent, conflict-safe registry only holds if plugin-contributed actions obey the exact rules 007 already established for host actions — this is the extension point 007 FR-016 explicitly reserved. It outranks overlays/settings/notify because a shortcut that silently double-fires or silently overrides a host control is a correctness and safety issue, not a cosmetic one.

**Independent Test**: Register a fixture plugin action bound by default to `L` (already the host's loop toggle); verify the map flags the conflict, `L` still toggles the host's loop, and the plugin's action never fires until the user rebinds it to a free key, at which point it fires correctly and appears un-flagged.

**Acceptance Scenarios**:

1. **Given** a plugin registers an action with the default binding `L`, already the host's loop-toggle binding, **When** the map is opened, **Then** the conflict is flagged on both rows, pressing `L` still toggles the host's loop exactly as before, and the plugin's action never fires (prompt acceptance).
2. **Given** the user rebinds the plugin's action to a free key, **When** they press it, **Then** the plugin receives `action_invoked` with its action id, `source: keyboard`, and, for a `continuous` action, its value; the conflict flag clears on both rows.
3. **Given** two bundled plugins each register a default binding for the same key, **When** the map is opened, **Then** both are flagged and neither fires until the user changes or removes one of the two bindings (EC-6.8).
4. **Given** a panel button names a plugin's own registered action instead of firing a plain interaction, **When** the user activates it, **Then** the same Action & Binding dispatch path a keyboard press would use is invoked, and the plugin receives `action_invoked` with `source: ui`.
5. **Given** a plugin action's owning plugin is disabled or suspended, **When** the map is shown, **Then** the action's row is greyed, excluded from conflict evaluation, and does not fire from any binding; **When** the plugin becomes Active again, **Then** the row un-greys with its bindings intact and conflicts are re-evaluated.
6. **Given** the user rebound a plugin action to `Shift+K` and restarts the app, **When** the plugin loads and registers that action again, **Then** the `Shift+K` override applies with no `keybindings-invalid-entries` warning having been raised at launch; **Given** the plugin is instead disabled at launch, **Then** the action has no row in the map and the override is still present in `settings.toml`.
7. **Given** a plugin registers an action whose default binding is `Tab`, **When** the call is made, **Then** it succeeds, the action appears in the map unbound, and a console warning names the rejected binding.
8. **Given** a `continuous` plugin action bound to a key, **When** the user presses it, **Then** `action_invoked` carries `value: 1.0` and `source: keyboard`.

### User Story 3 - A plugin draws on the waveform in track-time and the host keeps it aligned (Priority: P3)

A plugin draws lines, regions, labels, and glyphs on the waveform to annotate the music — a chord chart's chord boundaries, a practice tool's phrase markers. As the user zooms in or scrolls the waveform, every plugin drawing stays exactly aligned with the audio it annotates, without the plugin doing anything.

**Why this priority**: This is the visual payoff the prompt's persona scenarios (Chord Chart, Section Loop) depend on, but it is additive polish on top of Stories 1–2's safety-critical accessibility and shortcut-correctness guarantees, so it ranks after them.

**Independent Test**: Register a fixture plugin's overlay set (one of each primitive) on a loaded track; zoom the detail view in and scroll it, and verify every primitive re-projects to the same track-time position with zero plugin invocations, then change tracks and verify the overlays disappear.

**Acceptance Scenarios**:

1. **Given** a plugin registers a line, a region, a label, and a glyph anchored at specific track-time positions, **When** the waveform detail view zooms and scrolls, **Then** every primitive re-projects to the same track-time position with no event delivered to the plugin (Prompt; 005 FR-014).
2. **Given** a plugin's overlays are showing, **When** the track changes, **Then** the overlays are cleared; **When** the plugin registers new overlays for the new track, **Then** only those appear.
3. **Given** a plugin attempts to register a 501st overlay primitive, **When** the call is made, **Then** it is refused with `invalid_state`/`overlay_limit` and the plugin's previously registered 500 primitives are unchanged.
4. **Given** two plugins overlay the same waveform region, **When** both are shown, **Then** they draw in plugin-registration order, above host markers and the active loop region and below the playhead.
5. **Given** a plugin adds a line, a region, and a glyph, plus a label, **When** both waveforms are inspected, **Then** the line, region, and glyph appear on the overview and the detail view and the label appears on the detail view only; **When** the plugin re-adds the line's id at a new position, **Then** the line moves and the primitive count is unchanged.
6. **Given** a glyph names an icon that is neither a manifest `glyphs` key nor a host glyph, or a region has `from ≥ to`, or any position is negative, **When** the call is made, **Then** it is refused whole with `invalid_state`/`invalid_value` and nothing is drawn.

### User Story 4 - A plugin's settings page lives inside the host's Settings and its values persist (Priority: P4)

A plugin registers a small settings schema — a toggle, a number field. It appears as its own page under Settings › Plugins, is reachable from Settings search, and every edit the user makes there is persisted by the host and reported to the plugin.

**Why this priority**: FR-11.1.3 names this explicitly, and it reuses 009's storage and 001's Settings/search infrastructure almost entirely, making it lower-risk and lower-priority than the accessibility and shortcut-correctness stories above.

**Independent Test**: Register a fixture plugin's settings schema (one boolean, one number); open Settings, find the plugin's page directly and via search, change both fields, restart the app, and verify the values persisted and the plugin received `settings_changed` for each edit.

**Acceptance Scenarios**:

1. **Given** a plugin registers a settings schema with a boolean field, **When** Settings › Plugins is opened, **Then** a page named for the plugin shows the field with an accessible name, fully keyboard-operable.
2. **Given** a plugin's settings field, **When** the user searches Settings for its title, **Then** it appears in the results with its category path, exactly as any other setting does (001 FR-019).
3. **Given** the user changes a plugin's settings field, **When** the change is made, **Then** the host persists it to the plugin's own storage and the plugin receives `settings_changed` naming the field and its new value.
4. **Given** the app restarts after a settings change, **When** the plugin calls `get_settings()`, **Then** it sees the persisted value with no user action required.
5. **Given** a plugin's stored number value is outside the field's current `[min, max]` (e.g., after a plugin update narrowed the range), **When** the page renders or `get_settings()` is called, **Then** the field's `default` is used, a console warning is logged, and storage is left untouched until the user next edits the field.
6. **Given** a plugin holding `state.plugin`, **When** it calls `state.plugin` `get` for any key, **Then** no settings value is visible there — settings live in the store's host-owned `settings` scope, reachable only via `get_settings()`.
7. **Given** a schema with a `number` field whose `default` lies outside its `[min, max]`, **When** `register_settings` is called, **Then** it is refused `invalid_state`/`invalid_schema` naming `fields[<index>]`, and no page appears.

### User Story 5 - A plugin's notifications are attributed, non-blocking, and rate-limited (Priority: P5)

A plugin posts a notification — "chords loaded" — that appears in the host's existing notification area, clearly attributed to the plugin, never as a dialog that blocks anything. If the plugin posts too many in a short time, the host protects the user from being spammed.

**Why this priority**: This is the smallest, most self-contained surface in the feature — a thin wrapper over 001's existing notification area and severities — so it ranks last even though the rate-limit behavior is explicitly called out in the prompt's acceptance text.

**Independent Test**: Post one notification of each severity from a fixture plugin and verify attribution and non-blocking display; then post seven within a minute and verify the seventh is refused with `rate_limited` and never shown.

**Acceptance Scenarios**:

1. **Given** a plugin holding `ui.notify` posts a warning-level notification, **When** it is shown, **Then** it appears in the existing non-blocking notification area, attributed to the plugin's name and icon, and never as a modal dialog (FR-14.1.1, FR-14.1.2).
2. **Given** a plugin has posted six notifications within the last 60 seconds, **When** it posts a seventh, **Then** the call returns `rate_limited`, no notification is shown, and the call is not queued for later delivery (prompt acceptance).
3. **Given** 61 seconds have passed since the plugin's first notification in a rate-limited window, **When** it posts again, **Then** it succeeds, since the window has rolled forward.
4. **Given** a plugin has posted five notifications in the last 60 seconds, **When** it posts one with 201 characters of text, **Then** the call is refused `invalid_state`/`invalid_value`, nothing is shown, and the next well-formed call is refused `rate_limited` (the invalid call consumed the sixth slot).

### Edge Cases

- A `register_panel` call includes a widget without a label anywhere in its layout → the entire call is refused, `invalid_state`/`unlabeled_widget`, naming the widget's path; nothing in the call is registered (EC-6.19; Clarifications).
- A plugin re-registers a panel id it already used → the new layout atomically replaces the old one; any pending `panel_interaction` for the old layout's widgets is dropped (Clarifications).
- A `register_panel`, `add_overlays`, `register_action`, or `register_settings` call would exceed its cap — 100 widgets/panel, 16 panels/plugin, 500 overlay primitives/plugin, 64 actions/plugin, 100 settings fields — → refused whole, `invalid_state`/`panel_widget_limit`, `panel_limit`, `overlay_limit`, `action_limit`, or `settings_field_limit`, prior state unchanged (Clarifications).
- A widget has a missing, malformed, or duplicate `id` → the whole call is refused `invalid_state`/`invalid_widget_id` naming `widgets[<index>]` (Clarifications).
- The plugin owning an open panel is **suspended** → the panel's frame and placement stay, its body becomes a placeholder with Restart/Disable (source §5.4); the plugin is **disabled**, auto-disabled, or unloaded → the panel is removed per 009 FR-012. In both cases the panel's own close/disable visibility flag is unaffected and applies again when the plugin re-registers (Clarifications).
- A plugin calls `update_widget` for a widget path that does not exist on its registered panel → `not_found`; for a `label`, `button`, or `marker list` → `invalid_state`/`not_updatable`; with a value of the wrong type or outside a slider/knob's `[min, max]` → `invalid_state`/`invalid_value` (a `meter` value is clamped instead) (Clarifications).
- A plugin's panel is shown while the user is in the Library or Settings view → it is not visible (dock and floated panels belong to the Now Playing view); it is intact, with any `update_widget` changes applied, when the user returns (Clarifications).
- The window is smaller at launch than a floated panel's persisted position → the panel is clamped into the window bounds; its persisted entry is updated on the next move (Clarifications).
- A plugin calls `request_focus()` inside a `panel_interaction`/`action_invoked` handler under auto on interaction → granted immediately, revoking any current plugin holder (010's sequence); the same call from any other handler behaves exactly as 010 already specifies (Clarifications).
- A plugin's action default binding collides with the host's own binding → the host's binding keeps firing; the plugin's is flagged and inactive until the user rebinds it (prompt acceptance).
- Two bundled plugins' default bindings collide → both flagged, neither fires until the user changes or removes one (EC-6.8).
- A plugin's owning process is disabled while its action is bound to a key with no other claimant → the row greys, the binding is inert, and pressing the key does nothing until the plugin is re-enabled (Clarifications).
- A panel `button` names a target action that does not exist (typo, or the plugin never called `register_action` for it) → the button is inert; activating it does nothing and logs a console entry, exactly like calling an absent API method in 009's Clarifications precedent.
- A plugin's default binding is one 007 FR-007 rejects (`Tab`, `Esc`, lone modifier, macOS `Control` chord) or unparseable → the action registers unbound with a console warning; the call succeeds (Clarifications).
- `settings.toml` holds a `[keybindings]` override for a plugin action whose plugin is not loaded → the entry is retained dormant, never reported as invalid, and applies when that action next registers (Clarifications).
- A plugin's overlay glyph references an image outside its own manifest `glyphs` map or the host glyph set, a region has `from ≥ to`, or any position is negative or non-finite → the whole call is refused `invalid_state`/`invalid_value`, nothing rendered (Clarifications).
- A manifest `icon` or `glyphs` entry is missing, not PNG, or over-limit → not a manifest error; the generic plugin glyph is shown in its place and a console warning names the file (Clarifications).
- The track changes while a plugin has active overlays → they are cleared; the plugin must re-register for the new track if it wants overlays there (Clarifications).
- A user is mid-edit on a plugin's settings field when the plugin is disabled → the field keeps its last value in storage; the page itself disappears from Settings › Plugins along with the plugin's other UI (009 FR-012) and reappears, values intact, when the plugin is re-enabled.
- A plugin posts its seventh notification within a rolling 60-second window → `rate_limited`, nothing shown, not queued (prompt acceptance). A call refused at validation (bad level, text > 200 characters) still consumed a slot; a `permission_denied`/`rate_limited` call did not (009 FR-025 order).
- A plugin makes a 101st `ui`-category call within one second → `rate_limited`, no effect, never queued (009 FR-025 extended).
- A plugin string has no translation for the user's active locale → the host falls back to the plugin's declared default-locale string (PL-7.3); a `@key` reference absent from every locale renders literally with a console warning; in this slice the active host locale is always en-US, so the locale-fallback path is exercised only by a plugin fixture that deliberately omits an en-US string.
- A plugin's stored settings value is invalid for the field's current kind/range → the field's `default` is used, a console warning is logged, storage untouched until the user edits (Clarifications).
- A plugin's panel-interaction, overlay-update, or settings-render handler throws or hangs → contained by 009's existing per-handler budget and fault-isolation rules; only that plugin's contribution is affected (009 FR-010/FR-011).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Every widget kind a `register_panel` layout may use — `label`, `button`, `toggle`, `slider`, `knob`, `list`, `text`, `marker list`, `meter` — MUST carry a plugin-supplied label; the host MUST derive each widget's accessible name from it. A `register_panel` call containing any unlabeled widget anywhere in its layout MUST be refused whole (`invalid_state`/`unlabeled_widget`), naming the offending widget's path in the refusal `message`, with nothing in that call registered. *(PL-7.2; EC-6.19; NFR-6.3)*
- **FR-002**: Each widget kind MUST behave as follows: `label` is static, non-interactive text (≤ 256 characters); `button` is momentary and either fires `panel_interaction` on activation (`Space`/`Enter`/click) or, when it names a target action (FR-008), dispatches through the Action & Binding path instead; `toggle` is boolean, announces its state, and fires `panel_interaction` on flip (`Space`/click); `slider`/`knob` hold a number within a plugin-declared `min < max` and `step > 0` (optional initial `value` in range, default `min`), are adjustable by keyboard (arrows one `step`, Page Up/Down ten steps — each key press commits and fires one `panel_interaction`) and by pointer (a drag fires exactly one `panel_interaction` on release), and announce their numeric value; `list` is single-selection from a plugin-supplied `items` list of `{ id, label }` (≤ 256 items) whose selection follows focus — an arrow key or click changes the selection and fires `panel_interaction` with the item `id`, `Enter` is a no-op; `marker list` lists the current track's markers whose owner is this plugin (006 DM-6), sorted by position, live-updating, read-only, requiring only `ui.panel`, and a row selection seeks as a host user command (FR-3.3.2, no focus check) without firing `panel_interaction`; `text` is a plugin-updatable, read-only display (≤ 1,024 characters); `meter` is a read-only, plugin-driven level display over `[0.0, 1.0]`. A knob differs from a slider only in affordance. Every widget is keyboard-operable and exposes its label as its accessible name (FR-001); no widget has a plugin-settable disabled/hidden state in this slice. *(6.5; 007 FR-019; Clarifications)*
- **FR-002a**: A panel layout MUST be a flat, ordered list of widgets the host stacks vertically (scrolling when taller than its placement); there are no container or grouping nodes. Every widget MUST carry a plugin-supplied `id` (`[a-z][a-z0-9_]{0,63}`, unique within the panel), which is its **widget path**; a missing, malformed, or duplicate `id` refuses the whole call `invalid_state`/`invalid_widget_id`. Every refusal `message` that names a widget MUST name it as `widgets[<zero-based index>]`, appending the `id` when present. *(EC-6.19; Constitution X; Clarifications)*
- **FR-003**: A plugin holding `ui.panel` MAY register up to **16** independent panels via `register_panel(panel_id, title, widgets)` — `panel_id` namespaced by the plugin's identifier (no cross-plugin collision), `title` required (≤ 64 characters), `widgets` capped at 100 (a call exceeding either cap is refused whole, `invalid_state`/`panel_limit` or `panel_widget_limit`); re-registering an existing panel id atomically replaces its entire layout, dropping any pending `panel_interaction` for the old layout. *(6.5; PL-2.2; Clarifications)*
- **FR-004**: Every panel, in every placement, MUST display in its header the panel title, the owning plugin's name, and its icon — the manifest's `icon` PNG when valid, otherwise the host's generic plugin glyph. *(PL-7.4; Clarifications)*
- **FR-005**: The dock area MUST be a fixed-width column at the right edge of the **Now Playing view**, hidden when it holds no visible panel, stacking docked panels vertically (scrolling on overflow) ordered by owning plugin name, then by that plugin's registration order (not user-reorderable in this slice). A panel MUST open **docked** by default; the user MAY **float** it (a movable, resizable overlay confined to the app's own window bounds, opening at its docked size centered over the Now Playing content, minimum 200 × 120 px, rendered above Now Playing content and below the notification area and any sheet) or re-dock it. Docked and floated panels are visible only while the Now Playing view is shown and are retained intact otherwise. Detaching a panel into a separate OS window or to a second display is out of scope for this slice. Placement (`docked` | `floated`), floated position/size, and the FR-006 `disabled` flag MUST persist in `settings.toml` under `[plugin_panels]`, keyed `"<plugin-identifier>/<panel-id>"`, under that file's existing write/read rules; an entry for an unregistered panel is retained dormant, and a persisted floated position is clamped into the window bounds on restore. *(6.5; Scope boundary; 007 FR-013 convention; Clarifications)*
- **FR-006**: The user MAY **close** an open panel (its title-bar control), hiding it for the remainder of the running session (it reappears at next launch), and MAY separately **disable** a panel — from its title bar or from the plugin's row in the Plugins list (009 FR-023) — which hides it persistently across restarts until re-enabled from the same place. The plugin's Plugins-list row MUST list each of its registered panels with a **Show/Hide** (session; re-shows a closed panel) and an **Enable/Disable** (persisted) control. Both controls act on the panel's own visibility only, deliver no event to the plugin, and are unaffected by, and do not affect, the owning plugin's enabled/disabled/suspended state, which continues to be governed entirely by 009 FR-012. *(PL-7.4; Clarifications)*
- **FR-007**: A plugin holding `ui.panel` MAY update its widgets' displayed values at any time via `update_widget(panel_id, path, value)`, applied on the next UI frame and never itself producing an event back to the plugin, whether or not the panel is currently visible. Accepted values: `toggle` boolean; `slider`/`knob` number within `[min, max]`; `list` an item `id` (`not_found` if unknown) or `{ items, selected? }` replacing the item set; `text` string ≤ 1,024 characters; `meter` number, clamped to `[0.0, 1.0]`. A wrong type or out-of-range slider/knob value MUST be refused `invalid_state`/`invalid_value` (never clamped); `label`, `button`, and `marker list` MUST be refused `invalid_state`/`not_updatable`; an unknown panel id or path MUST return `not_found`. A user-driven change to an interactive widget (button press, toggle flip, committed slider/knob adjustment, list selection) MUST deliver `panel_interaction` (panel id, widget path, new value) to the owning plugin, subject to the plugin's existing per-handler CPU budget (009 FR-009) like any other event. *(6.5; Clarifications)*
- **FR-007a**: Plugin panel widgets MUST take part in 007 FR-019's single-consumer key precedence at step (2) exactly as host widgets do: a focused widget consumes only the keys its kind handles and every other key falls through to registered actions; no panel widget is a text field. The dock column MUST follow the Now Playing view's existing controls in `Tab` order, and each panel MUST be one focus group — title-bar controls (float/dock, close, disable), then its widgets in layout order. *(007 FR-019; NFR-6.1; Clarifications)*
- **FR-008**: A `button` widget MAY declare a target action identifier the same plugin registered via `ui.shortcuts` (FR-010) instead of producing `panel_interaction`; activating such a button MUST dispatch through the same Action & Binding path a keyboard press uses, including the FR-011 conflict/FR-013 enabled gate, delivering `action_invoked` with `source: ui` to the plugin rather than `panel_interaction`. *(6.5; Part 5 §5 `action_invoked`)*
- **FR-009**: Every widget on every open plugin panel MUST render using the host's currently active theme tokens (System/Light/Dark, 001 FR-017); when the user changes theme, every open plugin panel MUST re-render with the new tokens within the same UI update, and the owning plugin MUST NOT execute any code and MUST NOT receive any event as a result. *(Prompt acceptance; NFR-4.7)*
- **FR-010**: A plugin holding `ui.shortcuts` MAY register up to **64** actions (`invalid_state`/`action_limit` beyond that) via `register_action(id, label, kind, default_binding?, repeats_while_held?)`, each with an id namespaced `<plugin-identifier>.<action-id>` (`action-id` using the widget-id grammar; guaranteeing no cross-plugin or plugin-vs-host collision, EC-6.9), a label, a kind (`trigger` or `continuous`, per 007's DM-14 model), an optional default keyboard binding in the platform-neutral encoding 007 persists, and an optional `repeats_while_held` flag (default `false`). Every plugin action has activation scope `app`. A default binding 007 FR-007 would reject (lone modifiers, `Tab`/`Shift+Tab`, `Esc`, a macOS `Control` chord) or that cannot be parsed MUST register the action unbound with a console warning, not refuse the call. Re-registering an id replaces its label, kind, flag, and default binding while any user override is kept. Registered actions join 007's existing Action & Binding registry (DM-14/DM-15), appear in Settings › Controls' shortcut map grouped under the owning plugin's name, and are fully rebindable and removable exactly like a host action. *(6.5; EC-6.9; 007 FR-001/FR-007/FR-016/FR-018; Clarifications)*
- **FR-010a**: A persisted `[keybindings]` entry (007 FR-013) whose action id is outside the `host.` namespace MUST never be treated as unknown: it is retained dormant and applied the moment an action with that id registers; only `host.`-namespaced unknown ids and unparseable combinations raise `keybindings-invalid-entries`. A plugin disabled at launch therefore has no rows in the shortcut map until enabled; a plugin disabled or suspended mid-session keeps its rows greyed (FR-013) until the session ends. *(007 FR-013, extended; Clarifications)*
- **FR-011**: Every action's owner carries one of three ownership tiers — **host** > **bundled plugin** > **community plugin** (the community tier is modeled by this mechanism but unreachable until a later slice ships a non-bundled plugin source). When two enabled, currently-reachable bindings collide (007 FR-009/FR-010): if their owners are in different tiers, the higher tier's binding keeps firing and the lower tier's binding MUST be flagged inactive in the shortcut map automatically, with no user action required; if both owners share a tier, neither binding MUST fire until the user changes or removes one of the two, exactly as 007 FR-009 already specifies for two host actions. *(Prompt acceptance; EC-6.8; FR-7.4.1; Clarifications)*
- **FR-012**: Invoking a plugin action — by its keyboard binding, or via a panel button naming it (FR-008); MIDI is out of scope until a later slice — MUST deliver `action_invoked` to the owning plugin with the action id, source (`keyboard` or `ui`), and, for a `continuous` action, `value: 1.0` (007 FR-001's fixed keyboard step; MIDI supplies real values in a later slice). An inactive action (flagged by a same-tier conflict, or whose owning plugin is not Active per FR-013) MUST NOT be dispatched and MUST NOT deliver the event. *(Part 5 §5; Prompt acceptance)*
- **FR-013**: A plugin action's `enabled` flag MUST track its owning plugin's health: `false` whenever the plugin is disabled, suspended, or invalid — shown greyed in the shortcut map, excluded from conflict evaluation (007 FR-009), never dispatched — and MUST return to `true`, with its bindings and any user customization intact, the moment the plugin's context becomes Active again, at which point conflicts are re-evaluated. Uninstalling a plugin (unavailable for any bundled plugin, 009 FR-013) removes its actions and bindings entirely. *(007 FR-012 pattern, extended; PL-3.4)*
- **FR-014**: A plugin holding `ui.overlay` MAY maintain a set of overlay primitives via `add_overlays(primitives)` (additive, keyed by a plugin-supplied primitive `id` in the widget-id grammar; re-adding an id replaces that primitive in place), `remove_overlays(ids)` (`not_found` for an unknown id), and `clear_overlays()`. Primitives are `line { id, at, color? }`, `region { id, from, to, color? }` (`from < to`), `label { id, at, text ≤ 64 chars, color? }`, and `glyph { id, at, icon, color? }`, with positions in **track-time milliseconds** (006's unit) as non-negative integers anchored in the coordinate space 005 FR-014 exposes; a negative or non-finite position, `from ≥ to`, or an unknown `icon` refuses the whole call `invalid_state`/`invalid_value`; a position beyond the current best-known duration is accepted and not drawn until the duration allows. `color` is one of the closed host token set `accent` (default), `secondary`, `positive`, `warning`, `neutral`, resolved through the active theme; no other style input exists. `icon` names a key of the manifest's `glyphs` map (FR-014a) or one of the host glyph set `dot`, `flag`, `note`, `chord`, `star`, `warning` — never a URL or inline markup. The host MUST re-project every primitive automatically whenever the waveform's zoom or scroll state changes, without the owning plugin executing any code or receiving any event for that re-projection. *(6.5; FR-4.1.3; NFR-4.7; PL-2.1; Clarifications)*
- **FR-014a**: A plugin manifest MAY declare `icon` (package-relative PNG, square, ≤ 128 × 128 px, ≤ 256 KB) and `glyphs` (≤ 32 entries, key `[a-z][a-z0-9_]{0,31}` → package-relative PNG ≤ 32 × 32 px, ≤ 64 KB); SVG and every other format are not accepted (NFR-4.7). A missing, non-PNG, or over-limit asset MUST NOT invalidate the manifest: the plugin loads, the generic plugin glyph is shown in its place, and a console warning names the file. The manifest's `contributions` field remains descriptive (009 FR-001); runtime `register_*` calls are the sole source of truth and are not cross-checked against it. *(PL-2.1, PL-2.2; NFR-4.7; Clarifications)*
- **FR-015**: At most 500 overlay primitives (lines, regions, labels, and glyphs combined) MAY exist per plugin at once, evaluated on the count after a call; a call that would exceed this MUST be refused whole (`invalid_state`/`overlay_limit`), leaving previously registered primitives unchanged. The host owns vertical placement: lines and regions span the waveform height (regions translucent); glyphs and labels sit in a plugin lane above the waveform. Lines, regions, and glyphs MUST render on both the overview and the detail view; labels on the detail view only. Overlays are non-interactive, non-focusable, and not individually exposed to assistive technology in this slice. When multiple plugins overlay the same waveform region, they MUST render in plugin-registration order, above host markers and the active loop region and below the playhead. *(Constitution X; 005 FR-002; Clarifications)*
- **FR-016**: A plugin's overlay primitives MUST be cleared automatically when the current track changes and when the plugin is disabled, suspended, or unloaded (PL-3.4); none persist across an app restart. *(PL-3.4; Clarifications)*
- **FR-017**: A plugin holding `ui.settings` MAY call `register_settings(fields)` with ≤ 100 fields (`invalid_state`/`settings_field_limit`), each `{ id, kind, label, description?, default, … }` with the widget-id grammar: `boolean`; `number { min, max, step }` (`min ≤ default ≤ max`, `step > 0`); `string` (≤ 1,024 characters; the host input stops accepting beyond that); `choice { options: [{ id, label }] }` (1–64 options, `default` ∈ options). A malformed schema MUST be refused whole, `invalid_state`/`invalid_schema`, naming `fields[<index>]`; re-registering replaces the page. The host MUST render it as one page per plugin under **Settings › Plugins**, listed by plugin name, additive to that category's existing plugin-management placeholder content (009); every field MUST expose an accessible name, be fully keyboard-operable (NFR-6.1, NFR-6.2), and be reachable from Settings' existing search by title (001 FR-019). Boolean and choice edits apply on change; number and string edits apply on commit (`Enter` or focus leaving the field). *(FR-11.1.3; NFR-6.1/6.2; Clarifications)*
- **FR-018**: The host, not the plugin, MUST persist every settings-page edit into a host-owned **`settings` scope** of the plugin's own per-plugin store established by 009 FR-014 (counted against its 10 MB cap, written atomically, and not addressable through `state.plugin` get/set), without requiring the plugin to hold `state.plugin`. Every persisted change MUST deliver `settings_changed` `{ changes: { <field-id>: <new value> } }` to the plugin — only for user edits, never at startup or on re-registration. `get_settings()` MUST return every field's current value, substituting the field's `default` where nothing is stored or the stored value is invalid for the field's current kind/range (logging a console warning and leaving storage untouched until the user next edits). Values for fields removed by a re-registration are retained in storage untouched. *(Part 5 §5, §6.5; FR-11.1.3; Clarifications)*
- **FR-019**: A plugin holding `ui.notify` MAY call `notify(level, text)` with `level` ∈ `critical` | `warning` | `info` (001's existing severities) and `text` ≤ 200 characters; any other level or over-length text MUST be refused `invalid_state`/`invalid_value`. Every plugin notification MUST appear in the host's existing non-blocking notification area under 001's ordinary lifecycle, attributed by the plugin's icon (or generic glyph) and name before the text, and MUST NEVER be shown as a modal dialog. No key, replace, dismiss, or action parameter exists for plugins in this slice; already-shown notifications are unaffected by the plugin's later disable/suspend. *(FR-14.1.1, FR-14.1.2, FR-14.1.3; Clarifications)*
- **FR-020**: The host MUST allow at most 6 `notify` calls per plugin within any rolling 60-second window (PL-8.1). The 7th and any further call within that window MUST return `rate_limited` immediately, show nothing, and MUST NOT be queued for later delivery. The window is consumed at 009 FR-008's rate-limit step: a call refused at validation still counts; a `permission_denied` or `rate_limited` call does not. *(Prompt acceptance; PL-8.1; 009 FR-025; Clarifications)*
- **FR-020a**: 009 FR-025's per-category limit MUST gain a **`ui`** category — `register_panel`, `update_widget`, `add_overlays`, `remove_overlays`, `clear_overlays`, `register_action`, `register_settings`, `get_settings` — at 100 calls/second per plugin on a rolling 1-second window (`rate_limited`, no effect, never queued); `notify` is governed solely by FR-020. *(009 FR-025, extended; Clarifications)*
- **FR-021**: A plugin MAY declare per-string localized tables in its manifest; any user-facing string parameter it supplies to a panel, overlay, action label, settings schema, or notification is either a literal (rendered as-is, treated as default-locale) or a reference `@<key>` the host MUST resolve in the user's active locale, falling back to the plugin's declared default locale. A reference absent from every locale renders the literal `@<key>` with a console warning; a reference resolving to an empty widget label is an unlabeled widget (FR-001). This slice ships only the en-US host locale, consistent with 001–010, so locale fallback is not exercised by any shipped string. *(PL-7.3; Clarifications)*
- **FR-022**: None of `ui.panel`, `ui.overlay`, `ui.shortcuts`, `ui.settings`, or `ui.notify` may cause any markup, stylesheet, or script a plugin supplies to execute inside the host's UI process; every surface this feature adds MUST be rendered exclusively from the closed widget, primitive, and field vocabularies defined above, interpreted entirely by host code. *(PL-7.1; NFR-4.7, alongside Constitution II, NON-NEGOTIABLE)*
- **FR-023**: A plugin fault while rendering, updating, or handling an interaction for any UI contribution this feature adds (a thrown handler, a budget breach) MUST be contained exactly as 009 FR-010/FR-011 already contain any other plugin fault: only the offending handler aborts and the plugin's health degrades per those existing rules, while every other plugin's and the host's own UI keeps rendering and responding unaffected. *(009 FR-010/FR-011; Constitution II)*
- **FR-024**: Every refusal from `register_panel`, `update_widget`, `add_overlays`, `remove_overlays`, `clear_overlays`, `register_action`, `register_settings`, `get_settings`, or `notify` MUST use 009 FR-008's existing `{ code, reason, message }` shape, its closed six-code set, and its check order (permission → rate limit → validation): `permission_denied` when the call is made without the relevant `ui.*` grant (checked first); `rate_limited` for the 7th-in-a-minute `notify` call or the 101st-in-a-second `ui`-category call; `invalid_state` with reason `unlabeled_widget`, `invalid_widget_id`, `panel_widget_limit`, `panel_limit`, `overlay_limit`, `action_limit`, `settings_field_limit`, `invalid_schema`, `invalid_value` (wrong type, out-of-range slider/knob value, bad overlay position/region/icon, bad notify level/text), or `not_updatable`; `not_found` for an unknown panel id, widget path, list item id, or overlay primitive id. No `ui.*` call produces `no_focus` or `budget_exceeded`. *(009 FR-008; Clarifications)*
- **FR-025**: On a plugin's **suspension** (009 FR-011), each of its visible panels MUST keep its frame and placement and show a placeholder body — the plugin's name, "suspended," the cause, and **Restart**/**Disable** controls mirroring 009 FR-011's notice — with its widgets removed; on **disable**, auto-disable, or unload, its panels MUST be removed entirely (009 FR-012). In both cases its overlays are cleared (FR-016), its actions greyed (FR-013), and its settings page hidden. When the same identifier's context calls `ready()` again, placeholders are removed; panels reappear only when the plugin re-registers them. *(Source §5.4; PL-3.4; 009 FR-011/FR-012; Clarifications)*
- **FR-026**: A `request_focus()` call made synchronously inside the plugin's handler for a `panel_interaction` event or an `action_invoked` event (either source) is a user-interaction-originated request: under 010's **auto on interaction** policy it MUST be granted immediately, revoking any current plugin holder per 010's existing hand-over sequence; under **manual** and **first request wins** 010's rules apply unchanged. Interacting with a plugin's widget MUST never move transport focus by itself; the plugin must ask and must hold `transport.control`, exactly as in 010. *(FR-3.3.5; Source §5.3; 010 Clarifications; Clarifications)*

### Key Entities

- **Panel**: A plugin-registered, plugin-identifier-namespaced UI surface — id, title, owning plugin, flat ordered widget list (≤ 100 widgets; ≤ 16 panels per plugin), attribution (name/icon), placement (docked/floated, with persisted position/size in `settings.toml` `[plugin_panels]`), per-user visibility state (closed-this-session, disabled), and a suspended-placeholder state (FR-025).
- **Widget**: One entry in a panel's layout — kind (`label`/`button`/`toggle`/`slider`/`knob`/`list`/`text`/`marker list`/`meter`), `id` (= widget path), required label, and kind-specific value bounds (a slider/knob's `min`/`max`/`step`; a list's `items`; a button's optional target action).
- **Overlay Primitive**: A plugin-owned waveform drawing — `id`, kind (`line`/`region`/`label`/`glyph`), owning plugin, track-time anchor(s) in ms, optional color token, and content (label text / glyph icon key); cleared on track change or plugin teardown; bounded at 500 per plugin.
- **Plugin Action (extends DM-14/DM-15, 007)**: An Action whose `owner` is a plugin identifier rather than `host`, namespaced `<plugin-identifier>.<action-id>`, scope `app`, whose `enabled` flag tracks the owning plugin's health (FR-013), plus an ownership tier (`bundled`/`community`) used for cross-tier conflict resolution (FR-011); ≤ 64 per plugin; its user overrides persist dormant in `settings.toml` while unregistered (FR-010a).
- **Settings Schema / Field**: A plugin's declarative settings page — one page per plugin under Settings › Plugins, ≤ 100 fields, each with `id`, kind (boolean/number/string/choice), label, optional description, required `default`, and current value persisted in the host-owned `settings` scope of the plugin's own per-plugin store (009 DM-12, extended).
- **Plugin Icon / Glyph**: Manifest-declared PNG assets (`icon`; `glyphs` map) verified with the package; invalid ones degrade to the host's generic plugin glyph.
- **Plugin Notification**: An entry in the host's existing notification area (001) additionally carrying the posting plugin's identifier, name, and icon for attribution, and counted against that plugin's 60-second, 6-call rate window.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Every widget on every registered plugin panel exposes a correct accessible name and role to assistive technology and is fully operable by keyboard alone, and no panel containing an unlabeled widget is ever rendered, in 100% of trials.
- **SC-002**: A plugin action whose default binding collides with a host binding never fires from that key, and the host's own binding keeps working unchanged, in 100% of trials.
- **SC-003**: Every plugin overlay primitive stays visually aligned with its declared track-time position across every zoom and scroll change, with zero plugin code invoked for the re-projection, in 100% of trials.
- **SC-004**: Switching the app's theme updates every open plugin panel's appearance within the same UI update, with zero events delivered to any plugin, in 100% of trials.
- **SC-005**: A plugin's seventh notification within any 60-second window is refused and never shown, in 100% of trials.
- **SC-006**: A user can find a plugin's contributed setting through Settings search by its title, the same way they find any host setting, in under 10 seconds.
- **SC-007**: A fault in one plugin's panel, overlay, or settings handler never stops any other plugin's UI or the host's own UI from rendering or responding, in 100% of trials.
- **SC-008**: A user can hide an unwanted plugin panel, and separately re-dock a floated one, each in a single action.

## Assumptions

- `panel_interaction` is this spec's name for the interaction-event mechanism the source describes but does not name; it is additive to the Part 5 §5 events table (alongside `action_invoked` and `settings_changed`, which the table already names for this slice) and requires only `ui.panel`.
- The numeric caps introduced where the source gives none — 100 widgets/panel, 16 panels/plugin, 500 overlay primitives/plugin, 64 actions/plugin, 100 settings fields, 256 list items, 64 choice options, the 60-second/6-call notification window, the `ui` category's 100 calls/s, and the text-length bounds (label 256, text widget/string field 1,024, notify 200, overlay label 64, panel title 64) — follow the same convention as 009's own numeric defaults (64 markers, 256 timers, 100 calls/second/category) and may not be changed at plan time without recording the deviation.
- Plugin overlays are decorative for assistive technology in this slice (non-focusable, not individually exposed); the accessible channel for the same information is a panel `list`/`marker list`. A later slice may expose overlay labels through the waveform's accessible description without a plugin-facing contract change.
- Panels belong to the Now Playing view (like 008's Effect Chain panel and 010's Transport panel); app-wide or per-view panel placement is a possible later extension that changes layout only, not the plugin contract or the persisted `[plugin_panels]` shape.
- Plugin string references use the `@<key>` form; the manifest string-table file layout is a plan-time detail of 009's manifest schema (Constitution IX: one generated definition).
- Detaching a panel to a second OS-level display, the developer console (a future 002-developer-mode surface), and the plugin permission approval sheet are all explicitly out of scope per the source prompt's own scope boundary; this spec's docked/floated placements are both confined to the main application window.
- The `community` plugin-ownership tier (FR-011) is modeled now so the conflict-resolution rule is complete and stable, but is unreachable in practice until a later slice ships a plugin source other than "bundled" (009's own scope boundary and Assumptions already establish this timeline).
- A plugin's settings values live in its existing 009 per-plugin storage rather than a new subsystem, per Constitution III (host primitives, plugin behaviors) and Constitution X (YAGNI); this also means a plugin's settings data is bounded by, and shares, its 10 MB storage cap with any `state.plugin`/`state.track` usage.
- Only the en-US host locale ships in this slice (unchanged since 001); the plugin string-localization mechanism (FR-021, PL-7.3) is built now so a later localization slice needs no plugin-facing contract change.
- The two bundled reference plugins that will actually exercise these surfaces in practice (Section Loop, Key & Tempo — FR-13.1/13.2, 001-mvp/012 and 013) are not built in this slice; this feature's automated tests and manual scenarios exercise it via the same kind of fixture-plugin harness 009 established (`MODPLAYER_PLUGIN_FIXTURES=1`), extended with fixtures for each `ui.*` surface.
- Reordering multiple docked panels, and reordering panels relative to each other generally, is not built in this slice; the default registration-then-name order is a reasonable starting behavior a later slice may make user-configurable without a contract change.
