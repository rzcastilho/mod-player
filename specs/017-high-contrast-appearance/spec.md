# Feature Specification: High-Contrast Appearance Option

**Feature Branch**: `feature/017-high-contrast-appearance`

**Created**: 2026-09-23

**Status**: Clarified — clarify pass complete (2026-09-23); every ambiguity resolved from an authoritative source or a documented default written into the requirement body; no items escalated for human decision; ready for `/speckit-plan`

**Input**: User description: "Offer a high-contrast appearance for users who cannot read the default palette, satisfying the product's accessibility requirement that such an option exists alongside light and dark. Add a high-contrast choice to the appearance settings, orthogonal to the light/dark/system selection, so a user can run high-contrast light or high-contrast dark. In this mode secondary text is promoted to the primary text colour, every border and divider reaches at least a 3:1 ratio against its surface, focus rings thicken, and the accent, positive, warning and danger roles are replaced with variants that reach at least 7:1 against their surface. Elements whose colour is data rather than decoration — marker colours, plugin overlay colours — keep their hue but gain an outline so they stay distinguishable, since a marker's colour is meant to survive a theme change. The choice persists across restarts alongside the existing theme preference, applies live without relaunching, and reaches plugin-contributed panels and overlays through the same tokens the host uses, so a plugin panel never becomes the one unreadable area of the window. Acceptance: when high contrast is enabled, every text sample in every view measures at least 7:1 against its background. When a track has markers placed and high contrast is enabled, each marker remains individually identifiable on the waveform. When high contrast is enabled and a plugin panel is docked, that panel's text and controls follow the same palette. When the app restarts, the high-contrast choice and the light/dark choice are both restored."

**Source**: [ModPlayer-UI-UX-Review.md § 4.2 Measured contrast](../autonomous/ModPlayer-UI-UX-Review.md#42-measured-contrast-wcag-2x-sampled-from-the-captures) (`UX-39`), [§ 4.6 Accessibility versus the spec](../autonomous/ModPlayer-UI-UX-Review.md#46-accessibility-versus-the-spec), [§ 5.3 Semantic colour](../autonomous/ModPlayer-UI-UX-Review.md#53-semantic-colour-both-themes-contrast-verified), [§ 3.7 Settings](../autonomous/ModPlayer-UI-UX-Review.md#37-settings); [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) FR-14.4.1 (light/dark themes, plugins inherit theme tokens), NFR-6.5 (contrast minimums in both themes); [007-operations-and-polish/004-accessibility-hardening](../autonomous/breakdown/007-operations-and-polish/004-accessibility-hardening.md) (NFR § 6 Accessibility: "a high-contrast option is added under Appearance"). **Origin**: [specs/autonomous/breakdown/008-design-foundation/004-high-contrast-appearance.md](../autonomous/breakdown/008-design-foundation/004-high-contrast-appearance.md). **Prerequisites**: builds on the ten semantic colour roles, the divider value, and the once-per-frame token application shipped by [014-design-tokens-and-type-scale](../014-design-tokens-and-type-scale/spec.md) (`crates/modplayer-ui/src/theme/`), and on the focus ring and border strokes shipped by [015-control-variants](../015-control-variants/spec.md) (`crates/modplayer-ui/src/theme/controls.rs`) and adopted into card/row borders by [016-list-row-and-panel-components](../016-list-row-and-panel-components/spec.md) — all already applied host-wide. [007-operations-and-polish/004-accessibility-hardening](../autonomous/breakdown/007-operations-and-polish/004-accessibility-hardening.md) is not yet specified or built; this feature does not depend on it and instead ships the palette variant and setting that feature's later keyboard/accessible-name/200%-scale work will build on top of.

**Scope boundary**: Covers the palette variant and its setting only — the high-contrast colour/stroke values, the setting that turns it on, its persistence, and its reach into plugin panels and overlays. Keyboard operability, accessible names/roles/states, and the 200% text-scale requirement remain with [007-operations-and-polish/004-accessibility-hardening](../autonomous/breakdown/007-operations-and-polish/004-accessibility-hardening.md). This feature does not add a fourth `Theme` value, does not change `surface.base`/`surface.raised`, does not change any component's layout or interaction behaviour, and does not change the eight `MARKER_PALETTE` hues themselves (006, 014) — only whether they carry an outline.

### Session 2026-09-23 (specify pass)

- Q: The source document's own open question — should high contrast also follow an operating-system high-contrast preference automatically, or stay a manual choice? → A (A, the prompt's own words "Add a high-contrast choice to the appearance settings" describing a user selection, and the existing `Theme::System` auto-follow is scoped to light/dark only — no auto-detected axis exists in the codebase today): high contrast is a manual, user-chosen setting only. This feature does not read or follow any OS-level high-contrast/increased-contrast preference. A future feature may add that without breaking this one's setting, since the manual choice would simply become the default the OS preference seeds rather than overrides.
- Q: The prompt names four things that change in high contrast — secondary text, borders/dividers, the accent/positive/warning/danger roles, and focus-ring width — does anything else, such as `surface.base`/`surface.raised` or the type scale, change too? → D (the prompt's own enumeration is exhaustive and names no surface or size change): only those four are affected. `surface.base` and `surface.raised` keep their normal-mode values in both themes; the six type-scale roles (014) are unaffected — high contrast is a colour/stroke variant of the existing scale, not a second scale.
- Q: FR-012's marker outline must stay visible against all eight `MARKER_PALETTE` hues on either theme's waveform background — what colour and width is that outline? → A (assumed, and deferred as an unconstrained implementation detail): the exact outline colour and stroke width are left to `/speckit-plan`, constrained only by the distinguishability floor this spec states (FR-011, FR-012) — a colour and width that render legibly against every palette entry on both the light and dark waveform background, not a specific literal chosen here. **Superseded by the clarify pass below**, which picks the value (`text.primary`, 1 px) rather than leaving it to plan.

### Session 2026-09-23 (clarify pass)

Same ladder: (D) derived from an authoritative source — the constitution, the source review document, a ratified prior feature spec, or the shipped code those specs produced; (A) assumed conventional default, chosen as the simplest option consistent with the constitution and the feature's stated intent. Nothing below met the materiality bar for human escalation: each is either settled by a source or has one obvious conventional answer that is cheap to change later.

- Q: FR-005 promotes secondary text "to the primary text colour" — is that a rendering-time substitution only where text is drawn, or a substitution of the `text.secondary` role's *value* everywhere it is consumed (the switch thumb's off colour, the checkbox/radio mark's unchecked colour, `visuals.weak_text_color`, and a plugin's `OverlayColor::Neutral`, which all read `text.secondary` today)? → A (the value, at the role table): in high contrast the active theme's `text.secondary` value **is** `text.primary`. Substituting one table entry is the only change that reaches all four non-text consumers plus every text call site with no call-site branching, which is what 014's "one construction site" design note and Constitution X (simplicity) both ask for; the alternative — a rendering-time-only promotion — would leave a plugin's `Neutral` overlay and the switch thumb on the normal-mode value while the text around them changed. Testable: with high contrast on, the active `Roles` table satisfies `text_secondary == text_primary` in both themes, and a `Neutral` plugin overlay paints that same value. Written into FR-005.
- Q: FR-007 states a ≥3:1 floor for borders/dividers but names no value to replace normal mode's `text.primary` at 8 % alpha (`divider_color_for`) — what is it? → A (`text.primary` at full alpha): the divider is already defined as `text.primary` scaled by an alpha, so high contrast raises that alpha to 1.0 rather than introducing an eleventh role or a new literal (014 contract T10: the divider is "never a role of its own, never a call-site literal"; `tests/design_token_literals.rs` enforces it). It clears the 3:1 floor with margin on both surfaces in both themes (17.01:1 / 13.91:1 light, 16.48:1 / 13.48:1 dark — § 4.2's own measured `text.primary` figures) and is a one-line change at the single selection site every border, row divider, `Default` button outline and switch off-outline already reads from. Written into FR-007.
- Q: What colour and width is FR-012's marker outline (the prior session deferred this to plan; a default that lives only in plan is not resolved for `analyze`)? → A (the active theme's `text.primary`, 1 px, drawn around the glyph's silhouette): `text.primary` is its theme's extreme luminance end, so it holds ≥7:1 against both waveform surfaces no matter which of the eight mid-toned palette hues it encircles — no per-entry tuning, which is exactly what FR-012's "never a treatment that could itself fail against a given palette entry" asks for. 1 px is chosen over a thicker stroke because a marker glyph's own stroke already carries state: a focused glyph paints at 2 px against an unfocused 1.5 px (`markers.rs::paint_glyph`), and a fatter outline would swamp that 0.5 px difference. Written into FR-012.
- Q: FR-011 says "every marker and loop-region host glyph" gains the outline — does that include the other places a `MARKER_PALETTE` colour is painted (the Markers panel row's colour swatch, the armed loop region's span shading, a plugin overlay's shape fill), and do overlays coloured `Accent`/`Secondary`/`Neutral` get one too? → A (every palette-coloured surface; no outline for the role-coloured overlays): the outline exists because a palette colour is *data* exempted from the high-contrast recolouring, so it must apply wherever that exempt colour is painted — lane glyph (overview and detail lanes), loop-region span shading, the panel row's colour swatch, and any plugin overlay primitive whose `OverlayColor` resolves to a palette entry (`Positive` → `MARKER_PALETTE[2]`, `Warning` → `MARKER_PALETTE[3]`, per 011's ratified mapping). `Accent`/`Secondary`/`Neutral` overlays resolve through the recoloured roles instead, so they are already at the high-contrast values and adding an outline would only obscure them. Written into FR-011.
- Q: How is the new setting represented in the persisted settings file, and what exactly happens to a malformed value (FR-003 says only "defaults to disabled")? → D (mirroring `appearance.theme` in `crates/modplayer-core/src/settings/model.rs`): a boolean `high_contrast` field in the same `[appearance]` table as `theme`, serde-defaulted to `false` when absent, and, when present but not a TOML boolean, recovered to `false` **and** reported through the same invalid-field channel `InvalidField::Theme` uses today — a new `InvalidField` variant whose `field_name()` is `"appearance.high_contrast"` — so a corrupted appearance file surfaces the same way for both fields instead of one failing silently. Written into FR-003.
- Q: What shape is the control, where does it sit, and what strings label it? → A (a checkbox, below the Theme combo, from new Fluent keys): the Appearance screen's only other state control is the Theme combo, and the project already ships a checkbox for a persisted boolean (`switch(ui, SwitchKind::Checkbox, ..)`, 015) — a checkbox is the conventional shape for an independent on/off axis and is what makes FR-001's "alongside, not inside the combo" visible at a glance. Its label and description come from new `setting-high-contrast` / `setting-high-contrast-desc` keys in `locales/en-US/settings.ftl` through `tr()`, never a Rust string literal (Constitution X: all host strings externalized; `tests/fluent_keys.rs` gates it). Written into FR-015.
- Q: Is the new setting reachable from the Settings search, as every other setting is? → D (repo convention, `crates/modplayer-core/src/settings_registry.rs`): yes — every settings control has a `SettingDescriptor` row (category, id, `title_key`, `description_key`), and the Appearance screen already focuses a control when the search result's id arrives as `focus`. The high-contrast control gets a descriptor with category `Appearance`, id `appearance.high_contrast` and the FR-015 keys, and focusing it from a search result moves keyboard focus onto the checkbox. Written into FR-016.
- Q: By what mechanism does one palette choice reach both host chrome and plugin panels — per-call-site branching on a high-contrast flag, or a second palette table selected once? → D (one selection site, per 014's once-per-frame token application and contract A4): high contrast selects a different `Roles` table for the active theme at the single point the host already builds and applies its style once per frame; no call site, and no plugin, ever branches on the flag. This is what makes FR-013's zero-plugin-change promise structurally true rather than a convention — a docked panel reads the same applied style object as the host chrome, so it cannot diverge. The two values that are widths rather than roles (the focus ring, FR-008; the marker outline, FR-012) resolve from the same single selection, not from a flag read at their draw sites. Written into FR-017.
- Q: How is the 7:1 / 3:1 / 4.5:1 promise verified, given Constitution VIII ("test what the NFRs promise")? → D (014's own precedent): by extending the existing automated contrast test (`crates/modplayer-ui/tests/design_token_contrast.rs`, over `theme::contrast::ratio`) to the high-contrast tables, asserting each of `accent`/`positive`/`warning`/`danger` ≥7:1 against both surfaces per theme, `text.primary` (and therefore the promoted `text.secondary`) ≥7:1 against both surfaces, the divider ≥3:1 against both surfaces, and `text.on-accent` ≥4.5:1 against the high-contrast accent — the same gate that made 014's own swatch adjustments objective rather than eyeballed. Written into FR-018.
- Q: Do the interaction-state overlays (4 % hover fill, 8 % pressed fill) and the cue glyph's digit mark change in high contrast? → A (neither changes): the prompt's enumeration of what high contrast alters is exhaustive (FR-002) and names neither. Hover/pressed remain alpha overlays on `text.primary`, whose ordering — not their absolute weight — is 015's normative property; the operability signal high contrast is required to strengthen is the focus ring (FR-008), which it does. The cue digit keeps painting in `text.on-accent` over its unchanged palette fill, exactly as in normal mode; that pairing's legibility is a pre-existing property of the palette, not something this feature changes, and any improvement to it belongs with 007-operations-and-polish/004-accessibility-hardening. Recorded in Edge Cases.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Every text sample reads clearly in high contrast (Priority: P1)

A user who cannot read the default palette turns on high contrast and can read every piece of text in every view — track titles, row secondary lines, panel headers, help text, numeric readouts — instead of the same 4.5:1-floor text the app ships by default.

**Why this priority**: This is the feature's lead acceptance line and its core accessibility promise (`UX-39`, § 4.6, NFR-6.5). Without it, "high contrast" is a label with no measurable outcome.

**Independent Test**: With high contrast enabled, sample any text element in any view against its background using the project's contrast tool and confirm the ratio is at least 7:1.

**Acceptance Scenarios**:

1. **Given** high contrast is enabled in either theme, **When** any text sample (title, body, secondary, section, or mono role) is measured against its background, **Then** the contrast ratio is at least 7:1.
2. **Given** high contrast is enabled, **When** a `secondary`-role element (an artist/album line, help text, a metadata field) is measured, **Then** it renders using the same colour value as `text.primary` in the active theme, not its own normal-mode `text.secondary` value.
3. **Given** high contrast is disabled, **When** the same text elements are measured, **Then** their contrast is unchanged from today's normal-mode values (no regression outside high contrast).

---

### User Story 2 - High contrast is a setting, independent of light/dark, that applies live and survives a restart (Priority: P1)

A user opens Appearance settings, finds a high-contrast choice next to the existing System/Light/Dark theme selection, turns it on, sees every view repaint immediately with no relaunch, and finds it still on the next time they open the app — in whichever of light or dark they were using.

**Why this priority**: This is the feature's second acceptance line and the mechanism the whole feature depends on — without a persistent, live-applying, orthogonal setting, US1's contrast values are unreachable by a real user.

**Independent Test**: Open Appearance settings, enable high contrast, confirm the current view repaints without restarting the app, restart the app, and confirm both the high-contrast choice and the light/dark choice are exactly as left.

**Acceptance Scenarios**:

1. **Given** the Appearance settings screen is displayed, **When** it renders, **Then** a high-contrast control is shown alongside, not inside, the System/Light/Dark theme combo, and any of the three theme values can be combined with high contrast on or off.
2. **Given** high contrast is toggled on or off, **When** the change is made, **Then** every open view repaints with the new palette on its next frame, with no relaunch.
3. **Given** high contrast is enabled and the app is restarted, **When** the app reopens, **Then** high contrast is still enabled and the light/dark choice is unchanged from before the restart.
4. **Given** high contrast is enabled while the theme is Dark, **When** the user separately switches the theme to Light, **Then** high contrast remains enabled and the view shows high-contrast light, not normal-mode light.

---

### User Story 3 - Markers stay individually identifiable in high contrast (Priority: P2)

A user viewing a track's markers on the waveform with high contrast enabled can still tell each marker apart, because each one gains an outline, instead of markers whose colours were only tuned for the normal palette.

**Why this priority**: This is the feature's third acceptance line. Marker colour is host data, not decoration (006), so it is explicitly exempt from the high-contrast recolouring the rest of the palette gets — this story is what keeps that exemption from becoming an accessibility hole.

**Independent Test**: Place several markers of different palette colours on a track, enable high contrast, and confirm each marker remains visually distinguishable from its neighbours and from the waveform background.

**Acceptance Scenarios**:

1. **Given** a track has markers placed using different `MARKER_PALETTE` colours, **When** high contrast is enabled, **Then** each marker's rendered colour is unchanged from normal mode, but each marker additionally shows an outline that was not present in normal mode.
2. **Given** two markers on the waveform, **When** both are compared under high contrast, **Then** each remains individually identifiable — by its (unchanged) hue plus its new outline — even if the two markers' hues are close to one another.
3. **Given** a plugin overlay that maps onto a `MARKER_PALETTE` entry (011's `OverlayColor::Positive`/`Warning`), **When** high contrast is enabled, **Then** that overlay's colour is unchanged and it too gains the same outline treatment as a host marker.

---

### User Story 4 - A docked plugin panel is never the one unreadable area (Priority: P2)

A user with high contrast enabled who has a plugin panel docked in the window can read that panel's text and operate its controls exactly as clearly as the host chrome around it, instead of the panel silently staying on the normal-mode palette.

**Why this priority**: This is the feature's third-named acceptance line. A plugin panel that stayed low-contrast while the host around it went high-contrast would defeat the purpose of turning high contrast on at all.

**Independent Test**: Dock a plugin panel, enable high contrast, and confirm the panel's text and controls read at the same contrast levels as the surrounding host UI, with no plugin-side change required.

**Acceptance Scenarios**:

1. **Given** a plugin panel is docked and high contrast is enabled, **When** the panel renders, **Then** its text and controls use the same high-contrast token values as the host chrome around it.
2. **Given** a plugin panel was already docked before high contrast was turned on, **When** high contrast is enabled, **Then** the panel repaints with the new palette on its next frame with no plugin-side code running and no new call into the plugin.

---

### User Story 5 - Structure stays visible, not just text (Priority: P3)

A user with high contrast enabled can still see where one panel or control ends and another begins, and can see which control currently holds keyboard focus, because borders, dividers and the focus ring all gain enough weight to read clearly — instead of the normal mode's barely-visible 8%-alpha hairlines.

**Why this priority**: This is a supporting requirement named in the prompt (borders/dividers at 3:1, thicker focus rings) rather than one of the prompt's four numbered acceptance lines, but without it a high-contrast user can read every word while being unable to see where one control or panel stops and the next begins.

**Independent Test**: With high contrast enabled, sample a panel border/divider against its surface and confirm at least 3:1 contrast; separately, move keyboard focus onto a control and confirm the focus ring reads visibly thicker than in normal mode.

**Acceptance Scenarios**:

1. **Given** high contrast is enabled, **When** any border, outline or divider drawn from the token module's divider value is measured against its surface, **Then** the contrast ratio is at least 3:1.
2. **Given** high contrast is enabled, **When** keyboard focus lands on a control, **Then** the focus ring renders visibly thicker than the normal-mode 2px ring.

---

### Edge Cases

- The user is on `Theme::System` and the OS is in dark mode: high contrast applies to whichever of light/dark the system currently resolves to, live, exactly as the normal-mode palette already does (Clarifications).
- A user turns high contrast on and off repeatedly in quick succession: each toggle fully applies before the next input is processed; no view is left on a half-applied palette.
- A marker's palette colour already reads close to its outline colour in one theme: the outline is the theme's `text.primary` (FR-012) — its extreme luminance end — so it holds against every one of the eight palette entries on both waveform backgrounds without being tuned per-entry.
- A marker glyph is focused while high contrast is on: the outline is added *around* the glyph and the existing focused/unfocused stroke-width difference is preserved (FR-012), so focus is still readable and is not swallowed by the new stroke.
- A cue glyph's slot digit is drawn over its palette fill while high contrast is on: it keeps painting in `text.on-accent` over the unchanged palette colour, exactly as in normal mode. That pairing's legibility is a pre-existing property of the palette, not something this feature alters (FR-011 leaves palette fills untouched); improving it belongs with 007-operations-and-polish/004-accessibility-hardening.
- A control is hovered or pressed while high contrast is on: the hover/pressed overlays keep their normal-mode alphas (FR-020) — high contrast strengthens the focus ring, not the pointer-state tints.
- A plugin panel is undocked and redocked while high contrast is on: it re-reads the current style/visuals on the next frame like any other panel open event, so it never briefly shows the normal-mode palette.
- The settings file holds an unparseable value for the high-contrast field: the setting falls back to disabled (off) and is reported as invalid field `appearance.high_contrast` through the same channel `appearance.theme` uses (FR-003) — recovered, not silently dropped.
- A disabled control's label is visible while high contrast is on: it keeps the existing non-text 3:1 floor (`text.disabled`) rather than the 7:1 text floor — high contrast does not change which roles are text versus non-text-component (014's own distinction, unchanged here).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST add a high-contrast choice to the Appearance settings screen, presented as a control independent of and alongside the existing System/Light/Dark theme combo — never as a fourth `Theme` value — so any of the three theme values can be combined with high contrast on or off. *(Prompt: "orthogonal to the light/dark/system selection"; Clarifications)*
- **FR-002**: Enabling high contrast MUST NOT change which of Light/Dark is active, and MUST NOT change `surface.base` or `surface.raised` in either theme; it changes only the colour and stroke values named in FR-005 through FR-012 — the promoted `text.secondary`, the divider, the four named roles (and `text.on-accent` where FR-010 requires it), the focus-ring width, and the marker outline — within whichever theme (including the theme `System` currently resolves to) is active. *(Prompt; Clarifications)*
- **FR-003**: The high-contrast choice MUST persist across restarts as a boolean `high_contrast` field in the same `[appearance]` table of the same persisted settings store that holds `theme`, independent of `theme`, defaulting to disabled (`false`) when the field is absent. A present-but-malformed value (not a boolean) MUST recover to disabled **and** be reported through the same invalid-field channel `appearance.theme` already uses, as its own field name `"appearance.high_contrast"` — never silently dropped. *(Prompt: "persists across restarts alongside the existing theme preference"; the `appearance.theme` / `InvalidField::Theme` recovery pattern in `crates/modplayer-core/src/settings/model.rs`; Clarifications)*
- **FR-004**: Enabling or disabling high contrast MUST apply live, on the next frame, with no relaunch — the same once-per-frame token application the host already uses for a theme switch. *(Prompt: "applies live without relaunching"; 014-design-tokens-and-type-scale FR-002)*
- **FR-005**: When high contrast is enabled, the active theme's `text.secondary` role MUST resolve to the same colour value as that theme's `text.primary` — the promotion is a substitution of the role's value at the single palette-selection site (FR-017), not a rendering-time special case at text call sites. Every consumer of `text.secondary` therefore follows it: secondary text (artist/album lines, help text, metadata fields), the switch's off-state thumb, the unchecked checkbox/radio mark, the weak-text colour, and a plugin overlay coloured `OverlayColor::Neutral`. Testable: with high contrast on, the active role table satisfies `text.secondary == text.primary` in both themes. *(Prompt: "secondary text is promoted to the primary text colour"; Clarifications)*
- **FR-005a**: `text.primary` already meets at least 7:1 contrast against both `surface.base` and `surface.raised` in both themes (measured: light 17.01:1 / 13.91:1, dark 16.48:1 / 13.48:1). This feature MUST NOT lower those values, so FR-005's promotion is sufficient on its own to bring every non-disabled text sample to at least 7:1 without any further change to `text.primary` itself. *(§ 4.2; Prompt acceptance line 1)*
- **FR-006**: `text.disabled` is unaffected by this feature and keeps its existing non-text 3:1 contrast floor in both normal and high-contrast mode; the 7:1 requirement applies to active, readable text, not to a disabled control's label. *(014's text/non-text distinction, unchanged here; Edge Cases)*
- **FR-007**: When high contrast is enabled, the token module's divider value MUST resolve to the active theme's `text.primary` at full alpha, in place of normal mode's `text.primary` at 8 % alpha — no new colour role and no call-site literal. Every border, outline and divider drawn from it therefore reaches at least 3:1 against the surface it sits on (measured 17.01:1 / 13.91:1 light, 16.48:1 / 13.48:1 dark against `surface.base` / `surface.raised`), including panel borders, row dividers, the `Default` button variant's outline, and a switch's off-state outline. The ≥3:1 floor is the acceptance test; full-alpha `text.primary` is the normative starting value that satisfies it. *(Prompt: "every border and divider reaches at least a 3:1 ratio against its surface"; 014 contract T10; Clarifications)*
- **FR-008**: When high contrast is enabled, the focus ring MUST thicken beyond its normal-mode 2px width to a width clearly distinguishable at a glance (3px), while keeping its `accent`-role colour (the high-contrast accent variant, FR-009). *(Prompt: "focus rings thicken")*
- **FR-009**: When high contrast is enabled, the `accent`, `positive`, `warning`, and `danger` roles MUST each resolve to a distinct high-contrast variant value that reaches at least 7:1 contrast against both `surface.base` and `surface.raised` in the active theme, replacing their normal-mode values everywhere those roles are used (buttons, meters, plugin health, the focus ring, selection fill, hyperlink colour, tab underline) with no change required at any individual call site. Starting values (normative; the exact accepted values are whatever the automated contrast test accepts, matching 014's own precedent for adjusted swatches):

  | Role | Light: normal → high-contrast | Dark: normal → high-contrast |
  |---|---|---|
  | `accent` | `#0a63c9` → `#074a96` (8.65:1 / 7.07:1) | `#5aa9ff` → `#74b6ff` (8.65:1 / 7.08:1) |
  | `positive` | `#1f7a44` → `#165630` (8.72:1 / 7.13:1) | `#4caf50` → `#57c95c` (8.68:1 / 7.10:1) |
  | `warning` | `#8a5a00` → `#694400` (8.65:1 / 7.07:1) | `#e0a92a` → `#e0a92a` (unchanged — already 8.65:1 / 7.08:1) |
  | `danger` | `#b3261e` → `#931f19` (8.57:1 / 7.00:1) | `#ff6b5e` → `#ff9a91` (9.00:1 / 7.37:1) |

  *(Prompt: "the accent, positive, warning and danger roles are replaced with variants that reach at least 7:1 against their surface"; ratios computed against `surface.base`/`surface.raised` per theme)*
- **FR-010**: `text.on-accent` MUST continue to hold at least 4.5:1 contrast against the high-contrast `accent` value in its own theme; if the FR-009 accent substitution does not clear that floor against today's `text.on-accent` value, `text.on-accent` gets its own high-contrast counterpart to restore it. *(014 FR-010a's paired-role requirement, carried into the high-contrast variant)*
- **FR-011**: `MARKER_PALETTE` entries, and any plugin overlay colour drawn from them (`overlay_color`), MUST NOT change value when high contrast is enabled — a marker keeps its colour across every appearance change, per its existing theme-independence (006, 014). Instead, when high contrast is enabled, every host-rendered surface whose colour comes from a `MARKER_PALETTE` entry MUST gain an outline that is not present in normal mode: the marker/loop-region lane glyph in both the overview and the detail lane, the armed loop region's span shading, the Markers panel row's colour swatch, and any plugin overlay primitive whose `OverlayColor` resolves to a palette entry (`Positive`, `Warning` — 011's ratified mapping). Plugin overlays coloured `Accent`, `Secondary` or `Neutral` resolve through the recoloured roles instead and MUST NOT gain an outline. *(Prompt: "marker colours, plugin overlay colours — keep their hue but gain an outline"; Clarifications)*
- **FR-012**: The outline added by FR-011 MUST be a 1 px stroke in the active theme's `text.primary`, drawn around the outline of the palette-coloured shape. Because `text.primary` is its theme's extreme luminance end, this holds at least 7:1 against both waveform surfaces regardless of which of the eight palette entries it encircles, satisfying the requirement that no palette entry can defeat the treatment. The outline MUST NOT replace or obscure the glyph's existing focused/unfocused stroke-width distinction (2 px focused versus 1.5 px unfocused), so a focused marker stays identifiable as focused with high contrast on. *(Prompt: "so they stay distinguishable"; Clarifications)*
- **FR-013**: Because plugin-contributed panels and overlays already read colour and font exclusively from the host's shared style/visuals object and hold no colour literal of their own (contract A4, `011-plugin-ui-contributions/contracts/ui-panels.md`), enabling high contrast MUST reach every docked plugin panel and every plugin-drawn overlay with zero plugin-side code change and no new plugin API surface. *(Prompt: "reaches plugin-contributed panels and overlays through the same tokens the host uses"; contract A4)*
- **FR-014**: This feature MUST NOT add a fourth `Theme` value, MUST NOT add an automatic operating-system high-contrast preference follow mode, MUST NOT change the type scale or any text-scale setting, and MUST NOT change keyboard operability, accessible names/roles/states, or any component's layout or interaction behaviour beyond adding the FR-015 control to the Appearance screen — those remain the scope of 007-operations-and-polish/004-accessibility-hardening. *(Scope boundary; Clarifications)*
- **FR-015**: The FR-001 control MUST be a checkbox rendered on the Appearance settings screen below the Theme combo, and its label and description MUST come from new externalized `setting-high-contrast` / `setting-high-contrast-desc` message keys resolved through the host's translation lookup — no Rust string literal, matching every other settings control. *(Constitution X: all host strings externalized; 015's checkbox control; Clarifications)*
- **FR-016**: The high-contrast setting MUST be registered in the settings descriptor table like every other setting — category `Appearance`, id `appearance.high_contrast`, carrying the FR-015 message keys — so it is found by the Settings search, and arriving at the Appearance screen from one of its search results MUST move keyboard focus onto the checkbox, exactly as `appearance.theme` does today. *(Repo convention, `crates/modplayer-core/src/settings_registry.rs`; Clarifications)*
- **FR-017**: High contrast MUST be applied by selecting a different colour-role table for the active theme at the single site where the host already builds and applies its style once per frame. No host call site and no plugin may branch on the high-contrast flag to pick a colour: every colour, including the FR-008 focus-ring width and the FR-012 marker outline, MUST resolve from that one selection. A docked plugin panel therefore reads the identical applied style object as the host chrome around it and cannot diverge from it. *(014's once-per-frame token application; contract A4; Constitution X; Clarifications)*
- **FR-018**: The contrast promises of FR-005, FR-007, FR-009 and FR-010 MUST be verified by the project's existing automated WCAG contrast test rather than by inspection: with high contrast enabled, each of `accent`, `positive`, `warning`, `danger` measures at least 7:1 against both `surface.base` and `surface.raised` in its own theme, `text.primary` (and the `text.secondary` promoted onto it) measures at least 7:1 against both surfaces, the divider measures at least 3:1 against both surfaces, and `text.on-accent` measures at least 4.5:1 against the high-contrast `accent`. *(Constitution VIII; 014's `design_token_contrast` precedent; Clarifications)*
- **FR-019**: Every colour and stroke width this feature introduces MUST live in the theme module alongside the existing role tables — no new colour or width literal at any call site, host or plugin-facing. *(014/015's no-literals rule, gated by `crates/modplayer-ui/tests/design_token_literals.rs`)*
- **FR-020**: High contrast MUST NOT change the interaction-state overlays: the hover and pressed fills keep their normal-mode alphas over `text.primary`, their ordering (`0 < hover < pressed`) remaining the normative property. The operability signal high contrast strengthens is the focus ring (FR-008). *(FR-002's exhaustive enumeration; 015's interaction-state contract; Clarifications)*

### Key Entities

- **High-Contrast Appearance Setting**: A persisted boolean preference, independent of and orthogonal to the existing `Theme` (System/Light/Dark) preference, stored alongside it and restored on every restart.
- **High-Contrast Colour Variant**: A per-role, per-theme alternate value for `accent`, `positive`, `warning`, `danger`, and (where needed) `text.on-accent`, each holding at least 7:1 contrast against both surfaces in its theme, substituted in place of the role's normal-mode value while high contrast is enabled.
- **High-Contrast Border Value**: The divider/border/outline colour used in place of the normal mode's 8%-alpha divider while high contrast is enabled — the active theme's `text.primary` at full alpha, holding at least 3:1 against both surfaces.
- **Marker Outline**: A 1px `text.primary` stroke drawn around every surface whose colour comes from `MARKER_PALETTE` — lane glyph, loop-region span shading, panel row swatch, and a plugin overlay resolved to a palette entry — only while high contrast is enabled; the marker's own fill colour is never changed by it.
- **High-Contrast Setting Descriptor**: The Settings-search registry row for the new setting (category `Appearance`, id `appearance.high_contrast`, title/description message keys), which makes it findable by search and focusable from a search result.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: When high contrast is enabled, every readable text sample sampled across every view (excluding a disabled control's label) measures at least 7:1 contrast against its background, up from normal mode's 4.5:1 floor.
- **SC-002**: When high contrast is enabled and a track has markers placed, sampling any two markers on the waveform finds each one individually identifiable, with no two adjacent markers rendering indistinguishably.
- **SC-003**: When high contrast is enabled and a plugin panel is docked, 100% of that panel's sampled text and control colours match the host's high-contrast token values, with zero low-contrast elements found inside the panel.
- **SC-004**: After the app restarts, both the high-contrast choice and the light/dark choice are restored exactly as they were set before the restart, on 100% of restarts.
- **SC-005**: Turning high contrast on or off is visible on-screen on the very next frame, with no relaunch and no flash of unstyled content.
- **SC-006**: When high contrast is enabled, every sampled border, divider and outline measures at least 3:1 contrast against its surface.
- **SC-007**: When high contrast is enabled and keyboard focus moves onto a control, the rendered focus-ring width measures visibly greater than the normal-mode 2px ring.
- **SC-008**: The automated contrast test covers 100% of the high-contrast role/surface pairs named in FR-018 in both themes, and the build fails if any pair drops below its floor — the 7:1, 3:1 and 4.5:1 promises are machine-checked, never eyeballed.
- **SC-009**: Searching the Settings screen for the high-contrast setting returns it, and opening that result lands on the Appearance screen with keyboard focus on the high-contrast control — the same behaviour the Theme setting already has.

## Assumptions

- High contrast is a manual, user-chosen setting; this feature does not read or follow any OS-level high-contrast/increased-contrast system preference (Clarifications).
- `surface.base` and `surface.raised` are unchanged by high contrast in either theme; only `text.secondary` (promoted), borders/dividers, the four named colour roles, and the focus-ring width vary (Clarifications).
- `text.disabled` keeps its existing non-text 3:1 floor in high contrast; the 7:1 text floor does not apply to it (014's text/non-text distinction, unchanged).
- The focus ring widens to 3px in high contrast (from the normal mode's 2px); no source states an exact target width, so this is a reasonable, clearly-distinguishable default (Assumption).
- The high-contrast `accent`/`positive`/`warning`/`danger` swatches in FR-009 are normative starting values; the values an implementation actually ships are whatever the automated WCAG contrast test accepts, so long as each clears 7:1 against both surfaces in its own theme, mirroring 014's own precedent for adjusted swatches.
- The marker outline is a 1px `text.primary` stroke (FR-012, clarify pass) — no longer a plan-time choice.
- The high-contrast divider is `text.primary` at full alpha (FR-007, clarify pass), raising the existing 8%-alpha multiplier rather than adding a role or a literal.
- `text.secondary`'s promotion is a role-value substitution, so its non-text consumers (switch thumb, unchecked mark, weak text, plugin `Neutral` overlays) follow it (FR-005, clarify pass).
- The control is a checkbox below the Theme combo with externalized strings, registered in the settings descriptor table as `appearance.high_contrast` (FR-015, FR-016).
- Hover and pressed overlays, and the cue digit's `text.on-accent` mark, are unchanged by high contrast (FR-020, Edge Cases).
- No new `Theme` enum variant is added; high contrast is a second, independent boolean axis alongside the existing three-state theme preference.
- The plugin `OverlayColor` → `MARKER_PALETTE` mapping ratified in 011 is unaffected by this feature; only whether an outline is drawn around the resolved colour changes.
