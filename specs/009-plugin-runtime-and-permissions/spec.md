# Feature Specification: Plugin Runtime, Sandbox, and Permission Gateway

**Feature Branch**: `feature/009-plugin-runtime-and-permissions`

**Created**: 2026-09-19

**Status**: Clarified (2026-09-19, specify pass + clarify pass) — no open [NEEDS CLARIFICATION] markers, no human escalations; ready for `/speckit-plan`

**Input**: User description: "Let small scripted plugins act on the music while it plays, without ever being able to take the player down. A plugin is a folder with a manifest (immutable reverse-domain identifier, name, version, supported API version range, author/license/source, entry script, required and optional permissions each with a one-line justification, declared network hosts, declared UI contributions, intended effect nodes) plus scripts and resources. In this slice the only source is \"bundled\": plugins shipped with the host, enabled by default with pre-approved permissions. Each plugin runs in its own isolated script context with no shared memory, its own scheduler and timers, and budgets: 4 ms CPU per event handler, 10% of one core averaged over a second, 64 MB memory, 10 MB storage. Exceeding a handler budget aborts that handler; exceeding the share or memory cap suspends the plugin. Plugin code never runs on the real-time path. On load the host hands the plugin a single API object shaped by its granted permissions; the plugin calls `ready()` before receiving events, and is suspended if it never does. Every request returns success or a structured refusal — `permission_denied`, `no_focus`, `invalid_state`, `not_found`, `rate_limited`, `budget_exceeded` — never a crash. Capabilities in this slice, each gated by its permission: observe playback (`track_changed`, `position` up to 60/s coalesced, `play_state_changed`, `queue_changed`), control transport and queue, read and write markers/loops/cues (own markers only), create and parameterize effect nodes (own nodes only, with a suggested chain position honored on insertion), receive meters, persist plugin-scoped and per-track key-value state (per-track state restored before `track_changed`), and timers including `schedule_at_position`. A plugin list shows name, version, source, enabled state, health (ok/warning/suspended), permission summary, and CPU/memory, with enable and disable. Disabling or suspending a plugin removes its UI, releases focus, disarms its loops, cancels timers, and orphans (does not remove) its effect nodes after an `unloading` event with bounded time to persist state. Uninstall is unavailable for bundled plugins. Acceptance: when a plugin enters an infinite loop in a handler, the host suspends it within its budget window, audio and transport continue uninterrupted, a non-blocking notice names the plugin, and the user sees Restart / Disable; three suspensions in a session auto-disable it. When a plugin calls a transport request without `transport.control`, it receives `permission_denied` and nothing else happens. When a plugin issues 1,000 seeks per second, excess calls return `rate_limited`. When a manifest requests a permission not in the catalog, the plugin is listed as \"invalid manifest: <reason>\" and not loaded."

**Source**: [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) — Part 5 §1 Design principles, §2 Plugin package, §3 Lifecycle, §4 Permission catalog, §5 Events (host→plugin), §6 Requests (plugin→host) 6.1–6.4, 6.6, 6.10, §8 Sandboxing and budgets; FR-7.1 Sources and installation (bundled source), FR-7.3 Lifecycle, FR-1.4.2; DM-10 Plugin, DM-11 PermissionGrant, DM-12 PluginStateEntry; Part 9 §3 Plugin subsystem (AR-16 Plugin Runtime, AR-17 Capability Gateway), Part 9 §5 Key flows (5.1, 5.4), Part 9 §6 Trust boundaries; J-7 A plugin misbehaves during practice; EC §6 Plugins; NFR §2 Reliability (NFR-2.3), NFR §4 Security (NFR-4.3); JTBD-4, JTBD-15. Prerequisites: [006-markers-loops-and-cues](../006-markers-loops-and-cues/spec.md) (markers/loops/cues a plugin acts on), [007-keyboard-actions-and-shortcuts](../007-keyboard-actions-and-shortcuts/spec.md) (the action registry a later UI-contributions slice will let plugins extend), [008-effect-chain-and-built-in-nodes](../008-effect-chain-and-built-in-nodes/spec.md) (the effect chain, its owner field, and the overload/auto-bypass mechanism this slice activates for real by shipping the first non-host node owner).

**Scope boundary**: Does not cover panel/overlay/shortcut/settings-page UI contributions (`ui.*` permissions), transport focus arbitration policy or its panel (001-mvp/010), the community registry or sideloaded/dev-folder sources (only "bundled" ships), the permission approval sheet (so per-permission revocation and `permission_changed` are also deferred), network access (`network`), file access (`files.*`), clipboard, MIDI, or the custom buffer processor (`audio.process`) — only the plugin runtime, its sandbox and budgets, the Capability Gateway, and the bundled-source lifecycle/permission model.

- Q: The prompt's budget numbers (4 ms/handler, 10% of one core, 64 MB, 10 MB) match PL-8.1's *defaults*, and A-12 calls them "placeholders to tune after measurement" — are they requirements for this slice or configurable? → A (D, PL-8.1 "default"; A, A-12): they ship as the fixed values for this slice. PL-8.2's manifest-declared higher-budget override (with justification, shown at install) needs the approval-sheet UI this slice excludes, so no plugin can request a higher budget here, and neither bundled plugin does.
- Q: The scripting language and sandbox technology (breakdown Q-6) determine whether the runtime can hard-interrupt a genuinely blocking handler — is that choice part of this spec? → A (D, Constitution II: the sanctioned choice among WASM+fuel, Rhai, or Lua via mlua must be recorded in an Architecture Decision Record before the plugin-runtime crate is implemented): the choice is a plan-time/ADR decision. This spec states the requirement in technology-agnostic terms only — the runtime MUST be able to preemptively interrupt a handler at its CPU budget regardless of whether the plugin code cooperates — and the plan phase records the ADR.
- Q: PL-8.3 says exceeding a per-handler budget "aborts that handler" and the plugin keeps running, but the lifecycle diagram shows "budget exceeded / unresponsive" going straight from Active to Suspended — which applies to "a plugin enters an infinite loop... the host suspends it within its budget window"? → A (D, both rules read together, PL-3.6/PL-8.3 + the lifecycle diagram): one handler-budget abort does not by itself suspend the plugin; the handler is killed and the plugin's next event still runs. A genuinely looping handler keeps re-triggering the same abort on every subsequent invocation it's given (e.g., each `position` tick, each timer fire), and those repeated abort costs accumulate against the plugin's 1-second, 10%-of-one-core aggregate share; crossing that share (or the memory cap) is what suspends the whole context. A handler that blocks forever on a *single* invocation without ever returning control is suspended by the same preemptive interruption that enforces the 4 ms handler budget in the first place. Either path lands within the plugin's own budget window (≤ ~1 s), matching the acceptance text.
- Q: No numeric per-request rate limit exists anywhere in the source (only `network`, out of scope, gets 60 req/min) — what threshold turns "1,000 seeks per second" into `rate_limited`? → A (A, generous enough that nothing in this slice's legitimate usage — capped at 60 Hz for `position` — ever approaches it, yet far below the abuse case in the acceptance text): the Gateway enforces one limit per plugin per request category (transport, markers, effects, state, timers) of 100 calls/second on a rolling 1-second window; a call beyond the 100th in its category within that window returns `rate_limited` immediately, with no host-side effect, and is not queued or retried by the host.
- Q: PL-5.2 says `position` is delivered "at a plugin-chosen rate up to 60/s" that the host coalesces — what is delivered if a plugin never specifies a rate? → A (A, a low default that stays useful without spending budget): the default requested rate is 10 events/second when unspecified; any requested rate is clamped to `[1, 60]`/s (NFR-1.9), and the host coalesces intermediate updates so only the most recent position is delivered each interval.
- Q: Is `arm_loop`/`disarm_loop` gated by `markers.write` (the permission catalog's own explanation text, "arm loop regions") or by `transport.control` (whose request list in §6.1 also names `arm_loop(region)`/`disarm_loop()`)? → A **(superseded by the clarify pass, below)**: the specify pass resolved this as `markers.write` only, independent of focus. That contradicts three sources — §6.1 ("Transport mutations other than `request_focus` require the plugin to hold focus, or return `no_focus`", with `arm_loop`/`disarm_loop` in that list), EC-4.4 ("Only the focus holder can arm; the other receives `no_focus`"), and Part 9 §5.1 step 2 ("Gateway checks `markers.write` and transport focus (the plugin must hold focus to arm)"). See the clarify-pass entry for the corrected rule.
- Q: Part 5 §6.10 (timers) names no `Requires` permission, unlike every other request group, and the permission catalog table has no `timers` row — yet the prompt's lead-in says every capability in this list is "gated by its permission." Do timers need one? → A (D, absence of a catalog row and of a `Requires` column entry): timers (`set_timeout`, `set_interval`, `schedule_at_position`) are an ungated runtime facility available to any Active plugin regardless of its granted permissions, subject to the same per-handler and aggregate CPU budgets as everything else; the prompt's "each gated by its permission" describes the seven capabilities that do have one.
- Q: `transport.control`'s request surface includes `request_focus()`/`release_focus()`, but transport-focus *arbitration* (policy, contention, the panel, `focus_granted`/`focus_revoked`) is explicitly out of scope (010) — and plugins have no UI in this slice (`ui.*` excluded) so a user can never "interact with a plugin's controls" to trigger the auto-on-interaction policy. What do these two calls do here, given 010's own prerequisite line says it "assumes ... `transport.control` capability from 009"? → A (D, 010 must have something working to extend): this slice ships a single global focus holder defaulting to the host. `request_focus()` is granted immediately when no plugin currently holds focus; calling it while another plugin already holds focus returns `invalid_state` (multi-plugin contention resolution is 010's job). `release_focus()` always succeeds and returns focus to the host. Every other transport mutation (`play`, `pause`, `toggle`, `seek`, `skip_next`, `skip_previous`) requires the calling plugin to currently hold focus, returning `no_focus` otherwise. The user's own transport actions, from the host UI or keyboard, are unaffected and always take precedence (unchanged since 003/007; Constitution X). Full policy, the previous-holder notification chain, and the Transport panel ship in 010.
- Q: Does `queue.write` interact with transport focus at all? → A (D, FR-3.2 and the permission catalog describe queue modification independent of focus; nothing in Part 5 gates it on focus): no; any plugin holding `queue.write` may view, reorder, add to, and remove from the queue regardless of who holds transport focus.
- Q: PL-4.5 says a runtime permission revocation delivers `permission_changed`, but the only UI FR-7.2.4 names for changing an individual plugin's permissions (the approval sheet) is out of scope — is per-permission revocation possible in this slice? → A (D, scope boundary): no. A bundled plugin's permission grants are fixed to its manifest's declared, pre-approved set (FR-1.4.2) for as long as it is enabled; the only state change available to the user is enabling or disabling the whole plugin. `permission_changed` and per-permission revocation ship with the approval-sheet slice.
- Q: EC-6.4 says health becomes `warning` "after repeated errors" — how many, over what window, and does it clear? → A (A, no number given in the source): three handler exceptions within a rolling 60-second window flips health from `ok` to `warning`; health reverts to `ok` automatically once 5 minutes pass with no further handler exception. A `warning` plugin keeps running and receiving events throughout.
- Q: PL-3.4's "bounded time to persist state" after `unloading` — how long? → A (A, no number given; short enough that disabling a plugin never feels like it hangs the UI, long enough for a few key-value writes): 200 ms from `unloading` delivery to context teardown. Any `state.plugin`/`state.track` write still in flight when the window closes is abandoned without error to the (already-gone) plugin and without corrupting previously persisted values.
- Q: what happens if restoring `state.track` before `track_changed` is itself slow? → A (D, PL-3.6 — budgets apply to every host↔plugin interaction, and nothing exempts restore): the restore read is subject to the same per-handler budget as any other host→plugin call. A restore that does not complete in time is aborted like any other budget breach; `track_changed` is delivered on schedule with no per-track state applied, rather than being held up waiting for a slow plugin.
- Q: How exactly is a suggested effect-node position ("before time_stretch") honored, and what happens if the named node type is not in the chain? → A (D, PL-2.2's `effect_nodes` field and FR-7.4.2 "honors on insertion only"): the suggestion names an absolute index or "before/after node-type T"; if T is absent from the chain at insertion time, the node is appended at the end instead of being refused. The user's later reordering (008) is never overridden by the suggestion again.
- Q: Does the plugin list's `health` enum need `disabled_incompatible` or a "compatibility mode" flag (DM-10) in this slice? → A (D, PL-9.2/PL-9.4 version-mismatch and compatibility-mode handling are only reachable once a plugin can update or run on an older API major, and only "bundled," built against the host's current API version, ships this slice): health is exactly `ok` / `warning` / `suspended`, as the prompt states; the other two DM-10 values are inert until a later slice can produce a version mismatch.
- Q: Does the "three suspensions in a session" counter (DM-10 `suspensions this session`) survive an app restart? → A (D, the field's own name, and NFR-2.6's restore list does not mention it): no; it is in-memory only, reset to 0 on every launch, and incremented on every Active→Suspended transition regardless of cause.
- Q: PL-3.3 says a plugin that does not call `ready()` "within the load timeout" is suspended — how long is that timeout? → A (A, no number given in the source; long enough for a script to initialize, short enough that a genuinely stuck load is caught quickly): 5 seconds from context creation.
- Q: What does "invalid manifest: <reason>" actually enumerate, and does an invalid plugin still get a plugin-list row? → A (D, EC-6.1 "not loaded; reason logged" / "listed as 'invalid manifest: <reason>'" — the row exists, loading never proceeds): the plugin appears in the list with `enabled = false` and no health value. The reason is one of: a permission (in required or optional) not found anywhere in the full Part 5 §4 catalog; `network` listed as required rather than optional; a missing required manifest field; or a malformed value for a known field — always a single, specific, user-legible sentence, never a stack trace. A permission that *is* in the full catalog but whose capability this slice does not implement (`network`, `audio.process`, any `ui.*`/`files.*`/`midi.*`/`clipboard`/`library.*`/`analysis.*`) is not a manifest error; neither bundled plugin in this slice requests one, and doing so would simply be refused with `permission_denied` at call time like any ungranted permission.

Same ladder: (D) derived from a source, (A) assumed conventional default. Three specify-pass resolutions were found to contradict the source and are corrected here (loop arming, ownership refusals, `state.plugin` retention); the rest fill gaps. No item met the materiality bar for human escalation.

- Q: **Correction** — does arming a loop require transport focus? → A (D, §6.1 "Transport mutations other than `request_focus` require the plugin to hold focus, or return `no_focus`" with `arm_loop`/`disarm_loop` in that list; EC-4.4 "Only the focus holder can arm; the other receives `no_focus`"; Part 9 §5.1 step 2; FR-3.3.1 lists "loop" among the focus holder's transport commands): **yes**. `arm_loop(region)` requires `markers.write` (else `permission_denied`), the region to be the plugin's own (else `permission_denied`/`not_owner`), and the plugin to currently hold transport focus (else `no_focus`); `disarm_loop()` requires focus too and returns `invalid_state` when the plugin has no armed region. Arming applies 006 FR-008 unchanged: it disarms any previously armed region (whoever owned it) and refuses an incomplete or `< 1 ms` region with `invalid_state`. The user's own `L`/list toggle acts on any region regardless of owner and always wins (Constitution X, FR-3.3.2). Consequence: a plugin that only holds `markers.write` can create and edit regions but cannot arm one.
- Q: **Correction** — what does a plugin receive when it touches a marker, loop, cue, or effect node it does not own? → A (D, EC-4.5 "`permission_denied`-class refusal (`not_owner`)"; `not_owner` is not in the closed six-code set, so it is the `reason` detail of a `permission_denied`): `permission_denied` with `reason: not_owner`, not `not_found`. `not_found` is reserved for an identifier that does not (or no longer) exist — a deleted marker, a removed node, an unknown timer handle. The same rule applies to effect nodes, since `list_chain()` already exposes every node's existence and owner.
- Q: **Correction** — is `state.plugin` cleared on sign-out? → A (D, Part 6 §10 Retention summary: "Plugin state — until uninstall"; "per-track plugin state — sign-out"; FR-1.2.4 "plugin … settings that are not account-specific remain"): no. `state.plugin` survives sign-out and is cleared only on uninstall (never, for a bundled plugin). `state.track` is account-scoped and cleared on sign-out, alongside 006's per-track marker files. 006's per-track "clear" action does not touch plugin state in this slice (006 scoped it to markers only). The Assumptions section is realigned.
- Q: What is the shape of a refusal, and in what order does the Gateway evaluate checks when a call fails more than one? → A (D for the order, AR-17's own sequence "checks the permission grant, checks transport focus where needed, checks budgets and rate limits, … forwards to the owning core service"; A for the shape): a refusal is `{ code, reason, message }` — `code` is exactly one of the six; `reason` is a short machine-readable detail (`not_owner`, `chain_full`, `marker_limit`, `timer_limit`, `not_ready`, `unknown_id`, `storage_cap`, …); `message` is a user-legible sentence for the console. Checks run permission → focus → rate limit → per-call validation and state (`invalid_state`/`not_found`); the first failing check is the one reported, and a refused call performs no host-side work. `budget_exceeded` is used only for the plugin's own storage cap in this slice.
- Q: What does a plugin get when a host-side capacity limit, not its own budget, blocks a call — the 008 chain maximum or the 006 64-marker limit? → A (A, `budget_exceeded` is defined by PL-8 as the plugin's *own* budgets, and `invalid_state` is the catalog's catch-all for "the host can't do this right now"): `invalid_state` with `reason: chain_full` or `reason: marker_limit`. Transient markers count toward the 64 while present.
- Q: FR-5.1.2 says persisted markers survive "unless the owning plugin marked them transient," and §6.2's `create_marker` carries a `transient` flag that 006 deferred to this slice — what does a transient marker do? → A (D for existence, FR-5.1.2/§6.2; A for lifetime): `create_marker(…, transient: true)` creates a marker held in memory only — never written to the per-track file — that the host removes (emitting `marker_changed` to `markers.read` holders) on the next track change and whenever its owner is suspended, disabled, or unloaded. A non-transient plugin marker is persisted and restored exactly like a host marker and outlives its plugin (J-7 variant). A transient loop region (either endpoint transient) follows the same lifetime.
- Q: `set_cue(slot, position)` — cue slots 1–8 are shared host slots (006); what happens when the slot is occupied? → A (A, 006's "slot already has a cue → moves it" plus EC-4.5): an empty slot creates a plugin-owned cue; a slot holding the plugin's own cue moves it; a slot holding a cue owned by another owner (host or another plugin) returns `permission_denied`/`not_owner`. The user may still overwrite any slot from the host UI.
- Q: §6.2 lists `define_section(range, name)`, but 006 excluded sections and the breakdown maps FR-5.4 Sections to 006-practice-depth/002 — is it in this slice's API? → A (D, breakdown README coverage map; Constitution III — sections are not yet a host primitive to compose; Constitution IX — minor API versions only add): no. `define_section` is absent from this slice's API object and ships as an API minor addition with the sections slice. Likewise `serialize_state()`/`restore_state()` (PL-3.5, hot reload) ship with 002-developer-mode. Calling an absent method is an ordinary script error inside the handler (handler aborted, logged, counts toward the `warning` rule).
- Q: Which of Part 5 §5's permission-less events does this slice deliver, and what about `effect_chain_changed`? → A (D, §5 table): delivered — `ready_ack` (once, immediately after `ready()`, payload: API version, the plugin's granted permission list, host capability list), `unloading` (payload `reason`: `disable` \| `suspend` \| `shutdown`), and `effect_chain_changed` to `audio.effects` holders on every change to node order, bypass or auto-bypass state, or orphan flags, whether plugin- or user-driven (008 panel). Not delivered in this slice — `focus_granted`/`focus_revoked` (010), `permission_changed` (approval sheet), `performance_mode_changed` (004-performance/003), `connectivity_changed` (003-offline-and-library/002), `analysis_ready`, `action_invoked`, `settings_changed`, `midi_message`. Events are delivered in order on the plugin's own scheduler; a slow handler delays only that plugin's subsequent events (PL-5.1). App shutdown delivers `unloading(shutdown)` with the same 200 ms window before the host proceeds.
- Q: Does the `unloading` handler get 200 ms of CPU, contradicting the 4 ms per-handler budget? → A (D, PL-3.6 exempts nothing): no. The `unloading` handler runs under the ordinary 4 ms CPU budget; the 200 ms is the wall-clock window during which state writes the handler issued are committed before the context is torn down.
- Q: EC-6.5 and Part 9 §5.4 say the suspension notice is "silent in Performance Mode" — does that apply here? → A (D, breakdown README: Performance Mode is 004-performance/003): no Performance Mode exists in this slice, so the notice is always shown. Notice contract, reusing 002/008's keyed non-blocking notifications: suspension → `Warning`, key `plugin-suspended:<identifier>`, text names the plugin and the cause (hang / CPU share / memory / did not start), actions **Restart** and **Disable**; a repeat suspension replaces the same key. Auto-disable after the third → `Warning`, key `plugin-auto-disabled:<identifier>`, no actions. J-7 step 6's "report it" offer ships with crash reporting (opt-in, later wave), not here.
- Q: The spec says errors are "logged to the plugin's console," but the Plugin Console UI is 002-developer-mode/002 — what is the console here? → A (D, breakdown README): the host application log, each entry tagged with the plugin identifier and level. No console UI, and the notice does not "link to the console" in this slice.
- Q: What is a plugin's health after Restart or re-enable, and does the list show CPU/memory for a plugin that is not running? → A (A): health becomes `ok` when the recreated context calls `ready()` (it is `suspended` until then if the restart came from a suspension); the 60-second handler-error window is reset on every context creation; the session suspension counter is **not** reset by Restart (only by app launch). CPU and memory show "—" for a plugin that is disabled, invalid, or suspended.
- Q: Do handler aborts caused by the 4 ms budget count toward the 3-errors-in-60-s `warning` rule, or only thrown exceptions? → A (A, both are "handler aborted, plugin keeps running" outcomes and the user should see a plugin that keeps blowing its handler budget): every handler abort counts — exception, per-handler budget, or a failed `state.track` restore.
- Q: What exactly is measured for the CPU budgets and the memory cap? → A (D, PL-3.6 "every plugin call into the host and every event delivery"; A for the boundary): CPU is wall-clock time during which the plugin's context is executing, including the synchronous portion of any Gateway call it makes from inside a handler; it excludes asynchronous host work the call triggers (engine parameter apply, state file write, event fan-out). The aggregate share is re-evaluated at every handler completion or abort over the trailing 1 s. Memory is the script context's currently allocated heap as reported by the runtime; the cap is enforced by the runtime's allocator so an over-cap allocation fails inside the plugin and the context is suspended, never the host.
- Q: FR-7.3.1 leaves orphaned nodes "until the user removes them or the plugin is re-enabled" — what happens to them on re-enable/Restart? → A (D, that phrase; 008: the chain is session-scoped and empty at launch, so no orphan survives a relaunch): when the plugin's recreated context calls `ready()`, every orphaned node whose owner is that plugin's identifier is un-flagged and owned by it again; `list_chain()` reports them with the plugin as owner so the plugin can re-acquire handles (node identifiers are stable for the session). The plugin is responsible for not creating duplicates. A plugin may `bypass(node, false)` its own auto-bypassed node (008 overload rule), which clears the auto-bypass flag exactly as the user's re-enable does.
- Q: Timer semantics — handles, cancellation, limits, what `schedule_at_position` does across seeks and track changes? → A (A, conventional): `set_timeout(ms)`, `set_interval(ms)`, and `schedule_at_position(p)` each return a handle; `clear_timer(handle)` cancels any of them (`not_found` for an unknown or already-fired handle). `schedule_at_position` is one-shot and track-relative: it fires once, the first time the audio-clock position is observed `≥ p` at a buffer boundary, carrying the actual position; a seek backwards before it fires leaves it pending; a track change cancels every pending position timer silently. Interval and timeout minimum is 1 ms and fires on the plugin's scheduler, never the real-time path. Timers fire only while the plugin is Active and are cancelled on suspend/disable. At most 256 pending timers per plugin; the 257th returns `invalid_state`/`timer_limit`.
- Q: Is `position` delivered while paused, and what jitter is allowed? → A (D, NFR-1.9 "≤ 5 ms jitter"; A for the paused rule): `position` is delivered only while the position is changing (playing, or immediately once after a seek or loop wrap while paused); no events while paused or stopped at a constant position. At the requested rate the inter-event jitter is ≤ 5 ms.
- Q: Which calls belong to which rate-limit category? → A (A, completes FR-025): **transport** — `play`, `pause`, `toggle`, `seek`, `skip_next`, `skip_previous`, `request_focus`, `release_focus`, `arm_loop`, `disarm_loop`, and every `queue.write` call; **markers** — every §6.2 write and every `markers.read` read; **effects** — every §6.3 call including `list_chain`; **state** — every `get`/`set`; **timers** — every `set_*`/`schedule_at_position`/`clear_timer`. Rate-limited calls are counted after the permission and focus checks, so a `permission_denied` call does not consume the quota.
- Q: What bounds a state key/value, and where does the data live? → A (A, matching 006's per-track file conventions): keys are UTF-8 strings ≤ 256 bytes; values are JSON-serializable and ≤ 1 MB serialized; the 10 MB cap is the serialized size of all of the plugin's keys and values across both scopes; a `set` that would exceed any bound returns `budget_exceeded`/`storage_cap` and leaves the store unchanged. Storage is a plain (unencrypted — no decoded audio) per-plugin store under the app data directory, written atomically (tmp + sync + rename) and debounced like 006; the exact layout is a plan decision.
- Q: PL-2.3 also invalidates a manifest that requests `network` "without `network_hosts`" — did FR-002 cover it? → A (D, PL-2.3): now it does — requesting `network` (as optional; required is already invalid) with a missing or empty `network_hosts` is an invalid manifest.
- Q: PL-8.2 says budgets are visible in the plugin list — is that in FR-023? → A (D, PL-8.2): yes, now explicit: CPU is shown as a percentage of the plugin's 10 % share and memory as `<used> MB / 64 MB`.
- Q: Which bundled plugins actually ship in this slice? Section Loop and Key & Tempo are 001-mvp/012 and 013. → A (A, following the constitution's debug-toggle convention `MODPLAYER_LIBRARY_FIXTURE=large`): this slice ships **no production bundled plugin**. It ships a set of fixture plugins under the bundled source that are present only when `MODPLAYER_PLUGIN_FIXTURES=1` is set at launch (any build), used by the automated suite and the quickstart manual scenarios: at minimum an observer-only plugin, a well-behaved plugin holding every operable permission, a hanging plugin, a throwing plugin, a memory-leaking plugin, a plugin that never calls `ready()`, and an invalid-manifest plugin. Without the variable the plugin list is empty and shows an empty-state message. 012/013 add the real bundled plugins.
- Q: Where does the plugin list live? → A (D, 001 FR-015 already reserves a **Plugins** navigation section with placeholder content): the Plugins section, replacing its placeholder. Rows are sorted by name; every control is keyboard-operable with an accessible name and all strings are externalized (Constitution X). Settings › Plugins stays a placeholder until the approval-sheet slice.
- Q: Does a user's edit to a plugin-owned marker change its owner, and what does the plugin see? → A (D, FR-5.1.3 — the host UI is fully trusted and edits any marker; §5 `marker_changed` carries "by whom"): the owner is unchanged; the owning plugin (if it holds `markers.read`) receives `marker_changed` with the actor `host`.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - A misbehaving plugin never takes the player down (Priority: P1)

While a bundled plugin is active, it hangs in an infinite loop, throws repeatedly, or leaks memory. Audio keeps playing and transport keeps responding without interruption; the user sees a non-blocking notice naming the plugin with Restart and Disable, and if it keeps failing it disables itself.

**Why this priority**: This is the prompt's own headline promise ("without ever being able to take the player down") and Constitution II's non-negotiable fail-isolation guarantee (NFR-2.3). Nothing else in this feature matters if a single bad plugin can crash the host or click the audio.

**Independent Test**: Enable a bundled plugin instrumented to hang in an event handler; verify audio and transport continue uninterrupted, a notice names the plugin with Restart/Disable, and after three such episodes in one session the plugin is auto-disabled without further user action.

**Acceptance Scenarios**:

1. **Given** an active plugin, **When** one of its event handlers enters an infinite loop, **Then** the host suspends the plugin's context within its budget window, audio and transport continue with zero interruption, and a non-blocking notice names the plugin with Restart and Disable actions (prompt acceptance).
2. **Given** a plugin has been suspended twice already in the current session, **When** it is suspended a third time, **Then** the plugin is automatically disabled with no further user action required (prompt acceptance).
3. **Given** an active plugin, **When** its memory usage exceeds its 64 MB cap, **Then** it is suspended and a notice names it (EC-6.6).
4. **Given** an active plugin, **When** one of its event handlers throws an exception, **Then** that handler is aborted, the error is logged to the plugin's console, and the plugin keeps running and receiving further events; **When** this happens three times within 60 seconds, **Then** the plugin's health shows `warning`.
5. **Given** a suspended plugin held transport focus, **When** it is suspended, **Then** focus returns to the host immediately and any loop it had armed is disarmed, its transient markers are removed, and any non-transient markers it had persisted to the track remain.
6. **Given** a suspended plugin owns an effect node, **When** it is suspended, **Then** the node keeps running with its last parameters, flagged "orphaned," until the user bypasses or removes it or the plugin is re-enabled.
7. **Given** a suspended plugin, **When** the user clicks Restart, **Then** the plugin's context is recreated, its entry script runs again, and it must call `ready()` again before receiving events.

---

### User Story 2 - A plugin can only do what it was granted permission to do (Priority: P2)

A bundled plugin's manifest declares the permissions it needs with a one-line justification; the host enforces exactly those and refuses everything else cleanly, and a manifest that asks for something outside the permission catalog never loads at all.

**Why this priority**: Least-privilege enforcement (Constitution II, PL-1.3) is the other non-negotiable half of "guests, not owners" — it is what makes plugins trustworthy at all (JTBD-8, JTBD-15) — and it is independent of, though it works alongside, Story 1's fault isolation.

**Independent Test**: Enable a bundled plugin that requests only `playback.observe`, then have its script attempt a `transport.control` request; verify `permission_denied` and no side effect. Separately, load a plugin package whose manifest declares an unknown permission string; verify it is never loaded and is listed as invalid.

**Acceptance Scenarios**:

1. **Given** a plugin without `transport.control`, **When** it calls a transport request (e.g., `seek`), **Then** it receives `permission_denied` and nothing else happens — no state changes, no event fires (prompt acceptance).
2. **Given** a plugin manifest that declares a permission string not found in the Part 5 permission catalog, **When** the host attempts to load it, **Then** the plugin is not loaded and is listed as "invalid manifest: <reason>" (prompt acceptance).
3. **Given** a plugin without `markers.write`, **When** it attempts to create or move a marker, **Then** it receives `permission_denied` and no marker is created or moved.
4. **Given** a plugin with `markers.write` that owns no markers of its own, **When** it attempts to move or delete a marker created by another owner, **Then** it receives `permission_denied` with `reason: not_owner` and the marker is unchanged; **When** it names a marker identifier that no longer exists, **Then** it receives `not_found`.
5. **Given** a plugin with `audio.effects` that owns no nodes, **When** it attempts to set a parameter or remove a node it does not own, **Then** it receives `permission_denied`/`not_owner`; **When** it calls `list_chain()`, **Then** it sees every node in the chain (type, owner, bypass state) regardless of owner.
6. **Given** any request from any plugin, **When** it fails for any reason, **Then** the result is a `{ code, reason, message }` refusal whose `code` is one of exactly `permission_denied`, `no_focus`, `invalid_state`, `not_found`, `rate_limited`, or `budget_exceeded` — never an unhandled exception or host-visible crash.
7. **Given** a plugin with `markers.write` but without transport focus, **When** it calls `arm_loop` on its own complete region, **Then** it receives `no_focus` and no region is armed; **Given** the same plugin lacks `markers.write` as well, **Then** it receives `permission_denied` (permission is checked before focus).
8. **Given** a plugin manifest that lists `network` as an optional permission with no `network_hosts`, **When** the host attempts to load it, **Then** it is listed as "invalid manifest: <reason>" and not loaded.

### User Story 3 - A bundled plugin observes and acts on the music while it plays (Priority: P3)

With its declared permissions granted, a bundled plugin subscribes to playback events, controls transport, manages its own markers/loop/effect nodes, watches meters, persists its own settings, and schedules work against the playhead — the actual behaviors that make a plugin useful.

**Why this priority**: This is the payload Stories 1 and 2 protect (JTBD-1 through JTBD-4); it ranks after them because a capability that works but isn't safely sandboxed or permission-checked is worse than no capability at all.

**Independent Test**: Enable a fixture plugin holding `playback.observe`, `transport.control`, `markers.read`, `markers.write`, `audio.effects`, `audio.meter`, `state.plugin`, and `state.track`; drive it through a full behavior cycle (subscribe to position, request focus, arm its own loop, create and parameterize an effect node at a suggested position, read a meter tick, persist and recall per-track state, schedule a position-based timer) and verify each works exactly as declared.

**Acceptance Scenarios**:

1. **Given** a plugin with `playback.observe` requests `position` at a rate, **When** playback runs, **Then** it receives coalesced position updates at its requested, clamped `[1, 60]`/s rate with ≤ 5 ms jitter, none while paused at a constant position, plus `track_changed` (with its own per-track state already restored), `play_state_changed`, and `queue_changed`.
2. **Given** a plugin with `markers.read`, `markers.write`, and `transport.control` creates a loop region, requests focus (granted, nobody else holds it), and arms it, **When** the playhead reaches the region's end, **Then** playback loops exactly as a user-armed loop would, and the plugin receives `loop_armed` then `loop_wrapped`.
2b. **Given** a plugin calls `ready()`, **When** the host acknowledges it, **Then** the first event it receives is `ready_ack` carrying the API version, its granted permission list, and the host capability list.
2c. **Given** a plugin with `audio.effects`, **When** the user reorders or bypasses any node in the Effect Chain panel, **Then** the plugin receives `effect_chain_changed` with the new order, bypass states, and orphan flags.
3. **Given** a plugin with `audio.effects` calls `create_node(pitch_shift, suggested_position: "before time_stretch")` and a time-stretch node exists in the chain, **When** the node is created, **Then** it is inserted immediately before that node; **Given** no time-stretch node exists, **Then** the new node is appended at the end of the chain instead of being refused.
4. **Given** a plugin owns an effect node, **When** it calls `set_param` on it, **Then** the change applies at the next buffer boundary with the existing ramp/crossfade behavior (008), exactly as a user-driven change would.
5. **Given** a plugin with `audio.meter`, **When** playback runs, **Then** it receives `meter` events (pre/post peak, RMS, spectrum) at the same cadence the UI does.
6. **Given** a plugin with `state.track` previously stored a value for the current track, **When** that track is loaded again, **Then** the stored value is restored and available to the plugin's handler before `track_changed` is delivered.
7. **Given** a plugin calls `schedule_at_position(p)`, **When** the audio clock passes `p`, **Then** the plugin receives the corresponding event once, with the actual position, without having polled for it; **When** instead the track changes before `p` is reached, **Then** the timer is cancelled and no event fires.
8. **Given** a focus-holding plugin issues 1,000 `seek` calls within one second, **When** it exceeds its 100-calls-per-second transport rate limit, **Then** the excess calls in that second return `rate_limited` and produce no transport effect.
9. **Given** a plugin with `markers.write` creates a marker with `transient: true`, **When** the track changes or the plugin is disabled, **Then** the marker disappears (with `marker_changed` to `markers.read` holders) and is never in the persisted per-track file; a non-transient plugin marker survives both.
10. **Given** a suspended plugin left an orphaned node, **When** the user clicks Restart and the plugin calls `ready()`, **Then** the node is no longer flagged orphaned, `list_chain()` shows the plugin as its owner, and `set_param` on it succeeds.
11. **Given** the effect chain is at its maximum capacity (008), **When** a plugin calls `create_node`, **Then** it receives `invalid_state` with `reason: chain_full`; **Given** the track has 64 markers, **When** it calls `create_marker`, **Then** it receives `invalid_state`/`marker_limit`.

### User Story 4 - The user sees every installed plugin and controls it in one action (Priority: P4)

The plugin list shows, per plugin, its name, version, source, enabled state, health, permission summary, and live CPU/memory usage, and lets the user enable or disable any plugin — but never uninstall a bundled one.

**Why this priority**: JTBD-15 ("disable it in one action, so a bad plugin costs seconds, not a session") depends on Stories 1–3 already producing meaningful health and resource data to show; it is the user-facing control surface on top of a runtime that already works safely.

**Independent Test**: Launch with `MODPLAYER_PLUGIN_FIXTURES=1`, open the Plugins section; verify every required column is present and live, disable one plugin in a single action and verify its teardown sequence runs, and verify no uninstall control exists for any plugin. Launch without the variable and verify the empty state.

**Acceptance Scenarios**:

1. **Given** the Plugins section is open, **When** the user views it, **Then** each installed plugin shows name, version, source ("bundled"), enabled state, health (ok/warning/suspended), a plain-language permission summary, and live CPU (as % of its 10 % share) and memory (`<used> MB / 64 MB`), sorted by name (FR-7.3.6, PL-8.2); a disabled, invalid, or suspended plugin shows "—" for CPU and memory.
1b. **Given** the app was launched without `MODPLAYER_PLUGIN_FIXTURES`, **When** the user opens the Plugins section, **Then** it shows an empty-state message and no rows.
2. **Given** an enabled plugin, **When** the user disables it in one action, **Then** the host sends it `unloading`, waits up to 200 ms for it to persist state, then removes any UI it contributed, releases any transport focus it held, disarms any loop it owned, cancels its pending timers, and leaves its effect nodes in the chain flagged "orphaned."
3. **Given** a disabled plugin, **When** the user re-enables it, **Then** it runs the Loaded→Active lifecycle from scratch (fresh context, entry script re-run, `ready()` required again).
4. **Given** any bundled plugin, **When** the user looks for an uninstall action, **Then** none is available; only enable/disable is offered (EC-6.18).

### Edge Cases

- A manifest requests a permission not in the Part 5 catalog, lists `network` as required rather than optional, or requests `network` without `network_hosts` → not loaded, listed "invalid manifest: <reason>," `enabled = false`, no health value (EC-6.1, PL-2.3; Clarifications).
- A plugin never calls `ready()` within 5 seconds of load → suspended with a clear "did not start" error and a Restart action (EC-6.3; Clarifications).
- A plugin's handler throws → aborted, logged to console, plugin keeps running; three such errors within 60 s set health to `warning`, which clears after 5 minutes with no further error (EC-6.4; Clarifications).
- A plugin's storage writes would exceed its 10 MB cap → the write fails with `budget_exceeded`, a console entry is logged, and previously stored data is unaffected (EC-6.7).
- A plugin requests focus while another plugin already holds it → `invalid_state`, since this slice's focus model is unarbitrated (010 replaces this with real contention handling) (Clarifications).
- A suspended or disabled plugin held transport focus or an armed loop → focus returns to the host immediately, the loop disarms, its transient markers are removed, and any non-transient markers it had persisted to the track are unaffected (J-7 variant; FR-5.1.2).
- A suspended or disabled plugin owns an effect node → the node keeps running with its last parameters, flagged "orphaned," never removed automatically (J-7 variant; FR-7.3.1).
- A plugin is restarted after suspension and hangs again, reaching three suspensions in the same session → auto-disabled with no further prompt; the counter resets to 0 on the next app launch (Clarifications).
- The user attempts to uninstall a bundled plugin → the action is absent; only disable is offered (EC-6.18).
- A plugin issues far more requests in one category than any legitimate use would (e.g., 1,000 seeks/second) → calls beyond 100/second in that category return `rate_limited` with no host-side effect (Clarifications).
- A plugin's `state.track` restore does not complete within its handler budget → the restore is aborted like any other budget breach, and `track_changed` is delivered on schedule with no per-track state applied rather than being delayed (Clarifications).
- A plugin's `create_node` suggested position names a node type absent from the chain → the node is appended at the end instead of being refused (Clarifications; FR-7.4.2).
- A plugin attempts to modify, bypass, or remove an effect node, marker, loop, or cue slot it does not own → `permission_denied` with `reason: not_owner`; the resource is unchanged (EC-4.5; Clarifications).
- A plugin names a marker, node, or timer handle that no longer exists → `not_found` (Clarifications).
- A plugin with `markers.write` but no transport focus calls `arm_loop` → `no_focus`; a plugin calls `disarm_loop` with nothing of its own armed → `invalid_state` (EC-4.4; Clarifications).
- A plugin arms its own region while the user's region is armed → the user's region is disarmed (006 FR-008, one armed region per track); the user can re-arm theirs with `L` at any time, which disarms the plugin's.
- The user edits or deletes a plugin-owned marker from the host UI → allowed; owner unchanged; the plugin receives `marker_changed` with actor `host` (FR-5.1.3).
- The effect chain is at capacity or the track holds 64 markers → `invalid_state` with `reason: chain_full` / `marker_limit` (Clarifications).
- A plugin creates a 257th pending timer → `invalid_state`/`timer_limit`; a track change while position timers are pending → they are cancelled silently (Clarifications).
- A plugin calls a method absent from this slice's API (`define_section`, `serialize_state`, any `ui.*`/`network` request) → ordinary script error inside the handler: handler aborted, logged, counts toward the `warning` rule (Clarifications).
- The app quits while plugins are Active → each receives `unloading(shutdown)` and the same 200 ms persistence window before teardown (Clarifications).
- A `state.plugin`/`state.track` key exceeds 256 bytes or a value exceeds 1 MB serialized → `budget_exceeded`/`storage_cap`, store unchanged (Clarifications).
- The user signs out → `state.track` data is cleared with the rest of per-account state; `state.plugin` data survives (Retention summary; Clarifications).
- The app is relaunched while a plugin was suspended or mid-session → every enabled plugin loads fresh from Installed/Enabled; the suspension counter starts at 0; no orphaned node survives because the chain is empty at launch (008; Clarifications).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: A plugin package MUST be a folder containing a manifest, an entry script, optional additional scripts and resources, and a readme. The manifest MUST declare, at minimum: an immutable, reverse-domain-style identifier; name and description; semantic version; the supported API version range; author, license, homepage, and source; the entry script reference; required permissions (each with a one-line justification); optional permissions (each justified); declared network hosts (recorded, not exercised — network is out of scope); declared UI contributions (recorded, not rendered — `ui.*` is out of scope); intended effect nodes (type and suggested chain position); and an optional minimum host version. *(PL-2.1, PL-2.2)*
- **FR-002**: The host MUST validate every manifest before loading it. A manifest is invalid, and the plugin is not loaded, when: it declares a required or optional permission not found anywhere in the full Part 5 §4 permission catalog; it lists `network` as required rather than optional; it requests `network` with a missing or empty `network_hosts`; a required field is missing; or a known field holds a malformed value. An invalid plugin still appears as a plugin-list row with `enabled = false` and no health value, labeled "invalid manifest: <reason>" with a single, specific, user-legible reason. A permission that is in the catalog but whose capability this slice does not implement is not a manifest error. *(PL-2.3, PL-4.2; EC-6.1; Clarifications)*
- **FR-003**: This slice MUST support exactly one plugin source, "bundled" (plugins shipped with the host). Bundled plugins MUST be installed and enabled by default with their manifest's declared permissions pre-approved, with no approval-sheet prompt, because they ship with and are audited by the host project. Registry, sideloaded, and local-development-folder sources are out of scope. This slice ships no production bundled plugin (Section Loop and Key & Tempo are 001-mvp/012 and 013); it MUST ship fixture plugins under the bundled source that are discovered only when `MODPLAYER_PLUGIN_FIXTURES=1` is set at launch — at minimum: observer-only (`playback.observe`), well-behaved with every operable permission, hanging handler, throwing handler, memory-leaking, never-calls-`ready()`, and invalid-manifest — and without the variable the plugin list MUST be empty with an empty-state message. *(FR-7.1.1 partial, FR-1.4.2; Scope boundary; Clarifications)*
- **FR-004**: Each enabled plugin MUST run in its own isolated script context with no shared memory with any other plugin or with the host UI, and with its own scheduler and timers. Plugin scripts MUST NEVER execute on the audio real-time path; all plugin computation and every Capability Gateway call MUST run off it. *(PL-1.2, PL-3.1; Constitution I and II, NON-NEGOTIABLE)*
- **FR-005**: A plugin's lifecycle MUST follow: Installed → Enabled (permissions pre-approved for a bundled plugin) → Loaded (isolated context created, entry script run) → Active (after the plugin calls `ready()`) → Suspended (budget exceeded or unresponsive) → Loaded again (on user Restart) or Disabled (after three suspensions in one session, or user action); Active → Disabled on user action. Uninstall is unavailable for any bundled plugin; only Enabled ⇄ Disabled is offered. *(Part 5 §3 lifecycle; EC-6.18)*
- **FR-006**: A newly loaded plugin MUST receive no events until it calls `ready()`. A plugin that does not call `ready()` within 5 seconds of load MUST be suspended with a clear "did not start" error and a Restart action offered. *(PL-3.3; EC-6.3; Clarifications — no numeric timeout is given in the source, 5 s is this spec's fixed default)*
- **FR-007**: On load, the host MUST hand the plugin a single API object; every request the plugin makes through it MUST be checked against the plugin's granted permissions before it executes. A request for a capability the plugin was not granted MUST return `permission_denied` and produce no side effect, no event, and no partial application. *(PL-3.2, PL-1.5)*
- **FR-008**: Every request into the Capability Gateway MUST return either success with data, or exactly one structured refusal `{ code, reason, message }` whose `code` is one of `permission_denied`, `no_focus`, `invalid_state`, `not_found`, `rate_limited`, or `budget_exceeded`, whose `reason` is a short machine-readable detail (`not_owner`, `chain_full`, `marker_limit`, `timer_limit`, `storage_cap`, `unknown_id`, …), and whose `message` is a user-legible sentence — never an unhandled exception, a panic, or a host-visible crash. Checks MUST run in the order permission → transport focus → rate limit → per-call validation/state, reporting the first failure; a refused call MUST perform no host-side work. Touching a marker, loop, cue slot, or effect node owned by another owner MUST return `permission_denied`/`not_owner`; an identifier that does not or no longer exists MUST return `not_found`; a host-side capacity limit (chain full, 64 markers, 256 timers) MUST return `invalid_state` with the matching reason. *(PL-1.5; AR-17; EC-4.5; NFR-2.3, Constitution II NON-NEGOTIABLE; Clarifications)*
- **FR-009**: Each plugin context MUST be budgeted at: ≤ 4 ms CPU per event-handler invocation; ≤ 10% of one CPU core, averaged over a rolling 1-second window, aggregated across all of the plugin's handlers; ≤ 64 MB memory; ≤ 10 MB persistent storage. Exceeding the per-handler budget MUST abort only that handler, without suspending the plugin; exceeding the aggregate CPU share or the memory cap MUST suspend the whole plugin context. CPU is wall-clock time the plugin's context is executing, including the synchronous part of Gateway calls made from a handler and excluding asynchronous host work they trigger; the aggregate share is re-evaluated at every handler completion or abort over the trailing 1 s; memory is the context's allocated heap as reported by the runtime, enforced by the runtime's allocator so an over-cap allocation fails inside the plugin, never the host. *(PL-8.1, PL-8.3, PL-3.6; NFR-2.3; Clarifications)*
- **FR-010**: A handler that throws, or is aborted for exceeding its per-handler budget, MUST be aborted with the error logged to the plugin's console — in this slice, the host application log with entries tagged by plugin identifier and level — while the plugin keeps running and receiving further events. Three such aborts of any kind within a rolling 60-second window MUST set the plugin's health to `warning`; health MUST revert to `ok` automatically once 5 minutes pass with no further abort; the window is reset whenever the plugin's context is recreated. *(EC-6.4; Clarifications)*
- **FR-011**: The runtime MUST detect a handler that exceeds its budget without yielding, or a plugin that exceeds its aggregate CPU share or memory cap, and suspend that plugin's context without interrupting audio or transport. On suspension, the plugin's health MUST show `suspended`, a non-blocking `Warning` notification keyed `plugin-suspended:<identifier>` MUST name the plugin and the cause (hang / CPU share / memory / did not start) with **Restart** and **Disable** actions (a repeat suspension replaces the same key; there is no Performance Mode in this slice, so the notice is always shown), and a third suspension within the same running session MUST auto-disable the plugin with no further user action, shown as a `Warning` keyed `plugin-auto-disabled:<identifier>` with no actions. The suspension counter is in-memory only, is not reset by Restart, and MUST reset to 0 on every app launch. After Restart or re-enable, health MUST become `ok` when the new context calls `ready()`. *(PL-3.6; EC-6.5, EC-6.6; DM-10; J-7; Clarifications)*
- **FR-012**: On disable, suspend, or app shutdown, the host MUST, in order: deliver `unloading` (payload `reason`: `disable` | `suspend` | `shutdown`) to the plugin — the handler runs under the ordinary 4 ms CPU budget, and state writes it issues are committed within a 200 ms wall-clock window before teardown; remove any UI contributions it made (none exist in this slice); release any transport focus it held, returning focus to the host immediately; disarm any loop region it owns; remove its transient markers (emitting `marker_changed`) while leaving its persisted markers untouched; cancel its pending timers; and orphan (never remove) any effect node it owns, flagging each "orphaned" and leaving it running with its last parameters until the user bypasses or removes it, or the plugin is re-enabled. When a recreated context for the same identifier calls `ready()`, its orphaned nodes MUST be un-flagged and owned by it again, reported as such by `list_chain()` with session-stable node identifiers. *(PL-3.4; J-7; FR-7.3.1; Clarifications)*
- **FR-013**: The uninstall action MUST be unavailable for every bundled plugin; the plugin list offers enable/disable only for it. *(EC-6.18)*
- **FR-014**: A `state.plugin` or `state.track` write that would exceed the plugin's 10 MB storage cap (the serialized size of all its keys and values across both scopes), or whose key exceeds 256 UTF-8 bytes, or whose value exceeds 1 MB serialized, MUST fail with `budget_exceeded`/`storage_cap`, logged to the console, leaving previously stored data unaffected. Values are JSON-serializable. Storage is a plain per-plugin store under the app data directory (no decoded audio, so unencrypted), written atomically and debounced as 006's per-track files are; `state.plugin` survives sign-out and is cleared only on uninstall; `state.track` is account-scoped and cleared on sign-out. *(EC-6.7; Part 6 §10 Retention summary; FR-1.2.4; Clarifications)*
- **FR-015**: This slice's operable permission set is exactly: `playback.observe`, `transport.control`, `queue.write`, `markers.read`, `markers.write`, `audio.effects`, `audio.meter`, `state.plugin`, `state.track`. Manifest validation (FR-002) checks the requested permission against the full Part 5 §4 catalog (25 permissions), not only this operable subset; no fixture plugin requests a permission outside the operable subset except the invalid-manifest fixture, which names a string outside the catalog. *(PL-4.1; Clarifications)*
- **FR-016**: A plugin holding `playback.observe` MUST receive `track_changed` (with its own per-track state already restored), `position` (delivered at its requested rate, default 10/s if unspecified, clamped to `[1, 60]`/s, coalesced to the latest value per interval, with ≤ 5 ms inter-event jitter, delivered only while the position is changing plus once after a seek or loop wrap while paused), `play_state_changed`, and `queue_changed`. *(Part 5 §5 events; NFR-1.9; Clarifications)*
- **FR-017**: A plugin holding `transport.control` MAY call `request_focus()` (granted immediately if no plugin currently holds focus, else `invalid_state`) and `release_focus()` (always succeeds, returns focus to the host). Every other transport mutation (`play`, `pause`, `toggle`, `seek`, `skip_next`, `skip_previous`, `arm_loop`, `disarm_loop`) requires the calling plugin to currently hold focus, returning `no_focus` otherwise. A plugin holding `queue.write` MAY view, reorder, add to, and remove from the play queue regardless of who holds transport focus (`not_found` for an unknown queue item). Full multi-plugin focus policy, `focus_granted`/`focus_revoked`, and the panel are out of scope (010). *(Part 5 §6.1; EC-4.4; Clarifications)*
- **FR-018**: A plugin holding `markers.read` MUST receive `marker_changed` (carrying the actor — `host` or a plugin identifier), `loop_armed`, `loop_disarmed`, and `loop_wrapped` events and MAY read every marker, loop, and cue regardless of owner. A plugin holding `markers.write` MAY create (with an optional `transient` flag), move, rename, recolor, and delete markers; create loop regions; and set cues — but only for markers/loops/cue slots it owns; a request naming another owner's resource MUST return `permission_denied`/`not_owner`. `arm_loop(region)` additionally requires the plugin to hold transport focus (`no_focus` otherwise) and names the plugin's own complete region (`invalid_state` for incomplete or `< 1 ms`); it disarms any previously armed region per 006 FR-008. `disarm_loop()` requires focus and returns `invalid_state` when the plugin has nothing armed. `set_cue(slot, position)` creates in an empty slot, moves the plugin's own cue, and returns `permission_denied`/`not_owner` for a slot held by another owner. A transient marker is never written to the per-track file and is removed on the next track change and on its owner's suspend/disable/unload; a non-transient plugin marker persists and outlives its plugin. The user MAY edit or delete any plugin-owned marker from the host UI (owner unchanged). `define_section` is not part of this slice's API (006-practice-depth/002). *(Part 5 §6.2; FR-5.1.2, FR-5.1.3; EC-4.4, EC-4.5; Clarifications)*
- **FR-019**: A plugin holding `audio.effects` MAY call `create_node(type, suggested_position)`, receiving a handle scoped to the new node (`invalid_state`/`chain_full` when the chain is at 008's maximum); `set_param`, `schedule_param`, `bypass`, and `remove_node` operate only on nodes the plugin owns, returning `permission_denied`/`not_owner` for a node it does not own and `not_found` for one that no longer exists; `list_chain()` returns every node in the chain (identifier, type, owner, bypass, auto-bypass, and orphan state) regardless of owner. A suggested position names an absolute index or "before/after node-type T"; if T is absent from the chain at insertion time, the node is appended at the end instead of being refused. Parameter changes apply at the next buffer boundary through the existing ramp/crossfade mechanism (008). The plugin MUST receive `effect_chain_changed` on every change to order, bypass/auto-bypass state, or orphan flags, whether plugin- or user-driven; `bypass(node, false)` on its own auto-bypassed node clears the auto-bypass flag exactly as the user's re-enable does. *(Part 5 §5, §6.3; FR-6.2.4, FR-7.4.2; Clarifications)*
- **FR-020**: A plugin holding `audio.meter` MUST receive `meter` events (pre/post peak, RMS, spectrum) at the same cadence the host UI receives them. *(Part 5 §5, §6; FR-6.4)*
- **FR-021**: A plugin holding `state.plugin` and/or `state.track` MAY get/set key-value pairs scoped to itself, or to itself × the current track identity respectively, bounded by its 10 MB storage cap and key/value limits (FR-014). Per-track state MUST be restored before the corresponding `track_changed` event is delivered; the restore read is subject to the same per-handler budget as any other host→plugin call, and a restore that does not complete in time is aborted like any other budget breach rather than delaying the event. *(Part 5 §6.6; Clarifications)*
- **FR-022**: `set_timeout(ms)`, `set_interval(ms)`, `schedule_at_position(position)`, and `clear_timer(handle)` MUST be available to any Active plugin regardless of its granted permissions, subject to the same per-handler and aggregate CPU budgets as every other call; each `set_*`/`schedule_*` returns a handle, `clear_timer` cancels it (`not_found` for an unknown or already-fired handle), the minimum interval is 1 ms, and at most 256 timers may be pending per plugin (`invalid_state`/`timer_limit` beyond that). `schedule_at_position` is one-shot and track-relative: it MUST fire once, as an event carrying the actual position, the first time the audio-clock position is observed `≥ position` at a buffer boundary, evaluated host-side so plugins never need to poll; a backward seek before firing leaves it pending; a track change cancels every pending position timer silently. Timer callbacks fire on the plugin's scheduler, never the real-time path, only while the plugin is Active, and are cancelled on suspend/disable. *(Part 5 §6.10; Clarifications)*
- **FR-023**: The Plugins navigation section (replacing 001's placeholder) MUST list every installed plugin, sorted by name, showing: name, version, source ("bundled" in this slice), enabled state, health (`ok`/`warning`/`suspended`), a plain-language summary of its granted permissions (the catalog's explanation strings), live CPU as a percentage of its 10 % share, and live memory as `<used> MB / 64 MB`; CPU and memory show "—" for a disabled, invalid, or suspended plugin. Every control MUST be keyboard-operable with an accessible name; all strings externalized. With no plugins installed the section shows an empty-state message. *(FR-7.3.6; PL-8.2; 001 FR-015; Constitution X; Clarifications)*
- **FR-024**: The user MUST be able to enable or disable any plugin in one action. Enabling runs the Loaded→Active lifecycle fresh; disabling runs the FR-012 teardown sequence. Neither requires confirmation, since bundled permissions are pre-approved. *(FR-7.3.1)*
- **FR-025**: The Capability Gateway MUST enforce one rate limit per plugin per request category of 100 calls/second on a rolling 1-second window — **transport**: `play`, `pause`, `toggle`, `seek`, `skip_next`, `skip_previous`, `request_focus`, `release_focus`, `arm_loop`, `disarm_loop`, and every `queue.write` call; **markers**: every `markers.write` write and `markers.read` read; **effects**: every §6.3 call including `list_chain`; **state**: every `get`/`set`; **timers**: every `set_*`/`schedule_at_position`/`clear_timer`. A call beyond the 100th in its category within that window MUST return `rate_limited` immediately with no host-side effect, and MUST NOT be queued or retried by the host. Calls are counted after the permission and focus checks, so a `permission_denied`/`no_focus` call does not consume quota. *(Prompt acceptance; AR-17; Clarifications)*
- **FR-028**: Immediately after a plugin calls `ready()`, the host MUST deliver `ready_ack` (API version, granted permission list, host capability list) as its first event. Events MUST be delivered in order on the plugin's own scheduler; a slow handler delays only that plugin's subsequent events, never the host or another plugin. This slice MUST NOT deliver `focus_granted`/`focus_revoked`, `permission_changed`, `performance_mode_changed`, `connectivity_changed`, `analysis_ready`, `action_invoked`, `settings_changed`, or `midi_message`. *(Part 5 §5, PL-5.1; Clarifications)*
- **FR-026**: No plugin fault — a thrown exception, a hang, memory exhaustion, or a malformed request — may ever propagate as a panic or unhandled exception into the host process, cause an audible dropout, or affect another plugin. The Gateway and Runtime MUST catch and convert every such fault into a logged console entry and, where applicable, a structured refusal (FR-008) or a suspension (FR-011). *(NFR-2.3; NFR-4.3; Constitution II, NON-NEGOTIABLE)*
- **FR-027**: This slice's transport-focus model MUST be limited to a single global holder defaulting to the host, as specified in FR-017; no focus policy setting, no Transport panel, and no `focus_granted`/`focus_revoked` event delivery ship in this slice. *(Scope boundary; Clarifications; superseded by 010)*

### Key Entities

- **Plugin (DM-10)**: An installed plugin's runtime record — identifier, version, source (always "bundled" in this slice), its validated manifest, install path, enabled flag, health (`ok`/`warning`/`suspended`), suspensions this session (in-memory, resets on launch), API version range, and its effective budgets. `disabled_incompatible` health and "compatibility mode" are modeled but inert until a later slice can produce an API mismatch.
- **Plugin Manifest**: The declared contract inside a plugin package — identifier, name/description, version, API version range, author/license/homepage/source, entry script reference, required and optional permissions (each with a justification), declared network hosts (recorded, unused), declared UI contributions (recorded, unrendered), intended effect nodes (type + suggested position), and an optional minimum host version.
- **PermissionGrant (DM-11)**: One row per catalog permission per plugin — plugin identifier, permission, state (`granted`/`denied`/`not_requested`), granted at, granted by (`install`, the only source in this slice), and hosts (for `network`, unused).
- **PluginStateEntry (DM-12)**: A plugin-scoped (device-scoped, survives sign-out) or plugin×track-scoped (account-scoped, cleared on sign-out) key-value pair — key ≤ 256 bytes, JSON value ≤ 1 MB — with its last-updated timestamp, bounded by the plugin's 10 MB storage cap.
- **Refusal**: `{ code, reason, message }` — `code` one of the six catalog codes, `reason` a machine-readable detail, `message` a user-legible sentence (FR-008).
- **Effect node ownership**: The existing EffectNode's owner field (008), now populated with real non-host values for the first time, activating 008's overload/auto-bypass mechanism for plugin-owned nodes; the orphaned flag is set on owner suspend/disable and cleared when the same identifier's context calls `ready()` again.
- **Marker ownership (DM-6, 006)**: The existing Marker owner field, now taking plugin identifiers, plus the new `transient` flag (in-memory only; removed on track change and owner unload). Ownership gates plugin writes only — the host UI edits any marker.
- **Fixture plugins**: Bundled-source test plugins discovered only under `MODPLAYER_PLUGIN_FIXTURES=1` (FR-003); the sole plugins present until 012/013.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A plugin whose handler hangs or loops indefinitely is suspended with no audible dropout and no host crash, and audio and transport continue uninterrupted throughout, in 100% of trials.
- **SC-002**: When a plugin is suspended, the user sees a notice naming it and can restart or disable it in a single action, in 100% of trials.
- **SC-003**: A plugin that is suspended a third time within one session is disabled automatically, with no further user action, in 100% of trials.
- **SC-004**: Every plugin request lacking its required permission is refused with zero side effects — no state change, no event delivered, no partial action — in 100% of trials.
- **SC-005**: A plugin manifest naming a permission outside the full permission catalog is never loaded and is shown with a specific, readable reason, in 100% of trials.
- **SC-006**: A plugin issuing requests at far above normal load (1,000/second) is throttled with zero measurable effect on host responsiveness or audio continuity, in 100% of trials.
- **SC-007**: A plugin's own persisted settings and per-track data are available again the moment the relevant track next loads, with no user action, in 100% of trials.
- **SC-008**: A user can go from noticing a plugin problem in the plugin list to that plugin being disabled in a single action, without closing or restarting the app.
- **SC-009**: Disabling or suspending a plugin never audibly changes what is already playing — its owned effect nodes keep their last parameters, orphaned, until the user acts — in 100% of trials.

## Assumptions

- The scripting language and sandbox runtime (WASM+fuel, Rhai, or Lua via mlua) are a plan-time Architecture Decision Record per Constitution II, not a spec-level choice; this spec's requirements are written to hold under any of the three.
- No production bundled plugin ships in this slice; Section Loop and Key & Tempo (FR-13.1/FR-13.2, J-2/J-7) are 001-mvp/012 and 013 and will be built only on the public API described here. This slice's automated tests and manual scenarios run against the `MODPLAYER_PLUGIN_FIXTURES=1` fixture plugins (FR-003).
- `ui.*` is not implemented in this slice, so a plugin has no panel, overlay, shortcut, or settings page; its only user-visible surfaces are the plugin list (FR-023), the tagged host log (the "console" until 002-developer-mode/002), and host notices. There is no Performance Mode (004-performance/003), so suspension notices are always shown.
- Section markers (`define_section`) and hot-reload state hooks (`serialize_state`/`restore_state`) are absent from this slice's API object and arrive as API minor additions with 006-practice-depth/002 and 002-developer-mode respectively.
- `network`, `files.*`, `midi.*`, `clipboard`, `library.*`, `analysis.*`, and `audio.process` are recognized permission strings (so a manifest requesting one is not "invalid") but have no working capability behind them in this slice; no bundled plugin requests any of them.
- Transport-focus arbitration in this slice is intentionally minimal (FR-017, FR-027) and is fully superseded by 001-mvp/010, which this feature's own `transport.control` capability is a documented prerequisite for.
- Numeric defaults introduced where the source document gives none — the 5-second `ready()` load timeout, the 200 ms `unloading` persistence window, the 100 calls/second/category rate limit, the 10 events/second default `position` rate, the 3-aborts/60 s → `warning` → clears-after-5-minutes health rule, the 256-pending-timer cap, and the 256-byte key / 1 MB value state bounds — are fixed by this spec; the plan phase may not change them without recording the deviation.
- Per-track plugin state (`state.track`) is account-scoped like the rest of per-track user state (A-9, Retention summary) and is cleared on sign-out; plugin-scoped state (`state.plugin`) is device-scoped, survives sign-out, and is cleared only on uninstall (never, for bundled). The 10 MB cap is the only other retention bound in this slice.
- The plugin list's live CPU/memory figures use the same kind of rolling measurement window 008 already established for effect-node cost, so the two "load" concepts in the UI are consistent with each other.
