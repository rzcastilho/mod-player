# Feature Specification: Catalog Search and Library Browsing

**Feature Branch**: `feature/004-search-and-library-browse`

**Created**: 2026-09-16

**Status**: Clarified (2026-09-16, specify pass + clarify review) — no open human decisions

**Input**: User description: "Let a user find and start music at least as fast as in the official client, so they never need two players. This slice is search and browse plus play; editing the library is a later slice. Search takes free text and returns results grouped into tracks, albums, artists, and playlists, updating as the user types with a short debounce, showing at least the first 20 items per group with "show more". Podcasts, audiobooks, and other non-music content never appear. Every result offers play now, play next, add to queue, and (as placeholders wired later) add to playlist, save to library, and pin for offline. The Library view mirrors the account: saved tracks, saved albums, followed artists, and playlists (own and followed; playlists the user does not own are view-only), plus a Recently Played list of at least the last 100 tracks. For every track the app holds title, artists, album, artwork, duration, explicit flag, release date, and the service's stable track identifier, which becomes the key for all per-track state in later slices. Library sync runs on launch and periodically while online. Lists are virtualized and the UI never blocks on network: a rate-limited response shows stale data with a subtle "refreshing…" indicator, not an error. Empty states are explicit — "Your library is empty — search to add music" with a search action; "No playlists yet — create one" — and loading uses skeleton rows, never a spinner over the whole view. Acceptance: when the user types a query online, first results appear within 300 ms of the last keystroke. When a track is unavailable in the user's region or has been removed, its row is greyed with the reason and the queue skips it with a notice. When artwork fails to load, a placeholder with initials appears. When a library has 50,000 saved tracks and 1,000 playlists, scrolling and search show no visible degradation."

**Source**: [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) — FR-2.1 Search, FR-2.2 Library, FR-2.3 Playlists (view-only paths only), FR-2.4 Track metadata, INT-3 Streaming service — catalog and library, DM-3 PlaylistRef/AlbumRef/ArtistRef, EC §2 Catalog/library/playlists, EC §12 Empty/loading/first-run states, NFR §3 Scalability (local), § 4 Jobs-to-be-done (JTBD-14). Prerequisites: 002-first-launch-and-sign-in (signed-in AccountSession, *playback permitted* fact, the session-sourced read pattern established there); 003-streaming-playback-and-queue (Queue accepts a context plus play-next additions, transport commands, TrackRef, notification severities, the now-superseded "Play from account" developer scaffold).

**Scope boundary**: Does not cover saving/unsaving tracks or albums, following/unfollowing artists, playlist creation/rename/reorder/track-editing, offline search over a cached index, pinning for offline, sorting options, or any plugin access to catalog/library data (`library.read`/`library.write` land with plugin permissions in a later slice) — those land in the offline-and-library wave and the polish wave. Per the breakdown coverage map, FR-2.4.2 (provider audio features) belongs to 006-practice-depth/001 and sorting belongs to 007-operations-and-polish/005.

It is not extended to unloaded pages. FR-006 now names every origin list explicitly: search Tracks group, Saved Tracks, Recently Played, an album's track list, a playlist's track list, an artist's top tracks.
- Q: Are the three functional actions enabled on a greyed (unavailable) track row? → A (D, INT-3.3 / 003 FR-026 — the queue already handles unavailable items; A for keeping the controls enabled): yes, all six actions stay enabled and accessibly named on an unavailable row; Play now / Play next / Add to queue enqueue the acting list exactly as for any row, and 003's existing skip-with-notice behavior then applies when the cursor reaches the unavailable track. ## User Scenarios & Testing *(mandatory)*

### User Story 1 - Find and play any track by searching (Priority: P1)

A signed-in user types a free-text query and sees results grouped by tracks, albums, artists, and playlists, updating live as they type. Every result — and every subsequent action taken on it — is available fast enough that the user never feels a need to open the official client instead. Podcasts, audiobooks, and any other non-music content never appear.

**Why this priority**: This is the whole point of the slice and the product's stated JTBD-14 ("as fast and complete as the official client, so I do not need two players"). Until this ships, the only way to hear anything is 003's temporary developer scaffold.

**Independent Test**: With a signed-in account, type a query that matches tracks, albums, artists, and playlists; verify all four groups populate within budget, each result's six actions behave as specified, and no non-music result ever appears.

**Acceptance Scenarios**:

1. **Given** a signed-in user with connectivity, **When** they type a query and pause, **Then** at least one matching group's first page is painted within 300 ms of the last keystroke; groups render in the fixed order Tracks, Albums, Artists, Playlists, a group still pending shows skeleton rows, and a group with zero matches is omitted entirely (no header).
2. **Given** a search in progress, **When** the user keeps typing before a response arrives, **Then** only the response to the latest query is ever shown; any in-flight response to an earlier query is discarded on arrival.
3. **Given** a group has more than 20 matches, **When** the group is shown, **Then** exactly the first 20 items appear with a **Show more** action that reveals 20 more per activation.
4. **Given** search results include a podcast, audiobook, or other non-music item on the service, **When** results render, **Then** that item never appears in any group.
5. **Given** a track result, **When** the user activates **Play now** (or presses Enter / double-clicks the focused row), **Then** the Queue's context becomes that track's origin list — the rows currently loaded in the list it was shown in — in displayed order, and playback starts at that track.
6. **Given** an album or playlist result, **When** the user activates **Play now**, **Then** the Queue's context becomes that entity's full track list in its own order, starting at the first track (fetching the full list first if not already available, with a brief in-place loading indicator on the action).
7. **Given** any result, **When** the user activates **Play next** or **Add to queue**, **Then** the result's acting list (per the rule above) is inserted into the play-next block or appended to the upcoming context respectively, without interrupting current playback.
8. **Given** any result, **When** the user activates **Add to playlist**, **Save to library**, or **Pin for offline**, **Then** no network call is made, no state changes, and an info toast "Coming soon" appears; the control remains keyboard-operable and accessibly named.
9. **Given** a query with no matches at all, **When** results render, **Then** an empty state "No results for “<query>” — check your spelling, or you might be offline." appears instead of empty group headers.
10. **Given** the user is offline, **When** they type a query, **Then** search shows a clear inline "Search needs a connection — you're offline" state instead of attempting a request or showing the no-results empty state.

### User Story 2 - Browse and play from your own library (Priority: P2)

The Library view mirrors the signed-in account: saved tracks, saved albums, followed artists, and playlists (both owned and followed — a followed, non-owned playlist is view-only), plus a Recently Played list of the last 100 tracks played through ModPlayer. Every row offers the same play now / play next / add to queue / placeholder actions as search results. The library keeps itself in sync automatically.

**Why this priority**: Search finds new things; the Library is where a returning user goes first to resume listening to what they already have — equally core to "never needing two players," and ranked second only because Story 1 must exist before results are worth acting on.

**Independent Test**: With a signed-in account that has saved tracks, saved albums, followed artists, and both an owned and a followed playlist, open the Library view and verify every section lists correctly, a followed playlist shows no edit affordances, Recently Played lists past plays newest-first, and every row's six actions behave exactly as in Search.

**Acceptance Scenarios**:

1. **Given** a signed-in account with saved tracks, saved albums, followed artists, and playlists, **When** the Library view opens, **Then** it opens on Saved Tracks, offers sections in the order Saved Tracks, Saved Albums, Followed Artists, Playlists, Recently Played (and no "Pinned for offline" section), and each section lists the account's current items, sourced from a locally kept-in-sync index so the view renders immediately even before a fresh sync completes.
2. **Given** the Library view is open, **When** the user opens Playlists, **Then** both owned and followed playlists are listed, a followed (non-owned) playlist shows an "Owner: <name>" label, and no playlist — owned or followed — shows any rename, reorder, or track add/remove control.
3. **Given** the user opens an owned or followed playlist, **When** its detail view renders, **Then** its tracks are listed in playlist order, each with the standard six actions.
4. **Given** the user opens a saved album, **When** its detail view renders, **Then** its tracks are listed in album order, each with the standard six actions.
5. **Given** the user opens a followed artist, **When** its detail view renders, **Then** up to 10 top tracks are listed, each with the standard six actions.
6. **Given** at least one track has started playing through ModPlayer (including a track handed off by a Connect transfer), **When** Recently Played renders, **Then** the 100 most recently played distinct tracks are listed newest-play-first, each track appearing at most once even if replayed; a track that was only queued, browsed, or skipped as unavailable does not appear, and plays made on other devices do not appear.
7. **Given** the Library sections are all empty, **When** the Library view opens, **Then** it shows "Your library is empty — search to add music" with a Search action; an individually empty section (e.g., no followed artists while tracks exist) shows that section's own empty copy.
8. **Given** the Playlists section has zero playlists while other sections are non-empty, **When** it renders, **Then** it shows "No playlists yet — create one" (its action is a placeholder toast, per Clarifications).
9. **Given** the app is offline, **When** the Library view opens, **Then** the last-synced snapshot renders normally (not an offline error), consistent with the local-index behavior established in Clarifications.
10. **Given** the Library view is open online, **When** background sync runs (on launch, every 15 minutes, or immediately on reconnect), **Then** it never blocks scrolling, typing, or any row action, and updates the view in place when it completes.

### User Story 3 - Stay usable and honest at real-world scale and under network trouble (Priority: P3)

Whether the library holds a handful of tracks or 50,000 tracks and 1,000 playlists, scrolling and search feel identical. The UI never blocks on the network: a rate-limited response shows stale data with a subtle indicator instead of an error, loading uses skeleton rows instead of a spinner, unavailable tracks are clearly marked instead of silently missing or crashing playback, and failed artwork degrades to a readable placeholder.

**Why this priority**: This is what makes Stories 1 and 2 trustworthy in practice rather than only in a demo; it is scoped after them because there is nothing to scale or stress-test until search and library browsing exist.

**Independent Test**: Load a library fixture at 50,000 saved tracks / 1,000 playlists and confirm no visible scroll or search degradation; separately simulate a rate-limited response, a region-locked/removed track, and a failed artwork load, and confirm each degrades exactly as specified rather than erroring.

**Acceptance Scenarios**:

1. **Given** a library with 50,000 saved tracks and 1,000 playlists, **When** the user scrolls any library list or types a search query, **Then** there is no visible degradation in scroll smoothness or the 300 ms search budget (lists are virtualized; only visible rows render).
2. **Given** any list is loading for the first time, **When** it renders, **Then** it shows skeleton rows in place of content, never a spinner covering the whole view.
3. **Given** the streaming service rate-limits a library or search request, **When** the response is throttled, **Then** the view keeps showing its last-known (stale) data with a subtle "refreshing…" indicator, never an error message.
4. **Given** a track is unavailable in the user's region or has been removed from the service, **When** it appears in search, library, or a playlist/album detail view, **Then** its row is visibly greyed with the reason shown ("Unavailable in your region" or "Removed from the service"), all six actions remain enabled, and if it is played through the Queue, playback skips it with a notice (per 003's existing unavailable-track handling — this slice only supplies the availability mark, not a new skip mechanism).
5. **Given** a result or library row's artwork fails to load, **When** the row renders, **Then** a placeholder bearing the entity's initials (up to two uppercase letters: first letter of the first two words) appears in place of the artwork, never a broken-image icon or blank space.
6. **Given** the app's very first launch (no prior local library index) fails its initial sync (service unreachable), **When** the Library view opens, **Then** it shows a distinct "couldn't load your library — check your connection" state with a retry action, never the "your library is empty" empty state (which asserts a known-empty account, not an unknown one).

### Edge Cases

- What happens when the search box is cleared mid-typing, or contains only whitespace? → Results and group headers clear immediately back to the pre-search state; no request is issued; no stale results linger.
- What happens when a library sync fails for a reason other than rate-limiting (e.g., transient network error) and a prior snapshot exists? → Nothing visible: the snapshot stays, no toast or error appears, and the next scheduled or reconnect-triggered sync retries.
- What happens when the very first search query of a session is rate-limited (no results on screen yet)? → The groups show skeleton rows with the "refreshing…" indicator until the backed-off retry succeeds; never an error.
- What happens when connectivity drops while a search request is already in flight? → The in-flight request is treated as failed/discarded and the view falls back to the offline search state (User Story 1, AS 10), not a hung skeleton.
- What happens when the user switches Library tabs while a background sync is running? → Every tab renders its current local-index snapshot immediately; switching tabs never waits on the sync.
- What happens when a playlist has zero tracks (as opposed to zero playlists existing)? → Its detail view shows "This playlist has no tracks", distinct from the Playlists-section-level "No playlists yet" empty state.
- What happens when a followed artist's top tracks are all region-locked or removed? → The artist still appears in Followed Artists; its detail view lists the (greyed, reason-shown) tracks rather than substituting an empty state, since the artist itself is not "empty."
- What happens when the same track is both saved and appears in Recently Played? → It is shown independently in each section; no merging or cross-section deduplication occurs.
- What happens at exactly the 50,000-track / 1,000-playlist boundary named in the acceptance criteria? → Covered by Success Criteria SC-002; no additional behavior beyond continued virtualization.
- What happens when a placeholder action (Add to playlist, Save to library, Pin for offline) is activated repeatedly? → Each activation independently shows the "Coming soon" toast; nothing accumulates or errors.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST let a signed-in user search the streaming catalog by free text, returning results grouped into Tracks, Albums, Artists, and Playlists, updating as the user types with a 150 ms debounce after the last keystroke, discarding any response to a since-superseded query. Query text MUST be trimmed of leading/trailing whitespace before a request is issued; an empty or whitespace-only query MUST issue no request and MUST return the view to the pre-search state. *(FR-2.1.1, FR-2.1.2; Clarifications)*
- **FR-002**: Result groups MUST render in the fixed order Tracks, Albums, Artists, Playlists; a group with zero matches MUST be omitted entirely (no header); a group still awaiting its response MUST show skeleton rows. Each non-empty group MUST show the first 20 matching items with a **Show more** action that reveals 20 additional items per activation, with no artificial ceiling on total items shown. *(FR-2.1.2; Clarifications)*
- **FR-003**: Podcasts, audiobooks, and any other non-music content MUST be excluded from every search result group. *(FR-2.1.5)*
- **FR-004**: Every search result and every library row (Saved Tracks, Saved Albums, Followed Artists, Playlists, Recently Played, and album/playlist/artist detail views) MUST expose the same six actions: **Play now**, **Play next**, **Add to queue** (functional), and **Add to playlist**, **Save to library**, **Pin for offline** (placeholders — see FR-005). *(FR-2.1.3)*
- **FR-005**: Activating a placeholder action (**Add to playlist**, **Save to library**, **Pin for offline**) MUST make no network call, change no state, and MUST show a non-blocking **info** toast "Coming soon"; the control MUST remain keyboard-operable with an accessible name and role. *(Clarifications; Constitution X)*
- **FR-006**: Activating **Play now** on a track row (or pressing Enter / double-clicking the focused row) MUST replace the Queue's context (per 003 FR-011/FR-014) with that track's origin list — the rows currently loaded in the list it was shown in (the search Tracks group, Saved Tracks, Recently Played, an album's track list, a playlist's track list, or an artist's top tracks) — in displayed order, cursor at that track, and start playback; on an album or playlist row it MUST use that entity's full track list in its own order starting at the first track, fetching the full list first if not already cached; on an artist row it MUST use that artist's top tracks. *(Clarifications, reusing 003's Queue contract unchanged)*
- **FR-007**: Activating **Play next** or **Add to queue** on any row MUST insert that row's acting list (per FR-006's rule), in order, into 003's play-next block (Play next) or the end of the upcoming context (Add to queue), without interrupting current playback. *(Clarifications; 003 FR-011)*
- **FR-008**: For every track the system holds and can display title, artists, album, artwork, duration, explicit flag, release date, and the service's stable track identifier (the key for all per-track state in later slices, per DM-2). A track row MUST show artwork, title, artists, album, duration as m:ss, and an "E" badge (accessible name "Explicit") when the explicit flag is set; an album row MUST show artwork, name, artists, and release year; an artist row artwork and name; a playlist row artwork, name, and owner. *(FR-2.4.1; Clarifications)*
- **FR-009**: The Library view MUST show the account's saved tracks, saved albums, followed artists, and playlists (both owned and followed), plus Recently Played (FR-012), as sections in the fixed order Saved Tracks, Saved Albums, Followed Artists, Playlists, Recently Played, opening on Saved Tracks, with no "Pinned for offline" section in this slice. Sections are sourced from a locally kept-in-sync index (FR-011) so the view renders immediately from the last-synced snapshot, including while offline. *(FR-2.2.1; EC-2.6; Clarifications)*
- **FR-010**: A playlist the signed-in account does not own MUST be labeled with its owner's name and MUST NOT show any rename, reorder, or track add/remove control; no playlist — owned or followed — shows such a control in this slice (playlist editing is out of scope here). *(FR-2.3.2)*
- **FR-011**: The system MUST sync the library index automatically on launch, at least every 15 minutes while online, and immediately upon regaining connectivity, without blocking scrolling, typing, or any row action while it runs. A sync that fails for any reason other than rate-limiting while a prior snapshot exists MUST be silent (snapshot retained, no toast or error, retried at the next trigger); only the no-snapshot case is surfaced (FR-021). *(INT-3 "on launch and periodically while online"; Clarifications)*
- **FR-012**: The system MUST show a Recently Played list of the 100 most recently played distinct tracks, newest-play-first, deduplicated (each track appears once, at its most recent play time), persisted across restarts. An entry MUST be recorded when a track starts playing through ModPlayer (the transport makes it the current item and audio output begins, including tracks handed off by a Connect transfer); tracks that are only queued, browsed, or skipped as unavailable MUST NOT be recorded, and plays made on other devices are not shown. The per-track `last played` timestamp (DM-2) MUST persist even after the track leaves the 100-entry window. *(FR-2.2.2; DM-2; Clarifications)*
- **FR-013**: Opening a saved album's or a playlist's detail view MUST list its tracks in the album's or playlist's own order, each with the standard six actions (FR-004); opening a followed artist's detail view MUST list up to its 10 top tracks, each with the standard six actions. *(FR-2.2.1, FR-2.3.2; Clarifications)*
- **FR-014**: All lists in this slice (search result groups, every Library section, and every detail view) MUST be virtualized, rendering only visible rows, so that scrolling and search remain smooth at 50,000 saved tracks and 1,000 playlists with no visible degradation. *(NFR-3.1; EC-2.6)*
- **FR-015**: The UI MUST NOT block on network activity: when a search or library request is rate-limited by the service, the view MUST continue showing its last-known (stale) data with a subtle "refreshing…" indicator, never an error. For search, "last-known data" is whatever results are currently on screen; when none are, the groups MUST show skeleton rows with the indicator until the backed-off retry of the newest query succeeds. *(INT-3.1; EC-2.5; Clarifications)*
- **FR-016**: Every list's first-time loading state MUST use skeleton rows; a spinner covering the entire view MUST NOT be used anywhere in this slice. *(EC §12)*
- **FR-017**: An empty Library (every section empty) MUST show "Your library is empty — search to add music" with a Search action; an individually empty section MUST show its own empty-state copy (Clarifications) with a Search action, except Playlists, whose empty state "No playlists yet — create one" pairs with a placeholder action (FR-005). *(EC §12; Clarifications)*
- **FR-018**: When search returns no matches for a query, the system MUST show "No results for “<query>” — check your spelling, or you might be offline." instead of empty group headers; when the user is offline, search MUST instead show a clear inline "Search needs a connection — you're offline" state and MUST NOT attempt a request or show the no-results state. *(EC-2.1; Clarifications)*
- **FR-019**: A track that is unavailable in the user's region or has been removed MUST render its row visibly greyed with the reason shown as row text and in the row's accessible name ("Unavailable in your region" for `unavailable_region`, "Removed from the service" for `removed`), in search results, every library section, and every detail view; all six actions MUST remain enabled on such a row (the Queue's existing skip-with-notice applies when the cursor reaches it); this slice supplies the availability mark only — skipping it in the Queue with a notice is 003's existing behavior and is not re-implemented here. *(EC-2.2, INT-3.3)*
- **FR-020**: When a row's artwork fails to load, the system MUST show a placeholder bearing the entity's initials (album title for tracks/albums, artist name for artists, playlist name for playlists) instead of a broken image or blank space. Initials are up to two characters: the first letter of the first word and the first letter of the second word, uppercased (one letter for a single-word name); a name with no letter/digit characters yields a generic music glyph. *(EC-2.7; Clarifications)*
- **FR-021**: When the app's very first sync fails with no prior local library index available, the Library view MUST show a distinct "couldn't load your library — check your connection" state with a retry action, and MUST NOT show the "your library is empty" empty state. *(Edge Cases; distinguishes "known empty" from "unknown")*
- **FR-022**: This slice MUST remove 003's temporary "Settings › Developer › Play from account" surface; Search and the Library (Saved Tracks, Recently Played) become the permanent user-facing ways to source real tracks into the Queue. *(003 spec Assumptions; Clarifications)*
- **FR-023**: This slice MUST NOT introduce any UI for saving/unsaving tracks or albums, following/unfollowing artists, playlist creation/rename/reorder/track editing, offline search over a cached index, pinning for offline, sorting, or plugin access to catalog/library data — only the placeholder affordances named in FR-005. *(Scope boundary)*
- **FR-024**: All new interactive elements introduced in this slice (search box, group headers, Show more, every row and its six actions, Library section tabs, detail views, toasts, retry actions) MUST be operable by keyboard alone and MUST expose an accessible name, role, and state, consistent with 001–003. Every result/library row MUST be a focusable item where Enter activates **Play now** and all six actions are reachable through a per-row actions menu (accessible name "Actions for <name>") and its context-menu equivalent. *(NFR-6.1, NFR-6.2; Constitution X; Clarifications)*
- **FR-025**: All user-facing strings introduced in this slice MUST be externalized; English (en-US) is the only shipped locale in this slice, consistent with 001–003. *(NFR-7.1; Constitution X)*

### Key Entities

- **Search Query & Result Set**: The user's current free-text query and its live, grouped results (Tracks, Albums, Artists, Playlists), each group independently paginated (20 per page) and superseded in full by the next query; ephemeral, not persisted.
- **Library Index**: The locally kept-in-sync mirror of the account's Saved Tracks, Saved Albums, Followed Artists, and Playlists (per DM-3), plus its own sync metadata (last synced at, last sync outcome) driving the stale/refreshing and first-sync-failed states.
- **Recently Played Entry**: A track reference plus the timestamp of its most recent play through ModPlayer (DM-2 `last played`), recorded when the track starts playing; the list is deduplicated by track, ordered newest-first, shows the 100 most recent entries, and is persisted across restarts — distinct from 003's in-memory, session-only skip-back History, and never sourced from other devices' plays.
- **TrackRef** (per DM-2, shared with 003): identity, title, artists, album, artwork reference, duration, explicit flag, release date, availability (available / unavailable_region / removed) — the key for all per-track state in later slices.
- **PlaylistRef, AlbumRef, ArtistRef** (per DM-3): identity, name, artwork, owner and editable flag (playlist only), and a cached track list (full order for albums and playlists, top tracks for artists).
- **Row Action Set**: The six actions exposed on every result/library row — three functional (Play now, Play next, Add to queue, per FR-006/FR-007) and three placeholder (Add to playlist, Save to library, Pin for offline, per FR-005), identical across Search and every Library surface.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: When a signed-in, online user types a search query, at least one matching group's first page is painted within 300 ms of the last keystroke in at least 95% of trials.
- **SC-002**: With a library fixture of 50,000 saved tracks and 1,000 playlists, scrolling any list and issuing a search show no perceptible drop in responsiveness (frame pacing and input latency indistinguishable from a small-library baseline) in 100% of trials.
- **SC-003**: A user can find and start playing a specific, known track from a 50,000-track library via search in under 10 seconds in at least 90% of usability trials.
- **SC-004**: Every list's first load renders skeleton rows, never a full-view spinner, in 100% of observed loads across Search, every Library section, and every detail view.
- **SC-005**: A rate-limited search or library request always results in the view showing stale data with a "refreshing…" indicator rather than an error, in 100% of simulated rate-limit trials.
- **SC-006**: A region-locked or removed track is visibly greyed with its reason shown everywhere it can appear (search, every library section, every detail view) in 100% of trials.
- **SC-007**: A failed artwork load always resolves to an initials placeholder, never a broken image or blank space, in 100% of simulated load-failure trials.
- **SC-008**: Recently Played always lists exactly the 100 most recently started distinct tracks, deduplicated, newest-first, once that many tracks have been played through ModPlayer; a queued-but-unplayed or unavailable-skipped track never appears; and the list survives an application restart, in 100% of trials.
- **SC-009**: Every interactive element introduced in this slice is reachable and operable using only the keyboard, and exposes a correct accessible name, role, and state, verified by automated accessibility test coverage across 100% of the new elements.

## Assumptions

- Placeholder actions (Add to playlist, Save to library, Pin for offline) are inert by design in this slice; they exist to keep the row UI stable across this slice and 003-offline-and-library/003, which wires real behavior behind the same controls without a UI change.
- Recently Played is ModPlayer's own play log (DM-2 `first played / last played / play count`), not the account's cross-device history; no service read is required to populate it, and the offline-and-library wave's cache eviction (FR-8.1.3, least-recently-played first) will reuse the same per-track timestamps this slice records.
- Catalog reads in this slice (search queries, library sync, album/playlist/artist track-list fetches) are sourced through the same session-authenticated integration 003 already validated for tier and "Play from account" reads; the public per-track/library Web API is known to return HTTP 429 under this project's single desktop-receiver credential (confirmed in 003) and MUST NOT be relied on as the primary path.
- Artist browsing in this slice is bounded to top tracks (up to 10); full discography, related artists, and any artist "detail page" beyond top tracks are out of scope, reachable indirectly via Search's Albums group.
- The 150 ms search debounce, the 15-minute background sync interval, the 20-items-per-page group size, the 100-entry Recently Played window, the two-character initials rule, and the Library section order are conventional, internal constants; a later slice may tune them without a contract change, consistent with how 002 and 003 recorded their own timing constants.
- This slice's library/search rows are the same reusable component 003's temporary "Play from account" scaffold exercised informally; removing that scaffold (FR-022) does not remove any tested Queue behavior, since Search and Library now exercise the identical Queue contract through real, permanent UI.
- English (en-US) remains the only shipped locale; pt-BR localization is delivered by 007-operations-and-polish/003, consistent with 001–003.
