# Feature Specification: Key & Tempo Bundled Plugin and Getting Started Panel

**Feature Branch**: `feature/013-key-and-tempo-plugin`

**Created**: 2026-09-20

**Status**: Draft — specify + clarify passes complete; no open [NEEDS CLARIFICATION] markers, no human escalations; ready for `/speckit-plan`

**Input**: User description: "Ship Key & Tempo, the second bundled plugin: transpose a song to the key the band plays it in, or slow a solo to 60% without changing pitch, and have each track remember its setting. Like Section Loop it is built only on the public plugin API and released under the host's license. The plugin declares `audio.effects`, `ui.panel`, `ui.shortcuts`, and `state.track`. It creates one pitch-shift node and one time-stretch node in the effect chain, both labeled with the plugin's name, and exposes semitones (−12..+12 with fine cents), tempo percent (25..200), formant preservation, and quality mode (performance/quality). Actions: key up/down by one semitone, tempo up/down by a configurable step (default 10%), reset key, reset tempo, toggle 'remember for this track', and toggle 'keep across tracks'. Default shortcuts include `+` / `-` for tempo steps. Per-track memory is off by default. When 'remember for this track' is on, the current key and tempo are stored under the track's identity and restored on load, and the panel shows a small 'restored' badge so the user knows why the key is shifted. When a track has no stored setting, key and tempo reset to 0 and 100% on track change — unless 'keep across tracks' is on, in which case the current settings persist until changed. Also in this slice: after first sign-in the app shows a dismissible 'Getting started' panel introducing Section Loop and Key & Tempo, the default keyboard shortcuts, and a link to the plugin tutorial (a placeholder link until the tutorial ships). Both bundled plugins are installed and enabled by default with pre-approved permissions. Acceptance: when the user sets −2 semitones on a track, the pitch drops a whole step within 20 ms with no change in tempo and no obvious artifacts on typical mixed music. When the user turns on 'remember for this track' and skips to the next song, key returns to 0; returning to the first song restores −2 with the badge. When Section Loop is looping and the user drags tempo to 60%, the loop continues with pitch unchanged and the chain shows Key & Tempo's nodes as the only effects. When the user chose 'don't remember' and reopens the track, tempo is 100% while Section Loop's markers remain."

**Source**: [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) — FR-13.2 Key & Tempo, § 13 Bundled reference plugins, FR-1.4 Getting started, J-3 — Transpose a set (S-2), J-2 — Drill a solo with Section Loop (S-1) steps 5–8, § 5 Key scenarios (S-2), § 6 Success metrics, § 4 Jobs-to-be-done (JTBD-2, JTBD-3, JTBD-7), GOV § 1 Licensing (GOV-1.3). **Prerequisites**: [008-effect-chain-and-built-in-nodes](../008-effect-chain-and-built-in-nodes/spec.md) (the host-owned pitch-shift/time-stretch node types, their parameters, ramp/crossfade rules, the adjacency optimization, the `+`/`-` tempo-step host actions this feature's own default bindings collide with), [009-plugin-runtime-and-permissions](../009-plugin-runtime-and-permissions/spec.md) (plugin runtime, Capability Gateway, `audio.effects`/`state.track` grants, bundled-plugin enable/disable mechanics, node orphaning on suspend/disable), [011-plugin-ui-contributions](../011-plugin-ui-contributions/spec.md) (`ui.panel`/`ui.shortcuts`, the action cross-tier conflict rule this feature's tempo shortcuts exercise a second time), and [012-section-loop-plugin](../012-section-loop-plugin/spec.md) (the first bundled plugin, whose default-enable precedent, licensing package shape, and panel/action patterns this feature reuses; the two plugins' coexistence is this feature's own acceptance text). [002-first-launch-and-sign-in](../002-first-launch-and-sign-in/spec.md) (FR-1.4's "Getting started" panel content was explicitly deferred there to this feature).

**Scope boundary**: Does not cover showing the detected key from analysis (FR-13.2.5, SHOULD/deferred), MIDI-bound tempo/key control, or the plugin tutorial content itself (the Getting Started panel links to a placeholder). Does not modify the host-native effect chain DSP, node types, or ramp/crossfade mechanics shipped in 008, or the panel/shortcut mechanics shipped in 011 — this feature is a *consumer* of those APIs. Its one plugin-API change is the additive **1.3 → 1.4** minor of FR-020 (node parameter values become readable by plugins via `list_chain()`/`effect_chain_changed`, and `effect_chain_changed` also fires on parameter changes), which is the smallest addition that lets the plugin keep its panel and stored per-track entry equal to what its nodes actually hold after the host's own `+`/`-` action (008 FR-017) or an Effect Chain panel edit changes them — the same "bundled plugin needs a host primitive the current minor cannot express" shape as 012's FR-017 bump (Clarifications, clarify pass).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Transpose a song to the band's key (Priority: P1)

A musician plays a track that is in the wrong key for their instrument or voice and shifts it by semitones, instantly and audibly, with the tempo completely unaffected.

**Why this priority**: This is JTBD-3 (P0 in the source document) and the prompt's lead acceptance line — transposition with no tempo change is the plugin's most basic reason to exist for a performing musician (S-2, J-3).

**Independent Test**: With Key & Tempo enabled and no stored per-track setting, play a track, use the panel's Key control to set −2 semitones, and verify the pitch audibly drops a whole step within the latency budget with the tempo and duration unchanged and no obvious artifacts.

**Acceptance Scenarios**:

1. **Given** a track is playing at 0 semitones, **When** the user sets the Key control to −2 (via the panel, or via `key_down` invoked twice), **Then** `api.effects.set_param` is called on the plugin's pitch-shift node with the composed semitone value, the pitch audibly drops a whole step within 20 ms, the tempo and track duration are unchanged, and no obvious artifacts are present on typical mixed music (FR-13.2.2; prompt acceptance; 008 FR-010).
2. **Given** the Key control is at +7, **When** the user activates `reset_key` (panel button or its unbound action), **Then** the pitch-shift node's semitone value returns to 0 over the standard 20 ms ramp and the Fine tune control resets to 0 cents (FR-13.2.3).
3. **Given** the Key slider is at −5 semitones, **When** the user drags Fine tune to +30 cents, **Then** the pitch-shift node receives `-5 + 0.30 = -4.70` semitones, clamped by the host to the valid range, and the panel shows both the whole-semitone and cents values distinctly (Clarifications).
4. **Given** formant preservation is toggled on, **When** the Key control changes, **Then** only the pitch-shift node's `formant` parameter reflects the toggle — the time-stretch node has no such parameter and is unaffected (008 FR-006).

### User Story 2 - Slow a passage down without changing its pitch (Priority: P1)

A musician or DJ drags tempo down to practice a fast passage at reduced speed, or nudges it up in steps to build back to full speed, while the pitch stays exactly where it was — including while Section Loop is actively looping a section.

**Why this priority**: This is JTBD-2 (P0) and the prompt's third acceptance line, which explicitly names coexistence with Section Loop (J-2 steps 5–7) as part of this feature's own acceptance, not an incidental detail.

**Independent Test**: With Key & Tempo enabled, play a track, drag the Tempo control to 60%, and verify the tempo audibly drops with the pitch unchanged; separately, with Section Loop looping a marked section, drag tempo to 60% and verify the loop continues seamlessly with the chain showing only Key & Tempo's two nodes.

**Acceptance Scenarios**:

1. **Given** a track is playing at 100% tempo, **When** the user drags the Tempo control to 60%, **Then** `api.effects.set_param` is called on the plugin's time-stretch node with `ratio = 0.60`, the tempo change is audible within the latency budget, and the pitch of the material is unchanged (FR-13.2.2; prompt acceptance; 008 FR-001a/FR-010).
2. **Given** Section Loop is enabled and its region is armed and wrapping, **When** the user drags Key & Tempo's Tempo control to 60% via its panel, **Then** the loop continues gaplessly and click-free through the ratio change (008 FR-005's crossfade), the pitch remains unchanged, and the Effect Chain panel shows exactly Key & Tempo's pitch-shift and time-stretch nodes — Section Loop owns no effect node (010/012) — as the chain's only entries (prompt acceptance; FR-016).

### User Story 3 - The track remembers, or forgets, its own key and tempo (Priority: P1)

A musician sets a song's key and tempo once, tells the plugin to remember it for that track, and every future visit to that track restores exactly what was set — while every other track stays untouched at its defaults, and a small badge explains why a track sounds shifted.

**Why this priority**: This is JTBD-7 (P1) and the prompt's second and fourth acceptance lines; a practice/performance tool that forgets a musician's per-song key and tempo setup, or silently carries one song's shift into the next, fails a use the source document calls out explicitly (S-2, J-3).

**Independent Test**: On track A, set key −2 and turn on "remember for this track"; skip to track B and verify key is 0; return to track A and verify key −2 is restored with the "restored" badge visible. Separately, on a track where "remember for this track" was never turned on, set tempo to 60%, skip away and back, and verify tempo is 100% on return with no badge.

**Acceptance Scenarios**:

1. **Given** the user sets key −2 on track A and activates `toggle_remember` (on), **When** the change is made, **Then** the plugin writes `api.state.track.set("settings", { key = -2, cents = 0, tempo = 100, formant = false, quality = "performance" })` for track A immediately (not deferred to unload), and every further change to any of those values on track A while remember stays on — from the panel, an action, the host's `+`/`-`, or an Effect Chain panel edit — updates the same entry (FR-13.2.4; prompt acceptance; Clarifications).
2. **Given** track A has a stored entry (remember on, key −2), **When** the user skips to track B, which has no stored entry, **Then** Key & Tempo's `track_changed` handler resets key to 0 and tempo to 100% (formant and quality mode also reset to their defaults), and no "restored" badge is shown (prompt acceptance; FR-13.2.4).
3. **Given** the state from Scenario 2, **When** the user returns to track A, **Then** `track_changed` fires, the plugin reads `api.state.track.get("settings")` for track A, applies key −2 (and the stored tempo, formant, quality) to the pitch-shift/time-stretch nodes, sets the "Remember for this track" toggle on, and the `restored` text widget reads "Restored from this track's memory" (prompt acceptance; FR-13.2.4; Clarifications).
4. **Given** track C was never given "remember for this track," **When** the user sets tempo to 60%, skips away, and returns to track C, **Then** tempo shows 100% on return, Section Loop's own markers (if any, on a different plugin's state) are unaffected, and no badge is shown (prompt's fourth acceptance line).
5. **Given** the user turns "keep across tracks" on (a session-wide mode, not a per-track setting) while playing track A with key −2 set but remember **off**, **When** they skip to track D, which has no stored entry, **Then** key stays at −2 (the current settings persist rather than reset) and no badge is shown, because nothing was restored from storage — the value simply carried over (Clarifications; J-3 DP-3.4).
6. **Given** track A has a stored entry and the user turns "remember for this track" off, **When** the toggle flips, **Then** the plugin removes track A's stored entry via `api.state.track.remove("settings")`, and a later visit to track A behaves exactly like a track that was never remembered (Clarifications).
7. **Given** Key & Tempo was suspended mid-track with key −2 playing and remember on, **When** the user chooses Restart and the plugin's `ready()` runs, **Then** `list_chain()` lists its two nodes as own, no `set_param` is issued (the audio does not change), the panel shows Key −2 mirrored from `params`, "Remember for this track" shows on (an entry exists), and the `restored` text is `""` (Clarifications item 5; SC-005).
8. **Given** Key & Tempo is enabled mid-session while track A (stored entry key −2) is already playing and the chain holds none of its nodes, **When** `ready()` runs, **Then** it creates its two nodes and, from `api.playback.state().track`, applies track A's entry exactly as a `track_changed` would — key −2 audible, badge shown (Clarifications item 5).

### Edge Cases

- The user drags Tempo below 25% or above 200%, or Key beyond ±12 semitones (including via Fine tune pushing the composed value out of range): the host clamps the value and the clamped value, not the requested one, is what the engine applies and the panel displays (008 FR-010).
- `tempo_up`/`tempo_down` at the tempo bound (25% or 200%): the step clamps rather than refuses; the panel step control simply stops moving.
- The user activates `key_up`/`key_down` while Fine tune is non-zero: only the integer Key component changes by 1; Fine tune is untouched, and the composed value is re-sent and re-clamped (Clarifications).
- The user sets a value that pushes a node's mode into 008's out-of-range stage-use rule (`|semitones| > 3` or ratio outside `[0.5, 1.5]`) while in "performance" mode: the host auto-switches that node to "quality"; the resulting `effect_chain_changed` (FR-020) carries `quality_mode = "quality"`, `auto_switched = true`, and Key & Tempo's Quality mode toggle shows "on" (the OR of both nodes) even though the user never touched it; returning to the in-range band while the auto-switch flag is set reverts that node to "performance" automatically and the toggle follows (Clarifications; 008 FR-008).
- The user edits one of Key & Tempo's nodes directly in the host's Effect Chain panel (008 FR-004 — e.g. drags `semitones` to −4.7 or flips one node's `quality_mode`): the next `effect_chain_changed` carries the new `params`; the panel mirrors them (Key −5 / Fine tune +30 ¢ by the decomposition rule; Quality per the OR), and, with remember on, the stored entry is updated — the plugin never re-sends its own previous values over a host edit (Clarifications item 3).
- The user activates `toggle_remember` (on) while no track is current: `api.state.track.set` returns `invalid_state`/`no_track`; the plugin reverts the toggle to off and shows the refusal `message` in the `restored` text widget until the next successful action clears it (Clarifications item 7).
- The user removes one or both of Key & Tempo's nodes from the Effect Chain panel while the plugin is Active: the plugin receives `effect_chain_changed` without that node and does **not** fight the user's decision (Constitution X, the same stance as the 008 FR-012 auto-bypass case) — it does not recreate the node while running; the `restored` text widget shows "Effect node removed — disable and re-enable Key & Tempo to recreate it", controls bound to the missing node become no-ops (their `set_param` would be `not_found`; the plugin skips the call), and the remaining node keeps working. On the next `ready()` FR-005 creates whichever member is missing (Clarifications; FR-005).
- The user disables Key & Tempo while a pitch/tempo shift is active: per 009's existing rule, its two nodes remain in the chain with their last parameters, flagged "orphaned," continuing to process audio unchanged until the user bypasses/removes them or re-enables the plugin; the panel and its actions are removed/greyed exactly as 011 FR-013/FR-016/FR-025 already specify for any plugin (Clarifications; mirrors 012 FR-014/FR-015).
- Key & Tempo is suspended (budget breach) rather than disabled: its panel shows the 011 FR-025 placeholder (Restart/Disable), its two nodes stay in the chain, orphaned, with their last parameters; on Restart it calls `ready()`, finds and reclaims its existing nodes via `list_chain()` (not duplicating them), and mirrors its panel from their live `params` (FR-020), sets the remember toggle from whether the current track has a `settings` entry, and leaves `restored` at `""` (FR-005 path (a); Clarifications item 5).
- The Effect Chain panel's overload rule (008 FR-012) flags Key & Tempo's own pitch-shift or time-stretch node as the chain's most expensive **non-host** node: it is auto-bypassed at the next buffer boundary and labeled "auto-bypassed (over budget)"; Key & Tempo receives `effect_chain_changed` and its panel reflects the bypass, but the plugin does not fight the host's decision — the user re-enables it from the Effect Chain panel (008 FR-012; not expected in normal use given the DSP runs host-side, Constitution III).
- A track changes while the loop from Section Loop is armed (independent plugin, independent state): Key & Tempo's own reset/restore logic runs exactly as described in US3 and has no effect on, and is not affected by, Section Loop's own per-track marker restoration (prompt's fourth acceptance line; each plugin owns only its own `state.track` keys).
- The user has "keep across tracks" on and manually changes key/tempo mid-track: the new values are what carries forward to the next no-stored-setting track, exactly as the currently in-effect values (Clarifications; J-3 DP-3.4).
- The user signs out: `state.track` is account-scoped and is cleared on sign-out (009's own retention rule); every track's stored key/tempo entry is gone, and the next sign-in starts with no remembered tracks for any account.

### Key Entities

- **Key & Tempo Plugin**: A bundled, host-licensed reference plugin (identifier `org.modplayer.key-tempo`) holding `audio.effects`, `ui.panel`, `ui.shortcuts`, `state.track`, and `playback.observe`; its only persisted state is the small per-track key/value set FR-011 writes through `state.track` — nothing is written through `state.plugin`.
- **Pitch-shift Node** (reuses DM-17 EffectNode, `kind = pitch_shift`, `owner = org.modplayer.key-tempo`): parameters `semitones` (composed from the panel's Key + Fine tune, −12..+12), `formant` (on/off), `quality_mode` (performance/quality, kept in sync with the time-stretch node by FR-009).
- **Time-stretch Node** (reuses DM-17 EffectNode, `kind = time_stretch`, `owner = org.modplayer.key-tempo`, created immediately after the pitch-shift node so 008 FR-007's adjacency optimization applies): parameters `ratio` (0.25..2.0, shown 25%..200%), `quality_mode` (kept in sync per FR-009).
- **Per-track Key & Tempo Entry**: One `state.track` key, `settings`, holding `{ key, cents, tempo, formant, quality }` in the panel's units (FR-011); its existence *is* "remember for this track"; account-scoped, cleared on sign-out (009's existing retention rule); removed by `toggle_remember` going off.
- **NodeInfo (API 1.4)**: 009's node record as seen by plugins, extended by FR-020 with `params` (wire-name → current target value) and `auto_switched`; `effect_chain_changed` now also fires on parameter changes. The plugin's panel is a mirror of its own two nodes' `params`.
- **"Keep across tracks" flag**: A session-scoped, unpersisted plugin-memory flag (not `state.track`/`state.plugin`) governing only what happens on `track_changed` for a track with no stored entry (FR-012).
- **Panel `main`**: The 011 panel — Key/Fine tune/Tempo/Tempo-step sliders, Formant/Quality/Remember/Keep-across-tracks toggles, the `restored` and `step_note` text widgets, and Key/Tempo up-down/reset buttons (FR-003).
- **Getting Started Card**: A host-native, dismissible, non-modal card at the top of the Library view (not a plugin `ui.panel` contribution), shown while the device-scoped `getting_started_dismissed` settings flag is unset, introducing both bundled plugins, their default shortcuts, and the `GETTING_STARTED_TUTORIAL_URL` placeholder link (FR-018).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Setting a semitone shift on a playing track produces an audible pitch change within 20 ms with no measurable change in tempo or track duration, in 100% of trials, on a reference set of typical mixed-music tracks.
- **SC-002**: Dragging the tempo control to any value in 25%..200% produces an audible tempo change within the latency budget with no measurable change in pitch, in 100% of trials, whether or not Section Loop is concurrently looping the same track.
- **SC-003**: In 100% of trials, a track with "remember for this track" on restores its exact stored key and tempo, and shows the "restored" badge, the next time that track is opened, including after switching away to a track with no stored setting and back.

- **SC-005**: Disabling or suspending Key & Tempo never audibly changes what is already playing — its two nodes keep their last parameters, orphaned, until the user acts — in 100% of trials.
- **SC-006**: Every control this feature's panel introduces is reachable and operable by keyboard alone with a correct accessible name, in 100% of trials.
- **SC-007**: From a fresh install, the Getting Started card appears on every launch until dismissed and never again after, survives a sign-out/sign-in, names both bundled plugins and their default shortcuts, and both bundled plugins are already enabled with no permission prompt, in 100% of trials.
- **SC-008**: The plugin's source contains no reference to any host crate, private symbol, or API method outside the generated 1.4 schema, verified by an automated check in 100% of CI runs; this feature's only plugin-API change is the additive 1.4 minor of FR-020, and every 1.0–1.3 fixture and bundled plugin still loads and passes its existing tests.
- **SC-009**: After the host's `+`/`-` action or an Effect Chain panel edit changes one of Key & Tempo's nodes, the panel's corresponding control shows the new value within one host tick, and a remembered track's stored entry reflects it, in 100% of trials.

## Assumptions

- Key & Tempo ships enabled by default after first sign-in, alongside Section Loop, per FR-1.4.2/A-5; the enable/disable mechanism itself is 009's concern and unchanged here.
- `playback.observe` is added to FR-13.2.1's permission list as the read-side prerequisite the shipped API already imposes on `track_changed`/`api.playback.state()`, mirroring the identical addition 012 made to FR-13.1.1 for the same reason.
- "Semitones... with fine cents" is delivered as two composing panel controls (integer Key, −12..+12; Fine tune, −50..+50 cents) rather than a second host-side parameter, because the host's pitch-shift node exposes one continuous fractional-semitone value; `key_up`/`key_down` move only the integer component.
- "Quality mode (performance/quality)" is exposed as one panel toggle that writes both nodes' independent `quality_mode` parameters together and reads back their logical OR, rather than two separate per-node controls, matching 008's own treatment of the adjacent pair as one combined resampling stage.
- The shipped API 1.3 exposes no node parameter values to plugins and fires `effect_chain_changed` only on structural changes; the additive 1.4 minor (FR-020) is assumed to be the correct fix rather than a stale panel or a change to 008's host `+`/`-` action, because J-2 steps 6→8 require the plugin to remember a tempo the user set with the host's `+`/`-`. The panel is a mirror of the nodes (012's "never reinterpret intent" pattern), never the other way round.
- The "Restored" badge and the tempo-step note are `text` widgets toggled between a string and `""`, because 011 offers no hidden state and no updatable `label`; 012's `status` widget is the precedent.
- The Getting Started card's dismissal is device-scoped (like 002's disclosure acknowledgement), not account-scoped, so a sign-out/sign-in on the same install does not re-show a one-time onboarding aid; its tutorial link is a single host constant pointing at the repository's future `docs/plugin-tutorial.md`.
- "Keep across tracks" is a session-wide, unpersisted mode (per the source document's own words at J-3 DP-3.4), not a per-track or account-level preference; it resets to off on every app restart.
- Key & Tempo's default `+`/`-` tempo-step bindings collide with 008 FR-017's pre-existing, identically-bound, fixed-10%-step host action, and lose per 011 FR-011's tier rule; because that host action already targets "the first time-stretch node in chain order, any owner" and Key & Tempo is the only `audio.effects`-holding plugin in this slice, the keyboard shortcut still produces the promised user-visible effect on a fresh install at the default step, and the plugin's own panel buttons are the path that honors a user-configured step.
- Turning "remember for this track" off deletes that track's stored entry immediately rather than leaving an unused one behind, so a re-enabled remember on the same track always starts fresh from the values then in effect.
- The "restored" badge is a fact about how the current session's values were seeded for this track, shown for the track's entire time open once restored, and recomputed (never carried over) on every `track_changed`.
- The Getting Started card is host-native chrome, not a plugin `ui.panel` contribution (it must introduce plugins before assuming any are enabled, and must reference two plugins' shortcuts at once, which a single plugin's own panel cannot do); its dismissal persists per device in the per-user settings store, outside this feature's plugin-state mechanisms.
- The plugin tutorial itself, MIDI-bound key/tempo control, and the detected-key display (FR-13.2.5, SHOULD) are out of scope per this feature's Scope boundary and the breakdown prompt's own text.
