# Feature Specification: Effect Chain and Built-In Effect Nodes

**Feature Branch**: `feature/008-effect-chain-and-built-in-nodes`

**Created**: 2026-09-18

**Status**: Clarified (2026-09-18, clarify pass) — no open [NEEDS CLARIFICATION] markers, no human escalations; ready for `/speckit-plan`

**Input**: User description: "Let a user change how a song sounds in real time — slow it down without changing pitch, transpose it without changing speed, shape its tone — through an ordered chain of host-implemented effect nodes that a later plugin tier will parameterize. The chain sits between the decoder and the output limiter and holds at least 16 nodes. The Effect Chain panel lists nodes in processing order, each labeled with its type and owner (host for now), with a bypass toggle, a drag handle, and a per-node CPU-load indicator plus a whole-chain figure. Reorder, bypass, add, and remove take effect at the next buffer boundary with a short crossfade where needed, never a glitch. Processing runs at the source sample rate; conversion to the device rate happens only at output. Built-in nodes and their parameters: pitch shift (semitones −12..+12 fractional, formant preservation on/off), time stretch (ratio 0.25..2.0, quality mode performance/quality; combined with pitch shift into a single resampler stage when both are present), gain (−60..+12 dB, mute), equalizer (up to 8 bands with frequency, gain, Q, peak/shelf type), high-pass/low-pass filter (cutoff, resonance capped below self-oscillation the limiter cannot catch), and stereo tools (width 0..2, balance, mono sum with phase invert, channel swap). All parameters are automatable with sample-accurate scheduling at buffer resolution and smoothing that avoids zipper noise; out-of-range values clamp and the clamped value is returned. Peak and RMS meters pre- and post-chain, and a low-resolution spectrum (32–128 bands), are published to the UI. Hard boundary: no component can write decoded audio to a file, socket, or any interface outside the engine. Acceptance: when the user drags the time-stretch ratio from 1.0 to 0.6 during playback, the change is audible within 20 ms at p95 and pitch is unchanged. When total processing exceeds the real-time budget, the most expensive non-host node is bypassed and a warning names it; audio never drops out silently. When the user reorders EQ before time stretch, the swap happens at a buffer boundary with no click. When tempo is set to 25% or pitch to +12, the node UI notes that quality mode auto-switched. Chain plus host processing stays under 50% of one core at the performance buffer preset with pitch shift, time stretch, and an 8-band EQ active."

**Source**: [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) — FR-6.1 Engine, FR-6.2 Effect chain, FR-6.3 Built-in effect nodes, FR-6.4 Metering, FR-6.5 Audio access boundary, DM-17 EffectNode, DM-18 EffectChain, DM-20 AudioSettings, Part 9 §3 Real-time path (AR-3, AR-4), Part 9 §5 Key flows (5.2), J-8 (JTBD-13), EC §5 Audio engine and effects, NFR §1 Performance and latency (NFR-1.1, 1.8, 1.14, 1.15), NFR §8 Observability (local), §7 Hard constraints (C-2, C-4, C-5), §4 Jobs-to-be-done (JTBD-2, JTBD-3). Prerequisites: [001-walking-skeleton](../001-walking-skeleton/spec.md) (engine, buffer presets, limiter, AudioSettings), [003-streaming-playback-and-queue](../003-streaming-playback-and-queue/spec.md) (decoder feeding the engine, playback).

**Scope boundary**: Does not cover plugin-owned nodes, the custom buffer processor, chain presets, or the detected-key display — only host-owned nodes and the chain UI. No plugin runtime exists yet (that lands in 001-mvp/009); every node in this slice is owned by "host."

- Q: The source prompt's overload rule says "the most expensive **non-host** node is bypassed," but this slice ships only host-owned nodes (no plugin runtime exists until 001-mvp/009) — what does the bypass target today? → A (D, FR-6.2.6, EC-5.1 and the prompt's own acceptance text all say **non-host**, and NFR-1.8 makes the host responsible for its own nodes fitting the budget; *the specify pass originally extended the bypass to host nodes — corrected in the clarify pass, which also defines the overload event below*): the auto-bypass mechanism ranks **non-host nodes only** by measured cost and bypasses the single most expensive one. **Host-owned nodes are never auto-bypassed.** In this slice every node is host-owned, so an overload produces the warning and the underrun accounting of FR-012 but bypasses nothing; the mechanism itself ships now (owner field, cost ranking, auto-bypass command path) and is exercised by engine tests using the data model's non-host owner value, so 001-mvp/009 activates it with no data-model or engine change.
- Q: The prompt requires "quality mode auto-switched" at "25% tempo or +12 semitones" but gives no general threshold formula — what triggers the switch? → A (D, derived directly from NFR-1.14/NFR-1.15's own "acceptable for stage use" boundaries, which are the only authoritative quality thresholds in the source document): a pitch-shift node auto-switches from "performance" to "quality" the moment `|semitones| > 3`; a time-stretch node auto-switches the moment the ratio leaves `[0.5, 1.5]`. Both examples in the prompt (tempo 25%, pitch +12) fall outside these stage-use bounds, confirming the derivation. The user can still manually force "performance" mode afterward (FR-6.3.9 is a SHOULD, not a MUST), accepting the quality trade-off; the auto-switch note reappears if the parameter moves again.
- Q: "All parameters are automatable with sample-accurate scheduling at buffer resolution" describes the plugin automation API (FR-6.3.8), but no plugin runtime exists in this slice — what actually drives parameter changes here? → A (D, Constitution III — DSP and its parameter data model live in the host regardless of who calls it; 001-mvp/009's own prompt separately lists "create and parameterize effect nodes" as a plugin capability added later): in this slice, the only actuator is the host UI (drag, type a value, toggle). Every parameter change is applied through the same buffer-boundary, smoothed-ramp mechanism DM-17 already models (value + ramp), so a later plugin automation surface (001-mvp/009+) can schedule future ramps without a data-model or engine change. This slice does not expose a "schedule for a future buffer offset" surface — only "set now, ramp smoothly."

### Session 2026-09-18 (clarify pass)

Resolution ladder applied: (D) derived from an authoritative source, (A) assumed conventional default. Every item below was checked against the materiality test; none met the bar for human escalation, so no escalation section exists.

- Q: What exactly does "exceeds the real-time budget" mean, and what happens in this slice where no node is auto-bypassable? → A (D for the 3-callback pattern — EC-5.2 uses "three callbacks in a row" for the analogous custom-processor rule; A for the 90% threshold — a conventional headroom margin below an actual underrun): an **overload event** is raised when the engine's measured render time (chain plus host) exceeds **90% of the callback period on 3 consecutive callbacks**, or exceeds **100% on any single callback** (an underrun). On an overload event the system: (1) increments the audio underrun/overload counter published to the UI (NFR-8.2/8.3 groundwork); (2) shows one keyed `Warning` notification `effect-chain-over-budget` naming the most expensive node in the chain by type (and owner, once non-host owners exist), re-used rather than duplicated while the condition persists and cleared automatically once render time has stayed under 90% for a full rolling cost window (see the CPU-figure item below); (3) **only if the most expensive node is non-host** (never in this slice), auto-bypasses that node at the next buffer boundary, labels it "auto-bypassed (over budget)" in the panel, and never auto-restores it — the user re-enables it manually. At most one auto-bypass happens per rolling cost window; if the chain is still over budget after the window, the next most expensive non-host node is bypassed. "Never drops out silently" therefore means: an underrun may still occur under a host-only overload, but it is always counted and always surfaced. FR-012, US4 and SC-004 realigned.
- Q: What is the time-stretch "ratio" — a tempo multiplier or a duration multiplier — and how does the UI show it? → A (D, prompt "slow it down … 1.0 to 0.6", "tempo is set to 25%", J-2 step 5 "drags tempo to 60%", NFR-1.15 "50%–150%"): the ratio is a **tempo multiplier**: 0.6 plays at 60% speed (slower, longer), 2.0 at double speed. The model stores the ratio (`0.25..=2.0`); the node UI displays and accepts it as a percentage (`25%..=200%`). Test: ratio 0.5 makes a 10 s passage take 20 s of wall time.
- Q: The engine's clock and position are counted in source frames, and the playhead extrapolates between anchors using wall time — what happens to position, markers, loops and seeks under a non-unity time-stretch ratio? → A (D, FR-6.1.4/FR-6.1.5 — position is track time and loop decisions are evaluated on the source stream before the chain; 005's smooth-playhead contract): the chain's input is the post-loop/post-seek source stream, so **markers, loop regions, cue points and seeks stay in source frames and are unaffected by any node**; a loop at ratio 0.5 simply sounds twice as long. The published position advances at `ratio ×` real time, and the engine publishes the **effective advance rate** with its position anchor so the UI playhead extrapolates at that rate — no visible jump or stutter when the ratio is not 1.0 (test: at ratio 0.5, the displayed position after 2 s of wall time has advanced 1 s ± one buffer). Nodes that keep internal audio history (pitch shift, time stretch) **reset that history on a seek or cue jump** (so no pre-seek audio bleeds into post-seek output beyond one buffer, keeping NFR-1.4's 10 ms seek bound) and **do not reset on a loop wrap** (the seam crossfade happens upstream; resetting would defeat NFR-1.3's click-free seam).
- Q: FR-6.3.9 says *both* pitch shift and time stretch offer quality/performance mode, and FR-008 auto-switches the pitch-shift node — but FR-006 listed the mode only on time stretch. Also: does an auto-switched node ever switch back? → A (D, FR-6.3.9 for the parameter; A for the revert rule — the conventional "auto unless the user overrode it" behaviour, keeping a performer from being stuck in the higher-latency mode after a brief excursion): the pitch-shift node gains a `quality mode` parameter (performance/quality, default performance), and FR-006 is realigned. Rule, evaluated on every change to `semitones` or `ratio`: (1) new value **outside** the stage-use range (`|semitones| > 3`, ratio outside `[0.5, 1.5]`) and mode is *performance* → mode becomes *quality*, the node is flagged *auto-switched*, and the panel note appears; (2) new value **back inside** the range and the node is flagged *auto-switched* → mode reverts to *performance*, the flag and note clear; (3) the user explicitly setting the mode (either value) clears the *auto-switched* flag, so a user-forced *performance* at ratio 0.25 stays until the next excursion (a subsequent change that is *still* out of range re-applies rule 1, so the note reappears — Clarifications above). A mode change applies at a buffer boundary with the FR-005 crossfade, never a click. When two adjacent nodes are combined into one resampling stage (FR-007), the stage runs in *quality* if **either** node is in quality mode.
- Q: 007 registered `effects.tempo_step_up` (`=`/`+`) and `effects.tempo_step_down` (`-`) with `enabled: false` "until a later effects slice flips the flag", and left the `+`/`-` collision with 005's waveform zoom for that slice to reconcile — is 008 that slice, and what do the steps do? → A (D — 007 spec FR-012 names the effects slice; J-2 step 6 and S-1 fix the step at "`+`/`-` by 10%", i.e. 10 percentage points; the collision is already resolved by 007 FR-019's precedence order): **yes.** This slice flips both actions to `enabled: true`. Each press changes the ratio of the **first time-stretch node in chain order** (any owner, bypass state ignored and unchanged) by **±0.10** (ten tempo percentage points), clamped to `[0.25, 2.0]`, applied through the normal smoothed parameter path (so the FR-008 auto-switch rule runs). If the chain holds no time-stretch node the action is a no-op that shows one keyed `Info` notification `effects-no-time-stretch` ("Add a Time Stretch node to use tempo steps"); held-key repeats coalesce into that one notification. Conflict re-evaluation on enable (007 FR-012) finds no registered action on `=`, `+` or `-`, so nothing is flagged. The waveform-zoom collision needs no rebinding: per 007 FR-019, a focused waveform widget consumes `+`/`-` (zoom) at step (2) before the registered action is consulted at step (3); with focus anywhere else in the Now Playing view the same keys step tempo. 007's catalog row "enabled: **no** (no effect chain yet)" is superseded by this slice.
- Q: Where does the Effect Chain panel live, how is it opened, and which of its operations are registered actions? → A (A — the Queue panel (003/007, `Q`) and Markers panel (006) set the pattern: a panel inside Now Playing, no new nav-rail section; 007's narrow-cut precedent and Constitution X for the action set): the Effect Chain panel is a **toggleable panel in the Now Playing view**, opened by a header "Effects" toggle button and by a new registered navigation action **`nav.toggle_effect_chain`** (trigger, scope `now_playing`, default binding **`E`**, no repeat, rebindable; `E` collides with nothing shipped by 001–007). Its open/closed state persists for the session the same way the Queue panel's does and survives track changes. Adding a node is an "Add node…" control offering exactly the six FR-006 types. Node add, remove, bypass, reorder and every parameter control are **widget behaviours, not registered actions** in this slice (keyboard-operable per FR-015, not rebindable); nothing prevents a later slice from promoting them. Keyboard reorder: with a node's drag handle focused, `↑`/`↓` move that node one position earlier/later (same buffer-boundary crossfade as a pointer drag); Tab order runs node by node in processing order.
- Q: Where in the existing pipeline (`source → master gain → + test tone → limiter → output stage`) does the chain sit, and where exactly are the pre-/post-chain meters and the spectrum tapped? → A (D for the chain position — FR-6.2.1 "between the decoder and the output limiter"; A for the tap points — the conventional post-fader meter, and a visualiser shows what is heard): the render order becomes **`source (post-loop/seek) → [pre-chain meter] → effect chain → master gain → + test tone → [post-chain meter + spectrum] → limiter → output stage`**. The pre-chain meter sees the decoded signal before any node and before master volume; the post-chain meter and the spectrum see exactly what enters the limiter (so master volume moves the post-chain meter but not the pre-chain one — test). The spectrum is post-chain only; its default resolution is 64 bands (within the 32–128 range; a plan-time constant).
- Q: What are each node's default parameter values on add, and the numeric ranges the prompt left open (EQ frequency/gain/Q, filter cutoff/resonance, balance)? → A (A, conventional parametric-EQ/filter/stereo ranges; the governing default is that **adding a node never changes the sound** — every node is transparent at its defaults): **Pitch shift** — semitones 0, formant off, mode performance. **Time stretch** — ratio 1.0, mode performance. **Gain** — 0 dB, unmuted. **Equalizer** — exactly 8 always-present bands ("up to 8" = a band at 0 dB is transparent, no per-band enable flag); defaults 63/125/250/500/1k/2k/4k/8k Hz, gain 0 dB, Q 1.0, type peak; ranges frequency `20 Hz..=20 kHz` (further clamped to `0.45 × source rate` at the current rate), gain `−24..=+24 dB`, Q `0.1..=10`. **Filter** — one node type with a `mode` parameter (high-pass | low-pass); defaults mode high-pass, cutoff 20 Hz, resonance 0; ranges cutoff `20 Hz..=20 kHz` (same Nyquist clamp), resonance `0.0..=1.0` normalized, where 0 is the flat (Butterworth) response and 1.0 is the FR-009 self-oscillation cap — the exact Q that 1.0 maps to is a plan-time constant, and any request above 1.0 clamps to 1.0. **Stereo tools** — width 1.0, balance 0 (range `−1..=+1`, −1 full left, +1 full right), mono sum off, phase invert off (the invert control is only effective, and only enabled in the UI, while mono sum is on — it inverts one channel before the sum, which is what isolates or removes centre material), channel swap off.
- Q: How long are the parameter-smoothing ramp and the chain-edit crossfade, and is the latter really the user's per-region loop crossfade setting as the specify pass assumed? → A (D for the 20 ms ramp — key flow 5.2's own example `set_param(…, ramp 20 ms)`; A for the fixed 5 ms crossfade — NFR-1.3's seam default is the right *value*, but 006 made the loop crossfade a per-region user setting with a valid `0` (hard cut), and a user's gapless-loop choice must not make chain edits click): every continuous parameter (semitones, ratio, gain, EQ band frequency/gain/Q, cutoff, resonance, width, balance) ramps **linearly over 20 ms** from its current value to the new target, starting at the next buffer boundary; a new target arriving mid-ramp restarts the ramp from the current interpolated value. Every discrete switch (bypass, mute, mono sum, phase invert, channel swap, formant, quality mode, EQ band type, filter mode) and every chain edit (add, remove, reorder) crossfades old signal → new signal over a **fixed 5 ms engine constant**, independent of the loop-region crossfade setting. The stale Assumption is realigned.
- Q: What exactly do the per-node and whole-chain CPU-load figures show, and how is the combined pitch/stretch stage attributed? → A (A, the conventional DAW "% of callback period" meter; equal split is the least misleading attribution for a shared stage): a node's cost is the **percentage of the callback period** its processing consumed, as a **rolling mean over the last ~1 s of callbacks** (`N = ceil(1 s / buffer period)` callbacks — this is also the "rolling cost window" the overload rule uses); the whole-chain figure is the sum of the node figures; the engine separately measures total render time (chain plus host) for the overload rule and NFR-1.8. A combined resampling stage's cost is attributed **half to each** of its two nodes. Figures read 0% whenever no callback ran in the window (no track loaded, transport stopped, or a node just added).
- Q: Does the chain survive a track change, an app restart, or a crash? → A (D, breakdown: NFR-2.6's chain restore is allocated to 004-performance/003, presets to 006-practice-depth/003): the chain is **global and session-scoped** — it is empty on every launch, is never written to disk by this slice, and **persists unchanged across track changes** (only the FR-014 coefficient recompute happens on a rate change). Adjacency for FR-007's combined stage is evaluated on chain position regardless of bypass state (a bypassed node between the pair still separates them); when one member of an adjacent pair is bypassed, the combined stage applies only the active member's parameters.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Slow down or transpose a song in real time without breaking the other dimension (Priority: P1)

While a track plays, a musician drags the time-stretch ratio down to practice a fast passage at reduced speed with the pitch unchanged, or shifts the pitch by semitones to transpose the song for their instrument or voice without altering its tempo — and hears the result change smoothly and immediately, without a glitch.

**Why this priority**: JTBD-2 and JTBD-3 name this as the core reason the effect chain exists; the prompt's own acceptance scenario (tempo 1.0 → 0.6 during playback, audible within 20 ms, pitch unchanged) is built around exactly this. Nothing else in this spec matters if the two headline effects don't work.

**Independent Test**: Start playback, add a time-stretch node and a pitch-shift node to the chain, drag the time-stretch ratio and separately the pitch-shift semitone control while listening, and verify each dimension changes independently of the other with no dropout.

**Acceptance Scenarios**:

1. **Given** a track is playing through a chain containing a time-stretch node at ratio 1.0, **When** the user drags the ratio to 0.6, **Then** the tempo change is audible within 20 ms at p95 and the pitch of the material is unchanged.
2. **Given** a track is playing through a chain containing a pitch-shift node at 0 semitones, **When** the user sets it to +7 semitones, **Then** the pitch rises by 7 semitones and the tempo/duration of the material is unchanged.
3. **Given** both a pitch-shift node and a time-stretch node are present in the chain, **When** both are set to non-unity values, **Then** both effects apply simultaneously and audibly, without one canceling or overriding the other.
4. **Given** the time-stretch ratio is dragged to 0.25 (shown as 25%) or the pitch-shift is set to +12 semitones, **When** the change lands, **Then** the affected node's mode reads "quality" and its UI displays a note that quality mode auto-switched; **When** the user then drags the value back inside the stage-use range (ratio 1.0, or 0 semitones) without having touched the mode control, **Then** the mode reverts to "performance" and the note clears.
7. **Given** a time-stretch node at ratio 1.0 (100%) and focus anywhere in the Now Playing view other than the waveform, **When** the user presses `-` twice, **Then** the ratio reads 80% (two −10-point steps, applied smoothly), and pressing `+` while the waveform has focus zooms the waveform instead.
8. **Given** the chain holds no time-stretch node, **When** the user presses `+` or `-`, **Then** nothing in the chain changes and one notification tells the user to add a Time Stretch node — a held key produces no additional notifications.
9. **Given** a time-stretch node at ratio 0.5 and an armed loop region of 4 s (in track time), **When** the loop plays, **Then** each pass takes 8 s of wall time, the seam stays click-free, the displayed position advances at half speed without visible stutter, and the markers stay where they were.
5. **Given** the time-stretch and pitch-shift nodes are adjacent in the chain, **When** both are active, **Then** the engine internally combines them into a single resampling stage as a performance optimization; the UI still shows, controls, and meters each node separately.
6. **Given** formant preservation is toggled on for the pitch-shift node, **When** a semitone shift is applied, **Then** the shifted audio retains the original timbre's formant character rather than sounding "chipmunked" or "de-pitched."

### User Story 2 - Build and rearrange the effect chain without a glitch (Priority: P2)

A user opens the Effect Chain panel, sees every node listed in processing order with its type and owner, adds a new built-in node, drags it into a different position, bypasses one node to A/B compare, and removes another — all while the track keeps playing cleanly.

**Why this priority**: J-8 and FR-6.2 describe this as the primary way a user (and later a plugin) interacts with the chain; Story 1's effects are useless if the user cannot assemble or rearrange them. It is the second pillar because it is the container for every built-in node in Story 3.

**Independent Test**: While a track plays, open the Effect Chain panel (`E` or the header toggle), add an EQ node and a time-stretch node, drag the EQ above the time-stretch node, bypass the EQ, then remove the time-stretch node — verifying each action lands cleanly with no click or dropout and the panel reflects the new order/state immediately.

**Acceptance Scenarios**:

1. **Given** the Effect Chain panel is open, **When** the user adds a built-in node, **Then** it appears at the end of the list labeled with its type and owner "host," with a bypass toggle, a drag handle, and a per-node CPU-load indicator, at its transparent default parameters (the sound does not change), and starts processing at the next buffer boundary with no click.
1a. **Given** the Now Playing view is shown and no text field has focus, **When** the user presses `E`, **Then** the Effect Chain panel opens (and closes on a second press), exactly as the header "Effects" toggle does; the panel stays open across a track change.
1b. **Given** a node's drag handle has keyboard focus, **When** the user presses `↑`, **Then** the node moves one position earlier in the chain with the same glitch-free buffer-boundary swap as a pointer drag.
2. **Given** a chain containing an EQ node after a time-stretch node, **When** the user drags the EQ node above the time-stretch node, **Then** the swap takes effect at the next buffer boundary with no audible click (prompt acceptance).
3. **Given** a node is active in the chain, **When** the user toggles its bypass control, **Then** the node's processing is removed from (or restored to) the signal path at the next buffer boundary with a short crossfade where the transition would otherwise be audible, and the toggle's on-screen state updates immediately.
4. **Given** a node is present in the chain, **When** the user removes it, **Then** it disappears from the panel and its processing stops at the next buffer boundary with no glitch, and the rest of the chain's order is otherwise unaffected.
5. **Given** the chain already holds 16 nodes, **When** the user attempts to add a 17th, **Then** either the node is added (chain capacity is a host-defined constant of at least 16) or, if the host's configured maximum is reached, the attempt is refused inline with a reason — in no case does adding a node beyond capacity corrupt the chain or crash playback.
6. **Given** the chain is empty (no nodes), **When** playback runs, **Then** audio passes from the decoder to the limiter unaffected, with no error state.
7. **Given** the whole-chain CPU figure and each node's individual figure are shown, **When** the user adds or removes nodes, **Then** both figures update to reflect the current chain composition.

### User Story 3 - Shape tone with the full built-in node catalog (Priority: P3)

A user adds gain, an 8-band equalizer, a high-pass/low-pass filter, and stereo tools to the chain to shape the tone of what they're playing — boosting a frequency band, cutting rumble, narrowing or widening the stereo image, or isolating a center vocal — with every parameter clamped to a safe range and every change applied smoothly.

**Why this priority**: FR-6.3 names these as the remaining built-in nodes; they deliver real tonal control on top of Story 1's tempo/pitch nodes and Story 2's chain management, but the product is still useful (Story 1 + 2) without them, so they rank below the headline effects.

**Independent Test**: Add one of each remaining node type (gain, EQ, filter, stereo tools) to a playing chain, adjust each node's parameters across its documented range including past its bounds, and verify every value lands within range, clamped values are shown when needed, and each change is audible without a click.

**Acceptance Scenarios**:

1. **Given** a gain node in the chain, **When** the user sets gain to a value outside −60..+12 dB (e.g., +20 dB), **Then** the value is clamped to +12 dB and the clamped value is what the UI and the engine both use.
2. **Given** a gain node, **When** the user enables mute, **Then** the node's output is silenced smoothly (no click) until mute is disabled.
3. **Given** an 8-band equalizer node, **When** the user sets a band's frequency, gain, Q, and type (peak, low-shelf, or high-shelf), **Then** the audible tone changes accordingly and every value is clamped to the node's documented ranges.
4. **Given** a filter node (mode high-pass or low-pass), **When** the user raises resonance toward its maximum, **Then** the value is capped at 1.0 (the point below self-oscillation the output limiter cannot catch) — the filter never produces an uncontrolled runaway tone; **When** the user requests 1.5, **Then** the UI and engine both hold 1.0.
4a. **Given** a filter node just added, **When** the user listens without touching it, **Then** the sound is unchanged (defaults: high-pass at 20 Hz, resonance 0); **When** the user switches mode to low-pass and lowers the cutoff to 1 kHz, **Then** high frequencies are audibly attenuated with no click at the mode switch.
4b. **Given** an EQ node on a 44.1 kHz track, **When** the user types 30 000 Hz for a band's frequency, **Then** the value clamps to the rate-derived maximum (`0.45 × 44 100 ≈ 19 845 Hz`, itself ≤ 20 kHz) and the clamped value is displayed.
5. **Given** a stereo-tools node, **When** the user sets width to 0, **Then** the output collapses toward mono; **When** width is set to 2, **Then** the stereo image widens; both are clamped to `[0, 2]`.
6. **Given** a stereo-tools node, **When** the user enables mono sum with phase invert, **Then** center-panned material (e.g., a lead vocal) is attenuated relative to off-center material, consistent with phase-cancellation behavior; **Given** mono sum is off, **Then** the phase-invert control is shown disabled and has no effect on the signal.
7. **Given** a stereo-tools node, **When** the user enables channel swap, **Then** left and right channels exchange audibly and without a click.
8. **Given** the active track's source sample rate differs from the previous track's, **When** playback of the new track begins, **Then** every rate-dependent coefficient (EQ frequency/Q, filter cutoff/resonance) recomputes before the first buffer so the user's set frequency/Q values still mean the same thing in Hz.

### User Story 4 - See what the chain is doing and get warned before it breaks audio (Priority: P4)

A user watches per-node and whole-chain CPU-load figures and pre-/post-chain peak, RMS, and spectrum meters while performing, and if the chain ever asks for more processing than the system can deliver in real time, the system counts it, warns the user naming the most expensive node, and — once plugin-owned nodes exist — automatically bypasses the most expensive non-host node. Audio never drops out silently.

**Why this priority**: NFR §8 (Observability) and EC-5.1 describe this as a safety net and a diagnostic layer on top of Stories 1–3; it protects a live performance from a worst-case overload but adds no new tone-shaping capability, so it ranks last.

**Independent Test**: Build a chain heavy enough to approach the real-time budget (pitch shift + time stretch + 8-band EQ at the performance buffer preset), verify the CPU figures and meters update live, then push the chain over budget (e.g., by adding more nodes, or with a test node of deliberately inflated cost) and verify the overload counter increments, a warning names the most expensive node, audio keeps playing, and — in an engine test with a non-host-owned node — exactly that node is auto-bypassed.

**Acceptance Scenarios**:

1. **Given** a chain with pitch shift, time stretch, and an 8-band EQ active at the performance buffer preset, **When** processing runs, **Then** total chain-plus-host processing stays under 50% of one core.
2. **Given** the Effect Chain panel is open, **When** playback runs, **Then** each node shows a live CPU-load indicator (percentage of the callback period, ~1 s rolling mean) and the panel shows a whole-chain figure (their sum), both updating as nodes are added, removed, or bypassed; a node just added reads 0% until its first window elapses.
3. **Given** pre- and post-chain peak/RMS meters and a low-resolution spectrum are shown in the UI, **When** playback runs, **Then** all three update live and the post-chain meters reflect the effect of currently-active (non-bypassed) nodes and of master volume while the pre-chain meters reflect neither.
4. **Given** the chain's total processing exceeds the real-time budget (render time > 90% of the callback period on 3 consecutive callbacks, or any single underrun), **When** the overload is detected, **Then** the overload counter increments, one warning names the most expensive node in the chain, playback continues, and — because every node in this slice is host-owned — no node is bypassed; the warning clears by itself once render time has stayed under 90% for a full rolling window.
5. **Given** an engine-level test chain in which the most expensive node carries a non-host owner value, **When** an overload event fires, **Then** exactly that node is bypassed at the next buffer boundary, labeled "auto-bypassed (over budget)", and is not restored automatically; **When** the user manually re-enables it, **Then** it resumes at the next buffer boundary with no glitch.

---

### Edge Cases

- A parameter is set to a value outside its documented range (via UI, or any other write path into the chain) → the value is clamped to the nearest bound and the clamped value is returned/displayed; the change is never silently ignored and the app never enters an invalid state (EC-5.3).
- Filter resonance is pushed to its maximum → capped below self-oscillation; no uncontrolled tone escapes, and the (out of scope but always-on) output limiter is never relied upon to catch it.
- The chain is at its maximum node capacity → adding another node is refused inline with a reason; no crash, no corrupted chain order.
- The chain has zero nodes → audio passes through unaffected; not an error state.
- A pitch-shift node and a time-stretch node are both present but **not adjacent** in the chain (other nodes sit between them) → each processes independently in chain order; the single-resampler-stage optimization only applies when they are adjacent, since intervening nodes must see the signal between the two operations.
- The track changes to one with a different source sample rate mid-session → rate-dependent node coefficients (EQ, filters) recompute before the new track's first buffer; the audio clock and chain order are otherwise unaffected (FR-6.1.3).
- Total chain processing exceeds the real-time budget more than once in the same session → each overload event independently increments the counter and (re)raises the keyed warning naming the then-most-expensive node; at most one non-host node is auto-bypassed per rolling cost window; host nodes are never auto-bypassed; the system never drops audio silently, no matter how many events occur.
- The user presses `+`/`-` with two time-stretch nodes in the chain → only the first in processing order is stepped; with the waveform focused, the keys zoom instead (007 FR-019 precedence); with no time-stretch node, a single coalesced notification explains and nothing changes.
- A tempo step lands outside `[0.25, 2.0]` (e.g., `-` at 30%) → the ratio clamps to the bound (25%) and the clamped value is shown; the FR-008 auto-switch rule runs on the clamped value.
- The user seeks or jumps to a cue while pitch shift / time stretch are active → the nodes reset their internal history so no pre-seek audio bleeds beyond one buffer; on a loop wrap they do **not** reset, so the seam stays click-free.
- The user forces "performance" mode at ratio 0.25, then drags to 0.2 → the auto-switch rule re-applies (still out of range): mode returns to "quality" and the note reappears; dragging back to 1.0 afterwards reverts to "performance" and clears the note.
- The app is relaunched → the chain is empty (session-scoped; restore-after-crash belongs to 004-performance/003, presets to 006-practice-depth/003).
- The user bypasses every node in the chain → equivalent to an empty chain; audio passes through the (bypassed) nodes unaffected, with no glitch at each toggle.
- Reorder, bypass, add, or remove is requested while playback is stopped (not just paused) → applied immediately, since there is no live audio buffer boundary to wait for; the chain is in the new state the moment playback next starts.
- Two nodes of the same built-in type are both added to the chain (e.g., two EQ nodes) → both are allowed and process independently in their chain positions; only the pitch-shift/time-stretch pair has special combination behavior.
- Mono sum and channel swap are both enabled on the same stereo-tools node → mono sum is applied first (channel swap on a mono signal is a no-op), consistent with typical signal-flow expectations; documented, not a bug.
- The whole-chain or a per-node CPU figure is requested while no track is loaded → the chain reports zero load; no stale figures from a previous track are shown.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST decode audio itself and render it through an internal, host-owned effect chain positioned between the decoder and the (already-existing, non-bypassable) output limiter, in this order: `source (post-loop/seek) → [pre-chain meter] → effect chain → master gain → + test tone → [post-chain meter + spectrum] → limiter → output stage`; audio processing MUST run on the dedicated real-time path and MUST process at the source sample rate, converting to the device rate only at the output stage. The chain's input is the source stream *after* loop-seam and seek evaluation, so markers, loop regions, cue points and seeks remain in source frames and are unaffected by any node. *(FR-6.1.1, FR-6.1.3, FR-6.1.5, FR-6.1.2 host portion; Clarifications)*
- **FR-001a**: The time-stretch ratio is a tempo multiplier (0.6 = 60% speed, slower). The published track position MUST advance at `ratio ×` real time, and the engine MUST publish the effective advance rate with its position anchor so the UI playhead extrapolates at that rate with no visible jump or stutter at any ratio (at ratio 0.5, displayed position after 2 s of wall time has advanced 1 s ± one buffer). Nodes holding internal audio history (pitch shift, time stretch) MUST reset it on a seek or cue jump and MUST NOT reset it on a loop wrap. *(FR-6.1.4, FR-6.1.5, NFR-1.3, NFR-1.4; Clarifications)*
- **FR-002**: The effect chain MUST be an ordered list of effect nodes, each with a stable identifier, a type (from the built-in catalog in FR-006), an owner (a field that distinguishes "host" from a non-host owner; always "host" in this slice), a set of named parameters (each holding a current value and an active ramp), a bypassed flag, an auto-bypassed flag, and a measured processing cost. The chain MUST support at least 16 nodes simultaneously; the exact maximum is a host-defined constant of at least 16 (plan-time detail). The chain is global (not per-track) and session-scoped: empty on every launch, never written to disk by this slice, and unchanged across track changes apart from FR-014. *(DM-17 EffectNode, DM-18 EffectChain; FR-6.2.5; Clarifications)*
- **FR-003**: The Effect Chain panel MUST be a toggleable panel in the Now Playing view (opened by a header "Effects" toggle button and by the `nav.toggle_effect_chain` action of FR-017; open state kept for the session and across track changes) and MUST list every node in processing order, each labeled with its type and owner, and MUST provide per node: a bypass toggle, a drag handle for reordering, and a live per-node CPU-load indicator; the panel MUST also show a live whole-chain CPU-load figure and an "Add node…" control offering exactly the six FR-006 types. *(FR-6.2.1, FR-6.2.2, FR-6.2.5; Clarifications)*
- **FR-004**: The user MUST be able to reorder any node (via the drag handle by pointer, or with the handle focused via `↑`/`↓` one position at a time), bypass or un-bypass any node, add any built-in node type, and remove any node from the Effect Chain panel. These node operations and every parameter control are widget behaviours, not registered actions, in this slice. *(FR-6.2.1; NFR-6.1; Clarifications)*
- **FR-005**: Every reorder, bypass toggle, add, or remove MUST take effect at the next buffer boundary, never mid-buffer, and MUST crossfade the old signal into the new one over a fixed **5 ms** engine constant (independent of the per-region loop crossfade setting); none of these operations may produce an audible click, gap, or dropout. The same 5 ms crossfade applies to every discrete parameter switch (mute, mono sum, phase invert, channel swap, formant, quality mode, EQ band type, filter mode). When playback is stopped, the change MAY apply immediately since there is no live buffer boundary to wait for. *(FR-6.2.3; NFR-1.3; Constitution I; Clarifications)*
- **FR-006**: The system MUST provide exactly these built-in node types, each with the following automatable, clamped parameters and transparent defaults (adding a node at its defaults MUST NOT change the sound):
  - **Pitch shift**: semitones (−12..+12, fractional; default 0), formant preservation (on/off; default off), quality mode (performance/quality; default performance; subject to FR-008).
  - **Time stretch**: ratio (0.25..2.0, a tempo multiplier stored as a ratio and shown as 25%..200%; default 1.0), quality mode (performance/quality; default performance; subject to FR-008).
  - **Gain**: level (−60..+12 dB; default 0), mute (on/off; default off).
  - **Equalizer**: exactly 8 always-present bands (a band at 0 dB is transparent; no per-band enable), each with frequency (20 Hz..20 kHz, further clamped to `0.45 × source rate`; defaults 63/125/250/500/1k/2k/4k/8k Hz), gain (−24..+24 dB; default 0), Q (0.1..10; default 1.0), and type (peak, low-shelf, or high-shelf; default peak).
  - **Filter** (one node type): mode (high-pass | low-pass; default high-pass), cutoff (20 Hz..20 kHz with the same Nyquist clamp; default 20 Hz), resonance (0.0..1.0 normalized, 0 = flat/Butterworth, 1.0 = the FR-009 cap; default 0).
  - **Stereo tools**: width (0..2; default 1.0), balance (−1..+1, −1 full left, 0 centre; default 0), mono sum (on/off; default off) with phase invert (on/off; default off; effective and enabled in the UI only while mono sum is on — inverts one channel before the sum), channel swap (on/off; default off).

  *(FR-6.3.1 through FR-6.3.6, FR-6.3.9; Clarifications)*
- **FR-007**: When a pitch-shift node and a time-stretch node are both present and **adjacent** in the chain (adjacency by chain position, ignoring bypass state), the engine MUST combine them into a single resampling stage as an internal performance optimization; the stage runs in "quality" if either node is in quality mode, applies only the active member's parameters when the other is bypassed, and its measured cost is attributed half to each node. The UI MUST continue to show, control, and meter each node separately regardless of this optimization. When they are present but not adjacent, each MUST process independently in chain order. *(FR-6.3.2; EC-5.4; Clarifications)*
- **FR-008**: On every change to a pitch-shift node's semitones or a time-stretch node's ratio: (1) if the new value is outside the stage-use range (`|semitones| > 3`; ratio outside `[0.5, 1.5]`) and the mode is "performance", the mode MUST switch to "quality", the node MUST be flagged auto-switched, and a visible note MUST appear on the node in the Effect Chain panel; (2) if the new value is inside the range and the node is flagged auto-switched, the mode MUST revert to "performance" and the flag and note MUST clear; (3) the user explicitly setting either mode clears the auto-switched flag (a user-forced "performance" persists until the next out-of-range change re-applies rule 1). A mode change applies at a buffer boundary with the FR-005 crossfade. *(FR-6.3.9; NFR-1.14, NFR-1.15; EC-5.5; Clarifications)*
- **FR-009**: A filter node's resonance MUST be capped below the level at which the filter would self-oscillate in a way the output limiter cannot bring back under the ceiling (normalized 1.0 maps to that cap; the exact underlying Q is a plan-time constant); the cap MUST be enforced regardless of the value requested. *(FR-6.3.5)*
- **FR-010**: Every node parameter MUST be settable by the user at any time during playback; every continuous parameter change MUST ramp linearly over **20 ms** from the current value to the target starting at the next buffer boundary (a new target mid-ramp restarts from the current interpolated value), which is the smoothing that avoids zipper noise. An out-of-range value from any input path MUST be clamped to the nearest valid bound, and the clamped value (not the requested one) MUST be what the engine applies and the UI displays. *(FR-6.3.8; FR-6.1.2; EC-5.3; Clarifications)*
- **FR-011**: The system MUST publish, live, to the UI: peak and RMS levels measured pre-chain (after the decoder, before any node and before master volume) and post-chain (immediately before the limiter, i.e. after master gain), and a post-chain low-resolution spectrum (32–128 bands, default 64) suitable for a visual meter. Post-chain meters MUST reflect the currently active (non-bypassed) nodes and master volume; pre-chain meters MUST reflect neither. *(FR-6.4.1, FR-6.4.2; Clarifications)*
- **FR-012**: The engine MUST measure its total render time per callback and raise an **overload event** when it exceeds 90% of the callback period on 3 consecutive callbacks or 100% on any single callback. On an overload event the system MUST: increment an overload/underrun counter published to the UI; show one keyed `Warning` notification (`effect-chain-over-budget`) naming the chain's most expensive node by type and owner, reused while the condition persists and cleared once render time has stayed under 90% for a full rolling cost window; and, **only if that most expensive node is non-host**, auto-bypass it at the next buffer boundary, label it "auto-bypassed (over budget)", never auto-restore it, and bypass at most one node per rolling window. Host-owned nodes MUST never be auto-bypassed, so in this slice no node is bypassed by this rule; the mechanism MUST nonetheless ship and be covered by engine tests using the data model's non-host owner value. Audio MUST NOT drop out silently under any overload condition: every underrun is counted and surfaced. *(FR-6.2.6; EC-5.1, EC-5.2 pattern; NFR-8.2, NFR-8.3; Clarifications)*
- **FR-012a**: A node's CPU-load figure is the percentage of the callback period its processing consumed, as a rolling mean over the last `ceil(1 s / buffer period)` callbacks (the "rolling cost window"); the whole-chain figure is the sum of node figures; both read 0% when no callback ran in the window. *(FR-6.2.5; NFR-8.2; Clarifications)*
- **FR-013**: No component — including this feature's own nodes, meters, or diagnostics — may write decoded or chain-processed audio to a file, a network socket, or any interface outside the audio engine, under any configuration, debug flag, or code path. *(FR-6.5.1; FR-6.5.2; Constitution V, NON-NEGOTIABLE)*
- **FR-014**: When the active track's source sample rate differs from the previous track's, every rate-dependent node coefficient (EQ frequency/Q, filter cutoff/resonance) MUST be recomputed before the new track's first processed buffer, so that the user's set frequency/Q/cutoff values retain their intended meaning in Hz; the chain's node order and parameter values themselves MUST be unaffected by the rate change. *(FR-6.1.3)*
- **FR-015**: Every control introduced by the Effect Chain panel (per-node controls, drag handles, bypass toggles, add/remove controls, meters, CPU indicators, warnings) MUST expose an accessible name, role, and state, and MUST be fully operable by keyboard alone. *(NFR-6.1, NFR-6.2)*
- **FR-016**: This slice MUST NOT implement plugin-owned effect nodes, the custom buffer processor, chain presets (save/recall), chain persistence across restarts, or the detected-key display; the node data model (owner field, cost tracking, auto-bypassed flag) is deliberately forward-compatible with a later plugin-owned-nodes slice without requiring a breaking change. *(Scope boundary; Clarifications)*
- **FR-017**: This slice MUST flip 007's forward-declared `effects.tempo_step_up` (`=`, `+`) and `effects.tempo_step_down` (`-`) actions to `enabled: true` (their stored bindings, default or user-customized, apply unchanged; conflict re-evaluation finds none). Each invocation MUST change the ratio of the first time-stretch node in chain order (any owner; bypass state ignored and unchanged) by ±0.10 (ten tempo percentage points), clamped to `[0.25, 2.0]`, through the FR-010 smoothed path so FR-008 runs on the result. With no time-stretch node in the chain the action MUST do nothing to the chain and show one keyed `Info` notification `effects-no-time-stretch`; held-key repeats MUST coalesce into it. The `+`/`-` overlap with 005's waveform zoom is resolved by 007 FR-019's precedence (a focused waveform consumes the keys; otherwise the action fires) and MUST NOT be flagged as a conflict. This slice MUST also register `nav.toggle_effect_chain` (trigger, scope `now_playing`, default `E`, no repeat, rebindable) in 007's Action & Binding registry and catalog. *(007 FR-012/FR-018/FR-019; J-2 step 6; Clarifications)*
- **FR-018**: The slice MUST ship: an automated control-to-audio latency test for SC-001 against the synthetic source; a click-free test for every chain edit and discrete switch (no sample discontinuity above the seam-test threshold used by 006's NFR-1.3 test); property-based tests for parameter clamping (every FR-006 range, including the rate-derived Nyquist clamp) and ramp/crossfade arithmetic; an engine test that an overload event bypasses exactly the most expensive non-host node and never a host node; a real-time-safety test that no chain operation allocates on the audio thread; criterion benchmarks for each node type and for the SC-003 reference chain (001 deferred Constitution VIII's benchmarks "until an effect chain exists" — this is that slice); and a soak harness for NFR-2.7 that renders the SC-003 reference chain continuously and asserts no unbounded growth — run for 60 s in CI (extending 001's continuous-render stand-in) and runnable for 24 h under `#[ignore = "manual"]` on reference hardware. *(Constitution I, VIII; NFR-1.1, NFR-1.8, NFR-2.7; 001 plan Complexity Tracking)*

### Key Entities

- **EffectNode (DM-17)**: A single processing unit in the chain — identifier, type (from the built-in catalog), owner (host | non-host; "host" for every node in this slice), a set of named parameters (each with a current value and an active 20 ms smoothing ramp), a bypassed flag, an auto-bypassed flag, an auto-switched flag (pitch shift / time stretch only), an orphaned flag (unused until plugins exist), a measured cost (percentage of the callback period, rolling mean over the ~1 s cost window), and its position in the chain. Session-scoped; not persisted in this slice.
- **EffectChain (DM-18)**: The single, live, ordered list of EffectNode identifiers between the decoder and the output limiter, plus the chain's total measured cost, the engine's total render-time measurement and overload counter, and the limiter ceiling it feeds into. Global, not per-track; empty at launch.
- **Chain Meter Snapshot**: The live pre-chain and post-chain peak/RMS levels, the post-chain low-resolution spectrum, and the effective position-advance rate, recomputed continuously and published to the UI; never persisted, never exposed outside the engine/UI boundary.
- **Effect-chain actions**: `effects.tempo_step_up`, `effects.tempo_step_down` (007, now enabled) and the new `nav.toggle_effect_chain` (`E`), all in 007's registry with its scope, conflict and persistence rules.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: When a user changes the time-stretch ratio from 1.0 to 0.6 during playback, the tempo change is audible within 20 ms at p95, with the pitch of the material unchanged, in automated latency measurement.
- **SC-002**: Reordering two active nodes (e.g., moving an equalizer ahead of a time-stretch node) during playback produces no audible click or gap, in 100% of trials.
- **SC-003**: With pitch shift, time stretch, and an 8-band equalizer all active at the performance buffer preset, total chain-plus-host processing stays under 50% of one core, in 100% of measured runs.
- **SC-004**: When chain processing exceeds the real-time budget, the system increments the overload counter and names the most expensive node in a visible warning in 100% of trials; when that node is non-host (engine test) exactly it is bypassed, and a host node is never bypassed — zero silent (uncounted, unsurfaced) dropouts.
- **SC-005**: Every out-of-range parameter entry, from any input path, results in a clamped value that both the engine and the UI agree on, in 100% of trials — never a silently dropped or ignored change.
- **SC-006**: Setting time-stretch to 25% or pitch shift to +12 semitones surfaces a quality-mode auto-switch note on the affected node, and returning to 100% / 0 semitones (without touching the mode control) clears it, in 100% of trials.
- **SC-011**: With a time-stretch node at ratio 0.5, a 4 s loop region plays in 8 s of wall time with a click-free seam, and the displayed playhead never jumps or stalls by more than one buffer between consecutive UI frames, in 100% of trials.
- **SC-012**: `+`/`-` step the first time-stretch node by exactly ±10 percentage points (clamped) whenever the waveform is not focused, zoom the waveform when it is, and produce one coalesced notification (no chain change) when no time-stretch node exists, in 100% of trials; `E` toggles the Effect Chain panel from anywhere in the Now Playing view.
- **SC-013**: Adding any of the six node types at its defaults produces output identical to the empty chain (sample-exact for gain/EQ/filter/stereo tools; within the resampler's pass-through tolerance for pitch shift/time stretch at unity), in 100% of trials.
- **SC-007**: A chain of at least 16 nodes can be assembled, with every node independently reorderable, bypassable, addable, and removable, each action taking effect glitch-free at the next buffer boundary, in 100% of trials.
- **SC-008**: Pre-chain and post-chain peak/RMS meters and a low-resolution spectrum are visible and update live throughout playback, reflecting the chain's current bypass/parameter state within one buffer's latency.
- **SC-009**: No code path in this feature ever makes a decoded or chain-processed audio sample available outside the audio engine (no file, socket, or external API surface), verified by an automated code-path/API-surface check.
- **SC-010**: A user can shape a track's tone using gain, an 8-band equalizer, a filter, and stereo tools together, hearing each change take effect smoothly (no click) and immediately (within the same latency bound as SC-001).

## Assumptions

- No plugin runtime exists in this slice (it lands in 001-mvp/009); every effect node is owned by "host," and the non-host-only auto-bypass rule (FR-012) is present in the data model and engine but inert until then.
- Automation in this slice means direct, real-time host-UI parameter changes (drag, type, toggle) applied with buffer-boundary smoothing; the "schedule a future ramp" plugin automation surface (FR-6.3.8's full scope) is deferred to the plugin-runtime slice, which can build on this slice's value+ramp data model without a breaking change.
- Quality-mode auto-switch thresholds (`|semitones| > 3` for pitch shift, ratio outside `[0.5, 1.5]` for time stretch) are derived from NFR-1.14/NFR-1.15's own "acceptable for stage use" boundaries, since the source document names no other threshold (Clarifications).
- The pitch-shift/time-stretch single-resampler-stage optimization applies only when the two nodes are adjacent in the chain; this is an internal performance detail with no user-visible control surface beyond the two nodes' own parameters.
- Chain-edit and discrete-switch crossfades use a fixed 5 ms engine constant (the same *value* as NFR-1.3's seam default) and may reuse the seam's equal-power crossfade math, but are deliberately **not** tied to 006's per-region loop-crossfade setting, whose valid `0` (hard cut) must not make chain edits click (Clarifications; realigned from the specify pass).
- The exact maximum chain capacity (a fixed constant ≥ 16) and the underlying filter Q that normalized resonance 1.0 maps to are plan-time DSP constants. The spectrum band count (64), the parameter ramp (20 ms), the chain-edit crossfade (5 ms), the overload thresholds (90% / 3 callbacks / any underrun) and the cost window (~1 s) are fixed by this spec as defaults; plan may not change them without recording the deviation.
- The engine's `Command` queue carries `Copy`, ≤ 16-byte values; node insertion therefore requires the node's DSP state to be allocated off the real-time thread and handed over by identifier/pointer swap at a buffer boundary — a plan-level mechanism, but the spec's real-time-safety test (FR-018) must cover it.
- EQ band "type" offers exactly three shapes — peak, low-shelf, and high-shelf — the conventional parametric-EQ set implied by "peak/shelf" in the source prompt.
- This slice does not implement chain presets (save/recall a named chain configuration — 006-practice-depth/003), chain restore after an unexpected termination (NFR-2.6 — 004-performance/003), or the detected-key display; all are out of scope per the breakdown's allocation.
- 007's Default Action Catalog row for the two tempo actions ("enabled: no — no effect chain yet") and its Assumption about the unaddressed `+`/`-` waveform-zoom overlap are superseded by FR-017; the 007 spec itself is not edited by this slice.
- Egui's focus model already gives every FR-006 parameter control (slider/drag value, toggle, combo) its keyboard behaviour; FR-004's `↑`/`↓`-on-handle reorder is the only chain-specific keyboard gesture this slice adds.
- Metering, CPU-load figures, and the effect chain itself are read/observed by the UI only; no external API, file, or socket exposure of any of this data exists or is planned within this slice (Constitution V, NON-NEGOTIABLE).
