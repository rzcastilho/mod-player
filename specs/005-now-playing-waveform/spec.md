# Feature Specification: Now-Playing View with Waveform

**Feature Branch**: `feature/005-now-playing-waveform`

**Created**: 2026-09-17

**Status**: Clarified (2026-09-17, specify pass + clarify pass) — no open human decisions

**Input**: User description: "Give the user a now-playing view where they can see the song and navigate it by sight — the surface that markers, loops, and plugin overlays will later draw on. The view shows artwork, title, artists, album, elapsed and remaining time, a waveform overview of the whole track, and a zoomable waveform detail around the playhead. The waveform is generated locally from decoded audio by a background analysis service that pulls decoded buffers at low priority and never contends with the real-time path. For a track still streaming, the waveform fills in progressively and the undecoded region shows as a placeholder. The overview is cached per track identity as a multi-resolution peak set, versioned by analyzer version, so reopening a track shows the waveform immediately. The user can click or drag on either waveform to seek, and can zoom the detail view. Seeking is sample-accurate on fully decoded audio and lands within 50 ms of the requested position on streamed audio. Every seek and zoom action is also reachable by keyboard alone. The waveform area is designed to host the playhead, host markers, an active loop region, and plugin overlays in later slices, so it must expose a track-time coordinate space that re-projects on zoom and scroll. When nothing is loaded, the view shows a hint to pick a track. Analysis failing on a track (silence, corrupt stream) marks it "analysis unavailable" without blocking playback. Acceptance: when a track starts playing for the first time, the waveform begins filling within a second and completes as decoding does. When the user clicks at 1:23.500 on a cached track, playback resumes from exactly that position within 10 ms. When the user reopens a track whose waveform was computed yesterday, the full waveform appears instantly from cache. When the analyzer version changes, the waveform is recomputed on next play."

**Source**: [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) — FR-4.1 Now-playing view and waveform, FR-6.6 Local analysis (waveform overview only), DM-5 Analysis, Part 9 §3 Core services (AR-11 Analysis Service), EC §5.9 Analysis failure, EC §12 Empty, loading, and first-run states, NFR §6 Accessibility. Prerequisites: 003-streaming-playback-and-queue (decoded playback, transport, TrackRef, audio clock, position reporting).

**Scope boundary**: Does not cover markers, loops, beat grid, snapping, plugin overlays, or detaching the view into its own window. Per the breakdown coverage map: beat grid, key estimate, and loudness (the rest of DM-5/FR-6.6) belong to later slices — this slice implements only the waveform-overview portion of local analysis and the Analysis Service's waveform path. Markers (FR-5), loop regions, and plugin overlays (`ui.overlay`) are drawn on the coordinate space this slice establishes but are not built here.

## Clarifications

### Session 2026-09-17 (specify pass)

Resolution ladder applied: (D) derived from an authoritative source, (A) assumed conventional default, consistent with 001–004. No item below met the materiality bar for human escalation.

- Q: What exactly does "analysis unavailable" mean, and does a retry ever happen automatically? → A (D, EC-5.9 verbatim): analysis status becomes `failed`; any consumer (this slice's view; plugins in a later slice) reading it gets `failed`; there is **no automatic retry** until the analyzer version changes or the user explicitly requests re-analysis. If a partial waveform had already been computed before the failure, it stays shown (frozen, not cleared); otherwise the view shows the literal "analysis unavailable" message. Playback is entirely unaffected — analysis runs on the already-decoded audio the transport (003) already has, so a failure there has no bearing on the audio path.
- Q: Does this slice implement beat grid, key, and loudness too, since AR-11 and FR-6.6 name all four together? → A (D, breakdown source citation "waveform overview only" and scope boundary): no — this slice implements only the waveform-overview computation, cache, and rendering. The Analysis Service (AR-11) and the `Analysis` entity (DM-5) are shaped to hold beat grid / key / loudness later; those fields are simply not populated or exposed by this slice, and analysis `status` here reflects the waveform computation only.
- Q: Is the next queued track's waveform pre-computed ahead of time, the way 003 pre-fetches its audio? → A (A, Constitution X — no feature not asked for): no — only the currently loaded (playing or paused) track is analyzed. Pre-analyzing upcoming queue items is not requested by the prompt and is deferred; switching to a track starts its analysis if not already cached.
- Q: What does dragging on a waveform do while the pointer is still down — does audio audibly scrub, or does it only preview a position? → A (A, conventional desktop-player default, matches the lower-risk reading of FR-4.1.4's "click or drag ... to seek"): dragging shows a live position preview (a moving playhead/time readout) without changing the audible position; releasing the pointer commits the seek to the released position. This avoids the added complexity of audible time-stretched scrubbing, which the prompt does not ask for and no existing FR-6.3 node supports yet.
- Q: Where is the waveform peak cache stored, is it encrypted, and who evicts it? → A (D, DM-5 "cleared with the cache to avoid orphaned data" + Constitution V): the cache is on-disk, keyed by track identity and analyzer version, and lives separately from AR-9's **encrypted** stream cache — peak summaries are lossy, non-reversible aggregates, not decoded audio, so Constitution V's audio-secrecy boundary does not apply to them and they are stored unencrypted. This slice ships no active eviction policy for the analysis cache (consistent with 003/004 deferring cache-eviction mechanics); eviction lands with the offline-and-library wave's cache manager work and will reuse this same per-track key.
- Q: What are the zoom detail view's range bounds and default keyboard bindings? → A (A, conventional, internal constants documented here): the detail view zooms from the whole track down to a 200 ms window at maximum zoom. Mouse/trackpad: vertical scroll or pinch to zoom, centered on the pointer position. Keyboard: `+`/`=` and `-` zoom in/out centered on the playhead, `0` resets zoom to fit the whole track. *(Superseded in part by the clarify pass below: the specify pass's `←`/`→`-pan and click-drag-to-pan bindings conflicted with 003's seek-slider convention and with FR-4.1.4's drag-to-seek; the clarify pass's binding table is authoritative.)*
- Q: When does the "waveform begins filling within a second" acceptance apply — every play, or only the first time a track has never been analyzed? → A (A, plain reading of "starts playing for the first time"): it applies to a track with no valid cache entry (never analyzed, or its cached entry's analyzer version is stale). A track with a valid cache entry shows its full waveform immediately (near-instant, not a 1-second fill) per the separate cache acceptance criterion; the two are measured as distinct success criteria.
- Q: How precise/fast must the elapsed/remaining time readout and playhead motion be, given 003 reports position at ≥60 Hz? → A (A, conventional UI-refresh default; no need to re-render text at audio-clock rate): the playhead marker's position on the waveform is redrawn every rendered UI frame, tracking the audio clock continuously; the numeric elapsed/remaining time labels update at least 4 times per second, which is imperceptibly different from every-frame updates for text but avoids unnecessary re-layout.
- Q: Does "within 10 ms" for the 1:23.500 click-seek acceptance mean position accuracy or response latency? → A (D, prompt's own adjacent sentence: "Seeking is sample-accurate on fully decoded audio"): position accuracy on fully decoded audio is exact (sample-accurate, not merely within 10 ms); the 10 ms figure is the **response latency** budget — the time from the click to audible output resuming from the new position — for a track whose target region is already decoded (a superset of "cached" in 003's terminology: already-decoded audio available in memory).

### Session 2026-09-17 (clarify pass)

Resolution ladder re-applied against the constitution, the breakdown prompt, the source spec sections cited above, 003's shipped contracts (`specs/003-streaming-playback-and-queue/contracts/ui-surface.md`: seek slider `Left/Right` = ±5 s, `Home/End` = start/end, commits on release or key) and the current code (`crates/modplayer-audio-source-connect`: librespot decodes on its player thread into a small ring buffer consumed by the audio callback — no decoded PCM is retained). Every item below is either derived (D) or an assumed conventional default (A); none met the materiality bar.

- Q: Where do "decoded buffers" come from for analysis and for sample-accurate seeking, given 003's pipeline retains no decoded PCM (the ring holds a few hundred ms and is drained by the audio callback)? → A (D, prompt: "sample-accurate on fully decoded audio", "resumes from exactly that position within 10 ms", "pulls decoded buffers at low priority"; 003 US-4 AS1: "pre-buffers that track fully as fast as the connection allows (not throttled to real-time playback speed)"; Constitution VIII's future loop-seam sample-accuracy needs the same store): this slice introduces a **retained decoded-audio store** for the current track — the decoded PCM of the current track is kept in memory, owned by the engine/source side and never exposed outside it (Constitution V), decoded ahead of playback as fast as the source delivers it (not throttled to playback rate), and discarded when the track stops being current. "Decoded" throughout this spec means *present in that store*. Sample-accurate seeks and the Analysis Service both read from it; nothing reads from, or adds work to, the audio callback. The store's sample format (f32 vs. i16) and growth strategy are plan decisions, bounded by: a 10-minute 44.1 kHz stereo track MUST fit in ≤ 256 MB, and NFR-2.7 (no unbounded growth) holds because only the current track is retained (003's "next" item keeps its existing encoded prefetch; its decoded store is not built until it becomes current). Added as FR-021.
- Q: Does analysis tap decoded audio before or after the effect chain and master volume? → A (A, conventional — the waveform depicts the song, not the playback settings): analysis reads the decoded, **pre-effect-chain, pre-volume** signal. Test: changing master volume mid-analysis does not change the resulting peaks.
- Q: Are peaks per-channel or mono? → A (A, conventional for a player overview; keeps the cache small): **mono-folded** — each bucket stores one `min`/`max` pair as the min-of-mins / max-of-maxes across channels, quantized to 8 bits. The multi-resolution ladder MUST include a level with ≤ 3 ms of audio per bucket (so the 200 ms max-zoom window resolves to ≥ 60 buckets) and a level coarse enough to draw the whole-track overview from ≤ 4 096 buckets; intermediate levels are a plan decision. A complete entry for a 10-minute track MUST be ≤ 1 MB on disk.
- Q: What is the analyzer version, and where does it live? → A (A, conventional): a single integer constant in the analysis crate, bumped by hand whenever the peak computation or cache layout changes; it is written into every cache entry and compared on read. Test: bumping the constant makes every existing entry invalid on next play.
- Q: Where is the cache on disk, and which statuses are written? → A (A, conventional; DM-5): under the app's config/data directory (the same root 002–004 use) in an `analysis/` subdirectory, one file per track identity (003's `TrackId`). **Only `complete` entries are written**; `partial` and `failed` are in-memory session state and are never persisted, so a transient failure (corrupt stream this session) does not permanently brand the track. Writes are atomic (write-then-rename, per NFR-2.8's convention).
- Q: "No automatic retry" after a failure — for how long, and is there a "re-analyze" action in this slice? → A (A, Constitution X + EC-5.9's intent of "no retry loop"): `failed` lasts for the rest of the session for that track identity — switching away and back to the track does **not** retry; a new app launch may attempt again (the failure was never persisted). The explicit "user requests re-analysis" path of EC-5.9 is **not built** in this slice (no UI is asked for); it lands with the analysis-depth wave. The analyzer-version path (FR-007) is the only in-slice invalidation.
- Q: What exactly counts as "silence" failing analysis (EC-5.9 names silence)? → A (D, EC-5.9; A for the threshold): a track whose decoded audio is **entirely** silent over its full length (every bucket's `max`−`min` quantizes to 0) sets status `failed` once decoding completes; silent *stretches* inside an otherwise normal track are simply flat regions with status unaffected. Corrupt stream = the decoder reporting an unrecoverable error for the track.
- Q: Is the waveform filled from the playhead onward as the song plays, or from the start of the track regardless of where playback is? → A (D, FR-021 + 003 US-4 AS1): analysis consumes the decoded store as it fills, in decode order, which is independent of the playhead. Because 003 pre-buffers the whole track at connection speed, a first-play waveform completes in roughly the time the download takes, not the track's duration. If a seek causes decoding to jump ahead, the not-yet-decoded gap(s) are shown as placeholder region(s) — there may be more than one — and are filled when decoding covers them; `complete` requires full coverage.
- Q: Does the waveform overview replace 003's seek slider or sit beside it? → A (A, Constitution X simplicity — two seek controls for one value is clutter): the **overview replaces the seek slider** and inherits its accessibility contract: role slider, accessible name key `transport-seek`, value text `m:ss / m:ss`, `Left/Right` = ±5 s, `Home/End` = start/end, commit on release or key. 003's contract test "seek slider commits once per release" now exercises the overview. The elapsed / remaining labels replace 003's `transport-position` label.
- Q: What do the keyboard bindings actually do on each waveform — the specify pass bound `←/→` to *pan*, which contradicts 003's `←/→` = seek ±5 s, and left keyboard **seek** unbound? → A (D, 003 contract for parity; A for the rest — conventional DAW-style modifiers): with either waveform focused: `←`/`→` **seek** ±5 s (003 parity); `Shift+←`/`Shift+→` **seek** ±500 ms (fine nudge, the keyboard equivalent of clicking in a zoomed detail view); `Home`/`End` **seek** to track start/end (003 parity); `+`/`=` and `-` zoom the detail view in/out one step (×2 / ÷2) centered on the playhead; `0` resets the detail view to the whole track; `Alt+←`/`Alt+→` **pan** the detail view by 10% of its visible window without seeking (`Alt+Shift+←/→`: one full window). Pointer: click seeks; drag on **either** waveform = seek preview, committed on release (FR-4.1.4 — drag is never pan); vertical wheel/scroll or pinch = zoom centered on the pointer; horizontal scroll (trackpad) or `Shift`+wheel = pan; `Esc` during a drag cancels it (no seek). Same on macOS, Windows, Linux (Constitution X). Every action in this table is an explicit test case for FR-013.
- Q: What is the detail view's zoom at first use, and how does it "follow" the playhead (FR-012)? → A (A, conventional page-flip follow, which does not fight pointer-centered zoom): the detail view opens on a **30 s window centered on the playhead**; zoom level persists for the session (not across launches) and applies to the next track. **Follow** is on by default: while playing, when the playhead crosses the window's right edge, the window pages forward so the playhead sits at the window's left edge; the window never extends beyond the track (it clamps at start/end and the playhead moves off-centre there). Any seek (pointer, keyboard, transport, remote) that lands outside the window re-centers the window on the new position and re-enables follow. A user **pan or zoom that leaves the playhead outside the window suspends follow** until the next seek or `0` (reset). While paused/stopped nothing scrolls.
- Q: Does the overview indicate which part of the track the detail view is showing? → A (A, conventional and needed to make zoom legible): yes — the overview draws the detail view's visible window as a translucent region; it is decorative (not a separate focusable control) and its extent is part of the overview's accessible description ("showing 1:10–1:40").
- Q: Time label format? → A (D, 003's `m:ss` convention): elapsed `m:ss`, remaining `-m:ss` (leading minus, no leading-zero minutes, no milliseconds); while a drag preview is active both labels and the playhead show the previewed position and revert on `Esc`.
- Q: Artwork missing or failing to load? → A (D, 004 FR-020/EC-2.7 convention): the same initials placeholder 004 uses (up to two uppercase letters from the album title; generic music glyph if none), never a broken image.
- Q: Seek while paused or stopped? → A (D, 003 US-1 AS13): seeking via the waveform while paused keeps the transport paused at the new position; while stopped with a current track it sets the position and the transport enters `paused`. It never starts playback by itself.
- Q: Click vs. drag threshold? → A (A, toolkit convention): a press/release without pointer travel beyond the UI toolkit's standard drag threshold is a click; beyond it, a drag.
- Q: Where is the 10 ms seek-latency budget measured? → A (A, conventional engine-side measurement, consistent with 003's latency tests): from the pointer-release / key event reaching the UI to the first sample from the new position being handed to the output callback — device/driver output latency is excluded.
- Q: Analysis thread model? → A (A, conventional): one dedicated analysis thread at below-normal OS priority, processing the decoded store in bounded chunks and publishing progress to the UI through a lock-free channel; it never touches the audio callback, its queues, or the real-time allocator-free path.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - See the track and seek by clicking the waveform (Priority: P1)

While a track plays, the user sees its artwork, title, artists, album, and how much time has elapsed and remains, alongside a waveform overview spanning the whole track. Clicking anywhere on that waveform jumps playback to that point instantly and precisely.

**Why this priority**: This is the entire point of the slice — until this ships, the now-playing view is still 001's minimal transport with no visual sense of the song and no way to navigate it by sight. Nothing else in this spec matters if this doesn't work.

**Independent Test**: Play a fully decoded (or previously analyzed) track, verify artwork/title/artists/album/elapsed/remaining time are shown and update correctly, then click at a specific point on the waveform overview and verify playback resumes from exactly that position.

**Acceptance Scenarios**:

1. **Given** a track is loaded and playing, **When** the now-playing view is shown, **Then** it displays the track's artwork (or the 004 initials placeholder when artwork is missing/fails), title, artists, album, elapsed time as `m:ss`, and remaining time as `-m:ss`, all reflecting the current track; 003's seek slider and `transport-position` label are no longer shown — the overview and the two labels take their place.
2. **Given** a track is playing, **When** time passes, **Then** the elapsed and remaining time labels update at least 4 times per second and the waveform's playhead marker moves continuously in step with the audio clock (003's position reporting), not a separate UI timer.
3. **Given** a track whose audio at 1:23.500 is in the retained decoded store (FR-021), **When** the user clicks at 1:23.500 on the waveform, **Then** playback resumes from exactly that sample-accurate position, with the first sample from the new position handed to the output callback within 10 ms of the click.
4. **Given** a track is playing, **When** the user drags on either waveform, **Then** a live position preview (playhead + both time labels) follows the pointer without changing the audible position, and releasing the pointer seeks to the released position; pressing `Esc` mid-drag cancels with no seek.
5. **Given** either waveform is focused, **When** the user presses `←`/`→`, `Shift+←`/`Shift+→`, `Home`, or `End`, **Then** playback seeks by −5 s/+5 s, −500 ms/+500 ms, to start, or to end respectively, with exactly the result a pointer click at that position would produce.
6. **Given** the waveform overview is displayed, **When** the user or automated tooling inspects it, **Then** it exposes role slider, accessible name `transport-seek`, and value text `m:ss / m:ss` (003's contract), and the detail view exposes its own name and its visible window in its description, consistent with Constitution X and NFR-6.1/6.2.
7. **Given** the transport is paused or stopped, **When** the user clicks the waveform, **Then** the position changes and the transport is `paused` at that position; playback does not start.

### User Story 2 - Zoom into the waveform for precise navigation (Priority: P2)

Around the playhead, the user can zoom the waveform detail in to see individual seconds (or less) of audio clearly, and zoom back out, panning through the track, to place a seek precisely where a click on the whole-track overview would be too coarse.

**Why this priority**: The overview alone (Story 1) already delivers "navigate by sight," but fine navigation — the kind a musician cueing a specific note or a DJ finding a mix point needs — requires zoom. It ranks second because the view is useful without it, but not yet precise.

**Independent Test**: With a track playing, zoom the detail view in around the playhead using the pointer, then pan and zoom using only the keyboard, and click within the zoomed detail to seek; verify the seek lands at the exact zoomed-in position.

**Acceptance Scenarios**:

1. **Given** the waveform detail view is shown (first use: a 30 s window centered on the playhead), **When** the user vertical-scrolls or pinches to zoom in, **Then** the view zooms centered on the pointer position, down to a 200 ms minimum window, showing finer waveform detail; the overview highlights the detail view's visible window as a translucent region.
2. **Given** the detail view is zoomed in, **When** the user zooms out fully (or presses `0`), **Then** the view returns to showing the same window as the whole-track overview.
3. **Given** the detail view is zoomed in, **When** the user horizontal-scrolls, `Shift`+wheels, or presses `Alt+←`/`Alt+→`, **Then** the visible window pans along the track (10% of the window per key press; one full window with `Alt+Shift`) without changing the audible position, and clicking within the panned view seeks to that exact position.
4. **Given** either waveform is focused, **When** the user presses `+`/`=`, `-`, `0`, `Alt+←`, `Alt+→`, `Alt+Shift+←`, or `Alt+Shift+→`, **Then** each action performs the behavior in the Clarifications binding table (zoom in ×2, zoom out ÷2 centered on the playhead, reset, pan), with no action reachable only by pointer.
5. **Given** the detail view is zoomed to a narrow window and follow is active, **When** the playhead crosses the window's right edge during playback, **Then** the window pages forward so the playhead sits at its left edge; **When** any seek lands outside the window, **Then** the window re-centers on the new position.
6. **Given** the user has panned or zoomed so the playhead is outside the visible window, **When** playback continues, **Then** the window stays where the user put it (follow suspended) until the next seek or `0`, which re-centers on the playhead and re-enables follow.

### User Story 3 - Watch the waveform fill in as a track streams (Priority: P3)

For a track that has just started streaming and is not yet fully decoded, the user sees the waveform begin appearing almost immediately and keep filling in as more of the track decodes, with the not-yet-decoded portion shown as a clear placeholder rather than a blank or broken area.

**Why this priority**: This makes the view honest and useful during the common case of playing a track for the first time on a live connection, but it only matters once Stories 1–2 already give the user a working, seekable waveform to watch fill in.

**Independent Test**: Start playing a track that has never been analyzed and is still streaming; observe that the waveform begins filling within a second, the undecoded region is visibly a placeholder (not blank), and the whole overview is complete once decoding finishes.

**Acceptance Scenarios**:

1. **Given** a track with no cached analysis starts streaming, **When** playback begins, **Then** the waveform overview begins visibly filling in within one second.
2. **Given** a track is progressively decoding, **When** the user views the waveform, **Then** the decoded region(s) show real waveform peaks, every undecoded region shows a distinct placeholder, and the boundaries advance in decode order (independent of the playhead) as decoding progresses; the fill rate follows the download, not the track's playback speed.
3. **Given** a track finishes decoding, **When** the last buffer is analyzed, **Then** the waveform overview shows the complete track with no remaining placeholder region and status becomes `complete`, at which point (and only then) the cache entry is written.
4. **Given** the waveform is still filling in, **When** the user clicks in the already-decoded region, **Then** the seek behaves exactly as in Story 1 (sample-accurate, low-latency); **When** the user clicks in the still-undecoded region, **Then** the seek lands within 50 ms of the requested position once that audio is available, consistent with 003's streamed-seek behavior, and the region(s) skipped over remain placeholders until decoding covers them.
5. **Given** the background analysis is computing the waveform, **When** the audio engine's real-time callback is inspected under load, **Then** the analysis work shows no measurable contention with the real-time audio path (no added allocation, lock, or latency on the callback).
6. **Given** master volume is changed while analysis runs, **When** the waveform completes, **Then** the peaks are identical to those computed at any other volume (analysis taps pre-effect, pre-volume audio).

### User Story 4 - Get instant waveforms on repeat plays via caching (Priority: P4)

The second time (and every time after) the user plays a track whose waveform has already been computed, the full waveform overview appears immediately — no re-analysis, no progressive fill — because it was cached the first time. If the analysis logic itself has since changed, the cached waveform is recomputed automatically the next time that track plays.

**Why this priority**: This is a performance and polish guarantee layered on top of Stories 1–3 already working; it materially improves the experience of a session where the user replays familiar tracks, but the feature is fully functional (if slower to appear) without it.

**Independent Test**: Play a track once and let its waveform finish computing; stop and reopen it (or replay it later) and verify the full waveform appears immediately from cache; then simulate an analyzer version change and verify the waveform is recomputed on the next play of that track.

**Acceptance Scenarios**:

1. **Given** a track's waveform was fully computed in an earlier session, **When** the user plays that track again, **Then** the complete waveform overview appears immediately, with no progressive-fill placeholder shown.
2. **Given** a track's cached waveform was computed under an older analyzer version, **When** the user plays that track after the analyzer version has changed, **Then** the system discards the stale cache entry and recomputes the waveform as if analyzing for the first time (per Story 3).
3. **Given** two different tracks have both been analyzed and cached, **When** the user switches between them, **Then** each shows its own correct cached waveform — cache entries are never confused across track identities.

### Edge Cases

- What happens when nothing is loaded (no track selected or playing)? → The view shows a hint to pick a track instead of an empty or broken waveform area (EC §12).
- What happens when analysis fails on a track (entirely silent decoded audio, or the decoder reports an unrecoverable error)? → Analysis status becomes `failed` for the rest of the session; the view shows "analysis unavailable" in the waveform area (or the partial waveform computed before the failure, if any, left in place); no retry occurs this session even if the user switches away and back; the failure is not persisted, so a later launch may attempt again; playback is entirely unaffected (EC-5.9; Clarifications).
- What happens when the user clicks or drags past the end of the track on either waveform? → The position clamps to the track's end, consistent with 003's seek-past-end behavior (queue advancement rules apply exactly as they do for a transport-initiated seek).
- What happens when the user switches to a different track while a waveform is still filling in? → The in-progress analysis for the previous track is abandoned (its partial state is dropped — only `complete` entries are ever written to disk); its decoded store is released; analysis of the newly current track begins per Story 3.
- What happens when artwork is missing or fails to load? → The 004 initials placeholder (up to two uppercase letters from the album title; generic glyph if none) is shown, never a broken image.
- What happens when the user presses `Esc` during a drag? → The drag is cancelled: no seek, playhead and labels revert to the live position.
- What happens when the user pans the detail view away from the playhead during playback? → Follow is suspended; the window stays put until the next seek (any source) or `0`, either of which re-centers on the playhead and re-enables follow.
- What happens when the retained decoded store would exceed its memory bound (e.g., an unusually long track)? → The store is capped at the bound (Clarifications: ≤ 256 MB for the current track); audio beyond the cap is not retained, seeks into it fall back to 003's streamed-seek contract (within 50 ms), and the waveform for that region stays a placeholder with status `partial`. Defensive; catalog tracks fit comfortably.
- What happens when the track's duration is unknown or changes mid-stream (e.g., a live or variable-length source)? → The overview scales to the best-known duration and rescales without losing already-computed peaks if the duration estimate improves; this is a defensive fallback, not an expected case for the catalog sources this product supports.
- What happens if the output device or connection drops entirely while a waveform is still filling? → The waveform keeps whatever portion was decoded before the interruption and resumes filling when decoding resumes; it does not reset to empty (consistent with 003's "continues from buffered data" behavior).
- What happens when the same track is loaded twice in quick succession (e.g., replayed immediately)? → The second load reuses the same cache entry / in-flight analysis rather than starting a redundant second analysis pass.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The now-playing view MUST display the currently loaded track's artwork (falling back to 004's initials placeholder when missing or failed), title, artists, album, elapsed time formatted `m:ss`, and remaining time formatted `-m:ss`, sourced from the track's existing metadata (003's `TrackRef`), extending 001's minimal now-playing transport. The waveform overview MUST replace 003's seek slider and the two time labels MUST replace 003's `transport-position` label; no duplicate seek control remains. *(FR-4.1.1; Clarifications)*
- **FR-002**: The now-playing view MUST show a waveform overview spanning the entire current track and a zoomable waveform detail around the playhead. The detail view MUST open on a 30 s window centered on the playhead, keep its zoom level for the session, and the overview MUST highlight the detail view's visible window as a translucent, non-focusable region whose extent is included in the overview's accessible description. *(FR-4.1.1; Clarifications)*
- **FR-003**: The waveform MUST be generated locally from decoded audio by a background Analysis Service (AR-11) running on one dedicated thread at below-normal OS priority, reading the retained decoded store (FR-021) in bounded chunks, in decode order, from the **pre-effect-chain, pre-volume** signal, and publishing progress to the UI through a lock-free channel; this analysis work MUST NOT allocate on, lock, block, or otherwise contend with the real-time audio callback. *(FR-6.6.1, AR-11; Constitution I — Real-Time Path Is Sacred; Clarifications)*
- **FR-004**: This slice's Analysis Service implementation MUST compute the waveform-overview portion of analysis only; the beat grid, key estimate, and loudness fields of the `Analysis` entity (DM-5) are out of scope and remain unpopulated by this slice. *(Scope boundary; source citation "waveform overview only")*
- **FR-005**: For a track that is still streaming (not yet fully decoded), the waveform MUST fill in progressively as decoding proceeds — in decode order, independent of the playhead, at the rate the source delivers audio — and every not-yet-decoded region (there may be several after a seek-ahead) MUST be rendered as a visually distinct placeholder rather than left blank or shown as an error. Status is `pending` until the first bucket, `partial` while any placeholder remains, `complete` when coverage is full. *(FR-4.1.2; Clarifications)*
- **FR-006**: The waveform overview MUST be cached on disk per track identity (003's `TrackId`) as a multi-resolution set of mono-folded, 8-bit `min`/`max` peak buckets tagged with the analyzer version that produced it, in an `analysis/` subdirectory of the app's data directory, one file per track, written atomically (write-then-rename). The ladder MUST include a level with ≤ 3 ms of audio per bucket and a level that draws the whole-track overview from ≤ 4 096 buckets; a complete 10-minute entry MUST be ≤ 1 MB. **Only `complete` entries are written**; `partial` and `failed` are never persisted. Reopening or replaying a track with a valid (matching analyzer version) cache entry MUST show the complete waveform immediately, without a progressive-fill placeholder, and MUST NOT start an analysis pass. *(DM-5; prompt; Clarifications)*
- **FR-007**: The analyzer version MUST be a single integer constant in the analysis crate, written into every cache entry and compared on read. When it changes, any cache entry produced by an older version MUST be treated as invalid and the waveform MUST be recomputed the next time that track plays, exactly as for a never-before-analyzed track. *(DM-5 "analysis version"; prompt; Clarifications)*
- **FR-008**: The waveform cache MUST store only derived peak summaries, never decoded or reconstructable audio samples, and MUST be stored separately from the encrypted stream cache (AR-9); it is not subject to Constitution V's decoded-audio-secrecy boundary because it cannot reconstruct the original audio. *(Constitution V; DM-5)*
- **FR-009**: The user MUST be able to click or drag on either waveform (overview or detail) to seek. A press/release without travel beyond the toolkit's drag threshold is a click and MUST seek immediately to the clicked position; a drag MUST show a live position preview (playhead and both time labels) without changing the audible position while the pointer is held, commit the seek to the released position on release, and be cancelled without seeking by `Esc`. Drag on a waveform is **never** pan. Seeking while paused keeps the transport paused at the new position; seeking while stopped sets the position and enters `paused` (003's contract); a waveform seek never starts playback. *(FR-4.1.4; 003 US-1 AS13; Clarifications)*
- **FR-010**: Seeking via the waveform MUST be sample-accurate when the target position is in the retained decoded store (FR-021), with the first sample from the new position handed to the output callback within 10 ms of the click/release/key event (device output latency excluded), and MUST land within 50 ms of the requested position when the target position is not yet decoded (streamed), consistent with 003's seek contract. *(Prompt; 003 FR-005; Clarifications)*
- **FR-011**: The user MUST be able to zoom the waveform detail view in and out — vertical wheel/scroll or pinch centered on the pointer; `+`/`=` and `-` in ×2 / ÷2 steps centered on the playhead; `0` to reset — down to a minimum window of 200 ms and up to the whole track, and pan the visible window without changing the audible position — horizontal scroll or `Shift`+wheel; `Alt+←`/`Alt+→` by 10% of the window; `Alt+Shift+←`/`Alt+Shift+→` by one full window. *(FR-4.1.1; prompt; Clarifications)*
- **FR-012**: Follow is on by default. While playing with follow active, when the playhead crosses the detail window's right edge the window MUST page forward so the playhead sits at its left edge; the window MUST clamp to the track's bounds. Any seek (pointer, keyboard, transport, remote) landing outside the window MUST re-center the window on the new position and re-enable follow. A user pan or zoom that leaves the playhead outside the window MUST suspend follow until the next seek or `0`. Nothing scrolls while paused or stopped. *(Prompt — "zoomable waveform detail around the playhead"; Clarifications)*
- **FR-013**: Every seek and zoom action available via pointer (click, drag, scroll/pinch-to-zoom, scroll-to-pan) MUST have a keyboard-operable equivalent producing the same result, bound as follows on either focused waveform and identical on all three platforms: `←`/`→` seek ±5 s; `Shift+←`/`Shift+→` seek ±500 ms; `Home`/`End` seek to start/end; `+`/`=`, `-`, `0` zoom in/out/reset; `Alt+←`/`Alt+→` (and `Alt+Shift`) pan. These are the same bindings 003's seek slider used for seek, so no user-facing shortcut changes. *(Prompt; NFR-6.1; 003 contracts/ui-surface.md; Constitution X; Clarifications)*
- **FR-014**: The waveform view MUST expose a track-time coordinate space (a mapping between screen/pixel position and track time) that remains accurate and consistent as the detail view zooms and scrolls, in a form later slices can attach the playhead, host markers, an active loop region, and plugin overlays to without redesigning the waveform component. *(Prompt; `ui.overlay` permission's "host re-projects on zoom and scroll")*
- **FR-015**: When no track is loaded, the now-playing view MUST show a hint to pick a track instead of an empty or broken waveform area. *(EC §12)*
- **FR-016**: When analysis fails on a track — the decoder reports an unrecoverable error for it, or its decoded audio is entirely silent over the full track (every bucket's `max`−`min` quantizes to 0 once decoding completes) — the system MUST mark that track's analysis status as `failed` for the rest of the session, show "analysis unavailable" in the waveform area (or the partial waveform computed before the failure, if any, left in place) instead of blocking or erroring the view, and MUST NOT retry analysis for that track identity this session (including after switching away and back). The failure MUST NOT be persisted, so a later launch may attempt again; the analyzer-version change (FR-007) is the only in-slice invalidation, and no "re-analyze" UI is built here. Silent stretches inside an otherwise normal track are flat regions, not failures. Playback of the track MUST be entirely unaffected by an analysis failure. *(EC-5.9; Constitution X; Clarifications)*
- **FR-017**: Analysis MUST run only for the currently loaded (playing or paused) track in this slice; the system MUST NOT pre-analyze other queue items. Switching the current track MUST abandon any in-progress analysis of the previously current track (dropping its partial state; nothing incomplete is ever written), release its decoded store (FR-021), and begin analysis of the newly current track if no valid cache entry exists for it. *(Constitution X — YAGNI; prompt scope)*
- **FR-018**: All interactive elements introduced in this slice (waveform overview, waveform detail) MUST be operable by keyboard alone and MUST expose an accessible name, role, and state: the overview is role slider with accessible name `transport-seek` and value text `m:ss / m:ss` (003's contract, inherited); the detail view is role slider with its own accessible name and value text, plus its visible window (`m:ss–m:ss`) in its description. Consistent with 001–004 and Constitution X. *(NFR-6.1, NFR-6.2; Clarifications)*
- **FR-019**: All user-facing strings introduced in this slice (the "pick a track" hint, "analysis unavailable", time labels, accessible names/descriptions) MUST be externalized; English (en-US) is the only shipped locale in this slice, consistent with 001–004. *(NFR-7.1; Constitution X)*
- **FR-020**: This slice MUST NOT introduce any UI for markers, loop regions, beat grid display or snapping, plugin overlays, a "re-analyze" action, or a detached/full-screen now-playing window. *(Scope boundary)*
- **FR-021**: The decoded PCM of the current track MUST be retained in memory in a store owned by the engine/source side and never exposed outside it (Constitution V), decoded ahead of playback as fast as the source delivers audio (not throttled to playback rate, per 003 US-4 AS1), and released when the track ceases to be current. Sample-accurate seeks (FR-010) and the Analysis Service (FR-003) read from this store; nothing reads from the audio callback's ring. Only the current track is retained (003's "next" item keeps its existing encoded prefetch); a 10-minute 44.1 kHz stereo track MUST fit in ≤ 256 MB; beyond the bound audio is not retained and seeks/analysis into it fall back to the streamed contract (FR-010's 50 ms; FR-005's placeholder). Sample format and growth strategy are plan decisions. *(Prompt: "sample-accurate on fully decoded audio", "within 10 ms", "pulls decoded buffers"; 003 US-4 AS1; Constitution V, VIII; NFR-2.7; Clarifications)*

### Key Entities

- **Analysis (waveform subset of DM-5)**: Per-track-identity record holding the waveform overview (multi-resolution peak set), the analyzer version that produced it, and a status (`pending`, `partial`, `complete`, `failed`). This slice populates and consumes only the waveform-related fields; beat grid, key, and loudness fields exist in the schema but are not produced here.
- **Track-Time Coordinate Space**: The mapping between a position on the waveform view (screen/pixel coordinates, at any zoom/scroll state) and a position in track time (and vice versa), re-projected consistently whenever the detail view zooms or scrolls, so that the playhead and future overlays (markers, loop region, plugin overlays) stay correctly aligned.
- **Playhead**: The current playback position, continuously rendered on both the overview and the detail view, sourced from the audio clock (003) during playback and from the pending seek target during a drag preview.
- **Waveform Cache Entry**: The on-disk, unencrypted persisted form of a track's waveform peak data (mono-folded 8-bit min/max ladder), keyed by track identity and analyzer version, written only when `complete`, distinct from AR-9's encrypted stream cache; has no active eviction policy in this slice.
- **Retained Decoded Store**: The current track's decoded PCM, held in memory on the engine/source side for the track's lifetime (FR-021), with a coverage map of which frame ranges are present. Feeds sample-accurate seeks and the Analysis Service; never exposed outside the engine; released on track change.
- **Detail Window**: The detail view's visible `[start, end]` track-time range, its zoom level (window width), and a `follow` flag; persists for the session, re-centers on seek, and is highlighted on the overview.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: For a track with no valid cached waveform, the waveform overview begins visibly filling in within 1 second of playback starting, in at least 95% of trials.
- **SC-002**: For a streaming track, the waveform's filled portion never lags more than 2 seconds of track time behind the decoded portion, and the overview shows no remaining placeholder within 2 seconds of decoding completing, in at least 95% of trials.
- **SC-003**: Clicking a position on the waveform of a track whose target region is in the retained decoded store resumes playback from that exact sample-accurate position, with the first sample from the new position handed to the output callback within 10 ms of the click, in at least 95% of trials.
- **SC-011**: For a track streamed for the first time on a 10 Mbit/s connection, the waveform overview reaches `complete` within 30 s of playback starting (fill follows the download, not the track's duration), in at least 95% of trials.
- **SC-012**: Master volume changes and effect settings during analysis produce byte-identical cache entries to an analysis run at default settings, in 100% of trials.
- **SC-004**: Reopening or replaying a track with a valid cache entry shows its complete waveform overview within 200 ms of the view appearing, with no progressive-fill placeholder visible, in 100% of trials.
- **SC-005**: After an analyzer version change, 100% of tracks played thereafter show a freshly recomputed waveform rather than a stale cached one.
- **SC-006**: 100% of this slice's seek and zoom interactions (click-seek, drag-seek, zoom in/out, pan, jump-to-start/end) are completable using the keyboard alone, producing the same result as the equivalent pointer action.
- **SC-007**: When no track is loaded, the view shows the pick-a-track hint (never a blank or broken waveform area) in 100% of trials.
- **SC-008**: When analysis fails on a track, the track continues to play normally with no added latency or transport disruption, in 100% of trials, while the view shows "analysis unavailable" or the last valid partial waveform.
- **SC-009**: Across a continuous 10-minute session with a background waveform analysis in progress, the real-time audio path shows zero measurable additional latency or dropout attributable to analysis work, in 100% of trials.
- **SC-010**: Given a specific target moment in a playing track, a user can seek to within 1% of the track's total duration using only the waveform (zooming as needed) in under 10 seconds, in at least 90% of manual test-script trials.

## Assumptions

- Only the currently loaded track is analyzed; upcoming queue items are not pre-analyzed in this slice (see Clarifications).
- Dragging on a waveform previews position visually without audibly scrubbing; the seek commits on pointer release (see Clarifications).
- The waveform peak cache is unencrypted, on-disk, separate from AR-9's encrypted stream cache, and ships without an active eviction policy in this slice; eviction is deferred to the offline-and-library wave's cache manager, which will reuse the same per-track-identity key (see Clarifications).
- Zoom range bounds (200 ms minimum window, whole-track maximum, 30 s initial window) and the keyboard bindings for seek/zoom/pan are conventional internal defaults recorded in the Clarifications binding table and FR-013; seek bindings are 003's unchanged. A later slice may tune the zoom/pan bindings without a contract change.
- Elapsed/remaining time labels refresh at least 4 times per second; the playhead marker itself tracks the audio clock every rendered frame. This is a UI-refresh convention, not a change to 003's ≥60 Hz position-reporting contract.
- This slice extends 001's minimal now-playing transport (title, Play/Pause, Stop, volume, peak meter) and 003's full transport with the visual/waveform surface; it does not modify transport behavior itself. It does replace 003's seek slider and position label with the overview and the elapsed/remaining labels (same accessible contract), and it adds the retained decoded store (FR-021) beneath 003's source/engine pipeline — a plan-level change to how decoded audio is held, not to any user-facing transport behaviour.
- 003's contract test "seek slider commits once per release" is retargeted at the overview; 003's `transport-seek` accessible-name key is reused.
- Analysis failure state and partial progress are per-session memory; only complete waveforms reach disk. The EC-5.9 "user requests re-analysis" path is deferred to the analysis-depth wave.
- Beat grid, key estimate, loudness, markers, loop regions, and plugin overlays are anticipated consumers of the coordinate space and cache infrastructure this slice builds, but none of them are implemented here — they land in later slices per the breakdown coverage map.
