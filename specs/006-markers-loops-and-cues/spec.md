# Feature Specification: Markers, Loop Regions, and Cue Points

**Feature Branch**: `feature/006-markers-loops-and-cues`

**Created**: 2026-09-17

**Status**: Clarified (2026-09-17, clarify pass) — no open [NEEDS CLARIFICATION] markers, no human escalations; ready for `/speckit-plan`

**Input**: User description: "Let a practicing musician mark a passage, loop it gaplessly, and find it again tomorrow — without any plugin. Markers, loops, and cues are host primitives so that later plugins can share them and so they outlive any plugin. A marker is a sample-accurate named point in a track with a color, a kind (point, region-start/region-end pair, or cue), an owner (host or, later, a plugin), a transient flag, and visibility. The user can create, rename, recolor, move, and delete markers from the now-playing view, drag them on the waveform (the detail view zooms while dragging so a marker lands within 5 ms), and nudge them by a configurable step (default 10 ms) from the keyboard. A track holds at least 64 markers; the 65th is refused with an inline 'marker limit reached'. A loop region is an A/B marker pair with an armed state. When armed and the playhead reaches B, playback continues from A with no audible gap or click: the seam is rendered with a short crossfade (0–50 ms, default 5 ms) that never causes drift relative to the markers, and the loop decision is evaluated on the real-time path by the engine's audio clock, never by UI or script timing. Only one region is armed at a time. A loop can repeat N times then release; default is infinite. If the user seeks outside an armed region, the loop stays armed and re-engages only when the playhead reaches B from inside. A cue point is a point marker with a slot 1–8; jumping to a cue seeks instantly and keeps the current play state. Markers, regions, and cues persist per track identity and are restored whenever the track loads, with atomic writes so a crash mid-write never corrupts earlier markers. The empty state reads 'No markers — press I to set A'. Acceptance: when A is placed after B, they swap. When A equals B, the loop cannot be armed and the UI says why; when the region is shorter than the crossfade, the crossfade shrinks to fit. When a loop wraps 1,000 times on cached audio, the rendered loop length deviates by 0 samples and never accumulates drift. When the user reopens a track the next day, all markers and the loop region are back (the armed state is not)."

**Source**: [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) — FR-5.1 Markers, FR-5.2 Loop regions, FR-5.3 Cue points, FR-6.1 Engine (clock and loop evaluation), FR-11.3 Per-track state, DM-6 Marker, DM-7 LoopRegion, DM-9 TrackStateEntry, EC §4 Markers/loops/cues, NFR §1 Performance and latency (NFR-1.2, 1.3), NFR §2 Reliability (NFR-2.8), JTBD-1, JTBD-7. Prerequisites: 005-now-playing-waveform (waveform overview/detail, `TimeSpace`, `DetailWindow`, playhead, overlay hook).

**Scope boundary**: Does not cover beat snapping, sections, per-track state export, plugin-owned markers, or the Section Loop plugin panel — only the host-level primitives and their UI.

- Q: EC-4.2 reads "cannot arm; crossfade reduced to fit if region is between 1 ms and the crossfade length" — is a region shorter than its crossfade but ≥ 1 ms armable or not? → A (D, breakdown prompt: "when the region is shorter than the crossfade, the crossfade shrinks to fit" is listed as an acceptance behaviour, i.e. the loop still works): **armable**. Rule: a region with `B − A ≥ 1 ms` (at the source sample rate, rounded down to whole frames) is armable and its *effective* crossfade is `min(configured, B − A)`; a region with `B − A < 1 ms` (including `A == B`) is not armable and the UI shows the inline reason. The earlier edge-case bullet that said otherwise is realigned below.
- Q: What exactly is the seam crossfade (which audio is mixed, and where does the loop length come from)? → A (A, the common DAW/practice-tool "pre-roll" seam; simplest way to guarantee a constant period of exactly `B − A` frames): the seam mixes the outgoing `x` frames that end at B with the incoming `x` frames that end at A (equal-power), so that the frame rendered immediately after the seam is exactly frame A; the loop period between consecutive seams is therefore exactly `B − A` frames regardless of `x`. The effective `x` is further reduced to `min(x, A)` when fewer than `x` frames exist before A (A = 0 → hard cut, still gapless and still 0-sample). `x = 0` is a valid setting (hard cut). Testable: after N wraps the cursor is at `A + ((elapsed − A) mod (B − A))` frames.
- Q: What happens when the playhead reaches B but the seam's audio (frames `[A − x, A)` and `A` onward) is not yet in the retained decoded store (track still streaming, decode-ahead behind, or store `Failed`/partial)? → A (A, NFR-1.2 scopes the 0-sample guarantee to "cached audio"; the conventional fallback is the ordinary seek, never silently ignoring the loop): the host still jumps to A, but through the ordinary seek path used by 005 (an audible gap is possible, the region stays armed, wraps-so-far still increments). The gapless/0-sample/no-click guarantees (FR-008, FR-010, SC-001, SC-002) apply only when the store covers the seam. Arming a region MUST request caching of the region's audio (from `A − x`) ahead of the playhead so the seam becomes gapless promptly on a streaming track.
- Q: Is there a key to add a plain point marker and a key to arm/disarm the current loop region? The specify pass bound `I`/`O`/cues only. → A (A, conventional practice-tool defaults; no collision with 001–005 bindings `Space`, `Ctrl/Cmd+1..5`, `Ctrl/Cmd+F`, `/`, `Ctrl/Cmd+Q`, or 005 §3): `M` adds a point marker at the playhead; `L` toggles armed/disarmed on the current loop region (refused with the inline reason when the region is incomplete or `< 1 ms`). Both, like `I`, `O`, `1`–`8`, `Shift+1`–`8`, are active whenever the Now Playing view is shown and no text field has focus (the same scope as 003's `Space`), on the physical digit/letter keys with modifiers (identical on all three platforms). `1`–`8` on an empty slot is a no-op (no message). While an inline rename is open, only the text field receives keys (`Enter` commits, `Esc` cancels). `Esc` while a marker is focused (not dragging, not renaming) returns focus to the detail waveform.
- Q: What happens to a loop region when one of its endpoint markers is deleted? → A (A, mirrors the creation flow — `I` alone yields a region with only A): deleting one endpoint leaves the region **incomplete** (the other marker stays, the region is disarmed and unarmable until the missing endpoint is set again with `I`/`O`); deleting the last remaining endpoint deletes the region. An incomplete region persists as-is and its single marker counts toward the 64 limit.
- Q: Which region is "current" for `I`/`O`/`L`, and may regions overlap? → A (A, simplest rule consistent with the specify-pass decision): the current region is the one most recently created (via `I` on a track with no region, or the marker list's "new loop region" action) or most recently selected (selecting either of its endpoint markers, or its list row). Regions may overlap; only the armed one affects playback.
- Q: How do edits to an *armed* region take effect? → A (D, Constitution I / FR-6.1.2 buffer-boundary rule): moving A/B (drag, nudge, `I`/`O`, swap) or changing crossfade/repeat count on an armed region is applied on the real-time path at the next buffer boundary; a seam already in progress completes with the old bounds; if the playhead is outside the new bounds after the edit, FR-012's "armed but inactive" rule applies. "Inside" is defined as `A ≤ position < B`, however the playhead got there (natural playback from before A, a seek, or a cue jump).
- Q: Repeat-count bounds and reset? → A (A): repeat count is `1..=1000` or infinite (default infinite); wraps-so-far resets to 0 every time the region is armed; after the Nth wrap the region disarms itself and playback continues past B. Arming while paused/stopped does not start playback (arming is not a transport action).
- Q: Where is the nudge step configured, and with what bounds? → A (D, 001's settings contract and Settings › Playback category exist): `settings.toml` `[markers] nudge_step_ms = 10`, range `1..=1000` (out-of-range clamped, as 001), exposed as a numeric setting in Settings › Playback (`setting-nudge-step`). MIDI nudge (FR-5.2.6) is out of scope — no MIDI slice exists.
- Q: Default names, colours and visibility of new markers? → A (A, consistent with 005's "theme tokens only" rule): the colour is a persisted index `0..=7` into a fixed 8-entry accent palette defined in `theme.rs` (stable across theme changes); defaults by kind: region markers `0`, point markers `1`, cues `2`. Recolour cycles the palette (keyboard) or picks from the 8 swatches (pointer). Default names: point → "Marker n" (n = number of point markers on the track + 1); region-start/region-end and cue markers → empty name, with the UI always rendering the role label ("A"/"B", cue slot number) in front of the name. On an A/B swap the *roles* (kinds) swap and each marker keeps its own name. `visible` is always `true` in this slice (no hide control). Names are trimmed and limited to 64 characters; committing an empty name for a point marker keeps the previous name.
- Q: When are per-track state writes made, and what are the read rules? → A (D, 001 settings-file contract, reused verbatim as the project convention): the whole track's state is serialized in full on every mutation, debounced 250 ms on the controller thread, and flushed on track change, sign-out and shutdown; written to `<name>.tmp` + `sync_all` + `rename`. Location: `<data_local_dir>/track-state/<encoded track id>` with a `MODPLAYER_TRACK_STATE_DIR` override for tests (the encoding of the `spotify:track:<base62>` identity into a filename is a plan decision, must be filesystem-safe and reversible). Read rules: missing → no markers, no notice; unparseable → no markers + one `Warning` notification (`track-state-unreadable`), file replaced on the next change; newer schema version → no markers + `Warning` (`track-state-newer-version`), file not rewritten until the user changes something; unknown keys ignored; out-of-range values clamped.
- Q: "Clear all" is irreversible — confirm or not? → A (A, established convention for irreversible destructive actions; no undo exists): the marker list's "Clear all markers" is a two-step inline confirmation ("Clear N markers?" → confirm/cancel), keyboard-operable; confirming disarms, removes every marker/region/cue for the track and writes the (empty) state.
- Q: What does the marker list show and where does it live? → A (A): a "Markers" panel in the Now Playing view between the detail waveform and the master volume row, listing every marker sorted by position with: colour swatch, role/kind label (A, B, cue slot, point), name (inline-editable), position as `m:ss.mmm`, and — on loop-region rows — an arm toggle, repeat-count field (blank = infinite), crossfade field (`0..=50` ms, integer), and wraps-remaining while armed; plus "New loop region" and "Clear all markers" actions. The empty state replaces the list with "No markers — press I to set A".
- Q: SC-007 said cue jumps land "within 10 ms" — where does that number come from? → A (D, NFR-1.1 is the authoritative control-to-audio budget): realigned to NFR-1.1 (≤ 20 ms p95, ≤ 35 ms p99 control-to-audio at the performance buffer preset) on cached audio; an uncached cue position goes through the ordinary streaming seek and is exempt from the latency figure.

Recorded as FR-028 so `plan`/`tasks` carry them.
- Q: Same-identity reload in the same session (e.g. the track repeats from the queue) — do markers and armed state survive? → A (D, DM-7 "armed state is session-only" + FR-5.1.2 "restored whenever the track loads"): markers/regions/cues are restored on every load, including a same-session reload; the armed flag is cleared on **every** track change, including reloading the same identity.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Mark a passage and loop it gaplessly (Priority: P1)

While a track plays, the user presses a key to drop a loop-in point and another to drop a loop-out point around a passage they want to drill, arms the loop, and it repeats seamlessly — no click, no gap, no drift — for as long as they need, or for a set number of repeats.

**Why this priority**: This is the entire reason the feature exists (JTBD-1: "loop a precise section and repeat it hands-free, so I can drill it until it is solid"). Nothing else in this spec matters if this doesn't work.

**Independent Test**: While a track plays, press `I` at one point and `O` at a later point, arm the resulting loop region, and verify playback repeats the A–B span indefinitely with no audible seam; then set a repeat count and verify it releases after that many wraps.

**Acceptance Scenarios**:

1. **Given** a track is playing with no markers, **When** the user presses `I` then, later, `O`, **Then** a loop region is created with A at the first playhead position and B at the second, both visible on the waveform.
2. **Given** a loop region with A before B on cached audio, **When** the user arms it (`L` or the list's arm toggle), **Then** playback continues normally until the playhead reaches B, at which point it continues from A with no audible gap or click, rendered with the region's crossfade (default 5 ms).
3. **Given** an armed loop region, **When** the playhead wraps from B to A 1,000 times on cached audio, **Then** the rendered loop length deviates by 0 samples from the intended A–B length and the deviation never accumulates across wraps.
4. **Given** a loop region, **When** the user sets it to repeat 3 times, arms it, and it wraps 3 times, **Then** it automatically disarms (releases) and playback continues past B without looping again.
5. **Given** the user creates a second loop region while a first is armed, **When** the user arms the second, **Then** the first is disarmed automatically — only one region is ever armed at a time.
6. **Given** an armed loop region, **When** the user sets A to a position after B (by drag, nudge, or `I`), **Then** the system swaps their roles so A is always ≤ B and both markers' labels swap accordingly.
7. **Given** a loop region, **When** the user sets A equal to B (or within 1 ms of it), **Then** the region cannot be armed and the UI shows an inline reason why.
8. **Given** a loop region whose length is 3 ms and whose crossfade is the default 5 ms, **When** the user arms it, **Then** arming succeeds and the seam is rendered with an effective 3 ms crossfade.
9. **Given** an armed loop region on a track that is still streaming and whose seam audio is not yet cached, **When** the playhead reaches B, **Then** playback still jumps to A (via the ordinary seek, possibly with an audible gap), the region stays armed, and once the seam audio is cached subsequent wraps are gapless.

### User Story 2 - Markers and loops persist across sessions (Priority: P2)

The user quits and relaunches the app (or just switches away and back to a track) the next day. Every marker and loop region they placed is exactly where they left it, ready to arm again.

**Why this priority**: Without this, the previous story's value resets every session — JTBD-7 ("I want my markers, loops, and effect settings restored, so I pick up where I left off") is the second half of why this feature exists. It only ranks below Story 1 because there is nothing to persist until markers can be created.

**Independent Test**: Create markers and a loop region on a track, quit and relaunch the app (or use the crash-mid-write toggle), reopen the same track, and verify every marker and the loop region (but not its armed state) are restored exactly.

**Acceptance Scenarios**:

1. **Given** a track has markers and a loop region, **When** the user closes and reopens the track (same session or a new one), **Then** every marker's position, name, color, and kind, and every loop region's A/B, crossfade, and repeat count are restored exactly.
2. **Given** a loop region was armed when the track was last open, **When** the track is reopened, **Then** the region is present but **disarmed** — armed state is never persisted.
3. **Given** a per-track write is interrupted mid-write (simulated crash), **When** the app relaunches, **Then** the previously saved markers for that track are intact and uncorrupted.
4. **Given** a track was saved with markers and is later reopened under the same track identity but a shorter duration, **When** the track loads, **Then** markers beyond the new end are clamped to the new end and shown with a warning glyph; markers within the new duration are unaffected.
5. **Given** a track has no markers, **When** its now-playing view is shown, **Then** it reads "No markers — press I to set A" instead of an empty area.
6. **Given** a track has 12 markers, **When** the user activates "Clear all markers" and confirms "Clear 12 markers?", **Then** every marker, region and cue for that track is removed, the empty state appears, and reopening the track later shows no markers; cancelling leaves everything unchanged.
7. **Given** the track's state file is unparseable, **When** the track loads, **Then** it opens with no markers and exactly one `Warning` notification (`track-state-unreadable`); the next change replaces the file.

### User Story 3 - Precisely edit any marker (Priority: P3)

The user renames a marker to something meaningful, recolors it, drags it on the waveform to land it exactly on a transient, or nudges it one keystroke at a time — and deletes markers they no longer need, without ever exceeding the per-track limit unexpectedly.

**Why this priority**: Stories 1–2 already deliver a usable loop that survives the night; this story makes editing markers pleasant and precise rather than merely possible, and is naturally layered on top of marker creation already built by Story 1.

**Independent Test**: Create several markers, rename one, recolor one, drag one on the overview and verify it lands within 5 ms of the intended sample via the detail-view zoom-assist, nudge one by keyboard, delete one, and attempt to exceed 64 markers on a track.

**Acceptance Scenarios**:

1. **Given** a marker exists, **When** the user opens its inline rename (`F2`/`Enter` while focused, or the marker list) and types a new name, **Then** the marker's name updates and persists.
2. **Given** a marker exists, **When** the user recolors it, **Then** its color updates on both waveforms and in the marker list.
3. **Given** a marker exists, **When** the user drags its glyph on the overview, **Then** the detail view recenters and zooms toward the live drag position, the preview follows the pointer, and releasing places the marker within 5 ms of the intended sample; `Esc` cancels with no move.
4. **Given** a marker has keyboard focus, **When** the user presses `←`/`→`, **Then** it moves earlier/later by the configured step (default 10 ms); `Shift+←`/`Shift+→` moves it by 10× the step.
5. **Given** a marker has keyboard focus, **When** the user presses `Delete`, **Then** it is removed; if it was an endpoint of a loop region, the region is disarmed and becomes incomplete (its other endpoint remains and the region is unarmable until `I`/`O` sets the missing one); deleting the last remaining endpoint removes the region.
6. **Given** a track already has 64 markers, **When** the user attempts to create a 65th, **Then** creation is refused with an inline "marker limit reached" message and the existing 64 are unaffected.
7. **Given** a marker is placed by drag, nudge, or keyboard shortcut beyond the track's end, **When** the placement is committed, **Then** it is clamped to the track's end.
8. **Given** a track is playing, **When** the user presses `M`, **Then** a point marker named "Marker n" is created at the playhead with the point-marker default colour, and the marker list shows it sorted by position.
9. **Given** the nudge step is changed to 25 ms in Settings › Playback, **When** the user nudges a focused marker with `→`, **Then** it moves exactly 25 ms later (`Shift+→` moves 250 ms).

### User Story 4 - Jump instantly to a cue point (Priority: P4)

The user drops up to 8 cue points around a track — a solo entry, a bridge, a favorite mix point — and jumps straight to any of them with a single keypress, without disturbing whether the track is playing or paused.

**Why this priority**: Cue points are a convenient, independently useful capability (FR-5.3), but they neither block nor are blocked by the looping value in Story 1 and rank behind the loop and persistence stories that carry the feature's headline value.

**Independent Test**: While a track plays, set cue points in several of the 8 slots at different positions, jump to each with its number key, and verify each jump is instant and precise and never changes play/pause state; verify the same with the transport paused.

**Acceptance Scenarios**:

1. **Given** a track is playing, **When** the user presses `Shift+3`, **Then** a cue point is created (or moved, if slot 3 already had one) at the current playhead position in slot 3.
2. **Given** a cue exists in slot 3, **When** the user presses `3`, **Then** playback seeks instantly to that position and continues playing.
3. **Given** the transport is paused and a cue exists in slot 5, **When** the user presses `5`, **Then** the position updates to the cue and the transport remains paused there.
4. **Given** a track has cues in multiple slots, **When** the user reopens the track later, **Then** every cue's slot and position are restored exactly (Story 2's persistence contract applies to cues too).
5. **Given** slot 7 is empty, **When** the user presses `7`, **Then** nothing happens — no seek, no message.
6. **Given** a track already has 64 markers and slot 4 is empty, **When** the user presses `Shift+4`, **Then** the cue is refused with "marker limit reached"; if slot 4 already had a cue, `Shift+4` moves it (no new marker, no refusal).

### Edge Cases

- A is placed after B (by drag, nudge, or `I`) → the system swaps their roles so A is always ≤ B (EC-4.1).
- A equals B, or the region is shorter than 1 ms → the region cannot be armed and the UI states why. A region of at least 1 ms but shorter than its configured crossfade → armable; the effective crossfade shrinks to the region length (EC-4.2, as resolved in Clarifications).
- A is closer to the track start than the crossfade length (A = 0 in the extreme) → the effective crossfade shrinks to the audio available before A (down to a hard cut); the loop stays gapless and 0-sample.
- The playhead reaches B while the seam's audio is not yet cached (streaming track, decode-ahead behind, store failed/partial) → the host still jumps to A through the ordinary seek path (a gap is possible), the region stays armed, wraps-so-far increments; the gapless guarantees resume once the seam is cached.
- An endpoint of a loop region is deleted → the region is disarmed and becomes incomplete; the remaining endpoint stays; deleting it too removes the region.
- An armed region's A/B/crossfade/repeat count is edited → applied at the next buffer boundary; an in-progress seam completes with the old bounds; playhead now outside the new bounds → "armed but inactive".
- `1`–`8` pressed for an empty cue slot → no-op. `Shift+n` on an occupied slot → moves that cue (never a new marker); on an empty slot at the 64-marker limit → refused with "marker limit reached".
- Any marker/loop/cue shortcut pressed while an inline rename or another text field has focus → consumed by the text field, not the shortcut.
- The per-track state file is missing → no markers, no notice; unparseable → no markers + `Warning` `track-state-unreadable`; newer schema → no markers + `Warning` `track-state-newer-version`, file untouched until the user changes something.
- A marker is placed beyond the track's current end (drag, nudge, or `I`/`O`/cue shortcut at or after the last sample) → it clamps to the track end (EC-4.3).
- A 65th marker is attempted on a track already holding 64 → refused with the inline "marker limit reached" message; no marker is created (EC-4.6).
- A track is reopened under the same identity but a different (shorter) duration than when its state was saved → markers beyond the new end clamp and show a warning glyph; the rest of the saved state is kept unchanged (EC-4.8).
- A loop is armed and the user seeks outside the region → it stays armed, shown as "armed but inactive," and re-engages the gapless jump only when the playhead reaches B again from inside (EC-4.9).
- The app is interrupted mid-write of per-track state (crash, kill, power loss) → the previously saved markers for that track are intact and uncorrupted on next launch (NFR-2.8).
- Two markers end up at the exact same position (via drag or nudge) → both are kept; position collisions are allowed and nothing merges or is rejected.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST allow creating a point marker (`M` at the playhead, or the marker list), and a paired region-start/region-end (loop region) marker set, from the now-playing view without any plugin, each with a sample-accurate position (frames at the source rate), name, color (palette index `0..=7`; defaults by kind: region `0`, point `1`, cue `2`), kind, `owner: host`, `transient: false`, and `visible: true`. Default names: point "Marker n" (n = existing point markers + 1); region and cue markers empty, with the UI always rendering the role label ("A"/"B"/slot number) before the name. Names are trimmed, at most 64 characters; committing an empty name for a point marker keeps the previous one. *(FR-5.1.1, FR-5.1.3; DM-6)*
- **FR-002**: The system MUST support exactly 64 markers per track as the limit, counting all kinds together (point, region-start, region-end, cue — including the single endpoint of an incomplete region); a 65th creation attempt on a track already at 64 (by `M`, `I`/`O` creating a new endpoint, `Shift+n` on an empty slot, or the list) MUST be refused with an inline "marker limit reached" message, leaving the existing 64 unaffected. Actions that move an existing marker (`I`/`O` on an existing endpoint, `Shift+n` on an occupied slot) are never refused by the limit. *(FR-5.1.4; EC-4.6)*
- **FR-003**: The user MUST be able to rename, recolor, move (drag or nudge), and delete any host-owned marker from the now-playing view. *(FR-5.1.3)*
- **FR-004**: Selecting a marker — clicking its glyph on either waveform, or its row in the marker list — MUST move keyboard focus to it, distinct from the waveform's own seek focus, and MUST highlight it. While a marker has focus: `←`/`→` MUST nudge it earlier/later by the configured nudge step (FR-027), `Shift+←`/`Shift+→` MUST nudge it by 10× the step, `Delete`/`Backspace` MUST delete it (per FR-006's endpoint rule), `F2`/`Enter` MUST open inline rename (`Enter` commits, `Esc` cancels), a recolor control MUST cycle the palette, and `Esc` (not dragging, not renaming) MUST return focus to the detail waveform. `Tab` MUST reach every marker glyph and marker-list row in visual order, alongside 005's existing stops. *(FR-5.1.3, FR-5.2.6; extends 005 contracts/ui-waveform.md §3 with no key collisions)*
- **FR-004a**: The view-level shortcuts `M`, `I`, `O`, `L`, `1`–`8`, `Shift+1`–`Shift+8` MUST be active whenever the Now Playing view is shown and no text field has focus (the scope of 003's `Space`), bound to the physical letter/digit keys plus modifiers, identical on macOS, Windows and Linux; while any text field (including inline rename) has focus, keys go to the text field only. *(Constitution X; 003 contracts/ui-surface.md)*
- **FR-005**: Dragging a marker glyph on either waveform (press-and-move beyond the drag threshold) MUST show a live position preview and, for the drag's duration, MUST drive the waveform detail view to recenter on and zoom toward the live drag position, so that both the preview and the eventual drop position are computed from the detail view's finer coordinate space rather than the overview's coarser one; this MUST place the marker within 5 ms of the intended sample regardless of which waveform the drag started on. Release commits the move; `Esc` cancels with no move. *(Prompt; extends 005's `DetailWindow`/`TimeSpace`, FR-012/FR-014)*
- **FR-006**: `I` MUST set (creating if absent) the region-start (A) marker of the current loop region at the playhead; `O` MUST set (creating if absent) its region-end (B) marker — matching the empty-state hint "No markers — press I to set A." A track MAY hold more than one loop region (regions may overlap; only the armed one affects playback); `I`/`O`/`L` act on the **current** region — the most recently created (`I` on a track with no region, or the list's "New loop region" action) or most recently selected (either endpoint marker or its list row). Deleting one endpoint of a region MUST disarm it and leave it **incomplete** (other endpoint kept, unarmable until `I`/`O` restores the missing one); deleting the last endpoint MUST delete the region. Incomplete regions persist as-is. *(Prompt; DM-7)*
- **FR-007**: If a loop region's A marker is positioned after its B marker (by any means), the system MUST swap their roles (kinds) so A is always ≤ B; each marker keeps its own name. If `B − A` is less than 1 ms at the source rate (including A equals B), the region MUST NOT be armable and the UI MUST show an inline reason. *(FR-5.2.4; EC-4.1, EC-4.2)*
- **FR-008**: The system MUST allow arming exactly one loop region per track at a time (`L` toggles the current region; the list row's toggle arms any region); arming a different region MUST disarm the previously armed one; arming an incomplete or `< 1 ms` region MUST be refused with the inline reason. Arming MUST NOT change the transport state (arming while paused stays paused). When armed and the playhead reaches B from inside (`A ≤ position < B`, however it got there), playback MUST continue from A — with no audible gap or click when the seam audio is cached (FR-010); when it is not cached, the host MUST still jump to A through the ordinary seek path (a gap is permitted), keep the region armed, and count the wrap. Arming MUST request caching of the region's audio from `A − crossfade` onward ahead of the playhead. *(FR-5.2.1, FR-5.2.3; NFR-1.2 "on cached audio")*
- **FR-009**: The loop arm/release decision, the seam crossfade render, and the repeat-count evaluation MUST run entirely on the engine's real-time audio path, driven by the engine's monotonic audio clock, and MUST NEVER be evaluated by UI frame timing, a timer, or (in a future slice) plugin script code. *(FR-6.1.4, FR-6.1.5; Constitution I — Real-Time Path Is Sacred)*
- **FR-010**: Each loop region MUST render its seam with a crossfade configurable `0..=50` ms in whole ms (default 5 ms at creation; 0 = hard cut). The seam is the "pre-roll" form: the outgoing `x` frames ending at B are mixed equal-power with the incoming `x` frames ending at A, so the first frame rendered after the seam is exactly A and the period between consecutive seams is exactly `B − A` frames for any `x`. The effective `x` MUST be `min(configured, B − A, A)` (shrinks to the region length, and to the audio available before A). The crossfade MUST NEVER cause the rendered loop to drift relative to its A/B markers: after 1,000 consecutive wraps on cached audio the cumulative deviation is 0 samples (cursor = `A + ((elapsed − A) mod (B − A))`). *(FR-5.2.2; NFR-1.2, NFR-1.3; EC-4.2)*
- **FR-011**: Each loop region MUST support a repeat count — an integer `1..=1000` or infinite (default infinite) — after which it automatically releases (disarms) and playback continues past B; wraps-so-far MUST reset to 0 on every arm; the count and wraps-remaining MUST be visible while the region is armed. *(FR-5.2.5)*
- **FR-011a**: Edits to an armed region (A/B moved by any means, swap, crossfade, repeat count) MUST take effect on the real-time path at the next buffer boundary; a seam already in progress completes with the old bounds; if the playhead is outside the new bounds afterwards, FR-012 applies. *(FR-6.1.2; Constitution I)*
- **FR-012**: If the user seeks outside an armed loop region (`position < A` or `position ≥ B`), the region MUST remain armed (shown as "armed but inactive") and MUST re-engage its jump only when the playhead subsequently reaches B while inside the region (`A ≤ position < B`, reached by natural playback, seek, or cue jump) — a seek that lands past B from outside does not itself trigger a jump to A. *(Prompt; EC-4.9)*
- **FR-013**: A cue point is a point marker carrying a slot number 1–8, unique per track. `Shift+1`…`Shift+8` MUST set the cue in that slot at the current playhead (moving the existing cue if the slot is occupied — never a new marker — or creating one, subject to FR-002); `1`…`8` alone MUST jump to it, and MUST be a silent no-op when the slot is empty. Deleting a cue frees its slot. *(FR-5.3.1)*
- **FR-014**: Jumping to a cue point MUST seek instantly to its position and MUST NOT change the current transport play state: playing stays playing from the new position, paused stays paused there, stopped-with-a-current-track enters `paused` there. *(FR-5.3.1; 005's seek-while-paused/stopped contract)*
- **FR-015**: This slice implements only the plain instant-jump behavior of FR-5.3.1; the SHOULD "hot cue" hold-to-preview-and-return behavior (FR-5.3.2) is not built. *(Prompt scope; Constitution X)*
- **FR-016**: Markers, loop regions (A/B positions, repeat count, crossfade, incomplete regions as-is), and cue points MUST persist per track identity and MUST be restored whenever that track is loaded again, in any session — including a same-session reload of the same identity. A loop region's `armed` flag is session-only and is never persisted — every region is disarmed on restore, and the armed flag is cleared on every track change. Storage: one file per track identity under `<data_local_dir>/track-state/` (override `MODPLAYER_TRACK_STATE_DIR`), unencrypted, with a filesystem-safe reversible encoding of the `spotify:track:<base62>` identity (plan decision). Read rules mirror 001's settings contract: missing → empty, no notice; unparseable → empty + one `Warning` `track-state-unreadable`, replaced on the next change; newer schema → empty + `Warning` `track-state-newer-version`, not rewritten until the user changes something; unknown keys ignored; out-of-range values clamped. *(FR-5.1.2; DM-7; prompt acceptance; 001 contracts/settings-file.md)*
- **FR-017**: Per-track marker/loop/cue state MUST be written atomically (`<name>.tmp` + `sync_all` + `rename`), serialized in full on every mutation, debounced 250 ms on the controller thread (never the real-time path), and flushed on track change, sign-out and shutdown, so that a crash mid-write never corrupts the previously saved state for that track. A failed write keeps the previous file and raises `Warning` `track-state-save-failed` without automatic retry. *(NFR-2.8; 001 write rules)*
- **FR-018**: If a track is reopened under the same track identity but a different (typically shorter) duration than when its markers were saved, any marker whose position now falls beyond the new track end MUST be clamped to the new end and flagged with a warning glyph; the rest of the track's saved markers are unaffected. *(EC-4.8)*
- **FR-019**: A marker placed by any means (drag, nudge, `I`/`O`, cue shortcut) at or beyond the current track's end MUST be clamped to the track end. *(EC-4.3)*
- **FR-020**: When a track has no markers, the now-playing view MUST show the empty-state hint "No markers — press I to set A" in place of an empty marker area. *(Prompt)*
- **FR-021**: The Now Playing view MUST include a "Markers" panel between the detail waveform and the master volume row listing every marker for the current track sorted by position, each row showing colour swatch, role/kind label (A, B, cue slot, point), inline-editable name, position as `m:ss.mmm`, and — on loop-region rows — an arm toggle, repeat-count field (blank = infinite, else `1..=1000`), crossfade field (`0..=50` ms), and wraps-remaining while armed; plus "New loop region" and "Clear all markers" actions. "Clear all markers" MUST be a two-step inline confirmation ("Clear N markers?" → confirm/cancel, keyboard-operable) that disarms and removes every marker, region and cue for the track and writes the empty state; it is scoped to this slice's data only — sections and other plugin-scoped per-track state remain untouched and out of scope. *(FR-11.3.3, scoped)*
- **FR-022**: Every marker, loop-region, and cue interaction introduced in this slice MUST be operable by keyboard alone and MUST expose an accessible name, role, and state, consistent with 001–005. *(NFR-6.1, NFR-6.2; Constitution X)*
- **FR-023**: All user-facing strings introduced in this slice (empty-state hint, "marker limit reached", the region-too-short/incomplete-region arming reasons, "Clear N markers?" confirmation, default marker names, cue/loop labels, `setting-nudge-step`, the `track-state-*` warnings, accessible names/descriptions) MUST be externalized; English (en-US) is the only shipped locale in this slice, consistent with 001–005. *(NFR-7.1; Constitution X)*
- **FR-024**: The `owner` attribute on every marker created in this slice MUST be `host`; this slice MUST NOT build any plugin-facing API to create, own, or modify markers, since no plugin runtime exists yet. *(DM-6; Constitution II; scope boundary — "plugin-owned markers")*
- **FR-025**: This slice MUST NOT implement beat-grid snapping (FR-5.1.5, EC-4.7), sections (FR-5.4), per-track-state export/import (FR-11.3.4), or the Section Loop plugin panel (FR-13.1). *(Scope boundary)*

### Key Entities

- **Marker (DM-6)**: A sample-accurate (frames at source rate), named (≤ 64 chars, may be empty for region/cue kinds), colored (palette index `0..=7`) point in a track: kind (`point`, `region_start`, `region_end`, or `cue`), cue slot (1–8, only for `cue`), owner (`host` in this slice), transient (always `false` here), and visibility (always `true` here).
- **LoopRegion (DM-7)**: References an A (`region_start`) and/or a B (`region_end`) marker — a region with only one endpoint is *incomplete* and unarmable — plus an armed flag (session-only, never persisted), a repeat count (`1..=1000` or infinite), wraps-so-far (reset on arm), and a seam crossfade (`0..=50` ms; effective value `min(configured, B − A, A)`). A track may hold several, possibly overlapping, loop regions; at most one is armed at a time; one is the *current* region for `I`/`O`/`L`.
- **Cue Point**: The `cue` kind of Marker, distinguished by its 1–8 slot; jumping to it seeks instantly without changing play state.
- **Per-Track Marker State**: The persisted, atomically-written collection of a track's markers, loop regions, and cue points, keyed by track identity and restored whenever the track loads; scoped to this slice's data only (not the broader FR-11.3/DM-9 per-track state, which also covers sections and plugin data).
- **Marker Focus / Current Loop Region**: The marker currently holding keyboard focus for nudge/rename/recolor/delete, and the loop region `I`/`O` currently act on.
- **Drag Zoom-Assist**: The temporary recentering/zooming of the waveform detail view, driven by an in-progress marker drag, that makes ≤5 ms marker placement possible from either waveform.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A user can create a two-marker loop region on cached audio and hear it repeat with no audible gap or click, in at least 95% of trials.
- **SC-002**: An armed loop region's rendered length deviates by 0 samples from its intended A–B length after 1,000 wraps on cached audio, in 100% of trials, with no accumulation across wraps, for any crossfade `0..=50` ms including regions shorter than the crossfade and A = 0.
- **SC-003**: Dragging a marker on either waveform places it within 5 ms of the intended sample, in at least 95% of trials.
- **SC-004**: Nudging a focused marker with the keyboard moves it by exactly the configured step on every keypress, in 100% of trials.
- **SC-005**: The 65th marker-creation attempt on a track is refused with the inline limit message, in 100% of trials, with the existing 64 unaffected.
- **SC-006**: Placing A after B swaps them; setting `B − A < 1 ms` refuses arming with a visible reason; a region of ≥ 1 ms but shorter than its crossfade arms with the crossfade shrunk to fit — each in 100% of trials.
- **SC-007**: Jumping to any of the 8 cue slots on cached audio meets NFR-1.1's control-to-audio budget (≤ 20 ms p95, ≤ 35 ms p99 at the performance preset) and never changes the transport's play/pause state, in 100% of trials for the state rule.
- **SC-013**: With the seam audio uncached, an armed loop still jumps to A at B (100% of trials) and becomes gapless within one wrap of the seam becoming cached.
- **SC-014**: Every marker/loop/cue state file survives a simulated crash mid-write, an unparseable file loads as empty with exactly one warning, and "Clear all" followed by reload yields no markers — 100% of trials.
- **SC-008**: Reopening a track in a new session restores 100% of its markers and loop regions (positions, names, colors, crossfade, repeat count) with every loop region disarmed.
- **SC-009**: A simulated crash mid-write to per-track state never corrupts the previously saved markers for that track, in 100% of trials.
- **SC-010**: A loop armed and then seeked outside its region stays armed and does not jump until the playhead reaches B from inside, in 100% of trials.
- **SC-011**: Every marker/loop/cue action available via pointer has a keyboard equivalent producing the same result, in 100% of trials.
- **SC-012**: A track reopened with a shorter duration than when it was saved clamps and flags only the markers beyond the new end, leaving the rest exactly as saved, in 100% of trials.

## Assumptions

- A track may hold multiple, possibly overlapping, loop regions; `I`/`O`/`L` act on the current one (most recently created or selected), and starting an additional region is an explicit marker-list action (Clarifications). A region with one endpoint deleted stays as an incomplete, unarmable region.
- The seam is the pre-roll crossfade defined in FR-010 (effective length `min(configured, B − A, A)`); regions of ≥ 1 ms are armable. When the seam audio is not cached, the wrap falls back to the ordinary seek (gap permitted) and the gapless guarantees apply only on cached audio (NFR-1.2's own qualifier).
- Keys: `M` point marker, `I`/`O` A/B, `L` arm toggle, `Shift+1..8` set cue, `1..8` jump; all view-scoped like 003's `Space`, inactive while a text field has focus.
- The nudge step lives in `settings.toml` `[markers] nudge_step_ms` (`1..=1000`, default 10), Settings › Playback; MIDI nudge deferred.
- Per-track state writes and read rules mirror 001's settings-file contract (250 ms debounce, full serialize, `.tmp` + `sync_all` + `rename`, warning keys `track-state-unreadable` / `-newer-version` / `-save-failed`).
- No beat-grid snapping exists in this slice — the snap toggle and EC-4.7's "snap pending" glyph are deferred entirely to the slice that ships beat-grid analysis.
- The FR-5.3.2 "hot cue" hold-to-preview-and-return gesture is not built; cues are plain instant jumps only.
- Per-track marker/loop/cue state is stored unencrypted (not decoded audio; no Constitution V trigger), in its own `track-state/` file per track identity, separate from 005's analysis cache and AR-9's encrypted stream cache, written atomically.
- The `owner` field is always `host` in this slice; plugin-owned/transient markers and the plugin-conflict edge cases (EC-4.4, EC-4.5) are deferred until the plugin runtime lands (Constitution II).
- FR-11.3.2's "state restored before `track_changed` is delivered to plugins" ordering is honored internally (state loads before the track is marked ready) even though no plugin event bus exists yet to observe it.
- The marker color palette is a fixed 8-entry set of theme-token accent colors in `theme.rs` (consistent with 005's "no new literals" rule), persisted as an index, not a free-form color picker; defaults by kind (region 0, point 1, cue 2).
- FR-021's "view and clear" scopes FR-11.3.3 to markers/loop regions/cues only; sections and plugin-scoped track state remain untouched and out of scope.
- Keyboard bindings for marker create/select/nudge/rename/recolor/delete (`M`, `I`, `O`, `L`, `Shift+1`…`8`, `1`…`8`, arrows while a marker is focused, `F2`, `Delete`) are conventional practice-tool/DJ defaults chosen to avoid any collision with 005's waveform-focused bindings; a later slice may retune them without a contract-breaking change.
