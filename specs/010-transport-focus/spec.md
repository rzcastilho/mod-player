# Feature Specification: Transport Focus Arbitration

**Feature Branch**: `feature/010-transport-focus`

**Created**: 2026-09-19

**Status**: Clarified (2026-09-19, specify pass + clarify pass) — no open [NEEDS CLARIFICATION] markers, no human escalations; ready for `/speckit-plan`

**Input**: User description: "When several plugins can move the playhead, let the user decide which one is in charge so they never fight, and guarantee the user always wins over any plugin. At any moment exactly one party holds transport focus: the host or one plugin. Only the focus holder's programmatic transport commands (play, pause, seek, arm or disarm loops) take effect; every other plugin is an observer and its transport requests return `no_focus`. The user can always issue transport commands through the host UI, keyboard, or (later) MIDI, and commands from other controllers on the account count as user commands; user commands take precedence over any plugin. A plugin acquires focus by request and the host grants it according to the user's focus policy: manual (only the user assigns focus), auto on interaction (a plugin gains focus when the user interacts with its transport controls; a host user action returns focus to the host), or first request wins (the first plugin to request focus per track keeps it). Default is auto on interaction. The previous holder receives `focus_revoked` and drops to observer; the new holder receives `focus_granted`. A Transport panel shows which plugin holds focus and which have requested it; the user can hand focus to any plugin or take it back. When the focus-holding plugin is disabled, suspended, or crashes, focus returns to the host immediately and any loop that plugin had armed is disarmed — persisted markers stay, because the loop state belongs to the plugin and the markers belong to the track. Acceptance: when plugin X holds focus and plugin Y calls seek, Y receives `no_focus` and the playhead does not move. When the user presses the host's loop-toggle shortcut while a plugin holds focus under the auto policy, the toggle applies and focus returns to the host. When a remote controller pauses while a plugin holds focus, playback pauses and the plugin receives `play_state_changed`. When the focus holder is suspended for exceeding its budget, the Transport panel shows \"host\" within the same second and the armed loop is released."

**Source**: [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) — FR-3.3 Transport focus, FR-7.4 Conflicts and ordering (FR-7.4.3), Part 5 §5 Events (host→plugin) (`focus_granted`/`focus_revoked`), Part 5 §6.1 Transport (`transport.control` request surface), Part 9 §5 Key flows (5.3 Transport focus contention), J-8 Reorder and resolve effect chain and transport focus (JTBD-13), EC §3 Playback and transport (EC-3.4), EC §4 Markers, loops, cues (EC-4.4), JTBD-13. **Prerequisites**: [009-plugin-runtime-and-permissions](../009-plugin-runtime-and-permissions/spec.md) — the plugin runtime, the Capability Gateway, and the `transport.control` capability whose contended-request placeholder (`request_focus()` while another plugin holds focus returns `invalid_state`) this slice replaces with real arbitration.

**Scope boundary**: Does not cover effect-chain ordering (008), presets that snapshot focus (006-practice-depth/003), or the MIDI path (004-performance/001) — only focus arbitration, the three policies, and the Transport panel.

- Q: The auto-on-interaction policy grants focus "when the user interacts with a plugin's transport controls," but plugin-contributed UI (`ui.panel`/`ui.overlay`) is out of scope of this slice's only prerequisite (009) and ships in 011-plugin-ui-contributions — what counts as "interacting with a plugin's transport controls" here? → A (D, this slice's own Transport panel is the only plugin-specific transport surface that exists before 011; Constitution X — the user must always have a working override): the qualifying interaction, in this slice, is the user clicking "Give focus" on a specific plugin's row in the Transport panel. Once 011 ships plugin-contributed transport widgets, using one of those becomes an equivalent qualifying interaction (that slice's job to wire); this spec's auto-on-interaction acceptance is fully testable through the panel alone.
- Q: FR-3.3.5 defines "first request wins (the first plugin to request focus per track keeps it)" — does focus persist across a track change under the other two policies, and does a policy change move the current holder? → A (D, prompt's own Q-7 note "the spec implies persistent until changed"; JTBD-13 "when I use several plugins **at once**" describes an ongoing session, not a per-track reset): under *manual* and *auto on interaction*, the holder persists across track changes until the user reassigns it, disables/suspends the holder, or the holder releases; only *first request wins* is track-scoped — the "first requester" designation resets on every track change, and the current holder (host or plugin) is handed back to the host at that reset so the next `request_focus()` call establishes the new track's first-wins holder. Switching the policy itself never revokes the current holder; the new policy governs only future contention.
- Q: Under each policy, what does `request_focus()` return, and what happens to a request that cannot be granted immediately? → A (D, AR-17's refusal design plus FR-3.3.3 "acquires focus by request"; the six-code refusal set has no "pending" code, so a recordable-but-not-yet-granted request must not be reported as a Gateway error): `request_focus()` always returns success and records the caller as a pending requester; a real focus change is communicated separately via `focus_granted`/`focus_revoked`, not via the call's return value. Under *manual*, a request is recorded and surfaced in the Transport panel's requester list but is never auto-granted; only the user's own "Give focus" action grants it. Under *first request wins*, the very first `request_focus()` after a track loads (or after the policy resets, per the item above) is granted immediately; every later call in the same track window is recorded but not granted while a holder exists. Under *auto on interaction*, `request_focus()` alone never grants (the qualifying interaction, above, does); a plugin that only calls the API without a matching panel interaction stays a recorded, ungranted requester. A plugin already holding focus that calls `request_focus()` again is a no-op success.
- Q: When the holder stops holding focus involuntarily (disabled, suspended, or crashed) or voluntarily (`release_focus()`), does any pending requester get auto-promoted? → A (D, symmetry with the item above — the policy that governs *how* focus was acquired also governs how a vacancy is filled): focus always returns to the host first, per FR-3.3.6/the prompt's acceptance text, regardless of policy or reason. Under *first request wins* only, the host immediately re-evaluates the pending queue and grants the earliest still-pending, still-loaded requester (if any), becoming the track's first-wins holder from that point; under *manual* and *auto on interaction*, the vacancy stays with the host until the user acts (a "Give focus" click, or, under auto, the qualifying interaction), even if requesters are queued.
- Q: Does `focus_granted`/`focus_revoked` broadcast to every plugin holding `transport.control`, or only to the two plugins directly affected? → A (D, FR-3.3.3 "the previous holder is notified and demoted"; the prompt's own acceptance text names exactly two recipients): only the outgoing holder receives `focus_revoked` and only the incoming holder receives `focus_granted`. Other plugins learn the current holder only by reading the Transport panel (host UI) or, in a later slice, an explicit query; no broadcast event exists in this slice.
- Q: Is the focus policy a global, account-level preference or per-track/per-session? → A (D, FR-3.3.5 describes "the user's focus policy" as singular and un-scoped; nothing in Part 4/5/9 ties it to a track): one global setting, changeable at any time from the Transport panel (J-8 DP-8.3's "auto-focus on interaction" toggle), applying to every track and every plugin; it is not part of any per-track state and is not affected by track changes (only *first request wins*'s per-track "first" designation resets on track change, per above).

- Q: FR-002 said a focus-holding plugin "MUST NOT receive a focus change from a user command alone," yet FR-005's auto-on-interaction policy returns focus to the host on a host user transport action — and the prompt's acceptance text treats a remote-controller pause (`play_state_changed`, no focus change) differently from a keyboard loop-toggle (focus returns). Which user commands revoke focus under auto? → A (D, prompt acceptance + EC-3.4 + Part 9 §5.3 step 3 read together; INT-2.4 makes remote commands *win* like host commands but says nothing about focus): under **auto on interaction** only, a transport action the user performs **locally** — through the host UI (pointer) or the keyboard (and, in 004-performance/001, MIDI bound to a host action) — returns focus to the host as part of the same action. A command from a **remote controller on the account** is a user command for precedence (it always wins) but is never an "interaction" for focus purposes: it changes focus under **no** policy; the holder receives only the ordinary playback-state event. Under manual and first request wins, no user transport command of any origin changes focus. FR-002 is realigned accordingly.
- Q: Which local host actions count as "transport actions" for the auto-policy revoke? → A (A, the set of playhead/play-state/loop mutations — the same class a plugin's `transport.control` surface covers): exactly the 007 catalog's transport actions (`play`, `pause`, `toggle`, `stop`, `next`, `previous`, `seek_forward_step`, `seek_backward_step`), the loop action (`toggle current loop region`), the eight `jump to cue slot n` actions (they move the playhead), and their pointer equivalents (transport buttons, the seek slider / click-to-seek on the waveform, the loop toggle control, cue jump buttons). **Not** transport actions for this purpose: `volume_up`/`volume_down` and the volume slider, every marker action (add point marker, set A/B, nudge, clear all, and 006's rename/drag/delete/recolor), `set cue slot n`, queue edits, navigation, effect-chain and tempo actions, and any Transport-panel control other than "Take back."

The armed loop stays armed exactly as it is; the demoted plugin can no longer `disarm_loop()` it (`no_focus`), but the user's loop toggle (`L`/list/button) acts on it at any time, a new holder's `arm_loop` supersedes it per 006 FR-008, and the track change clears it as usual. Only disable, suspension, and crash disarm (FR-007). Note the auto-policy acceptance case is unaffected: there the user's own loop toggle is what changes the loop, not the focus transition.
- Q: FR-3.3.4 / J-8 say the panel lists "plugins that have requested" focus and the user "clicks a different plugin"; the prompt says "the user can hand focus to any plugin." Does the panel list every eligible plugin or only requesters? → A (D, the prompt is the feature's stated intent and is the stricter reading): the panel lists **every enabled, non-suspended plugin holding `transport.control`** (a plugin without that permission cannot hold focus and is not listed), each row carrying a "Give focus" control; rows with an outstanding request are marked as requesting and show their request order (1st, 2nd, …) so the J-8 "who has requested it" view is preserved. Granting focus to a plugin that never called `request_focus()` still delivers `focus_granted`.
- Q: When is a pending request cleared, and does it survive a track change? → A (A, follows each policy's own scope rule, above): a pending request is cleared when it is granted; when its plugin is disabled, suspended, crashes, or is uninstalled (FR-011); when its plugin calls `release_focus()` while pending (the call withdraws the request — the only way a plugin can un-ask; still a success return); and, under **first request wins only**, on every track change (the per-track window ends). Under manual and auto on interaction, pending requests persist across track changes until one of the other events occurs. Re-calling `request_focus()` while pending is a no-op success and does not change the plugin's queue position.
- Q: Under first request wins, the user clicks "Take back" while requesters are pending — does FR-006's immediate refill hand focus straight back to a plugin? → A (D, Constitution X: the user must be able to take control back in one action and keep it): **no**. FR-006's auto-refill applies only to vacancies created by `release_focus()`, disable, suspension, or crash. A user "Take back" makes the host the track's first-wins holder for the rest of that track: no plugin is auto-granted until the next track change resets the window (or the user gives focus manually). Likewise a user "Give focus" under first request wins simply makes that plugin the holder; it is not re-evaluated against earlier requesters.
- Q: What is a "track change" for the first-request-wins reset? → A (D, reuse 009 FR-016's definition): every emission of the `track_changed` event — including a queue advance or repeat that re-loads the same track — is a track change; a seek within the current track is not.
- Q: Does the focus policy survive an app restart? → A (A, it is a user preference like 007's keybinding overrides; the *holder* state is session-scoped per the Assumptions): **yes** — the policy is persisted in the existing `settings.toml` under the same atomic-write contract 007 uses, with `auto on interaction` when absent; on relaunch the policy is restored and the holder is the host with an empty request queue (FR-012). The Transport panel's selector is its only edit surface in this slice (no Settings-page duplicate; 011+ may add one).
- Q: What do `focus_granted`/`focus_revoked` carry, in what order are they delivered, and how does adding them square with Constitution IX given 009 declared them undelivered? → A (D, Part 5 §5 table describes both events as "which plugin holds focus now"; §5.3 step 2 orders revoke before grant; Constitution IX — minor versions only add): both events carry one payload field, `holder`: `"host"` or the plugin identifier that holds focus after the transition. On a plugin→plugin transition, `focus_revoked` is delivered to the outgoing holder before `focus_granted` is delivered to the incoming one. When the auto policy returns focus on a local host action, the demoted holder receives `focus_revoked` first and then the resulting playback/loop event (`play_state_changed`, `loop_armed`/`loop_disarmed`, or the `position` update), in that order on its own scheduler. Shipping the two events is an additive **minor** bump of plugin API v1 (schema-generated per Constitution IX) accompanied by the written change request in the PR; 009's FR-028 "MUST NOT deliver" exclusion for these two events is superseded by this slice, exactly as 009 FR-027 anticipates.

After restart or re-enable it starts as an observer with no pending request and must call `request_focus()` afresh (joining the end of the queue). Hot-reload focus retention is 002-developer-mode's job.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Exactly one party is in charge, and the user always wins (Priority: P1)

While plugin X holds transport focus, another plugin's transport calls are refused and the playhead never moves for anyone but X. Whatever policy is active, the user's own transport commands — from the host UI, the keyboard, or a remote controller on the account — always take effect immediately, and under the default policy a host action even takes focus back from a plugin automatically.

**Why this priority**: This is the prompt's headline guarantee ("guarantee the user always wins over any plugin") and the reason transport focus exists at all (JTBD-13, "so they do not fight"). Nothing else in this feature matters if two plugins can still both move the playhead, or if the user can ever be blocked by a plugin.

**Independent Test**: With plugin X holding focus, have plugin Y call `seek`; verify `no_focus` and no playhead movement. Separately, with a plugin holding focus, press the host's loop-toggle shortcut; verify the toggle applies immediately and, under the default policy, focus returns to the host. Separately, trigger a remote-controller pause while a plugin holds focus; verify playback pauses and the plugin receives `play_state_changed`.

**Acceptance Scenarios**:

1. **Given** plugin X holds transport focus, **When** plugin Y calls `seek` (or `play`, `pause`, `toggle`, `skip_next`, `skip_previous`, `arm_loop`, `disarm_loop`), **Then** Y receives `no_focus`, the playhead does not move, and no other plugin state changes (prompt acceptance; FR-3.3.1, FR-7.4.3).
2. **Given** any plugin holds transport focus, **When** the user issues a transport command locally through the host UI or keyboard (e.g., the loop-toggle shortcut), **Then** the command applies immediately regardless of who holds focus, and, under the auto-on-interaction policy, focus returns to the host as part of the same action — the plugin receives `focus_revoked` (`holder: "host"`) and then the resulting loop/playback event; its armed loop, if the action did not toggle it, stays armed (prompt acceptance; FR-3.3.2; Clarifications).
3. **Given** a plugin holds transport focus under any policy, including auto on interaction, **When** a remote controller on the account (e.g., another Connect-capable device) sends pause, **Then** playback pauses immediately (host-user precedence), the focus-holding plugin receives `play_state_changed`, and no focus change occurs — the plugin still holds focus (EC-3.4; Clarifications).
4. **Given** the focus-holding plugin is suspended for exceeding its CPU or memory budget (009 FR-011), **When** the suspension takes effect, **Then** the Transport panel shows "host" as the holder within the same second, and any loop region that plugin had armed is disarmed while its persisted markers remain untouched (prompt acceptance; FR-3.3.6).
5. **Given** the focus-holding plugin is disabled or crashes, **When** that happens, **Then** focus returns to the host immediately, any armed loop it owned is disarmed, and the plugin's own persisted markers are unaffected (FR-3.3.6).

### User Story 2 - The user picks how focus gets assigned (Priority: P2)

The user chooses one of three focus policies — manual, auto on interaction (the default), or first request wins — and each governs contention differently: manual never reassigns focus without an explicit user action, auto on interaction grants focus the moment the user engages a specific plugin's transport control, and first request wins locks focus, per track, to whichever plugin asked first.

**Why this priority**: Different musicians work differently — some want total manual control during a set, others want the plugin they're touching to just take over. This is the configuration surface that makes Story 1's single-holder guarantee usable in practice (JTBD-13), and it depends on Story 1's arbitration already existing.

**Independent Test**: Set the policy to manual; have two plugins call `request_focus()`; verify neither is granted until the user clicks "Give focus" in the Transport panel. Switch to auto on interaction; interact with one plugin's transport control in the panel; verify it is granted immediately. Switch to first request wins; have plugin A request before plugin B on a fresh track; verify A is granted and B's later request is recorded but not granted; change tracks and have B request first; verify B is now granted.

**Acceptance Scenarios**:

1. **Given** the policy is manual, **When** two plugins each call `request_focus()`, **Then** neither is granted focus, both appear in the Transport panel's requester list, and focus changes only when the user explicitly picks one (FR-3.3.5).
2. **Given** the policy is auto on interaction (the default) and no plugin holds focus, **When** the user interacts with a specific plugin's transport control (in this slice, its "Give focus" row in the Transport panel), **Then** that plugin is granted focus immediately, receiving `focus_granted` (FR-3.3.5; prompt).
3. **Given** the policy is first request wins and a track has just loaded with no holder, **When** plugin A calls `request_focus()` before plugin B does, **Then** A is granted focus and receives `focus_granted`; **When** B calls `request_focus()` afterward, **Then** B's request is recorded in the panel but not granted while A holds focus (FR-3.3.5).
4. **Given** the policy is first request wins and plugin A holds focus for the current track with plugin B pending, **When** the track changes (`track_changed` fires), **Then** A's hold ends, focus returns to the host, B's pending request is cleared, and the next plugin to call `request_focus()` on the new track becomes its first-wins holder (Clarifications).
5. **Given** the user switches the active policy while a plugin holds focus, **When** the switch happens, **Then** the current holder is unaffected; the new policy governs only the next contention event (Clarifications).
6. **Given** the policy is first request wins, plugin A holds focus and plugin B is pending, **When** the user clicks "Take back," **Then** the host holds focus for the rest of the track, B is **not** auto-granted (it stays listed as requesting), and B is granted only if the user clicks "Give focus" on it or a new track loads and B requests first (Clarifications).
7. **Given** the policy is first request wins, plugin A holds focus and plugin B is pending, **When** A calls `release_focus()`, **Then** B receives `focus_granted` immediately and becomes the track's holder (FR-006).
8. **Given** any policy and the app is relaunched, **When** the Transport panel is opened, **Then** the policy selector shows the value chosen before relaunch, the holder is "host," and no requester is listed (FR-012).

### User Story 3 - The Transport panel shows and controls who's in charge (Priority: P3)

The user opens the Transport panel at any time and sees exactly which plugin (or "host") holds focus and which plugins have requested it; from there they can hand focus to any listed plugin or take it back to the host in one action, and they can change the active focus policy.

**Why this priority**: Stories 1 and 2 make focus arbitration correct and configurable, but without visibility and a direct control surface the user has no way to exercise the manual reassignment Story 2 depends on, or to confirm Story 1's guarantee is holding (J-8 step 3, JTBD-13).

**Independent Test**: With one plugin holding focus, a second one pending, and a third enabled `transport.control` plugin that never requested, press `T` in the Now Playing view; verify the panel opens and shows the current holder, all three plugins with the pending one marked "requesting · 1st," and "Give focus"/"Take back" controls; exercise both controls and verify the state and events match.

**Acceptance Scenarios**:

1. **Given** the Transport panel is open, **When** the user views it, **Then** it shows the current holder (a specific plugin, by name, or "host") and one row per enabled, non-suspended plugin holding `transport.control`, each row marked as requesting (with its request order) or not; a plugin without `transport.control`, or one that is disabled or suspended, has no row (J-8 step 3; FR-3.3.4; Clarifications).
2. **Given** a plugin holds focus and another plugin is listed (requesting or not), **When** the user clicks "Give focus" on it, **Then** the previous holder receives `focus_revoked` (`holder: <new plugin id>`) first and drops to observer, the chosen plugin receives `focus_granted` next, its pending request (if any) is cleared, the previous holder's armed loop (if any) stays armed, and the panel updates to reflect the new holder (prompt; FR-3.3.3; Clarifications).
3. **Given** a plugin holds focus, **When** the user clicks "Take back" (host), **Then** focus returns to the host, the plugin receives `focus_revoked` (`holder: "host"`), and the panel shows "host" as the holder (FR-3.3.4; Constitution X user-override guarantee).
4. **Given** the Transport panel is open, **When** the user changes the focus policy (manual / auto on interaction / first request wins), **Then** the new selection takes effect immediately for future contention, is reflected in the panel, and is written to `settings.toml` (J-8 DP-8.3; FR-012).
5. **Given** the Transport panel and every control it introduces, **When** the user operates it, **Then** each element (holder display, plugin rows, "Give focus," "Take back," the policy selector) is reachable and operable by keyboard alone with an accessible name (Constitution X, NFR-6.1/6.2).
6. **Given** the Now Playing view is shown and no text field has focus, **When** the user presses `T`, **Then** the Transport panel opens (and closes on a second press), exactly as the header "Transport" toggle does; the panel stays open across a track change (FR-013; mirrors 008 US1 scenario 1a).

### Edge Cases

- Two plugins race to arm a loop region: only the focus holder's `arm_loop` succeeds; the other receives `no_focus` (EC-4.4).
- The focus holder is disabled, suspended, or crashes while it has an armed loop: focus returns to the host immediately, the loop is disarmed, and the plugin's own persisted markers are left untouched — the loop state belongs to the plugin, the markers belong to the track (prompt; FR-3.3.6).
- A remote controller on the account issues a transport command while a plugin holds focus, under **any** policy including auto on interaction: it is treated as a user command, takes effect immediately, and the focus holder is only informed via the ordinary playback-state event (`play_state_changed`), never a focus change (EC-3.4; Clarifications).
- The user presses a host keyboard shortcut (or uses the pointer equivalent) that maps to a transport action — play/pause/toggle/stop/next/previous/seek step/loop toggle/cue jump, or waveform click-to-seek — while a plugin holds focus: the action applies regardless of policy; under auto on interaction specifically, focus also returns to the host as part of the same action, `focus_revoked` reaching the plugin before the resulting playback/loop event (prompt acceptance; distinguishing this from manual/first-request-wins, where the host action applies but the holder is unchanged, per Clarifications).
- The user changes volume, adds/moves/deletes a marker, sets A/B, sets a cue slot, edits the queue, or reorders the effect chain while a plugin holds focus under auto on interaction: none of these is a transport action; focus is unchanged (Clarifications).
- Focus leaves a plugin for a non-fault reason (user "Give focus"/"Take back," auto-policy host action, `release_focus()`, first-request-wins track reset) while it has an armed loop: the loop stays armed; the plugin can no longer disarm it (`no_focus`), the user's loop toggle can, and a new holder's `arm_loop` supersedes it (Clarifications).
- A plugin calls `request_focus()` while it already holds focus, or while already pending: no-op success, no event fires, queue position unchanged.
- A plugin calls `release_focus()` while it does not hold focus: success; if it had a pending request, the request is withdrawn and its row stops showing "requesting"; otherwise a pure no-op (extends 009's behavior; no error).
- A pending requester is disabled, suspended, crashes, or is uninstalled before ever being granted focus: its request is cleared and its row leaves the Transport panel (FR-011).
- The user clicks "Give focus" on a listed plugin that never called `request_focus()`: it is granted and receives `focus_granted` all the same (Clarifications).
- A suspended or disabled former holder is restarted or re-enabled: it returns as an observer with no pending request and must call `request_focus()` again; it is never re-granted automatically (Clarifications; hot-reload retention per EC-6.17 is 002-developer-mode's).
- Under first request wins, the current holder voluntarily calls `release_focus()` mid-track: focus returns to the host, and the earliest remaining pending requester (if any) is granted immediately as the track's holder from that point (Clarifications).
- The focus policy is changed while requesters are pending: existing pending requests are preserved and are evaluated under the new policy's rules from that point forward (e.g., switching from manual to first request wins does not retroactively grant the earliest manual-era requester; the next qualifying event under the new policy decides).
- The app is relaunched: the focus **policy** is restored from `settings.toml` (auto on interaction if absent or unreadable); the holder is "host" and the request queue is empty until a plugin next requests, matching a fresh session (no persisted focus holder across restarts; consistent with 008's session-scoped chain and 009's session-scoped plugin state) (FR-012).
- The user presses `T` while a text field has keyboard focus, or outside the Now Playing view: nothing happens (Now Playing scope, per 007 FR-018); the header toggle still works whenever the Now Playing view is shown (FR-013).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: At any moment, exactly one party — the host, or exactly one plugin — MUST hold transport focus. Only the focus holder's programmatic transport commands (`play`, `pause`, `toggle`, `seek`, `skip_next`, `skip_previous`, `arm_loop`, `disarm_loop`) MUST take effect; every request of that kind from any other plugin MUST return `no_focus` and produce no side effect. *(FR-3.3.1, FR-7.4.3)*
- **FR-002**: The user's own transport commands — issued locally through the host UI or the keyboard, and commands originating from any other controller on the user's account (e.g., a remote Connect-capable device) — MUST always take effect immediately, regardless of which party currently holds focus, and MUST take precedence over any plugin command. A focus-holding plugin affected by such a command MUST receive the corresponding playback/loop event (`play_state_changed`, `loop_armed`/`loop_disarmed`, `position`). A **remote-controller** command MUST NOT change focus under any policy. A **local** host transport action changes focus only under the auto-on-interaction policy, as FR-005 specifies; under manual and first request wins it never does. *(FR-3.3.2; INT-2.4; EC-3.4; Clarifications)*
- **FR-002a**: For the purposes of FR-005's auto-on-interaction revoke, a "local host transport action" is exactly: the 007 catalog actions `host.transport.{play,pause,toggle,stop,next,previous,seek_forward_step,seek_backward_step}`, `host.loop.toggle` (toggle current loop region), and `host.cues.jump_{1..8}`, plus their pointer equivalents (transport buttons, the seek slider and waveform click-to-seek, the loop toggle control, cue jump buttons). Volume actions and the volume slider, every marker action (including 006's rename/drag/delete/recolor), `set cue slot n`, queue edits, navigation, effect-chain and tempo actions, and Transport-panel controls other than "Take back" are NOT transport actions and MUST NOT change focus. *(Clarifications)*
- **FR-003**: A plugin MUST acquire focus only by calling `request_focus()`. This call MUST always return success and record the caller as a pending requester; whether focus is actually granted is governed by the active policy (FR-005–FR-007) and communicated only via `focus_granted`/`focus_revoked`, never via the call's own return value. Calling `request_focus()` while already holding focus MUST be a no-op success with no event. This supersedes 009's placeholder, where `request_focus()` returned `invalid_state` whenever another plugin already held focus. *(FR-3.3.3; Clarifications; 009 Clarifications)*
- **FR-004**: When focus changes from one holder to another, the outgoing holder (if a plugin) MUST receive `focus_revoked` and immediately drop to observer status; the incoming holder (if a plugin) MUST receive `focus_granted`. No other plugin MUST receive either event for that transition. `release_focus()` MUST always succeed and return focus to the host; calling it while not the holder MUST be a no-op success. *(FR-3.3.3; Part 5 §5 event catalog)*
- **FR-005**: The user MUST be able to select one of exactly three focus policies, changeable at any time and taking effect immediately for future contention without altering the current holder: **manual** — focus is granted or taken back only by an explicit user action in the Transport panel, never automatically; **auto on interaction** (the default) — focus is granted to a plugin the moment the user performs the qualifying interaction with that plugin's transport control (in this slice, clicking "Give focus" on its Transport-panel row), and a *local* host transport action (FR-002a; never a remote-controller command) returns focus to the host as part of the same action; **first request wins** — the first plugin to call `request_focus()` after a track loads (or after the previous first-wins holder's track ends) is granted focus for that track, and later requests in the same track window are recorded but not granted while a holder exists. *(FR-3.3.5; J-8 DP-8.3; Clarifications)*
- **FR-006**: Under **first request wins** only, focus is scoped to the current track (every `track_changed` emission, per 009 FR-016, including a same-track repeat or queue advance): the "first requester" designation resets on every track change, the outgoing track's holder is returned to the host, the pending queue is cleared, and vacancies created by `release_focus()`, disable, suspension, or crash are immediately refilled from the earliest still-pending requester, if any, without waiting for a new `request_focus()` call. A user "Take back" is NOT such a vacancy: it makes the host the track's holder and no plugin is auto-granted until the next track change (or a user "Give focus"); a user "Give focus" makes the chosen plugin the holder without re-evaluation against earlier requesters. Under **manual** and **auto on interaction**, the holder and the pending queue persist across track changes until explicitly reassigned, withdrawn, or vacated, and a vacancy is never auto-filled from the pending queue — it stays with the host until the user (manual) or the qualifying interaction (auto) grants it. *(FR-3.3.5; Constitution X; Clarifications)*
- **FR-007**: When the focus-holding plugin is disabled, suspended, or crashes, focus MUST return to the host immediately (before any policy-driven refill per FR-006), and any loop region that plugin had armed MUST be disarmed; the plugin's own persisted markers MUST remain untouched, since loop-arm state belongs to the plugin and markers belong to the track. This transition MUST be reflected in the Transport panel within the same second the suspension, disable, or crash occurs. Focus loss for any **other** reason (user "Give focus"/"Take back," the auto-policy host action, `release_focus()`, the first-request-wins track reset) MUST NOT disarm or otherwise alter the plugin's armed loop; the demoted plugin's subsequent `disarm_loop()` returns `no_focus`, the user's loop toggle and a new holder's `arm_loop` act on it as usual. *(FR-3.3.6; FR-7.3.1 rationale; prompt acceptance; Clarifications)*
- **FR-008**: A Transport panel MUST show, at all times: the current focus holder (a specific plugin by name, or "host"), and one row per enabled, non-suspended plugin holding `transport.control`, each marked as requesting (with its request order among outstanding, ungranted `request_focus()` calls) or not requesting; plugins without `transport.control`, disabled plugins, and suspended plugins MUST NOT be listed. From the panel, the user MUST be able to grant focus to any listed plugin in one action (whether or not it requested; the grant delivers `focus_granted` and clears its pending request), and take focus back to the host in one action, regardless of the active policy. The panel MUST also expose the focus-policy selector (manual / auto on interaction / first request wins). *(FR-3.3.4; J-8 step 3, DP-8.3; prompt "hand focus to any plugin"; Clarifications)*
- **FR-009**: Every control the Transport panel introduces (holder display, plugin rows and their requesting badge, "Give focus," "Take back," the policy selector, the header toggle) MUST be fully operable by keyboard alone and expose an accessible name, role, and state; every string is externalized (en + pt-BR). *(Constitution X; NFR-6.1, NFR-6.2, NFR-7.1)*
- **FR-010**: A plugin that is not the focus holder MUST remain a pure observer of transport: it MUST continue to receive permission-gated observation events it is entitled to (e.g., `play_state_changed`, `position`) unaffected by its observer status, while every transport-mutation request it issues returns `no_focus`. *(FR-3.3.1; 009 FR-008 refusal contract)*
- **FR-011**: A pending request MUST be cleared when it is granted; when its plugin is disabled, suspended, crashes, or is uninstalled (the plugin is then also removed from the panel and from any policy's refill consideration); when its plugin calls `release_focus()` while pending (a success return that withdraws the request); and, under first request wins only, on every track change (FR-006). Re-calling `request_focus()` while pending MUST be a no-op success that keeps the plugin's queue position. *(Derived from 009's plugin-lifecycle teardown; Clarifications)*
- **FR-012**: The focus policy MUST be persisted in the existing `settings.toml` under 007's atomic-write contract whenever it is changed, and restored on launch; when the key is absent or unreadable the policy is `auto on interaction`. The focus holder and the pending queue MUST NOT be persisted: every launch starts with the host holding focus and an empty queue. The Transport panel's selector is the policy's only edit surface in this slice. *(FR-3.3.5 default; Clarifications)*
- **FR-013**: The Transport panel MUST be reachable from the Now Playing view by a header "Transport" toggle and by one new navigation action `host.nav.toggle_transport_panel` (display label "Toggle Transport panel," category navigation, kind `trigger`, scope Now Playing, `repeats_while_held: false`) with default binding `T`, listed and rebindable in the 007 shortcut map like every other action and not conflicting with any shipped default. The panel MUST stay open across a track change. *(FR-9.1.1; mirrors 008's `E`/`host.nav.toggle_effect_chain`; Clarifications)*
- **FR-014**: `focus_granted` and `focus_revoked` MUST each carry exactly one payload field, `holder` — `"host"` or the identifier of the plugin holding focus after the transition — and be delivered only to the plugin gaining or losing focus (FR-004). On a plugin→plugin transition `focus_revoked` MUST be dispatched to the outgoing holder before `focus_granted` to the incoming one; on an auto-policy host action the demoted holder MUST receive `focus_revoked` before the resulting playback/loop event. Both events are delivered on the plugin's own scheduler in order (009 FR-028). Adding them is an additive **minor** version bump of plugin API v1, made in the single machine-readable schema with a written change request in the PR; 009 FR-028's exclusion of these two events is superseded. *(Part 5 §5; Part 9 §5.3; Constitution IX; Clarifications)*

### Key Entities

- **Transport Focus State**: A single, global, session-scoped record of which party (host or exactly one plugin) currently holds transport focus and the ordered queue of plugins with an outstanding, ungranted focus request. Not persisted across app restarts; not part of any per-track saved state (only the *first request wins* policy's "current track" bookkeeping is track-scoped, and that resets on track change, not on save).
- **Focus Policy**: One of `manual` | `auto_on_interaction` | `first_request_wins`; a global user preference persisted in `settings.toml` (FR-012), default `auto_on_interaction`; read by the arbitration on every contention event, never per track or per plugin.
- **Focus Event**: `focus_granted` / `focus_revoked`, payload `{ holder: "host" | <plugin id> }`, delivered only to the plugin gaining or losing focus (FR-014).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In 100% of trials, a non-focus-holding plugin's transport mutation request (`play`/`pause`/`toggle`/`seek`/`skip_next`/`skip_previous`/`arm_loop`/`disarm_loop`) is refused with `no_focus` and produces zero observable playback or loop-state change.
- **SC-002**: In 100% of trials, a user-issued transport command (host UI, keyboard, or a remote controller on the account) takes effect regardless of which party holds focus, within the same control-to-audio latency budget (NFR-1.1) it met before this slice — focus arbitration adds no measurable latency to the user path.
- **SC-006**: Under auto on interaction, in 100% of trials a local host transport action (FR-002a) returns focus to the host in the same action and a remote-controller command leaves the holder unchanged; under manual and first request wins, no user command of either origin changes the holder.
- **SC-007**: The focus policy chosen before an app relaunch is shown as selected after relaunch in 100% of trials, while the holder is "host" and the request queue is empty.
- **SC-003**: When the focus holder is suspended, disabled, or crashes, the Transport panel reflects "host" as the new holder within one second of the event, and any loop it had armed shows disarmed in the same window, in 100% of trials.
- **SC-004**: A user can reassign transport focus to any listed requester, or take it back to the host, in exactly one action from the Transport panel, in 100% of trials across all three focus policies.
- **SC-005**: Under the first-request-wins policy, across 20 consecutive track loads with two competing plugins, the plugin that calls `request_focus()` first is granted focus in 100% of loads, and the other is never granted while the first holds focus for that track.

## Assumptions

- The focus policy is a single global user preference (not per-track, per-plugin, or per-session), selectable from the Transport panel and persisted in `settings.toml` (FR-012), consistent with FR-3.3.5's singular, un-scoped phrasing.
- The Playback Controller already distinguishes remote-controller input (`RemoteCommand`) from local host actions, so FR-002's local-vs-remote focus rule needs no new input classification.
- Q-7 from the source document (per-track vs persistent focus) is resolved as the breakdown prompt itself leans: persistent under manual/auto, per-track only under first request wins. Its blast radius is confined to this slice's arbitration rules (no data model, no cross-feature contract), so it was defaulted rather than escalated.
- Because plugin-contributed UI (`ui.panel`/`ui.overlay`) ships in 011-plugin-ui-contributions, this slice's auto-on-interaction policy is fully exercised and testable through the Transport panel's own "Give focus" control; once 011 ships, using a plugin's own transport widget becomes an equivalent qualifying interaction without requiring changes to this slice's arbitration rules.
- Transport focus state is session-scoped only: it is not saved to disk and does not survive an app restart (mirrors 008's session-scoped effect chain and 009's session-scoped orphan/suspension bookkeeping); a preset that would snapshot focus is explicitly out of scope (006-practice-depth/003).
- The Transport panel is a new UI surface introduced by this slice (no earlier feature reserves a placeholder for it, unlike the Plugins section in 009); it is opened like 008's Effect Chain panel (header toggle + `T`, FR-013); its exact layout inside the Now Playing view is a plan-time decision, not a specification constraint.
- Performance Mode's "minimal indicator" for a focus-affecting plugin fault (FR-10.1.4) and hot-reload focus retention (EC-6.17) belong to 004-performance/003 and 002-developer-mode respectively; the Transport panel's holder display is this slice's only fault-time surface.
- `focus_granted`/`focus_revoked` are delivered only to the two plugins directly party to a given transition (matching the prompt's own acceptance wording); no broadcast "who holds focus" event is introduced for uninvolved plugins in this slice.
- A "crash" is treated identically to a suspension for focus-return purposes, consistent with 009's fault-isolation model where a plugin fault of any kind (panic, hang, budget breach) results in the same Suspended state and the same host-side cleanup sequence.
