# Feature Specification: Named Actions and Keyboard Shortcuts

**Feature Branch**: `feature/007-keyboard-actions-and-shortcuts`

**Created**: 2026-09-17

**Status**: Clarified (2026-09-17, specify pass + clarify pass) — no open [NEEDS CLARIFICATION] markers, no human escalations; ready for `/speckit-plan`

**Input**: User description: "Let a musician with hands on their instrument drive the whole player from the keyboard, and lay the foundation for MIDI and plugin-registered controls later. Every host operation — transport (play, pause, toggle, stop, next, previous, seek step, volume up/down), markers (set A, set B, nudge active marker earlier/later, clear), loops (toggle loop), cues (set cue 1–8, jump to cue 1–8), effect-chain and navigation commands — is exposed as a named action with a stable identifier, a label, and a kind: trigger (fires once) or continuous (carries a value). Actions live in a central Action & Binding service that dispatches invocations to the owning component with minimal latency; later slices let plugins register actions in their own namespace and let MIDI messages bind to the same actions. The host ships a default shortcut set covering all transport, marker, loop, cue, and volume actions, so the player is fully operable without a mouse. Defaults include `I` set A, `O` set B, `L` toggle loop, `[` / `]` nudge the active marker, and `+` / `-` for tempo steps once effects exist. Modifier conventions follow each platform. A settings page shows the shortcut map; the user can rebind any shortcut, and a single action can carry several bindings. Conflicts are detected and displayed: when two bindings claim the same key, the map flags both and neither is active until the user resolves it. A shortcut bound to an action whose owner is currently disabled is kept but shown greyed and inactive. Acceptance: when the user presses `I` then `O` then `L` during playback, markers A and B appear on the waveform and the loop arms, with no mouse involved. When the user rebinds \"toggle loop\" to a key already bound to \"play/pause\", the map shows the conflict and neither fires until one is changed. When a binding is rebound and the app restarts, the custom binding is still in effect."

**Source**: [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) — FR-9.1 Actions, FR-9.2 Keyboard, DM-14 Action, DM-15 Binding, Part 9 §3 Core services (AR-8 Action & Binding Service), EC §8 Controls, NFR §6 Accessibility (NFR-6.1, NFR-6.2), NFR §9 Portability (NFR-9.2), §1 Primary personas (Marina), JTBD-5 (Théo). Prerequisites: [001-walking-skeleton](../001-walking-skeleton/spec.md) (transport, nav rail, Settings shell and its "Controls" category), [003-streaming-playback-and-queue](../003-streaming-playback-and-queue/spec.md) (transport, queue), [004-search-and-library-browse](../004-search-and-library-browse/spec.md) (search focus, nav rail), [005-now-playing-waveform](../005-now-playing-waveform/spec.md) (waveform keyboard), [006-markers-loops-and-cues](../006-markers-loops-and-cues/spec.md) (marker/loop/cue keyboard).

**Scope boundary**: Does not cover MIDI, global (app-unfocused) shortcuts, media keys, or plugin-registered actions — only host actions and in-app keyboard bindings.

Can one press fire twice? → A (A, standard toolkit convention — a focused widget's own keys are the accessibility contract NFR-6.1 depends on, so they must never be shadowed): strict precedence, exactly one consumer per key press: (1) a focused text field consumes every key; (2) otherwise the focused widget's own key handling (button activation on `Space`/`Enter`, slider arrows, 004's list keys, 005's waveform-focus keys, 006's marker-focus keys) consumes the key if it handles it; (3) otherwise the registered action whose scope is live consumes it; (4) otherwise the key is ignored. - Q: Does OS key auto-repeat (key held down) re-fire a registered trigger action? Today 006's nudge keys and 005's seek keys repeat while held (egui counts repeat events as presses); a repeating `Space` would flip play/pause several times per second. → A (A, convention: repeat only for stepwise actions): each action carries a `repeats_while_held` attribute. `true` for the 4 nudge actions, `volume_up`/`volume_down`, `seek_forward_step`/`seek_backward_step` and the 2 tempo actions (each auto-repeat event fires the action again, preserving 006's nudge feel); `false` for every other action (fires exactly once per physical key-down; repeat events ignored). Written into FR-001/FR-019 and the catalog.
- Q: What exactly identifies a "key" in a Binding — a physical scancode or the layout-resolved logical key — and which modifiers are bindable? 001–006 match on egui's logical `Key` values (`Key::Slash`, `Key::Plus`/`Key::Equals`, …), not scancodes. → A (D for key identity — keep what 001–006 use, Constitution X; A for the modifier set — the smallest set that is platform-uniform): a binding's key is the toolkit's **logical key** (the layout-resolved key value, e.g. the key that produces `/` on the active layout); punctuation therefore follows the user's layout, letters/digits/arrows/function keys are layout-stable. Bindable modifiers are exactly three, platform-uniform: **Primary** (`Ctrl` on Windows/Linux, `Cmd` on macOS), **Shift**, **Alt** (`Option` on macOS). The physical macOS `Control` key is not a bindable modifier in this slice — capture rejects a chord that includes it inline ("Use ⌘ instead"), so no binding can exist that means one thing on macOS and nothing elsewhere. - Q: The catalog listed `effects.tempo_step_up` as `+` / `=` — one binding or two? And the two tempo actions are `continuous` while `volume_up`/`volume_down` (the same "step" shape) are `trigger` — which is it? → A (A, consistency: a "step" is a trigger regardless of the parameter it steps; 005's waveform zoom already accepts `+` *or* `=` as two distinct logical keys): tempo step up ships **two** default bindings, `=` and `+` (two chips; the `Shift+=` chord on a US layout arrives as `+`); tempo step down ships one, `-`. - Q: During binding capture, which keys can never become a binding, and what ends capture besides a key press? → A (A, convention): `Esc` cancels capture (so `Esc` is never capturable); `Tab`/`Shift+Tab` are rejected inline as reserved for focus navigation (NFR-6.1); a chord consisting only of modifiers is rejected (already in FR-007); a chord including the physical macOS `Control` key is rejected (see modifier item); everything else — including `Space`, `Enter`, arrows, function keys, digits, punctuation — is capturable. Capture has no timeout; losing keyboard focus (click elsewhere, window blur) cancels it with no change. Capturing a chord that another simultaneously-reachable action already holds is **accepted** and immediately produces the FR-009 conflict (this is the US3 flow), with the capture control's inline message naming the other action. FR-007 realigned.
- Q: Does a *disabled* action's binding participate in conflict detection? FR-011 realigned.
- Q: What does the filter box match? → A (A, convention): case-insensitive substring match against the action's label and its category label; an empty filter shows the whole catalog; a category header is shown only when at least one of its actions matches; a filter that matches nothing shows an externalized "No actions match" line. FR-006 realigned.
- Q: AR-8 says dispatch has "minimal latency" — is there a testable bound? → A (D, NFR-1.10 "any UI interaction reflects within 100 ms" and NFR-1.1's control-to-audio budget apply unchanged; the dispatcher must not add a hop): a key press MUST be dispatched to the owning component synchronously, in the same UI frame in which the key event was received, with no intermediate queue, thread hop or deferred tick — so the controller call happens no later than the direct per-widget call did before this slice. ## User Scenarios & Testing *(mandatory)*

### User Story 1 - Every transport control has a keyboard shortcut (Priority: P1)

A musician with both hands on their instrument can play, pause, stop, skip to the next or previous track, nudge the position forward or back, and change volume — all from the keyboard, from any view in the app, with no default shortcut left uncovered the way play/pause, stop, next, previous, seek and volume are today.

**Why this priority**: JTBD-5 ("every action I use to be on a physical control … so I never look at the screen") and FR-9.2.1 (MUST) name this as the baseline the whole feature exists to close: today no transport operation has a keyboard path at all (003's contract promised `Space` for play/pause, but the repository never implemented it). Nothing else in this spec matters if basic transport still requires a mouse.

**Independent Test**: While a track plays, press each transport shortcut in turn (toggle, previous, next, seek back, seek forward, volume down, volume up, stop) from the Now Playing view and again from the Library view, and verify each produces the same effect as clicking its equivalent button/control.

**Acceptance Scenarios**:

1. **Given** a track is playing, **When** the user presses `Ctrl/Cmd+→`, **Then** the queue advances to the next track exactly as clicking "Skip forward" would.
2. **Given** a track is playing, **When** the user presses `Ctrl/Cmd+←`, **Then** playback returns to the previous track exactly as clicking "Skip back" would.
3. **Given** a track is playing at position *p*, **When** the user presses `Ctrl/Cmd+Shift+→` / `Ctrl/Cmd+Shift+←`, **Then** the playhead seeks to *p* + 5 s / *p* − 5 s (clamped to the track's `[0, end]`).
4. **Given** master volume is at *v* %, **When** the user presses `Ctrl/Cmd+↑` / `Ctrl/Cmd+↓`, **Then** master volume becomes *v* + 5 / *v* − 5 (clamped to `[0, 100]`), with the same smooth level change the volume slider produces.
5. **Given** a track is playing, **When** the user presses `Shift+Space`, **Then** playback stops exactly as clicking "Stop" would.
6. **Given** a track is playing and no button, text field or list row holds keyboard focus, **When** the user presses `Space`, **Then** playback pauses; pressing it again resumes — the behaviour 003's contract specified, implemented for the first time here.
7. **Given** the Now Playing view has focus, **When** the user presses `I` then `O` then `L`, **Then** markers A and B appear on the waveform and the loop arms — unchanged from 006, with no mouse involved (prompt acceptance).
8. **Given** the Library view is shown and a track is playing, **When** the user presses `Ctrl/Cmd+→` or `Space` (with no list row focused), **Then** the transport responds exactly as it would from Now Playing (transport actions are app-wide, FR-018).
9. **Given** the "Stop" transport button holds keyboard focus, **When** the user presses `Space`, **Then** playback stops (the focused button wins, FR-019) and play/pause is not also toggled — exactly one effect.
10. **Given** `Ctrl/Cmd+↑` is held down, **When** OS auto-repeat delivers further key events, **Then** volume keeps stepping up by 5 % per event; **Given** `Space` is held down instead, **Then** play/pause toggles exactly once (FR-019 `repeats_while_held`).
11. **Given** the Now Playing view is shown, **When** the user presses `Q`, **Then** the queue panel toggles (the default moved off `Ctrl/Cmd+Q`, which macOS reserves for Quit — Clarifications).

### User Story 2 - View and rebind the entire shortcut map (Priority: P2)

The user opens Settings › Controls, sees every action the host exposes grouped by category with its current keyboard binding(s), and can change, add, remove, or reset any of them without touching a config file.

**Why this priority**: FR-9.1.1/FR-9.2.2 (MUST) require every operation to be a discoverable, rebindable named action; this is the central capability the feature adds on top of Story 1's coverage, and everything else (conflicts, persistence, disabled actions) is a property of this same page.

**Independent Test**: Open Settings › Controls, filter to an action by name, add a second binding to it, remove one of its bindings, reset a different action to its default, and verify each change is reflected immediately in the map.

**Acceptance Scenarios**:

1. **Given** Settings › Controls is open, **When** the user types part of an action's label into the filter box, **Then** only matching actions remain visible, grouped by category.
2. **Given** an action's row, **When** the user activates "Add binding" and presses a key combination (not a lone modifier), **Then** that combination is added as a new binding chip for the action; the action now fires from either its old or new binding.
3. **Given** an action already has a binding, **When** the user presses `Esc` during capture, or keyboard focus leaves the capture control (click elsewhere, window loses focus), **Then** no binding is added or changed.
4. **Given** an action already bound to `X`, **When** the user attempts to add `X` again to the same action, **Then** the attempt is rejected inline as a duplicate and no second identical binding is created.
4a. **Given** capture is active, **When** the user presses `Tab`, `Shift+Tab`, a lone modifier, or (macOS) a chord including the physical `Control` key, **Then** the candidate is rejected inline with an externalized reason and capture stays active; **When** the user presses any other key or chord — including `Space`, `Enter`, an arrow or a function key — **Then** it is accepted as the candidate.
4b. **Given** capture is active for "toggle loop", **When** the user presses a chord already held by another currently-reachable action (e.g. `Space`), **Then** the binding is added, the FR-009 conflict is flagged on both rows immediately, and the inline message names the other action.
5. **Given** a binding chip, **When** the user activates its remove control, **Then** that binding is removed immediately; an action may end up with zero bindings, which is not an error state.
6. **Given** an action has been rebound away from its shipped default, **When** the user activates that action's "Reset to default", **Then** its bindings revert exactly to the shipped default set.
7. **Given** several actions have been rebound, **When** the user activates the page-level "Reset all to defaults" and then its inline **Confirm**, **Then** every action's bindings revert to the shipped defaults and no action's `enabled` flag changes; **When** the user instead activates **Cancel**, presses `Esc`, or moves focus away, **Then** nothing changes.
8. **Given** the two tempo actions (registered, disabled, no effect chain exists yet), **When** the user views their rows, **Then** they appear visually de-emphasized ("greyed") relative to enabled rows, their default `=`/`+` and `-` bindings are shown, and they remain fully rebindable and removable despite being inactive.
8a. **Given** the filter box contains `vol`, **When** the map renders, **Then** exactly "Volume up" and "Volume down" are visible under a single "Transport" header; **Given** it contains `transport`, **Then** all ten transport actions are visible (category label matches); **Given** it contains `zzz`, **Then** an externalized "No actions match" line is shown and no rows.
9. **Given** every control on the page, **When** the user reaches it via `Tab` alone, **Then** it exposes an accessible name, role, and state, and is fully operable with the keyboard (NFR-6.1, NFR-6.2).

### User Story 3 - Conflicting shortcuts are caught and must be resolved (Priority: P3)

When the user rebinds an action to a key already claimed by a different, currently-reachable action, the shortcut map immediately shows both as conflicting, and neither one fires until the user changes or removes one side.

**Why this priority**: FR-9.2.2 (MUST) and the prompt's own acceptance scenario name this explicitly; it is a safety net on top of Story 2's rebind capability and has nothing to protect until rebinding exists.

**Independent Test**: Rebind "toggle loop" to the key currently bound to "play/pause toggle," verify the map flags both and that pressing the shared key does neither, then resolve by removing one binding and verify both become active again (each on its own remaining key).

**Acceptance Scenarios**:

1. **Given** "play/pause toggle" is bound to `Space` and "toggle loop" is unbound, **When** the user rebinds "toggle loop" to `Space`, **Then** the map flags both "play/pause toggle" and "toggle loop" as conflicting on `Space`.
2. **Given** the conflict in Scenario 1, **When** the user presses `Space` during playback, **Then** neither action fires (playback does not pause/resume, the loop does not toggle).
3. **Given** the conflict in Scenario 1, **When** the user removes "toggle loop"'s `Space` binding (or changes it to a different key), **Then** the conflict flag clears from both rows and `Space` again toggles play/pause; if a different key was chosen instead, "toggle loop" now fires from that key.
4. **Given** two bindings whose activation scopes can never both be live at once (e.g. a waveform-focused shortcut and a marker-focused shortcut sharing a key, as already shipped by 005/006), **When** the shortcut map is displayed, **Then** neither is flagged as conflicting.
5. **Given** a conflict exists between two actions, **When** the user resolves it by rebinding a third, unrelated action to yet another key, **Then** the original conflict is unaffected by that unrelated change.
6. **Given** "tempo step up" is disabled and bound to `=`, **When** the user rebinds "play/pause toggle" to `=`, **Then** no conflict is flagged and `=` toggles play/pause (disabled actions are excluded from conflict evaluation, FR-009); **When** a later slice enables "tempo step up" with both bindings still on `=`, **Then** the conflict is flagged on both rows at that moment and neither fires from `=`.

### User Story 4 - Custom bindings survive a restart (Priority: P4)

A user who spends a few minutes tuning their shortcut map does not want to redo that work every session.

**Why this priority**: The prompt's own acceptance scenario requires this explicitly; it depends on Story 2's rebind capability existing first and is otherwise independent of Stories 1 and 3.

**Independent Test**: Rebind an action, quit and relaunch the app, open Settings › Controls, and verify the custom binding (and only that customization) is exactly as left.

**Acceptance Scenarios**:

1. **Given** the user rebinds "toggle loop" from unbound to `K`, **When** the app is closed and relaunched, **Then** "toggle loop" is still bound to `K` and every other action's bindings are unchanged.
2. **Given** the settings file's `[keybindings]` table contains an entry naming an action id that no longer exists or a malformed key combination, **When** the app loads, **Then** that one entry is dropped, every other customization still applies, one `Warning` (`keybindings-invalid-entries`) is raised, and the table is rewritten clean on the next successful change.
3. **Given** the settings file is interrupted mid-write (simulated crash), **When** the app relaunches, **Then** the previously saved keybinding customizations are intact and uncorrupted (same guarantee `settings.toml` already provides for every other setting).
4. **Given** no customizations have ever been made, **When** the app loads, **Then** every action uses its shipped default binding and no `[keybindings]` table is required to exist.

---

### Edge Cases

- Two bindings, belonging to different actions with overlapping activation scopes, are set to the same key (by direct rebind or import) → both are flagged conflicting and neither fires until the user changes or removes one (US3).
- A binding whose scope can never coexist with another binding's scope shares the same key → not flagged, matching 005/006's existing context-scoped reuses (US3 AS4).
- A capture attempt records only a modifier key (e.g. `Ctrl` alone, no other key pressed) → rejected inline, no binding created.
- A capture attempt duplicates a binding the same action already has → rejected inline as a no-op, no second identical binding.
- The user removes an action's only binding → the action has zero bindings; this is not an error, and the action stays fully functional through any other invocation surface it has (e.g. a button) or simply becomes keyboard-unreachable until rebound.
- The user rebinds an action to a chord the operating system or window manager intercepts before the app ever receives it (e.g. `Cmd+Q` on macOS, `Alt+F4` on Windows) → the app accepts and stores it like any other binding, but it never fires in practice; a known, undetected platform limitation, not a bug.
- A key is pressed while a text field (including an inline rename) has focus → consumed by the field; no action fires (inherits 006's FR-004a guard, generalized to every registered action — this also closes 004's shipped gap where `/` fired inside a text field).
- A key is pressed while a non-text widget that handles that key has focus (a button on `Space`/`Enter`, the volume slider on `←`/`→`, a marker glyph on `←`, the waveform on `+`) → the widget's own behaviour runs and the registered action does not; never both (FR-019).
- A key bound to a `repeats_while_held: false` action is held down → the action fires once on key-down; OS auto-repeat events are ignored. Held on a `repeats_while_held: true` action (nudge, volume, seek step, tempo) → fires once per auto-repeat event.
- A registered action's key is pressed outside the action's scope (e.g. `I` while the Library view is shown) → the action does not fire and the key falls through to whatever the focused widget does with it, exactly as before this slice.
- Capture receives `Tab`/`Shift+Tab`, a lone modifier, or (macOS) a chord with the physical `Control` key → rejected inline with an externalized reason; capture stays active. `Esc` or loss of keyboard focus → capture cancelled, no change.
- A disabled action's bound key is pressed → nothing happens; the row stays visible and greyed, and its bindings remain freely editable.
- A disabled action's binding shares a chord with an enabled action's binding → not a conflict (disabled bindings are excluded from evaluation); the enabled action fires. The moment the disabled action becomes enabled, the pair is evaluated and flagged like any other conflict.
- A disabled action becomes enabled in a later slice → its stored bindings (default or user-customized) apply immediately with no re-configuration and no data loss.
- The `[keybindings]` table in `settings.toml` is unparseable as a whole → the whole file falls back to its existing `settings-unreadable` handling (defaults for every setting including keybindings); a single malformed entry inside an otherwise valid table is dropped in isolation with `keybindings-invalid-entries` instead.
- `settings.toml` is interrupted mid-write while saving a new binding → the previous, valid keybindings are intact on next launch (same atomic write/rename guarantee as every other setting).
- "Reset all to defaults" is activated while a conflict exists → the conflict is resolved as a side effect, since the shipped defaults never conflict with each other by construction.

The physical macOS `Control` key is not a bindable modifier in this slice. A binding has identical semantics on macOS, Windows, and Linux; the map displays it with platform-native modifier names/glyphs and it is persisted in one platform-neutral encoding (plan-time detail). *(FR-9.1.2; NFR-9.2; DM-15; Clarifications)*
- **FR-004**: The system MUST ship the default bindings in the § Default Action Catalog table. Every default inherited from 001/004/006 is reproduced unchanged except one: `nav.toggle_queue` moves from `Ctrl/Cmd+Q` (dead on macOS, where the OS reserves `Cmd+Q` for Quit) to plain `Q` in the Now Playing scope. `Space` (play/pause toggle) is shipped for the first time. Both step sizes are internal constants in this slice. *(Clarifications)*
- **FR-005**: Invoking an enabled, non-conflicting action's binding MUST dispatch to the same owning component and produce the exact same observable result the operation already produced before this slice (for every action whose binding is inherited from 001/004/006), routed through the central Action & Binding service instead of ad hoc per-widget key matching. Dispatch MUST be synchronous: the owning component's call happens in the same UI frame in which the key event arrived, with no intermediate queue, thread hop or deferred tick, so the dispatcher adds no latency over the direct per-widget call it replaces (NFR-1.10 and NFR-1.1 apply unchanged). *(AR-8; regression safety, Constitution VIII)*
- **FR-006**: Settings MUST gain a shortcut map at the existing "Controls" category (reserved, empty, in 001's Settings registry) listing every action from the catalog, grouped by category, each row showing: label, kind, `enabled` state (visually de-emphasized/"greyed" when `false`), and its current binding(s) as individually removable chips; the page MUST include a text filter (case-insensitive substring match against the action label and its category label; empty shows everything; a category header appears only when at least one of its actions matches; no match shows an externalized "No actions match" line), an "Add binding" affordance per action, and both a per-action "Reset to default" and a page-level "Reset all to defaults." *(FR-9.2.2; NFR-6.1, NFR-6.2; Clarifications)*
- **FR-007**: Activating "Add binding" MUST enter a capture mode where the next key press (with any modifiers) becomes the candidate binding. The following candidates MUST be rejected inline, with an externalized reason, leaving capture active and no binding created: a chord consisting solely of modifier keys; `Tab` or `Shift+Tab` (reserved for focus navigation); on macOS, any chord including the physical `Control` key; a candidate identical to a binding the same action already holds (duplicate). `Esc`, or keyboard focus leaving the capture control (click elsewhere, window blur), MUST cancel capture with no change; `Esc` is therefore never capturable. Capture has no timeout. Every other key or chord — including `Space`, `Enter`, arrows, function keys, digits and punctuation — MUST be accepted; a candidate already held by another currently-reachable action MUST be accepted and MUST immediately produce the FR-009 conflict, with the inline message naming that other action. *(FR-9.2.2; prompt UX; Clarifications)*
- **FR-008**: Removing a binding via its chip MUST take effect immediately; an action reduced to zero bindings is a valid, non-error state and remains otherwise fully functional. *(FR-9.1.2)*

Bindings of a disabled action are excluded from evaluation (never flagged, never block another action); conflicts MUST be recomputed on every load, every binding change and every `enabled` transition, so enabling an action flags any collision it then has. *(FR-9.2.2; prompt acceptance: "toggle loop" vs. "play/pause"; Clarifications)*

Under FR-018's nested scopes (`marker_focused` ⊂ `now_playing` ⊂ `app`) every pair of registered actions is comparable, so within this registry the rule reduces to FR-009; FR-010 exists so a later slice can add a disjoint scope without changing the contract. *(Clarifications; Constitution X)*
- **FR-011**: "Reset to default" (per action) and "Reset all to defaults" (page-level) MUST restore the exact shipped default binding set from FR-004 without altering any action's `enabled` flag, and MUST resolve any conflicts that existed purely between now-reset actions (the shipped defaults never conflict with each other by construction). Per-action reset applies immediately with no confirmation; "Reset all" is a two-step inline confirmation (activate → "Reset all bindings? Confirm / Cancel"; `Esc` or focus loss cancels; no modal dialog). *(Prompt UX; Clarifications)*
- **FR-012**: An action's `enabled` flag reflects whether its owning host component currently supports it, independent of any plugin (none exists yet). While `enabled` is `false`, the action's row and bindings MUST remain visible, fully rebindable, and removable, MUST be shown visually de-emphasized ("greyed"), MUST NOT fire from any of their bindings, and MUST NOT participate in conflict evaluation (FR-009); when a later slice flips the flag to `true`, the stored bindings (default or user-customized) apply immediately with no reconfiguration and conflicts are re-evaluated at that moment. This slice ships exactly `effects.tempo_step_up`/`effects.tempo_step_down` with `enabled: false` as the concrete instance (no effect chain exists yet). *(EC-8.6 pattern; DM-14 `enabled`)*
- **FR-013**: The set of binding customizations that differ from the shipped defaults MUST persist across restarts, written to the existing `settings.toml` under a new `[keybindings]` table using that file's exact write rules (serialize in full on every mutation, debounced, `.tmp` + `sync_all` + atomic rename, previous file kept intact on any write failure with a `Warning`, never on the real-time path) and equivalent read rules (missing table → every action uses its shipped default, no notice; a single entry naming an unknown action id or an unparseable key combination is dropped in isolation with one `Warning` `keybindings-invalid-entries`, the remaining valid entries still apply; the file as a whole being unparseable falls back to the existing `settings-unreadable` handling). *(Prompt acceptance: "restart... still in effect"; 001 `contracts/settings-file.md`, extended)*
- **FR-014**: Every control introduced by this slice (shortcut map rows, filter box, capture mode, chips, conflict indicators, disabled-state styling, reset controls) MUST expose an accessible name, role, and state, and MUST be fully operable by keyboard alone with a logical `Tab` order. *(NFR-6.1, NFR-6.2)*
- **FR-015**: Every user-facing string introduced by this slice (action labels, capture-mode prompt, duplicate/invalid-combination messages, conflict indicator text, disabled-state label, reset confirmations, the two new warning keys) MUST be externalized; en-US is the only shipped locale in this slice, consistent with 001–006. *(NFR-7.1; Constitution X)*
- **FR-016**: This slice MUST NOT implement MIDI device listing, learn mode, MIDI profiles, or continuous-control range/curve/pickup behavior (FR-9.3.*); global (app-unfocused) shortcuts or media-key handling (FR-9.2.3); or any plugin-registered action or plugin-disable interaction (Constitution II — no plugin runtime exists). The namespaced action identifier, `kind`, and `enabled` fields already model the extension points DM-14/DM-15 require so a later slice can add these without a breaking change to this one. *(Scope boundary)*

The slice MUST also ship property-based tests for conflict detection (symmetric; scope-aware; disabled actions never participate; shipped defaults conflict-free), capture-mode validation (reject lone-modifier, `Tab`, macOS `Control`, exact duplicate; accept everything else), and the FR-019 precedence/repeat rules (one consumer per press; repeat honoured only where `repeats_while_held`). *(Constitution VIII)*
- **FR-018**: Every action MUST carry one activation scope, and a binding MUST fire only while its action's scope is live and no text field has focus. This slice defines three nested scopes: **`app`** — anywhere in the main window: all 10 transport actions and all 7 navigation actions; **`now_playing`** — the Now Playing view is shown (nests inside `app`): add marker, set A, set B, clear all markers, toggle loop, the 16 cue actions, toggle queue panel, the 2 tempo actions; **`marker_focused`** — a marker glyph or marker-list row holds keyboard focus (nests inside `now_playing`): the 4 nudge actions. - **FR-019**: Key dispatch MUST have exactly one consumer per key press, in this precedence: (1) a focused text field consumes every key; (2) otherwise the focused widget's own key handling (button activation on `Space`/`Enter`, slider arrows, 004's list keys, 005's waveform-focus keys, 006's marker-focus keys) consumes the key if it handles it; (3) otherwise the enabled, non-conflicting registered action whose binding matches and whose scope is live consumes it; (4) otherwise the key is ignored. A single press MUST never trigger both a widget behaviour and an action. OS auto-repeat events MUST re-fire an action only when its `repeats_while_held` flag is `true` (the 4 nudge actions, `volume_up`/`volume_down`, `seek_forward_step`/`seek_backward_step`, the 2 tempo actions); every other action fires exactly once per physical key-down and ignores repeat events. *(NFR-6.1; Clarifications)*

### Key Entities

- **Action (DM-14)**: A named, dispatchable host operation — identifier (namespaced), label, category, kind (`trigger` | `continuous`), owner (`host` in this slice), an `enabled` flag independent of any plugin, an activation `scope` (`app` | `now_playing` | `marker_focused`), and a `repeats_while_held` flag.
- **Binding (DM-15)**: A keyboard input mapped to exactly one action — one logical key plus any subset of {Primary, Shift, Alt}, platform-uniform. (MIDI-only fields — channel, message type, range, curve, pickup mode — and the `global` flag are reserved by the data model for a future slice and go unused here.)
- **Activation Scope**: The view/focus condition under which an action's bindings are live; this slice's three scopes nest (`marker_focused` ⊂ `now_playing` ⊂ `app`), and none is live while a text field has focus.
- **Action Catalog**: The fixed, versioned list of every action this slice ships (§ FR-002); later slices append to it and never renumber or remove an existing identifier.
- **Binding Conflict**: A transient, computed relationship between two bindings of different, simultaneously-reachable actions that share the same key-plus-modifiers combination; never persisted, recomputed on every load and every binding change.
- **Keybinding Overrides**: The persisted, sparse record (action id → binding list) of only the customizations that differ from the shipped Action Catalog defaults, stored in `settings.toml`.

## Assumptions

- 006's already-shipped marker-nudge scheme (`←`/`→`, `Shift+←`/`Shift+→`, scoped to a focused marker) is retained unchanged; the breakdown prompt's own `[`/`]` mention is superseded prose from before that decision (Clarifications).
- The Action & Binding registry covers exactly the operations the prompt names per category — transport, the eight listed marker operations, loop toggle, the sixteen cue operations, the pre-existing navigation/queue/search-focus shortcuts, and two forward-declared tempo actions. Marker rename/delete/recolor/drag and every waveform pointer/keyboard gesture (005 §2–3) are unaffected and stay outside the registry (Clarifications; Constitution X).
- Discrete `play`, `pause`, and `clear all markers` ship with no default binding — each function is already keyboard-reachable through `toggle` (play/pause) or the existing focusable button (clear-all) — keeping the shipped default map lean.
- New transport defaults (`Space`, `Ctrl/Cmd+←/→`, `Ctrl/Cmd+Shift+←/→`, `Ctrl/Cmd+↑/↓`, `Shift+Space`) follow the desktop-Spotify-client convention already familiar to this product's users (Marina, Théo) and collide with nothing reserved by 001–006. `Space` was promised by 003's contract but never implemented; it is treated as new here. Seek step 5 s and volume step 5 % are internal constants (Clarifications).
- Transport actions are app-wide (scope `app`); markers/loop/cues/queue are Now Playing-scoped; nudges require a focused marker (FR-018). Widening transport beyond 003's "Now Playing has focus" wording is additive and per-action; a later slice can narrow or widen any scope without a data-model change.
- `nav.toggle_queue` moves from `Ctrl/Cmd+Q` to `Q` because macOS reserves `Cmd+Q` for Quit (006's own manual scenario quits the app with it), so the shipped default was dead on one platform; no other inherited default changes.
- The two tempo actions are registered now, disabled, bound to `=`/`+` and `-` per the prompt, purely to exercise the generic disabled/greyed mechanism; no effect chain is built in this slice. Disabled actions are excluded from conflict evaluation, so these bindings block nothing today; a later effects slice that enables them will see any collision flagged at that moment (FR-009), and a collision with a widget-local, non-registered shortcut (e.g. 005's waveform-zoom `+`/`-`) remains an unaddressed limitation until that slice reconciles it.
- Bindings match on the toolkit's logical key (as 001–006 already do) with exactly three platform-uniform modifiers (Primary, Shift, Alt); the physical macOS `Control` key is not bindable in this slice. Chords the OS intercepts before the app (e.g. `Cmd+Q`, `Cmd+Tab`, `Alt+F4`) are accepted by capture but never fire — a known, undetected limitation.
- Key dispatch is strictly one-consumer-per-press (text field → focused widget → registered action), and only stepwise actions honour OS auto-repeat (FR-019).
- Settings › Controls is the existing, previously-empty "Controls" category from 001's eleven fixed Settings categories.
- Keybinding customizations are persisted as a sparse (defaults-diff-only) `[keybindings]` table inside the existing `settings.toml`, reusing its atomic-write contract verbatim; the table's exact internal shape (per-action-id key naming, key-combination string encoding) is a plan-time data-model decision.
- Conflict detection is scope-aware and limited to bindings recorded in this registry; it does not, and in this slice cannot, detect a collision with a widget-local shortcut that was never made a registered action (005's raw waveform keys).
- Global (app-unfocused) shortcuts, media keys, MIDI (device listing, learn mode, profiles, continuous range/curve/pickup), and plugin-registered actions are all out of scope, per the breakdown's own scope boundary; this slice's data shapes are deliberately forward-compatible with all four.
