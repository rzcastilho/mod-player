# Feature Specification: Waveform Legibility and Scrub Feedback

**Feature Branch**: `feature/022-waveform-legibility`

**Created**: 2026-09-28

**Status**: Clarified — specify and clarify passes complete; no items escalated for human decision; ready for `/speckit-plan`

**Input**: User description: "Make the waveform tell the user where they are, where the loop is, and where they are about to seek to — none of which it currently shows clearly. Draw the waveform with two tones so peak and average energy are distinguishable, and give the played portion a different treatment from the unplayed portion so progress is readable without checking the clock. The playhead becomes a clearly visible indicator that meets a minimum contrast ratio against the waveform fill in both themes; today it is a single dark line that nearly vanishes against the dark theme's fill. An armed loop region is shaded across the waveform itself rather than being indicated only by markers in the lane above it, and the shading distinguishes an armed loop from a defined but inactive one. Add hover feedback: moving the pointer across either the overview or the detail waveform shows a scrub position line with the timestamp under the pointer, so a user can find a passage before committing to a seek. Keep the existing click and drag seeking, the elapsed and remaining labels, and the marker lane, all using the monospace numeric style so the times do not jitter as they count. The overview and detail heights follow the proportional sizing introduced with the window work, with minimums that keep both usable. Acceptance: when a track is playing in the dark theme, the playhead is clearly distinguishable from the waveform fill. When a loop region is armed, the looped span is visibly shaded in both the overview and the detail view. When the pointer hovers over the detail waveform, a position line and its timestamp follow the pointer. When the loop is defined but not armed, its shading differs from the armed state."

**Source**: [§ 3.5 Now Playing](../autonomous/ModPlayer-UI-UX-Review.md#35-now-playing) (`UX-23`), [§ 5.3 Semantic colour](../autonomous/ModPlayer-UI-UX-Review.md#53-semantic-colour-both-themes-contrast-verified), [§ 5.5 Layout rules](../autonomous/ModPlayer-UI-UX-Review.md#55-layout-rules), [§ 4.1 No design tokens](../autonomous/ModPlayer-UI-UX-Review.md#41-no-design-tokens). **Origin**: [specs/autonomous/breakdown/010-now-playing-workbench/002-waveform-legibility.md](../autonomous/breakdown/010-now-playing-workbench/002-waveform-legibility.md). **Prerequisites**: the waveform overview/detail and track-time coordinate space from [005-now-playing-waveform](../005-now-playing-waveform/spec.md), the loop regions and marker lane from [006-markers-loops-and-cues](../006-markers-loops-and-cues/spec.md), the theme tokens from [014-design-tokens-and-type-scale](../014-design-tokens-and-type-scale/spec.md), and the proportional waveform-height formula from [018-window-sizing-and-responsive-dock](../018-window-sizing-and-responsive-dock/spec.md) / [021-transport-bar-and-panel-layout](../021-transport-bar-and-panel-layout/spec.md).

**Scope boundary**: Covers what the waveform draws and how it responds to hovering. It does not change seeking behaviour, marker or loop-region semantics (creation, arming rules, persistence), the marker lane's own contents, or the beat-grid overlay planned in [006-practice-depth/001-beat-grid-key-and-loudness-analysis](../autonomous/breakdown/006-practice-depth/001-beat-grid-key-and-loudness-analysis.md). It does not change the overview/detail proportional-sizing formula or minimums (018/021) — it only repaints within whatever height that formula already produces.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Know where you are, even in the dark theme (Priority: P1)

While a track plays, the user can always pick out the playhead against the waveform fill, in either theme — including the dark theme, where today it is a single dark line that nearly vanishes.

**Why this priority**: This is the most severe of the four defects the prompt names (`UX-23`): a playhead a user cannot see defeats the entire purpose of a waveform view built specifically so a user could "navigate by sight" (005). Nothing else in this feature matters if the user still cannot tell where playback is.

**Independent Test**: Play a track in the dark theme, sample the playhead's rendered color against the waveform fill immediately behind it, and confirm the contrast ratio is at least 3:1; repeat in the light theme.

**Acceptance Scenarios**:

1. **Given** a track is playing in the dark theme, **When** the playhead is sampled against the waveform fill directly behind it, **Then** the contrast ratio (core or casing) is at least 3:1.
2. **Given** a track is playing in the light theme, **When** the playhead is sampled against the waveform fill directly behind it, **Then** the contrast ratio (core or casing) is at least 3:1.
3. **Given** the playhead is rendered on both the overview and the detail view, **When** either is sampled, **Then** both meet the same contrast floor — the fix is not limited to one view.
4. **Given** high contrast (017) is enabled in either light or dark, **When** the playhead is checked against every backdrop colour listed in FR-003, **Then** each pair reaches at least 3:1.

---

### User Story 2 - Know where the loop is, and whether it's armed (Priority: P1)

While a track plays, the user can tell at a glance, by looking at the waveform itself, which span is the armed loop and which spans are loop regions they defined but did not arm — without reading the marker lane or the markers panel.

**Why this priority**: This is the feature's second acceptance line and the direct fix for the practice workflow (006, JTBD-1) where a musician arms one of several regions: today only the *current* region's span is drawn (and its treatment follows the global loop state, not that region's own armed flag), so any other region — including an armed non-current one — shows nothing on the waveform, and telling "this is looping" from "this exists but isn't looping" requires reading text elsewhere.

**Independent Test**: Define two loop regions on a track, arm one, and confirm both are shaded across the waveform (overview and detail) with visibly different treatments; disarm and rearm the other and confirm the shading follows the armed state.

**Acceptance Scenarios**:

1. **Given** a loop region is armed, **When** the waveform is viewed, **Then** its span is visibly shaded across both the overview and the detail view, not only indicated by its A/B markers in the lane above.
2. **Given** a second loop region exists on the same track and is not armed, **When** the waveform is viewed, **Then** its span is also shaded, using a treatment visually distinct from the armed region's shading.
3. **Given** the armed region's playhead is currently outside its span ("armed but inactive," per 006 FR-012), **When** the waveform is viewed, **Then** its shading remains the armed treatment — not the defined-but-not-armed treatment — consistent with 006's existing active/inactive-while-armed distinction, which this feature does not change.
4. **Given** the user arms a different region, **When** the change takes effect, **Then** the previously armed region's shading switches to the defined-but-not-armed treatment and the newly armed region's shading switches to the armed treatment, on both views.
5. **Given** the armed region is not the current region (armed from its marker-list row, 006 FR-008), **When** the waveform is viewed, **Then** the armed region shows the armed treatment and the current-but-disarmed region shows the defined-but-not-armed treatment — treatment follows each region's own armed flag, never "current".

---

### User Story 3 - Preview where you're about to seek (Priority: P2)

Before committing to a click, the user moves the pointer across either waveform and sees exactly where that click would land — a position line and its timestamp, following the pointer — so they can find a passage by eye first.

**Why this priority**: This is the feature's third acceptance line and a genuinely new capability (not a fix to something broken), so it ranks behind the two legibility defects in Stories 1–2 but still delivers real navigation value on its own.

**Independent Test**: With a track loaded, move the pointer across the detail waveform without clicking and confirm a position line and timestamp appear and follow the pointer; repeat on the overview; move the pointer off the waveform and confirm both disappear.

**Acceptance Scenarios**:

1. **Given** the pointer moves across the detail waveform, **When** it is anywhere over the waveform, **Then** a scrub position line appears at that track-time position with its timestamp shown in the existing monospace numeric style.
2. **Given** the pointer moves across the overview waveform, **When** it is anywhere over the waveform, **Then** the same position-line-and-timestamp feedback appears there too.
3. **Given** the scrub position line and timestamp are shown, **When** the pointer leaves the waveform, **Then** both disappear.
4. **Given** the scrub position line is shown, **When** the user does not click, **Then** the audible playback position, the transport state, and the playhead are all unaffected — hover is preview-only.
5. **Given** the user is mid-drag (005's drag-to-seek preview or 006's marker drag), **When** the pointer is also technically over the waveform, **Then** only the drag preview is shown — hover feedback does not appear as a second, conflicting indicator during a drag, and reappears on the next pointer move after release or `Esc`.
6. **Given** the pointer hovers near the right edge of either waveform, **When** the timestamp would overflow, **Then** it is drawn on the line's left side and stays fully inside the waveform rect; its text is `m:ss.mmm` (e.g. `1:23.500`).

---

### User Story 4 - Read progress and energy at a glance (Priority: P3)

While a track plays, the user can tell how much of the track has played and how much remains just by looking at the waveform's fill, and can distinguish quieter, sustained passages from loud transients by the fill's two tones — without reading the elapsed/remaining labels.

**Why this priority**: This is a supporting legibility improvement named first in the prompt but, unlike Stories 1–2, it is not called out as broken by the source review's acceptance lines; it makes an already-functional waveform easier to read at a glance rather than fixing something unusable.

**Independent Test**: Play a track partway through and confirm the played portion of the fill is visually distinct from the unplayed portion; separately, confirm the fill uses two distinguishable tones for peak versus average energy, in both themes.

**Acceptance Scenarios**:

1. **Given** a track is partway through playing, **When** the waveform is viewed, **Then** the played portion of the fill (before the playhead) renders with a different treatment from the unplayed portion (after the playhead), on both the overview and the detail view.
2. **Given** the waveform is showing decoded audio, **When** its fill is viewed in either theme, **Then** the peak-energy tone and the average-energy tone are distinguishable, verifiably different color values.
3. **Given** a track is still streaming and partially decoded (005 Story 3), **When** its waveform is viewed, **Then** the two-tone fill and played/unplayed treatment apply to the decoded region exactly as on a fully decoded track, and the undecoded placeholder region is unaffected by this feature.

---

### Edge Cases

- No track is loaded → the waveform shows 005's existing "pick a track" hint; no playhead, loop shading, or hover feedback is drawn (FR-015 of 005, unchanged).
- The pointer hovers the waveform while a marker drag is in progress (006) → the drag's own live preview is shown; hover scrub feedback does not appear as a second indicator (User Story 3, AS5).
- The pointer hovers over a still-undecoded placeholder region of a streaming track → the scrub position line and `m:ss.mmm` timestamp still appear at that track-time position (a click there would seek); only the fill's two-tone/played treatment is absent there, since no decoded energy exists yet to render.
- Several defined loop regions overlap on the waveform → each region's shading is drawn independently and composites over the others (no merge or special-case rendering); the armed region (at most one, 006 I6) is drawn last so its treatment reads on top; the playhead still meets FR-003 against every such composite.
- The transport is paused or stopped → hover scrub feedback still works exactly as while playing, since it never depends on playback state; the played/unplayed fill distinction still reflects the current (frozen) position.
- The window is resized down to the application's minimum, shrinking the waveform to its smallest proportional height (018/021: overview ≥ 64 px, detail ≥ 120 px) → the playhead's contrast floor, the loop shading distinction, the two-tone fill, and the hover feedback all remain legible at that minimum height; this feature does not change the minimums themselves.
- Analysis for a track fails (005 FR-016, "analysis unavailable") → no waveform fill exists to paint the two-tone/played treatment on, and the existing "analysis unavailable" state is unchanged; the playhead, loop shading and hover scrub line/timestamp still draw over that area exactly as elsewhere, since seeking remains available there.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The waveform fill (overview and detail) MUST render each bucket in two visually distinguishable tones: the peak envelope (`min`…`max`) in a peak tone, and the ±RMS band within it in an average tone, in all four appearances (light, dark, high-contrast light, high-contrast dark). *(Prompt; `UX-23` "peak/RMS distinction"; Clarifications)*
- **FR-002**: The waveform fill MUST render the played portion (left of the **displayed** playhead — the drag-preview position while a 005 drag is active) with a treatment distinct from the unplayed portion (right of it), for both tones, on both views. Together with FR-001 this yields four fill tokens per appearance — played-peak, played-average, unplayed-peak, unplayed-average — which MUST be pairwise distinct values. *(Prompt; Clarifications)*
- **FR-003**: The playhead MUST reach at least 3:1 contrast against every colour that can appear directly behind it — waveform background, each of the four FR-002 fill tokens, the undecoded placeholder, and each loop-shading treatment (FR-004/FR-005) composited over those — in all four appearances, on both views. A core stroke plus a contrasting casing is permitted; the floor is met for a backdrop if either the core or the casing reaches 3:1 against it. - **FR-004**: The armed loop region's (006) `[A, B)` span MUST be shaded across the waveform itself on both views, using 006's existing armed treatments unchanged: translucent fill (A-marker palette colour, 25 % alpha) while armed-active, diagonal hatch while armed-inactive. ### Key Entities

- **Waveform Fill (two-tone)**: The per-bucket rendering of a track's peak envelope (peak tone) and ±RMS band (average tone), each in a played or unplayed treatment — four pairwise-distinct theme tokens per appearance; extends 005's waveform rendering, identical on overview and detail.
- **Average-Energy Bucket Value**: A new 8-bit per-bucket RMS field on 005's existing Waveform Cache Entry, present at every ladder level, computed by the Analysis Service alongside `min`/`max`, invalidated by the same analyzer-version mechanism.
- **Playhead Treatment**: A ≥2 px core stroke plus optional contrasting casing, both theme tokens, holding ≥3:1 (core or casing) against every backdrop listed in FR-003, in all four appearances, on both views; topmost layer.
- **Loop Region Shading**: The waveform-level rendering of every complete loop region's `[A, B)` span in one of three treatments chosen from that region's own state — armed-active (25 % translucent fill), armed-inactive (hatch), or defined-but-not-armed (1 px outline + fill at ≤ half the armed-active alpha) — hue from its A marker's palette colour.
- **Scrub Position Indicator**: The hover-driven 1 px position line and `m:ss.mmm` timestamp label on whichever view the pointer is over, using 005's track-time coordinate space; below the playhead, suppressed during drags, purely a preview, never committing a seek.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: The automated contrast test asserts the playhead (core or casing) reaches ≥3:1 against every backdrop listed in FR-003 in all four appearances; a manual capture in the dark theme confirms it on both views.
- **SC-002**: With one armed and at least one other complete, not-armed region on a track, the armed region shows the fill (active) or hatch (inactive) treatment and the other shows outline plus a fill at ≤ half the armed-active alpha, on both views, in 100% of trials — including when the armed region is not the current region.
- **SC-003**: Moving the pointer across either waveform shows a scrub position line and timestamp that follows the pointer within one rendered frame, and both disappear within one rendered frame of the pointer leaving the waveform, in at least 95% of trials.
- **SC-004**: Hovering either waveform without clicking never changes the audible playback position or the transport state, in 100% of trials.
- **SC-005**: The four fill tokens (played/unplayed × peak/average) are pairwise distinct in each of the four appearances (automated token test), and a cache entry written by the new analyzer version carries an RMS byte per bucket at every level while a complete 10-minute entry stays ≤1 MB.
- **SC-006**: Sampling the waveform fill before and after the playhead during playback finds two distinct treatments (played versus unplayed), in 100% of trials.
- **SC-007**: Every existing acceptance scenario and contract test from 005 (click/drag seek, elapsed/remaining labels, keyboard seek/zoom bindings) and 006 (marker lane, marker glyphs, armed/inactive-while-armed distinction) continues to pass unmodified after this feature ships, in 100% of trials.

## Assumptions

- Adding a per-bucket average-energy value to the waveform cache is a data-model extension that reuses 005's existing analyzer-version invalidation mechanism (FR-007 of 005); no new migration mechanism is introduced (Clarifications, FR-013).
- The playhead's ≥3:1 contrast floor applies in both themes, not only the dark theme the source review's own recommendation names as today's broken case, because the prompt itself asks for a contrast floor "in both themes" (Clarifications, FR-003).
- Every loop region 006 defines on a track gets a span shading treatment, not only the currently armed one; the armed treatment covers both of 006's existing "armed and active" / "armed but inactive" sub-states unchanged (Clarifications, FR-004/FR-005).
- Hover scrub feedback requires no new keyboard binding: it previews a position without committing anything, and the seek it previews is already fully keyboard-operable via 005's existing bindings, so Constitution X's keyboard-operability requirement is already satisfied for the underlying function (Clarifications, FR-016).
- The two-tone fill and played/unplayed distinction apply identically to both the overview and the detail view; the prompt only calls out "overview or detail" explicitly where the behavior is genuinely view-specific (hover, loop shading) (Clarifications).
- Exact colour values for the fill, playhead and hover tokens, and the exact defined-but-not-armed fill alpha, are chosen at `/speckit-plan` time, constrained by this spec's measurable rules (FR-002 pairwise-distinct tokens; FR-003 3:1 floor; FR-005 alpha ≤ half armed-active) — consistent with how 014/017 left exact swatch values to whatever the automated contrast test accepts.
- This feature does not touch the overview/detail proportional-sizing formula or its minimums (018/021); it only repaints within whatever height that formula already produces at any window size.
