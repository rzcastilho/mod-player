# Feature Specification: Streaming Playback, Transport, and Queue

**Feature Branch**: `feature/003-streaming-playback-and-queue`

**Created**: 2026-09-15

**Status**: Clarified (2026-09-15, two passes) — no open human decisions

**Input**: User description: "Let a signed-in Premium user actually hear their catalog. ModPlayer registers itself with the streaming service as a Connect receiver device named "ModPlayer on <machine name>" (user-editable), receives track load requests and the encrypted stream, decrypts and decodes it in-client, and renders it through the audio engine built in the walking skeleton. This real Audio Source implements the same interface as the synthetic source, is the only component that knows the service's protocols, and is packaged as a separately versioned module so it can be replaced or disabled if the protocol changes. The user gets a full transport: play, pause, stop, skip forward, skip back (restart the track, or go to the previous track if within the first three seconds), seek to any position, and volume. Position is reported from the audio clock at least 60 times per second. Track transitions are gapless where the format allows. Playback continues when the window is minimized, hidden, or on another virtual desktop. A play queue derives from the current context (playlist, album, search results) plus user-added "play next" items; the user can view, reorder, and remove queue items, and use shuffle and repeat (off, one, all). The current track is pre-buffered fully as fast as the connection allows and the next queued track is pre-fetched. Other controllers on the same account can transfer playback to ModPlayer (it accepts and starts playing) or away from it (it stops locally, keeps UI state, and shows "playing on <other device>"); commands from other controllers count as user commands. Acceptance: when the user presses play on an already-buffered track, audio starts within 50 ms; on a freshly streamed track, within 1.5 s on a 10 Mbit/s connection. When the connection degrades mid-track, playback continues from buffered data; if the buffer runs dry, the transport shows "buffering" and resumes automatically rather than skipping. When the user seeks past the end of the track, the position clamps and the queue advances. When the receiver protocol breaks, the Audio Source reports "source unavailable" and the app shows a clear message with a link to the project's status page instead of crashing."

**Source**: [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) — FR-3.1 Core transport, FR-3.2 Queue, FR-8.3 Streaming behavior, INT-2 Streaming service — Connect receiver protocol, INT-6 Operating system services, DM-2 TrackRef, Part 9 §3 Core services, EC §1 (1.2–1.5) and EC §3 Playback and transport, NFR §1 Performance and latency, NFR §2 Reliability and availability, §5 Scope. Prerequisites: 001-walking-skeleton (app shell, `AudioSource` trait, Real-Time Audio Engine, synthetic source, transport shell, notifications, settings incl. Settings › Developer); 002-first-launch-and-sign-in (signed-in Premium AccountSession, "playback permitted" fact, OS secure credential store, sign-out / revocation / expiry handling).

### Session 2026-09-15 (specify pass)

Resolution ladder applied: (D) derived from an authoritative source, (A) assumed conventional default, consistent with 001 and 002. No item below met the materiality bar for human escalation — the source document's open questions touching this slice (Q-2, Q-3) are protocol-mechanism details the client-facing contract does not depend on, and A-11 is an architecture note already settled by Constitution Principle IV.

- Q: How does the user get tracks into the queue in this slice, given search and library views are explicitly out of scope? → A (D, phased-delivery pattern established by 001's synthetic test track and its Now Playing minimal transport; A for the mechanism): this slice ships the Queue and transport engine as reusable, fully-tested machinery, exercised end-to-end by (a) automated tests constructing queues directly from `TrackRef` fixtures resolved through the real Connect Audio Source, and (b) a minimal, temporary "Play from account" developer/demo action (analogous to 001's Device Check test tone) that lets a human tester fetch a small, real set of the signed-in user's own tracks and enqueue them. This is not library or search UI — no browsing, filtering, or playlist views ship here — it only proves the transport, queue, and streaming Audio Source against real account data. The permanent way users build queues (search, library, playlists) lands in a later slice and plugs into the same `Queue` without changes. Concrete shape (see review pass, item "Play from account"): the action lives in **Settings › Developer › "Play from account"**.
- Q: Q-2 — does the receiver protocol allow seeking into an unbuffered offset, or only sequential fetch? Affects the 500 ms uncached-seek target (NFR-1.5). → A (A, Constitution IV — only the Audio Source module knows the protocol): the `AudioSource` trait's seek contract is defined as **best-effort**: it always accepts a seek to any position and always makes forward progress, but does not promise random-access latency. The Connect Audio Source implementation is free to satisfy a seek via direct range fetch when the protocol allows it, or by discarding the current buffer and re-fetching sequentially from the nearest point at or before the target when it does not. Either way the host contract is identical: the transport shows the requested position immediately, enters `buffering` if the target isn't yet decoded, and resumes automatically once data arrives, targeting the 500 ms figure (NFR-1.5) as the product-level goal rather than a per-call guarantee. This means the 500 ms target is validated against the actual protocol behavior once the Connect Audio Source is implemented, and is allowed to regress gracefully (bounded by `buffering`, never a skip or crash) if the protocol turns out to be sequential-only. Independent versioning (A-11, Constitution IV) means a future protocol change that adds random access improves this without a host-side change.
- Q: Q-3 — which quality tiers/formats does a receiver get, and do any preclude gapless playback? → A (A, Constitution IV; FR-3.1.4): quality-tier and format selection are entirely internal to the Connect Audio Source and invisible to the rest of the system — the host only ever consumes decoded PCM frames at the source's declared sample rate, per 001's `AudioSource` interface. Gapless is therefore evaluated per adjacent pair of decoded tracks, independent of which tier produced them: when both tracks are available at the point of transition with no engine-imposed silence, the transition is gapless; when the outgoing track's audio hasn't finished decoding/buffering in time, the transition is not gapless for that pair but still plays back-to-back without an error or crash. A user-facing quality-tier selector (FR-8.3.3, marked SHOULD in the source document) is deferred to a later slice; only the tier the account negotiates automatically applies here.
- Q: A-11 — independent versioning of the Audio Source module. → A (D, Constitution IV, INT-2.7): confirmed as an architectural constraint, not a product decision: the Connect Audio Source ships as its own versioned crate (`audio-source-connect` or equivalent) behind the same `AudioSource` trait as 001's synthetic source, so a protocol-breaking change can ship a fix to that one component without a full client release. This governs the plan/implementation phase; it has no independent user-facing acceptance criteria beyond FR-020's "source unavailable" behavior (see Functional Requirements).

### Session 2026-09-15 (clarify review pass)

Same ladder and notation. Every item below was checked against the materiality test; each has either an authoritative source or a single conventional default, so none is escalated.

- Q: Which INT-6 and NFR §2 items cited by the breakdown actually belong to this slice? → A (D, breakdown README coverage map): only INT-6.1 (audio output, delivered by 001), NFR-2.1 and NFR-2.5. Media keys / OS now-playing (INT-6.3), OS notification routing (INT-6.5), sleep inhibition (INT-6.4), and state persistence across restarts (NFR-2.6) are mapped to 004-performance/002 and /003. Consequences, testable: (a) queue, cursor, shuffle/repeat mode, and position are **in-memory only** in this slice — every launch starts with an empty queue and transport stopped (001 FR-015), then applies FR-019's Connect-state query; (b) closing the main window quits the application on all three platforms (Constitution X, identical behavior): playback stops, buffers are discarded, and the Connect device deregisters — there is no tray or background mode in this slice; (c) no media-key or sleep-inhibition behavior is specified or tested here.
- Q: How does the real-time-only `AudioSource` contract from 001 (`fill`/`seek` MUST NOT do I/O) accommodate a streaming source? → A (D, Constitution I and IV; 001 contract `audio-source.md`): the Connect Audio Source is split into a real-time half (implements `fill`/`seek`, reads decoded PCM from a lock-free ring buffer, never blocks) and an off-real-time streaming half (registration, heartbeat, stream fetch, decryption, decoding, buffer management). The 001 trait/module MAY be extended **additively** with track-load, buffer-status, and source-health reporting; it MUST NOT be replaced or given a second abstraction. Test: the synthetic source remains a valid implementor and every 001 `AudioSource` test passes unchanged. When `fill` is called with no decoded data available, it writes silence, does not advance the reported track position, and raises an underrun flag via an atomic; the host maps that flag to the `buffering` transport state.
- Q: What exactly is the transport state model, and what do stop / seek-while-stopped / pause-while-buffering do? → A (A, conventional; 001 FR-015 stopped/playing/paused): states are `stopped | playing | paused | buffering`, where `buffering` is a sub-state of `playing` (the user intent is "play"). Pause while buffering → `paused`; play while buffering → no-op. **Stop**: position resets to 0, the current track and the queue are retained, ModPlayer remains the active Connect device. **Seek while stopped**: position is set and the state becomes `paused` (position retained). **Pause → play**: resumes from the same position with no re-buffering when the audio at that position is already decoded. **Volume** is 001's master volume (0–100 %, applied before the limiter, persisted per 001; the safe-volume cap applies only at launch per 001 FR-011); there is no separate per-track or per-source volume. Remote-controller volume commands set master volume directly on the same scale.
- Q: When does `buffering` start and end, and what gates first audio on a freshly streamed track? → A (A, conventional pre-roll; NFR-1.7): the **readiness threshold** is ≥ 2 s of decoded audio ahead of the playhead, or the end of the track, whichever comes first. The same threshold gates (a) first audio after play on an un-streamed track, (b) resume after `buffering`, and (c) resume after a seek into an unbuffered region. The transport enters `buffering` the moment `fill` reports an underrun and leaves it when the threshold is met; the track position does not advance while buffering. Test: with a throttled protocol double, audio resumes exactly when ≥ 2 s is decoded and never skips.
- Q: How much is pre-buffered/pre-fetched, and where is it held? → A (D, FR-8.3.1; Constitution V; offline cache out of scope): the current track is fetched fully, as fast as the connection allows; once complete, the **next item** (per the advancement order below — the head of the play-next block if any, the current track itself under repeat-one) is fetched fully. At most the current and the next track are held, in memory only (encoded stream plus a decode window); nothing is written to disk. On advance, the previous track's buffers are discarded (a skip back that needs it re-fetches). When the queue order, shuffle, or repeat mode changes, the pre-fetch target is recomputed within 1 s and a no-longer-next fetch is cancelled.
- Q: What is the queue model — are played items consumed, and where is "history"? → A (A, conventional cursor model, matches Key Entities): the queue is an ordered list with a **play cursor**; items are not removed when played. **History** is the ordered list of items actually played this session (shuffle-aware, most recent last, bounded at 100 entries), used only by skip-back-within-3-seconds; it is not shown in the queue view. The queue view shows the current item plus upcoming items in **effective play order** (the shuffled order when shuffle is on). Skip back at ≤ 3 s with empty history restarts the current track.
- Q: "Play next" ordering with multiple additions, and interaction with shuffle? → A (A, conventional FIFO): play-next items form a contiguous **play-next block** immediately after the current item; each new addition is appended to the end of that block (add order preserved). Turning shuffle on keeps the current item and the play-next block in place and randomizes only the remaining upcoming context items (uniform random permutation); turning shuffle off restores the original context order after the block, with the cursor on the current item. Under repeat-all with shuffle, the queue is re-shuffled at each wrap. Reordering while shuffled edits the effective order; dragging an item into or out of the play-next block changes its origin accordingly.
- Q: Precedence between repeat-one, play-next, shuffle, repeat-all at track end (AS 2.7 vs. former AS 2.10 conflicted)? → A (A, conventional — repeat-one repeats the track; explicit skip overrides it): **advancement order on natural track end** (and on seek-past-end, which is equivalent): (1) repeat-one → the same track restarts; else (2) the head of the play-next block; else (3) the next upcoming context item (shuffled order if shuffle is on); else (4) end of queue: repeat-all → wrap to the first upcoming item (re-shuffled if shuffle is on); repeat-off → transport `stopped`, cursor stays on the last item at position 0. **Explicit skip forward** uses the same order but skips step (1) — a manual skip always moves to the next item even under repeat-one. **Removing the current item** also skips step (1) (a removed item cannot repeat). Play-next items therefore wait while repeat-one is on; they play on the next skip forward or when repeat leaves "one". Former AS 2.10 is realigned to this rule.
- Q: What happens with an unavailable track in the queue (region-locked, removed, or the service refuses to load it)? → A (D, INT-3.3, FR-8.2.4 applied narrowly): the item stays in the queue, is visibly marked "Unavailable", and is skipped with an info notification "Skipped <title> — unavailable"; advancement continues per the order above. If every remaining candidate is unavailable, the transport stops as at end of queue.
- Q: Transient protocol error vs. unrecoverable "source unavailable" — who decides, and what does the user see for each (FR-021 previously referenced a connectivity indicator that does not exist yet)? → A (D, INT-2.6/2.7; A for thresholds and UI, reusing 002's backoff): the Connect Audio Source classifies. **Transient** = network errors, timeouts, disconnection, or an expired credential: the source retries indefinitely with backoff starting at 1 s, doubling to a 60 s cap (002's convention); playback continues from buffer; the transport shows an inline status "Reconnecting…"; after 30 s of continuous failure a **warning** notification "Connection lost — playback continues from buffered audio" is raised and auto-cleared on recovery. No global connectivity indicator is introduced (that is DM-22 in 003-offline-and-library/002). **Unrecoverable** = the service rejects the registration/handshake or protocol version, or a required message cannot be parsed; transient retries never escalate to unrecoverable on their own. On unrecoverable: the source reports `source unavailable` (optionally flagged "client update required"); the transport is disabled with the inline reason; a **critical** notification "Streaming is unavailable — the receiver protocol may have changed" carries a **Status page** action (build-time-configured URL, opened in the system browser) and a **Retry** action that re-initializes the source. When the flag says a client update is required, the message says so and **Retry** is omitted. Navigation, Settings, and the queue view stay usable.
- Q: How do account-session events from 002 interact with playback? → A (D, EC-1.2, EC-1.3, EC-1.4, 002 FR-010/019/021; A where 002 and EC conflict): **registration** as a Connect device happens only while an AccountSession exists and *playback permitted* is true (Premium). **Non-Premium or unknown tier**: no registration; the transport is disabled with an inline reason ("Premium required" / "Subscription not verified"), and "Play from account" is hidden. **Sign-out** (002 FR-015) and **remote revocation** (002 FR-019): playback stops immediately, the queue and buffers are cleared, and the device deregisters before 002's "Deleted:" report — 002's already-ratified immediate deletion takes precedence over EC-1.3's "finish current track" because the main window is replaced by the sign-in step. **Credential expiry** (EC-1.2): buffered audio continues; a failed next-track load is treated as transient (the source waits for 002's refresh / re-sign-in), the transport shows `buffering`, and 002's existing critical "Session expired — sign in again" notification is the only message. **Downgrade mid-session** (EC-1.4): detected when the service rejects a load with a tier reason or when **Re-check subscription** reports non-Premium; the current track finishes from buffer, then the transport is disabled and the device deregisters, with a **warning** notification carrying an **Open upgrade page** action.
- Q: Connect device name — default source, where edited, validation, persistence? → A (D, INT-2.1; A for details): default is "ModPlayer on <OS hostname>" ("ModPlayer" if the hostname is unavailable). Edited in **Settings › Playback › "Device name"** (shown with the hint "as seen by other apps on your account"). Value is trimmed; 1–64 characters after trimming; an empty value restores the default; longer input is rejected inline. Device-scoped (survives sign-out), persisted through 001's atomic settings store. A rename re-registers the device so other controllers see the new name within 5 s.
- Q: Transfer semantics — what happens to the local queue on transfer-to, does ModPlayer mirror the remote device when inactive, and which local commands request transfer back? → A (D, INT-2.2/2.3/2.5; A for queue replacement and the command set): **Transfer-to**: the local queue is **replaced** by the transferred context (the current track plus whatever upcoming items the protocol supplies; if only the current track is supplied, the queue is that single item); shuffle/repeat are taken from the transferred state when supplied, else the local values are retained; any in-flight local command is discarded; playback starts without local action. **Transfer-away**: local output stops, the transport freezes with paused semantics (track, position, queue, shuffle/repeat unchanged), a banner "Playing on <device name>" with a **Play here** action replaces the transport status; ModPlayer does **not** mirror the remote device's track or position (INT-2.5, it is not a controller). **While inactive**: play, skip forward/back, seek, and **Play here** request transfer to ModPlayer and, once granted, apply that command (Play here = play); pause and stop are no-ops; volume changes local master volume only. If the transfer request is not granted within 5 s, a **warning** notification "Couldn't take over playback" is raised and local state is unchanged. On transfer back, the incoming protocol state is authoritative and replaces the frozen local state.
- Q: Does ModPlayer report its playback state to the service (INT-2 "Outbound: playback state reports") so other controllers reflect it? → A (D, INT-2): yes — play state, current track, position, volume, shuffle, and repeat are reported on every transport state change within 1 s, and on the protocol's heartbeat cadence while active. Test: a second controller double observes ModPlayer's pause/seek/volume/track changes within 1 s. Added as FR-025.
- Q: What is the concrete "Play from account" surface? → A (A, mirrors 001's Settings › Developer sample-notification actions): **Settings › Developer › "Play from account"** fetches up to 20 of the signed-in user's most recently played tracks (falling back to saved tracks when there are none) through the account read integration, **replaces** the queue with them, and starts playing the first. Hidden when playback is not permitted. Temporary; may be removed once a library/search slice ships.
- Q: Position reporting jitter and behavior while not advancing? → A (D, FR-3.1.3, NFR-1.9): while state is `playing`, position updates are published at ≥ 60 Hz with ≤ 5 ms jitter, each value read from the engine's audio clock; while `paused`, `stopped`, or `buffering`, the published value stays constant and the publish rate MAY drop.
- Q: Keyboard alternative to drag reorder? → A (D, Constitution X, NFR-6.1): each queue row exposes **Move up**, **Move down**, **Play next**, and **Remove** as keyboard-operable actions with accessible names; drag is an addition, never the only path.
- Q: Locale? → A (D, 001/002 convention): all strings externalized; en-US is the only shipped locale in this slice.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Hear real music through a full transport (Priority: P1)

A signed-in Premium user plays a track from their actual streaming catalog — not the synthetic test track from the walking skeleton — and controls it with a complete transport: play, pause, stop, skip forward, skip back, seek anywhere in the track, and volume. The position shown updates smoothly and in real time, driven by the audio clock, and playback keeps running even when the ModPlayer window is minimized, hidden, or the user switches to another virtual desktop.

**Why this priority**: This is the entire point of the slice — and of the product up to this point. 001 proved the engine can make sound; 002 proved the user can sign in. Until this story ships, ModPlayer has never played a single second of the user's real music. Nothing else in this spec matters if this doesn't work.

**Independent Test**: With a signed-in Premium account, enqueue real tracks via Settings › Developer › "Play from account" (see Clarifications), press play, and verify audio is audible, the full transport responds correctly, and reported position advances at the audio clock's rate while the window is hidden and restored.

**Acceptance Scenarios**:

1. **Given** a signed-in Premium user with a track loaded and already fully buffered, **When** the user presses play, **Then** audible output begins within 50 ms.
2. **Given** a signed-in Premium user selects a track that has not been streamed yet, **When** the user presses play, **Then** the transport shows `buffering` until ≥ 2 s of audio is decoded, and audible output begins within 1.5 s on a 10 Mbit/s connection.
3. **Given** a track is playing, **When** the user presses pause, then play again, **Then** playback suspends immediately and resumes from the exact same position with no re-buffering delay for already-buffered audio.
4. **Given** a track is playing, **When** the user presses stop, **Then** playback halts, the position resets to the start of the track, the current track and queue are retained, and ModPlayer remains the active Connect device (distinct from pause, which retains position).
5. **Given** a track is playing more than 3 seconds in, **When** the user presses skip back, **Then** the current track restarts from position 0 and does not move to the previous queue item.
6. **Given** a track is playing 3 seconds or less in (or paused at such a position) and history is non-empty, **When** the user presses skip back, **Then** playback moves to the most recently played item in history, restarted from 0; with empty history the current track restarts.
7. **Given** a track is playing, **When** the user presses skip forward, **Then** playback advances to the next item per the advancement order (play-next block, then context order / shuffle, then repeat-all wrap), ignoring repeat-one.
8. **Given** a track is playing or paused, **When** the user seeks to a specific position via the transport, **Then** playback (once resumed) continues from that position, landing within 50 ms of the target for already-buffered audio.
9. **Given** a track is playing, **When** the user adjusts volume, **Then** the audible level changes smoothly with no click or discontinuity, consistent with 001's master-volume behavior (this is the same master volume control).
10. **Given** the transport reports position while a track plays, **When** position updates are sampled, **Then** they arrive at least 60 times per second with ≤ 5 ms jitter and are derived from the audio clock, not a UI timer.
11. **Given** two adjacent queued tracks are both fully buffered and their format allows it, **When** the first track ends, **Then** the second begins with no audible gap or click (gapless transition).
12. **Given** playback is running, **When** the user minimizes the window, hides it, switches virtual desktops, or brings another application to the foreground, **Then** playback continues uninterrupted and position keeps advancing.
13. **Given** the transport is stopped with a current track, **When** the user seeks, **Then** the position is set and the transport enters `paused`.
14. **Given** playback is running, **When** the user closes the main window, **Then** the application quits: audio stops, buffers are discarded, and the Connect device is deregistered.

### User Story 2 - Manage the play queue (Priority: P2)

The user builds up what plays next: tracks are added to a queue derived from the current listening context plus explicit "play next" additions, and the user can see the whole queue, reorder it by dragging or an equivalent keyboard control, remove items from it, and turn on shuffle and a repeat mode (off, one track, or the whole queue).

**Why this priority**: A transport that can only play one track at a time is a toy; the queue is what makes ModPlayer usable for an actual listening or practice session. It is second priority because User Story 1 must work before queue transitions mean anything.

**Independent Test**: Enqueue several tracks, open the queue view, reorder an item, remove an item, then verify playback and skip-forward respect the new order; toggle shuffle and each repeat mode and verify next-track selection changes accordingly.

**Acceptance Scenarios**:

1. **Given** the user is listening in some context (the "Play from account" surface in this slice; playlist/album/search context in later slices), **When** tracks are added, **Then** the queue reflects that context's track order plus any user-added "play next" items positioned immediately after the currently playing item, in the order they were added.
2. **Given** a non-empty queue, **When** the user opens the queue view, **Then** the current item and every upcoming item are listed in effective play order with enough detail to identify them (title, artist), the currently playing item is visibly distinguished, play-next items are visibly distinguished from context items, and history is not shown.
3. **Given** the queue view is open, **When** the user reorders an item by dragging it, or by the keyboard **Move up** / **Move down** actions, **Then** the queue's play order updates immediately and subsequent skip-forward navigation follows the new order.
4. **Given** the queue view is open, **When** the user removes an item that is not currently playing, **Then** it disappears from the queue without affecting current playback.
5. **Given** the queue view is open, **When** the user removes the currently playing item, **Then** playback advances to what is now the next item per the advancement order, ignoring repeat-one (or stops with no current track if the queue becomes empty).
6. **Given** a queue with multiple items, **When** the user enables shuffle, **Then** the current item and the play-next block stay in place, the remaining upcoming context items are randomized (each played once before any repeats), the queue view shows the new effective order and indicates shuffle is active; disabling shuffle restores the original context order after the play-next block.
7. **Given** repeat is set to "one", **When** the current track ends (or the user seeks past its end), **Then** the same track plays again from the start, regardless of shuffle and of any pending play-next items.
8. **Given** repeat is set to "all", **When** the last track in the queue ends, **Then** playback continues from the first upcoming item (re-shuffled if shuffle is active) instead of stopping.
9. **Given** repeat is set to "off", **When** the last track ends (or the user skips forward on it), **Then** playback stops, the transport shows the stopped state with the cursor on that last item at position 0, and the queue is retained.
10. **Given** a "play next" item exists and shuffle and/or repeat-all are active, **When** the current track ends, **Then** the explicit "play next" item plays before shuffle or repeat-all logic picks the following track.
11. **Given** repeat is set to "one" and a "play next" item exists, **When** the user presses skip forward, **Then** the "play next" item plays (a manual skip overrides repeat-one).
12. **Given** a queue item that the service reports as unavailable, **When** advancement reaches it, **Then** it is marked "Unavailable" in the queue, an info notification "Skipped <title> — unavailable" is raised, and playback advances to the next candidate.

### User Story 3 - Transfer playback to and from another Connect controller (Priority: P3)

The same account is also open in another app or device that can control playback on the account (a "controller"). That controller can hand playback over to ModPlayer, which accepts it and starts playing immediately with no extra step from the user. Conversely, the user (via that other controller) can move playback away from ModPlayer, which then stops locally, keeps its window and queue state intact, and clearly shows that audio is now playing somewhere else. Any transport command that arrives from another controller while ModPlayer holds playback is treated exactly like a command the local user gave, and ModPlayer reports its own state back so other controllers stay in sync.

**Why this priority**: This is what makes ModPlayer a genuine Connect receiver rather than an isolated player, and it's explicitly named in the prompt — but a user can get real value from Stories 1 and 2 with zero other controllers ever appearing, so it ranks after them.

**Independent Test**: From a second Connect controller on the same account, transfer playback to ModPlayer and confirm it starts playing; then transfer away and confirm ModPlayer stops locally, retains its UI/queue state, and shows the other device's name; then issue a play/pause/seek from the other controller while ModPlayer holds playback and confirm ModPlayer's transport reflects it; finally pause locally and confirm the other controller shows ModPlayer paused within 1 s.

**Acceptance Scenarios**:

1. **Given** ModPlayer is signed in with a Premium account and not currently the active Connect device, **When** another controller on the same account transfers playback to ModPlayer, **Then** ModPlayer accepts the transfer, replaces its local queue with the transferred context, and begins playing the handed-off track without requiring a local user action.
2. **Given** ModPlayer is actively playing as the Connect device, **When** the user transfers playback away using another controller, **Then** ModPlayer stops local audio output, retains its current queue, position, shuffle/repeat, and window state exactly as they were, does not mirror the remote device's progress, and displays a "Playing on <other device name>" banner with a **Play here** action.
3. **Given** ModPlayer shows "Playing on <other device>", **When** the user brings playback back to ModPlayer from that other controller or presses **Play here**, **Then** ModPlayer resumes acting as the active Connect device with the incoming protocol state as authoritative and plays normally again.
4. **Given** ModPlayer is the active Connect device, **When** a play, pause, seek, skip, or volume command arrives from another controller on the account, **Then** ModPlayer's transport and UI update exactly as if the local user had issued that command (volume commands set master volume).
5. **Given** ModPlayer is not the active Connect device (another device is playing), **When** the user presses play, skip, or seek in ModPlayer, **Then** ModPlayer requests the transfer back to itself and applies the command once granted; pause and stop do nothing; volume changes only the local master volume.
6. **Given** ModPlayer requested a transfer to itself, **When** the request is not granted within 5 s, **Then** a warning notification "Couldn't take over playback" is raised and local state is unchanged.
7. **Given** ModPlayer is the active Connect device, **When** the local user pauses, seeks, changes volume, or the track changes, **Then** a second controller on the account observes the new state within 1 s.
8. **Given** the account is signed in but playback is not permitted (non-Premium or unknown tier), **When** other controllers list devices, **Then** ModPlayer is not registered and its transport is disabled with an inline reason.

### User Story 4 - Stay playing through network trouble, and fail clearly when the protocol breaks (Priority: P4)

While a track is playing, ModPlayer is always working ahead of the playhead: fully pre-buffering the current track as fast as the connection allows and pre-fetching the next queued track. If the connection degrades, playback keeps going from what's already buffered; only if the buffer genuinely runs dry does the transport show "buffering" and resume automatically once data returns, without ever skipping the track. If the receiver protocol itself breaks (the service changes something ModPlayer's Connect Audio Source can no longer speak), the app reports this clearly instead of crashing or behaving unpredictably.

**Why this priority**: This is resilience and error-handling on top of a working transport and queue; it materially matters for a real listening session on imperfect Wi-Fi or a live gig, but the app must already play tracks correctly (Stories 1–3) before its failure behavior is meaningful to test.

**Independent Test**: Start playback, then simulate degraded and then fully cut connectivity mid-track and confirm playback continues from buffer and then shows "buffering" without skipping; separately, simulate a receiver-protocol failure and confirm the app shows the "source unavailable" message with a status-page link instead of crashing.

**Acceptance Scenarios**:

1. **Given** a track begins playing, **When** streaming starts, **Then** the client pre-buffers that track fully as fast as the connection allows (not throttled to real-time playback speed) and, once complete, pre-fetches the next item per the advancement order; only the current and next tracks are held, in memory.
2. **Given** a track is playing and enough of it is already buffered, **When** the connection quality drops significantly, **Then** playback continues uninterrupted from the buffered data with no audible dropout, and the transport shows "Reconnecting…" while the source retries with backoff.
3. **Given** a track is playing, **When** the buffer runs completely dry because the connection can't keep up, **Then** the transport shows `buffering`, the position stops advancing, the track is not skipped, and playback resumes automatically once ≥ 2 s of audio is decoded again.
4. **Given** the user seeks past the end of the current track, **When** the seek is applied, **Then** the position clamps to the end of the track and the queue advances exactly as on natural track end (repeat-one restarts the same track).
5. **Given** the Connect receiver protocol breaks in a way the client cannot recover from (registration/handshake or version rejected, or a required message cannot be parsed), **When** the failure is detected, **Then** the Audio Source reports `source unavailable`, the transport is disabled with an inline reason, a critical notification with **Status page** and **Retry** actions is raised, the app does not crash, and navigation, Settings, and the queue view remain usable.
6. **Given** the app is showing "source unavailable", **When** the user presses **Retry** after the underlying issue is resolved, **Then** the source re-initializes and normal streaming resumes without restarting the application; when the source flagged "client update required", the message says so and no **Retry** is offered.
7. **Given** a transient failure has lasted 30 s, **When** the threshold is reached, **Then** a warning notification "Connection lost — playback continues from buffered audio" is raised, and it clears automatically when the connection recovers; transient failures never escalate to "source unavailable" by duration alone.
8. **Given** the session credential expires mid-track, **When** the next track must be loaded, **Then** buffered audio finishes, the transport shows `buffering` for the next load, and only 002's "Session expired — sign in again" notification is shown; playback resumes after a successful refresh or re-sign-in.
9. **Given** the user signs out, or the session is revoked, during playback, **When** the operation is applied, **Then** playback stops immediately, the queue and buffers are cleared, and the Connect device is deregistered before the sign-in step is shown.
10. **Given** the account is downgraded from Premium mid-session, **When** the downgrade is detected, **Then** the current track finishes from buffer, the transport is then disabled with an inline reason, the device deregisters, and a warning notification with **Open upgrade page** is raised.

### Edge Cases

- What happens when the user seeks into a portion of a streamed track that hasn't been fetched yet? → The transport shows the requested position immediately and enters `buffering` until ≥ 2 s from that position is decoded, then plays from there (see Clarifications, Q-2).
- What happens when a remote controller pauses ModPlayer while a local seek or skip is already in flight? → The most recently applied command wins; there is no plugin transport focus in this slice, so host-local and remote-controller commands are peers, both treated as user commands, applied in arrival order.
- What happens when the output device is removed while streaming? → Covered by 001's existing device-fallback behavior (FR-012 in 001-walking-skeleton); this slice adds no new output-device handling.
- What happens if the queue becomes empty (every item removed)? → Playback stops, the transport shows a stopped state, and the now-playing view shows no current track.
- What happens when the last item ends (or is skipped) with repeat off? → Transport `stopped`, cursor on the last item at position 0, queue retained; pressing play replays that item.
- What happens if "play next" targets a track that becomes unavailable before it's reached? → It is marked "Unavailable", skipped with an info notification, and the queue advances to the following item; if every remaining candidate is unavailable, the transport stops as at end of queue.
- What happens when a transfer-to-ModPlayer request arrives while ModPlayer itself is mid-seek or mid-skip? → The transfer is honored: the incoming track/state from the protocol becomes authoritative and any in-flight local command targeting the previous state is discarded without error.
- What happens when two transfer-away and transfer-to events arrive in quick succession? → They are applied strictly in the order received from the service; ModPlayer never ends up in an inconsistent "half transferred" state (it is either the active device or it isn't).
- What happens when the app is closed and reopened while another device is the active Connect device? → On launch, the queue is empty (no persistence in this slice); ModPlayer queries current Connect state and, if another device is active, shows the "Playing on <other device>" banner rather than an empty local transport.
- What happens when the device name is edited to whitespace only or to more than 64 characters? → Whitespace-only restores the default name; over-length input is rejected inline and the previous name is kept.
- What happens when the OS hostname cannot be read? → The default device name is "ModPlayer".
- What happens when shuffle is toggled while paused or stopped? → The effective order is recomputed immediately; the current item and position are unchanged.
- What happens when a remote controller sets volume while safe-volume-on-startup is enabled? → The remote value is applied to master volume as-is (the cap applies only at launch, per 001).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The system MUST provide a Connect Audio Source that registers ModPlayer with the streaming service as a named receiver device — default name "ModPlayer on <OS hostname>" ("ModPlayer" if the hostname is unavailable), editable in Settings › Playback › "Device name" (trimmed, 1–64 characters, empty restores the default, over-length rejected inline, device-scoped, persisted via 001's settings store, re-registered within 5 s of a rename); receives track load requests and the encrypted stream for the signed-in account; and decrypts and decodes the stream in-client. Registration MUST occur only while an AccountSession exists and playback is permitted (Premium); it MUST deregister on sign-out, revocation, downgrade, and application exit. *(FR-3.1, INT-2.1; 002 FR-010; Constitution V — decoded audio never leaves the engine)*
- **FR-002**: The Connect Audio Source MUST implement the same `AudioSource` interface as 001's synthetic source (extended only additively — track load, buffer status, source health — such that the synthetic source remains a valid implementor and 001's tests pass unchanged), MUST split into a real-time half that never performs I/O in `fill`/`seek` and an off-real-time streaming half, MUST be the only component in the system that knows the streaming service's protocols, and MUST be packaged as an independently versioned module so it can be updated, replaced, or disabled without requiring changes to any other component. *(Constitution I, IV; A-11; INT-2 Constraints; 001 contract `audio-source.md`)*
- **FR-003**: The system MUST provide a full transport: play, pause, stop, skip forward, skip back, seek to any position, and volume, applying to the currently playing item regardless of whether it originated locally or from another controller. Transport states are `stopped | playing | paused | buffering` with `buffering` a sub-state of `playing`. Stop MUST reset position to 0 while retaining the current track, the queue, and active-device status. Seek while stopped MUST set the position and enter `paused`. Volume MUST be 001's master volume (0–100 %); no separate per-track or per-source volume exists. *(FR-3.1.1; 001 FR-011/FR-015)*
- **FR-004**: Skip back MUST restart the current track from position 0 when invoked more than 3 seconds into the track, and MUST move to the most recently played item in history (restarted from 0) when invoked at or before 3 seconds in; with empty history it MUST restart the current track. History is the session-only, shuffle-aware ordered list of items actually played, bounded at 100 entries. *(FR-3.1.1)*
- **FR-005**: Seeking MUST land within 50 ms of the requested position on already-buffered audio; seeking into an unbuffered position MUST show the requested position immediately, enter `buffering`, and resume once ≥ 2 s of audio from that position is decoded (or track end is reached), targeting 500 ms on a 10 Mbit/s connection as the product-level goal (see Clarifications, Q-2). Seeking past the end of the track MUST clamp the position to the track's end and advance exactly as on natural track end per FR-014. *(FR-3.1.2, NFR-1.5, EC-3.1, EC-3.2)*
- **FR-006**: The system MUST report playback position to the UI at least 60 times per second with ≤ 5 ms jitter while `playing`, derived from the Real-Time Audio Engine's audio clock (per 001), not a UI timer; while `paused`, `stopped`, or `buffering` the reported value MUST NOT change. *(FR-3.1.3, NFR-1.9)*
- **FR-007**: Track transitions MUST be gapless whenever both the outgoing and incoming decoded audio are available at the point of transition and the format allows it; when they are not, the transition MUST still occur without an error, crash, or added silence beyond what streaming state requires. *(FR-3.1.4; Clarifications, Q-3)*
- **FR-008**: Playback MUST continue unaffected when the main window is minimized, hidden, moved to a non-visible virtual desktop, or loses focus to another application. Closing the main window MUST quit the application on all platforms (stop audio, discard buffers, deregister the device); no tray or background mode ships in this slice. *(FR-3.1.6; Constitution X)*
- **FR-009**: The system MUST pre-buffer the currently playing track fully as fast as the connection allows (not rate-limited to real-time playback speed) and, once complete, MUST pre-fetch the next item per FR-014's advancement order fully. At most the current and next tracks MUST be held, in memory only; nothing MUST be written to disk. On advance the previous track's buffers MUST be discarded. On any queue-order, shuffle, or repeat change the pre-fetch target MUST be recomputed within 1 s and a stale fetch cancelled. *(FR-8.3.1; Constitution V)*
- **FR-010**: When the connection degrades mid-track, playback MUST continue from already-buffered data with no dropout; when the buffer is exhausted, the transport MUST enter `buffering`, stop advancing position, and resume playback automatically once ≥ 2 s of audio ahead of the playhead is decoded (or track end is reached), and MUST NOT skip the track. The same ≥ 2 s readiness threshold gates first audio on a freshly streamed track. *(FR-8.3.2, EC-3.3, NFR-2.5, NFR-1.7)*
- **FR-011**: The system MUST maintain a play queue derived from the current listening context plus user-added "play next" items, which form a contiguous block immediately after the current item in add order (FIFO). The queue MUST use a play cursor (played items are not removed). Queue, cursor, shuffle/repeat mode, and position are in-memory only in this slice; every launch starts with an empty queue. *(FR-3.2.1; NFR-2.6 deferred to 004-performance/003)*
- **FR-012**: The user MUST be able to view the queue (current item plus upcoming items in effective play order, play-next items visibly distinguished, history not shown), reorder items within it by drag and by keyboard **Move up** / **Move down**, add an upcoming item to the play-next block via **Play next**, and remove items from it (including the currently playing item, which advances playback per FR-014 ignoring repeat-one rather than leaving a gap). *(FR-3.2.2; NFR-6.1)*
- **FR-013**: The system MUST support shuffle and repeat modes off, one, and all. Enabling shuffle MUST keep the current item and play-next block in place and randomize only the remaining upcoming context items (each played once before any repeat); disabling it MUST restore the original context order after the play-next block with the cursor on the current item. Under repeat-all with shuffle, the order MUST be re-shuffled at each wrap. *(FR-3.2.3)*
- **FR-014**: On natural track end or seek-past-end, the system MUST advance in this order: (1) repeat-one → restart the same track; else (2) head of the play-next block; else (3) next upcoming context item (shuffled order if shuffle is on); else (4) repeat-all → wrap to the first upcoming item, or repeat-off → `stopped` with the cursor on the last item at position 0 and the queue retained. Explicit skip forward and removal of the current item MUST use the same order but skip step (1). If the queue is empty, the transport MUST be `stopped` with no current track. *(FR-3.2.1, FR-3.2.3)*
- **FR-015**: The system MUST accept a Connect transfer of playback initiated by another controller on the same account, replacing the local queue with the transferred context (the current track plus any upcoming items the protocol supplies; shuffle/repeat from the transferred state when supplied, else local values retained), discarding in-flight local commands, and immediately starting playback of the handed-off track with no additional local user action required. *(INT-2.2)*
- **FR-016**: When another controller transfers playback away from ModPlayer, the system MUST stop local audio output, retain the current queue, position, shuffle/repeat, and window/UI state unchanged, MUST NOT mirror the remote device's track or position, and MUST display a "Playing on <other device name>" banner with a **Play here** action. *(INT-2.3, INT-2.5)*
- **FR-017**: Playback commands (play, pause, seek, skip, volume) arriving from another controller on the account MUST be applied exactly as host user commands, taking effect immediately and updating ModPlayer's own transport UI to match; remote volume MUST set master volume on the 0–100 % scale. *(INT-2.4, FR-3.3.2 precedence rule applied to remote controllers since no plugin transport access exists in this slice)*
- **FR-018**: When ModPlayer is not the active Connect device, local play, skip forward/back, seek, and **Play here** MUST request transfer of playback to ModPlayer and apply the command once granted; local pause and stop MUST be no-ops; local volume MUST change only master volume. If the transfer is not granted within 5 s, the system MUST raise a warning notification "Couldn't take over playback" and leave local state unchanged. *(INT-2, derived to make FR-3.1's transport meaningful whenever ModPlayer is signed in)*
- **FR-019**: On application launch (or reconnect) while signed in with playback permitted, the system MUST query current Connect device state and reflect it accurately — showing the "Playing on <other device>" banner if another device is active, or a stopped, empty local transport otherwise — rather than assuming a default state. *(INT-2, edge case handling; 001 FR-015)*
- **FR-020**: When the Connect Audio Source classifies a failure as unrecoverable (registration/handshake or protocol version rejected, or a required message cannot be parsed), it MUST report `source unavailable` (optionally flagged "client update required") to the host, and the system MUST disable the transport with an inline reason and raise a **critical** notification "Streaming is unavailable — the receiver protocol may have changed" with a **Status page** action (build-time-configured URL opened in the system browser) and a **Retry** action that re-initializes the source; when the flag indicates a client update is required the message MUST say so and **Retry** MUST be omitted. The app MUST NOT crash, and navigation, Settings, and the queue view MUST remain usable. *(INT-2.7)*
- **FR-021**: On a transient failure (network error, timeout, disconnection, expired credential), the Connect Audio Source MUST retry indefinitely with backoff starting at 1 s and doubling to a 60 s cap, playback MUST continue from any available buffer, the transport MUST show an inline "Reconnecting…" status, and after 30 s of continuous failure the system MUST raise a **warning** notification "Connection lost — playback continues from buffered audio" that clears automatically on recovery. Transient failures MUST NOT escalate to `source unavailable` by duration alone. No global connectivity indicator is introduced in this slice. *(INT-2.6; 002 backoff convention)*
- **FR-022**: This slice MUST NOT introduce any UI for search, library browsing, playlists, the waveform, crossfade configuration, media keys, sleep inhibition, or plugin transport access; the only track-sourcing surface is **Settings › Developer › "Play from account"**, which fetches up to 20 of the user's most recently played tracks (falling back to saved tracks), replaces the queue with them, starts playing the first, and is hidden when playback is not permitted. *(Scope boundary)*
- **FR-023**: All new interactive elements introduced in this slice (transport controls, queue view rows and their Move up / Move down / Play next / Remove actions, device-name field, transfer banner and Play here, notification actions) MUST be operable by keyboard alone and MUST expose an accessible name, role, and state, consistent with 001 and 002. *(NFR-6.1, NFR-6.2; Constitution X)*
- **FR-024**: All user-facing strings introduced in this slice MUST be externalized; English (en-US) is the only shipped locale in this slice, consistent with 001 and 002. *(NFR-7.1; Constitution X)*
- **FR-025**: While registered, the system MUST report its playback state (play state, current track, position, volume, shuffle, repeat) to the streaming service on every transport state change within 1 s and on the protocol's heartbeat cadence, so that other controllers on the account reflect ModPlayer's state. *(INT-2 outbound state reports)*
- **FR-026**: When a queue item cannot be loaded because the service reports it unavailable, the system MUST mark it "Unavailable" in the queue, skip it with an **info** notification "Skipped <title> — unavailable", and continue advancing per FR-014; if no playable candidate remains, the transport MUST stop as at end of queue. *(INT-3.3, FR-8.2.4 applied narrowly)*
- **FR-027**: Account-session events MUST affect playback as follows: non-Premium or unknown tier → not registered, transport disabled with inline reason ("Premium required" / "Subscription not verified"); sign-out or remote revocation → playback stops immediately, queue and buffers cleared, device deregistered before 002's sign-in step is shown; credential expiry → buffered audio continues, the next load is treated as transient (`buffering`) until 002's refresh or re-sign-in succeeds, with no additional notification beyond 002's; downgrade detected (load rejected with a tier reason, or Re-check subscription reports non-Premium) → current track finishes from buffer, then transport disabled, device deregistered, and a **warning** notification with **Open upgrade page** raised. *(EC-1.2, EC-1.3, EC-1.4; 002 FR-010/015/019/021)*

### Key Entities

- **Connect Receiver Device**: The registration ModPlayer holds with the streaming service identifying it as a controllable playback endpoint on the signed-in account — a display name (default "ModPlayer on <OS hostname>", user-editable in Settings › Playback, device-scoped) and current active/inactive status relative to other controllers. Exists only while signed in with playback permitted.
- **Connect Audio Source**: The independently versioned module implementing the `AudioSource` interface for the streaming service; a real-time half (`fill`/`seek` over a lock-free ring buffer) and an off-real-time streaming half (registration, heartbeat, fetch, decrypt, decode, buffer management, outbound state reports); owns all protocol knowledge; reports playback-relevant state (underrun/buffering, transient vs. unavailable health, "client update required") to the host engine and nothing else.
- **TrackRef**: A reference to a track in the user's catalog (per DM-2) sufficient to enqueue and play it — identity, title, artists, album, artwork reference, duration, and availability.
- **Queue**: An ordered, cursor-based list of queue items (played items are not removed) derived from a listening context plus a contiguous play-next block after the current item, with shuffle state (effective order over the remaining context items), repeat mode (off / one / all), and a session-only, bounded (100) play history supporting the skip-back-within-3-seconds rule. In-memory only in this slice.
- **Queue Item**: One entry in the Queue — a TrackRef plus its origin (context-derived vs. user-added "play next"), position in effective order, and an availability mark.
- **Playback Transport State**: `stopped | playing | paused | buffering` (`buffering` a sub-state of `playing`), position (sourced from the audio clock), current track, and volume (001's master volume) — extending 001's minimal transport with position tracking, skip, and seek.
- **Buffer State**: Pre-buffer progress for the current track and pre-fetch progress for the next item (per advancement order); readiness = ≥ 2 s decoded ahead of the playhead or track end; drives the `buffering` transport state. Only current + next are held, in memory.
- **Remote Transfer Event**: A record of a transfer to or away from ModPlayer initiated by another controller, including the other device's name and, on transfer-to, the transferred context (current track, upcoming items, shuffle/repeat if supplied), used to drive the "Playing on <other device>" banner and the active/inactive Connect Receiver Device status.
- **Source Health**: The Connect Audio Source's classification of its last failure — `ok`, `transient` (with retry backoff state and time since first failure), or `unavailable` (with an optional "client update required" flag) — driving the Reconnecting… status, the 30 s warning, and the source-unavailable message.

## Amendment (2026-09-16): Session-sourced reads, not the public Web API

**Status**: Supersedes the parts of FR-001/FR-019/FR-022/FR-027 and research
R3/R8/R9 that assumed the signed-in OAuth token can call the public Web API
(`api.spotify.com`). Verified false in live testing (see plan.md
"Post-Implementation Findings (T098)" and research R8 amendment).

**Problem**: The receiver session must authenticate with Spotify's own
"Keymaster" desktop `client_id` (002 R1; a third-party id gives
`INVALID_CREDENTIALS` at session login — verified). But as of 2026 Spotify
returns a blanket **HTTP 429** for every public-Web-API call bearing a
Keymaster-minted token (verified; independently confirmed by go-librespot
#282 / #378 and librespot-python #328). Shipping our own Dashboard
`client_id` to escape the 429 is not viable: Dashboard apps are development
mode (≤ 5 allow-listed users; extended quota needs ≥ 250k MAU — 002 R4), so
it would require every end user to register their own app. No token serves
both surfaces; a per-user second credential is developer-only, not
shippable.

**Decision**: keep a **single** Keymaster credential (002's existing flow, no
second sign-in) and source every read this slice needs from the **session**
instead of the public Web API — the approach the librespot ecosystem itself
adopted after the same discovery (go-librespot removed its Web API
passthrough in #378 and reads via the session's internal `SpClient`):

- **Tier / playback permission (FR-027)**: derive from the receiver session,
  not `GET /v1/me`. A session that establishes and is not rejected is
  Premium; a `PremiumAccountRequired` rejection at login (already surfaced as
  `SourceEvent::TierRejected`) means non-Premium → transport disabled,
  "Premium required". Because permission now comes from the session, the
  device attempts to register as soon as an account session is **Active**
  (signed in), rather than being gated on a prior tier check; the session
  result then sets the tier. The public tier check is removed from the
  hot path (it can remain only as a best-effort enrichment that silently
  ignores a 429/`Unknown`).
- **Other device's name & launch Connect state (FR-016/019)**: from the
  Connect cluster state the session already receives, not `GET
  /v1/me/player`. Fallback "another device" is retained when a name is
  absent.
- **"Play from account" (FR-022)**: source real tracks through the session's
  `SpClient` (e.g. `get_rootlist` → a playlist's tracks, or track metadata),
  not `GET /me/player/recently-played` / `/me/tracks`. This surface is
  explicitly throwaway dev scaffolding (see Assumptions); if a suitable
  session read is unavailable it degrades to a clear "unavailable" state
  rather than blocking.

**Non-goals of this amendment**: no second OAuth flow, no second SecureStore
entry, no Dashboard-app requirement, no change to the streaming/transport/
queue behaviour already specified. The `MODPLAYER_OAUTH_CLIENT_ID` /
`MODPLAYER_OAUTH_PORT` overrides remain for developer BYO-app use only.

**Acceptance delta**: SC-013's "non-Premium never registers a device"
becomes "non-Premium registers, is rejected by the session with
`PremiumAccountRequired`, and is then deregistered with transport disabled" —
observationally equivalent (no playable device remains) but reflecting that
the session is now the tier authority.

## Assumptions

- The "Play from account" surface (Settings › Developer) used to source real tracks for this slice is a temporary, developer/demo-facing entry point, not a designed user feature; it is superseded when the search/library slice ships and may be removed or hidden from the release build at that point. It uses the same minimal account read integration 002 already exercises for the account check.
- The "current listening context" that seeds the queue (playlist, album, search results) is a concept the queue mechanism supports generically; this slice does not implement any of those context sources' UI, only the queue's ability to be seeded from a context and to accept "play next" additions.
- "Cached" in the 50 ms seek/play target (NFR-1.4/1.6) refers to audio already pre-buffered in memory for the current streaming session, not the offline disk cache (out of scope for this slice, which does not persist decrypted or encrypted audio beyond the in-memory pre-buffer).
- A quality-tier selector (FR-8.3.3) is deferred; the account's automatically negotiated tier is used without a user-facing choice in this slice.
- Transport focus arbitration (FR-3.3) is out of scope; with no plugin execution shipped yet, the host and relayed remote-controller commands are the only command sources, so no focus-holder concept is needed in this slice.
- "Another controller on the same account" is assumed reachable via the same streaming-service integration this slice's Connect Audio Source already implements (INT-2); no separate test harness beyond the service's own multi-device support is assumed necessary, though automated tests will use a protocol test double per Constitution IV/VIII (including throttled, disconnecting, handshake-rejecting, and second-controller behaviors).
- The project's status page referenced in the "source unavailable" message is assumed to already exist or to be a simple external link configured at build time; standing it up is not part of this slice's engineering work.
- The 2 s readiness threshold, 30 s transient-warning delay, 5 s transfer timeout, 64-character device-name limit, and 100-entry history bound are conventional defaults recorded under Clarifications; all are internal constants that a later slice may tune without a contract change.
- Media keys, OS now-playing, sleep inhibition, OS notification routing, and cross-restart persistence of queue/position are delivered by 004-performance/002 and /003 and are intentionally absent here.
