# Feature Specification: Section Loop Bundled Plugin

**Feature Branch**: `feature/012-section-loop-plugin`

**Created**: 2026-09-20

**Status**: Clarified (2026-09-20, specify pass + clarify pass) — no open [NEEDS CLARIFICATION] markers, no human escalations; ready for `/speckit-plan`

**Input**: User description: "Ship Section Loop, the first bundled plugin: the tool a practicing musician uses to drop A and B around a four-bar solo and drill it hands-free. It must be built only on the public plugin API — no private host interface — because it doubles as living documentation and a starting point others copy, and it is released under the same license as the host. The plugin declares `transport.control`, `markers.write`, `ui.panel`, `ui.overlay`, and `ui.shortcuts`, with `analysis.read` as an optional permission reserved for beat snapping in a later wave. It registers actions: set A, set B, toggle loop, nudge A earlier/later, nudge B earlier/later, set cue 1–8, jump to cue 1–8, snap toggle, and clear markers, with default shortcuts `I`, `O`, `L`, and `[` / `]`. Its panel offers A/B/Loop controls, a marker list with rename and color, a loop count field (default infinite), and a 'snap to beat' toggle that stays disabled with an explanation until analysis exists. It draws A/B and cue markers as overlays on the waveform. Markers are persisted through the host's per-track state, not the plugin's own storage, so they survive the plugin being disabled and are visible to other plugins. When the user presses `L`, the plugin requests transport focus and arms the loop; the seam is gapless because the host evaluates it on the real-time path. Cue points are single named, colored markers in slots 1–8. Acceptance: when the user plays a track, presses `I` at 1:02 and `O` at 1:10, then `L`, the waveform shows A and B and playback loops gaplessly between them until `L` is pressed again. When the user closes the app and reopens the same track tomorrow, A and B are exactly where they were. When another plugin holds transport focus and the user presses `L` in Section Loop's panel under the default policy, focus moves to Section Loop and the loop arms. When the user disables Section Loop mid-loop, the loop releases, markers stay on the waveform, and the host's own marker UI can still edit them."

**Source**: [ModPlayer-Software-Specification.md](../autonomous/ModPlayer-Software-Specification.md) — FR-13.1 Section Loop, § 13 Bundled reference plugins, J-2 — Drill a solo with Section Loop (S-1), § 5 Key scenarios (S-1), § 4 Jobs-to-be-done (JTBD-1), GOV § 1 Licensing (GOV-1.3), FR-5 Markers/loops/cue points (host primitives), FR-3.3 Transport focus, Part 5 § 6.1/6.2/6.5 Plugin API (`transport.control`, `markers.write`, `ui.*`). **Prerequisites**: [009-plugin-runtime-and-permissions](../009-plugin-runtime-and-permissions/spec.md) (plugin runtime, Capability Gateway, permission grants, fault isolation), [010-transport-focus](../010-transport-focus/spec.md) (`request_focus`/`arm_loop` arbitration this plugin drives), [011-plugin-ui-contributions](../011-plugin-ui-contributions/spec.md) (`ui.panel`/`ui.overlay`/`ui.shortcuts`, whose own worked examples already anticipate this plugin — see Clarifications), and [006-markers-loops-and-cues](../006-markers-loops-and-cues/spec.md) (the host-native Marker/LoopRegion primitives and `I`/`O`/`L`/marker-list UI this plugin composes rather than reimplements).

**Scope boundary**: Does not cover beat snapping, "loop last N beats", or MIDI mappings — those arrive with the analysis and MIDI waves (FR-13.1.6 is explicitly SHOULD/deferred). Does not modify the host-native marker/loop editor shipped in 006, the Transport panel shipped in 010, or the plugin runtime/UI-contribution mechanics shipped in 009/011 — this feature is a *consumer* of those APIs. The one exception is a single **additive** plugin-API minor bump (FR-017: two new `markers.write` calls and one new field on `markers.list()`), required because the shipped `markers` API cannot express an A-only loop region or a repeat count — both host primitives FR-13.1 obliges this plugin to drive (see Clarifications, clarify pass).

- Q: 006 already binds `I` (set A), `O` (set B), and `L` (toggle loop) as **host** default actions operable without any plugin (FR-5.1.3), and this feature's own prompt asks Section Loop to register the *same* three keys as its own default bindings. Does Section Loop's plugin ever actually receive these keystrokes? → A (D, 011 FR-011/EC-6.8 — already-ratified cross-tier conflict rule, whose own acceptance text uses this exact `L` collision as its worked example, line 29 of 011's Clarifications): no, not by default. Per 011 FR-011, a binding collision between a **host** action and a **bundled plugin** action is resolved automatically in the host's favor: the host's `I`/`O`/`L` keep firing exactly as 006 shipped them, and Section Loop's identically-bound actions are flagged inactive in the shortcut map until the user rebinds one side in Settings › Controls (fully supported, 011 FR-010). Section Loop still registers these three defaults per FR-13.1.2/the prompt — the registration itself always succeeds (011 FR-010) — but a fresh install's raw keypresses drive the host's pre-existing marker/loop editor, not this plugin, until the conflict is resolved once. This is expected product behavior, not a defect: Constitution X guarantees the user (via the host's own default) is never silently overridden by a plugin. Section Loop's **panel controls** (FR-004 below) are unaffected by this conflict — they dispatch `action_invoked`/`panel_interaction` directly (011 FR-002/FR-008), never through the contested keyboard binding — so every acceptance scenario in this spec that must be true unconditionally, from a fresh install, is written against the panel, and the keyboard-driven scenario is written as the state reached after the one-time rebind.
- Q: FR-13.1.2 lists "nudge A/B earlier/later" (naming both markers) while the prompt's own default-shortcut list gives only `[`/`]` (two keys, not four) and J-2 step 2 (source doc) says "`[`/`]` to nudge **the active marker**." How do two keys cover both markers? → A (D, J-2's own wording, read as the mechanism FR-13.1.2's phrase describes): `[`/`]` nudge whichever of A or B was more recently placed or moved in the current session — the "active marker," defaulting to B when neither has been touched yet (matching the prompt's own worked example: set A, then B, then nudge near the just-placed B; **refined by the clarify pass**: B if it exists, else A, else no-op; step fixed at 10 ms — see FR-006). This is exactly two registered actions (`nudge_earlier`, `nudge_later`), not four; a plugin implementing "nudge A specifically" or "nudge B specifically" as separate, explicitly-mappable actions is left to a future MIDI-mapping wave (out of scope here, mirroring J-3's explicit per-control MIDI mapping of "loop-in"/"loop-out" individually).
- Q: FR-13.1.3 asks for "a marker list with rename and color," but 011 FR-002 already fixes the `marker list` widget kind as **read-only** (seek-on-select only; no rename/recolor interaction it can emit) — a widget contract this feature cannot reopen. How is "rename and color" delivered? → A (D, 011 FR-002's fixed contract; the prompt's own closing acceptance line — "the host's own marker UI can still edit them"): Section Loop's panel includes a `marker list` widget listing the plugin's own markers (A, B, cues 1–8), live-updating, whose row selection seeks (011 FR-002) — satisfying the "marker list" element. Renaming and recoloring happen through the host's own, already-shipped Markers panel and waveform marker glyphs (006 FR-004/FR-021), which edit any marker regardless of owner (FR-5.1.3) and are always available side-by-side with Section Loop's panel. This reuses an existing, universal capability instead of duplicating it inside a widget contract that cannot support it, and is the literal mechanism the prompt's own last sentence names.
- Q: FR-13.1.4 asks the plugin to "draw A/B and cue markers as overlays," but FR-4.1.3 already has the host natively render every host-model marker (`markers.write`-created ones included) on the waveform regardless of plugin state — and the prompt's disable acceptance requires markers to "stay on the waveform" after Section Loop is disabled, while 011 FR-016 clears a disabled plugin's own overlays. Are these in tension? → A (D, FR-4.1.3 + 011 FR-016 read together): no. Section Loop's A/B and cue markers are visible on the waveform through **two** independent layers at all times the plugin is enabled: (1) the host's own native marker rendering (FR-4.1.3), which shows every `Marker`/`LoopRegion` record regardless of owner or plugin state and is what keeps them visible after disable; and (2) Section Loop's own `ui.overlay` contribution (FR-13.1.4; e.g., labeled A/B brackets and cue-slot glyphs in the plugin overlay lane), an additive decoration that disappears on disable/suspend per 011 FR-016 without affecting layer (1). The disable acceptance scenario is satisfied by layer (1) alone; layer (2) exists to exercise `ui.overlay` as the living-documentation surface FR-13.1.4 asks for.
- Q: FR-13.1.3's "snap to beat" toggle and the optional `analysis.read` permission — does this slice's Section Loop ever call an analysis API? → A (D, this feature's own Scope boundary: "does not cover beat snapping... arrives with the analysis wave"): no. The panel's "Snap to beat" toggle is registered and ~~always rendered **disabled**~~ — **realigned by the clarify pass**: always shows **off** (011 has no plugin-settable disabled state; a flip is immediately reverted) — with an explanatory label ("Needs beat analysis — coming in a later update"), for the entire life of this slice; the plugin manifest declares `analysis.read` (matching FR-13.1.1's exact permission list, so the manifest and the later analysis wave need no shape change) but makes no call under it. Snapping activates only once a later wave ships both host beat analysis and this toggle's live-enable logic — out of scope here.
- Q: What is "clear markers" scoped to? → A (D, `markers.write`'s "delete (own markers only)" rule, Part 5 § 6.2): clears every marker Section Loop owns for the current track — A, B (~~disarming the loop region first if armed~~ — **realigned by the clarify pass**: the host disarms when an endpoint is deleted, no `disarm_loop` call), and any of its cue slots 1–8 that are set — and nothing else; host-created or another plugin's markers on the same track are untouched. This mirrors, at plugin-owned scope, what 006's host-level "Clear all markers" already does at track scope.
- Q: Is Section Loop enabled by default? → A (A, carried forward from the source document's own tag at J-2 step 2: "it is enabled by default after first run *[Assumption]*"): yes, consistent with its role as the reference/living-documentation plugin; the enable/disable mechanism itself, and first-run onboarding generally, are 009's concern and unchanged by this feature.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Drop A and B and drill hands-free (Priority: P1)

A musician plays a track, marks the start and end of a passage while it plays, and loops it gaplessly with one control — repeatedly, without touching the mouse for anything but the initial marks — so they can drill it until it's solid.

**Why this priority**: This is the plugin's entire reason to exist (JTBD-1, S-1, J-2) and the concrete acceptance text the prompt leads with. Nothing else in this feature matters if a musician cannot mark a passage and loop it without an audible seam.

**Independent Test**: With Section Loop enabled and no other plugin holding transport focus, play a track, use its panel's Set A / Set B controls at two points, use its Loop control to arm, and verify the loop wraps with no audible gap or click and the waveform shows both markers; toggle Loop off and verify playback continues past B.

**Acceptance Scenarios**:

1. **Given** a track is playing and Section Loop is enabled, **When** the user activates Set A at 1:02 (via the panel, or via `I` once resolved to Section Loop per Clarifications), **Then** a Section-Loop-owned loop region with only A exists, A appears at 1:02 on the waveform (host rendering plus the plugin's overlay line/label) and in Section Loop's marker list; **When** the user then activates Set B at 1:10, **Then** B appears likewise and the region is complete (FR-13.1.2, FR-13.1.4; FR-007, FR-017).
2. **Given** markers A and B exist and the focus policy is the default, **When** the user flips the panel's Loop toggle on (or presses `L` once resolved), **Then** Section Loop calls `request_focus()` inside that interaction's handler and is granted focus (011 FR-026), calls `arm_loop` on its region, receives `loop_armed`, the toggle shows on, and when the playhead reaches B playback continues from A with no audible gap or click — the seam evaluated entirely on the host's real-time path (FR-13.1's prompt text; 006 FR-010; FR-6.1.5).
3. **Given** the loop is armed and wrapping, **When** the user flips Loop off, **Then** Section Loop calls `disarm_loop()`, the region disarms, the toggle shows off, and playback continues past B without looping (prompt acceptance).
4. **Given** the panel's "Repeat count (0 = infinite)" slider is set to 4, **When** the loop is armed and has wrapped 4 times, **Then** it releases automatically (host-side, FR-5.2.5), Section Loop receives `loop_disarmed` and shows the Loop toggle off, and playback continues past B.
5. **Given** the user flips Loop on with only A set (or with A and B less than 1 ms apart), **When** `arm_loop` is refused, **Then** the toggle reverts to off and the Status text shows the host's reason (FR-007; 006 FR-007).
6. **Given** A and B exist, **When** the user presses `]` three times, **Then** B (the most recently touched endpoint) moves 30 ms later, the overlays and marker list follow, and if the region is armed the change applies at the next buffer boundary (FR-006; 006 FR-011a).

### User Story 2 - Markers outlive the session and the plugin (Priority: P1)

The user's A/B markers and cue points are exactly where they left them tomorrow, and they remain visible and editable even if Section Loop itself is later disabled — because they belong to the track, not to the plugin.

**Why this priority**: This is the prompt's second acceptance line and the reason markers are a host primitive at all (FR-5.1.2, FR-11.3.1). A practice tool that forgets a musician's markers between sessions, or hides them the moment the plugin is turned off, fails its one job.

**Independent Test**: Set A, B, and one cue point; close and relaunch the app; reopen the same track and verify all three are at their original positions. Separately, disable Section Loop while a loop is armed and verify the loop releases, but A, B, and cue markers remain visible on the waveform and editable from the host's own Markers panel.

**Acceptance Scenarios**:

1. **Given** the user has set A, B, cue slot 1 and a repeat count of 4 on a track, **When** the app is closed and the same track is reopened later, **Then** A, B, and cue slot 1 are restored at their exact original positions before Section Loop observes `track_changed`; on `track_changed` Section Loop rediscovers its region via `markers.list()`, redraws its overlays, and its repeat slider shows 4; flipping Loop on arms that restored region (FR-5.1.2, FR-11.3.1, FR-11.3.2; FR-013, FR-012).
2. **Given** a loop is armed and Section Loop holds transport focus, **When** the user disables Section Loop, **Then** transport focus returns to the host immediately, the loop region disarms, and A, B, and any cue markers remain visible on the waveform via the host's native marker rendering (FR-3.3.6/010 FR-007; Clarifications).
3. **Given** Section Loop is disabled, **When** the user opens the host's own Markers panel, **Then** A, B, and the cue markers are listed there like any other marker and can be renamed, recolored, moved, or deleted without re-enabling Section Loop (FR-5.1.3).
4. **Given** Section Loop is later re-enabled, **When** its panel opens, **Then** its marker list shows the same A, B, and cue markers, unchanged by the disable/re-enable cycle.
5. **Given** Section Loop is enabled and the user drags A on the waveform or renames it in the host's Markers panel, **When** the edit commits, **Then** Section Loop receives `marker_changed` (actor `host`), re-lists, and its overlay line/label and marker list reflect the new position within the next UI update (009 clarify entry; FR-012).

### User Story 3 - The user's plugin choice always wins on transport focus (Priority: P2)

While another plugin holds transport focus, the musician can still bring Section Loop's loop under control in one action from its own panel, under the host's default focus policy — without fighting the other plugin or losing control.

**Why this priority**: This demonstrates Section Loop composing 010's transport-focus arbitration correctly (a core "living documentation" goal of GOV-1.3) and is the prompt's third acceptance line. It is P2 rather than P1 because it only matters once a second transport-controlling plugin is in play, which is not the primary single-plugin drilling flow of Story 1.

**Independent Test**: Enable Section Loop alongside a second fixture plugin holding `transport.control` (`MODPLAYER_PLUGIN_FIXTURES=1`); give the fixture plugin focus; then, under the default auto-on-interaction policy, flip Section Loop's Loop toggle and verify focus moves to Section Loop and the loop arms; switch to manual and verify the refusal path.

**Acceptance Scenarios**:

1. **Given** another plugin currently holds transport focus and the user's focus policy is the default (auto on interaction), **When** the user flips Section Loop's Loop toggle in its panel, **Then** the previous holder receives `focus_revoked`, Section Loop receives `focus_granted`, and the loop region arms in the same action (011 FR-026; 010 FR-004; prompt acceptance).
2. **Given** the user's focus policy is manual, **When** the user flips Section Loop's Loop toggle, **Then** `request_focus()` is recorded but not granted, `arm_loop` returns `no_focus`, the toggle reverts to off, and the Status text reads "Needs transport focus — give Section Loop focus in the Transport panel (T)"; **When** the user then gives Section Loop focus from the Transport panel, **Then** nothing arms by itself — flipping Loop again arms it (010 FR-005; Clarifications).
3. **Given** Section Loop holds transport focus with an armed loop, **When** another plugin's own transport call (e.g., `seek`) is attempted, **Then** it is refused `no_focus` and the loop's wrap behavior is unaffected (010 FR-001).
4. **Given** the user pressed the host's `L` (a local host transport action) while Section Loop held focus under the default policy, **When** the host disarms Section Loop's region and returns focus to the host, **Then** Section Loop receives `focus_revoked` then `loop_disarmed` and shows its Loop toggle off; **When** the user flips Section Loop's Loop toggle on again, **Then** the plugin re-requests focus inside the interaction, is granted it, and re-arms (010 FR-002/FR-014; Clarifications).
5. **Given** a cue is set in slot 3 and the default policy is active, **When** the user invokes `jump_cue_3` (via its user-bound key), **Then** Section Loop requests focus inside the handler, is granted it, and seeks to the cue with the play state unchanged (010 FR-001; 006 FR-014; FR-010).

### Edge Cases

- The user activates Set B before Set A: `set_loop_endpoint(nil, "b", pos)` creates the region with only B; a later Set A completes it. Set A after B's position (or vice versa): the host swaps the roles (A is always earlier; 006 FR-007) and Section Loop re-lists on `marker_changed` — it never reinterprets the host's result (FR-5.2.4).
- The user flips Loop on with only one endpoint set, or with A and B less than 1 ms apart: `arm_loop` is refused `invalid_state`/`region_incomplete` or `region_too_short`; the toggle reverts to off and the Status text shows the host's `message` (FR-5.2.4; 009 contract).
- The user flips Loop on before ever setting A or B (no region exists): no `arm_loop` call is made; the toggle reverts to off and the Status text reads "Set A and B in Section Loop first" (Clarifications).
- The user activates `[`/`]` before the plugin's region has any endpoint: no-op. With endpoints restored from disk but none touched this session: the active marker is B if present, else A (Clarifications).
- Two markers are nudged in quick succession such that both A and B are moved: each nudge always acts on whichever of the two was touched most recently, including by the nudge itself (Clarifications).
- `set_a`/`set_b`/`set_cue_n` at the 64-marker limit on an empty endpoint/slot: `invalid_state`/`marker_limit`, shown in Status; moving an existing endpoint/cue is never refused by the limit (006 FR-002). With no current track: `invalid_state`/`no_track`, shown in Status.
- The user sets a cue in a slot 1–8 that already holds **Section Loop's own** cue: it moves to the new position, name/colour kept. The slot holds a **host-owned or another plugin's** cue: `permission_denied`/`not_owner`; Status reads "Cue n belongs to the host — move or delete it in the Markers panel"; nothing changes (009 FR-018; Clarifications).
- `jump_cue_n` on a slot holding a cue of **any** owner: seeks to it (after the in-handler focus request); on an empty slot: silent no-op; under manual/first-request-wins without focus: `no_focus`, Status hint, no seek (Clarifications).
- The user activates `clear_markers` while the loop is armed: the plugin deletes A, B and its cues via `markers.delete`; deleting an endpoint of the armed region disarms it host-side (006 FR-006), so no `disarm_loop` and no focus is needed; transport focus, if held, is unaffected; host-owned or other plugins' markers on the same track are untouched (Clarifications).
- The user arms Section Loop's region with the **host's** `L`/list toggle (selecting its marker first makes it the host's current region, 006 FR-006): Section Loop receives `loop_armed` and shows its Loop toggle on; flipping it off later calls `request_focus()` + `disarm_loop()` per the ordinary rule (Clarifications).
- Focus leaves Section Loop for a non-fault reason (user "Take back"/"Give focus", auto-policy host action, first-request-wins track reset): the loop stays armed (010 FR-007), the Loop toggle stays on; the next flip re-requests focus inside the interaction.
- Section Loop is suspended (budget breach) rather than disabled: its panel shows the 011 FR-025 suspended placeholder (Restart/Disable), its overlay decoration clears, its actions grey, and — exactly as on disable — an armed loop releases, focus returns to host, and A/B/cue markers stay visible via the host's native rendering (010 FR-007; 011 FR-025). After Restart the plugin re-registers its panel, actions and overlays from `ready()` and rediscovers its region from `markers.list()`; the session-only active-marker pointer and any un-applied repeat value are lost.
- The host's `I`/`O`/`L` bindings and Section Loop's identical defaults have not yet been resolved by the user (fresh install): raw keypresses continue to operate the host's own 006 marker/loop editor and create a **host-owned** region; Section Loop's panel controls create and arm the plugin's **own** region, which coexists with it (Clarifications).
- The user flips "Snap to beat" or invokes `toggle_snap`: the toggle is immediately set back to off via `update_widget`, the action does nothing, the explanatory label stays; no snapping ever occurs in this slice (Clarifications).
- The user selects a row in Section Loop's marker list: the host seeks there as a user command; transport focus is unchanged under every policy (011 FR-002; 010 FR-002a).
- The user edits, renames, recolours, moves or deletes Section Loop's markers from the host UI: allowed, owner unchanged; Section Loop receives `marker_changed` (actor `host`) and re-lists — a deleted endpoint leaves its region incomplete (Loop toggle shows off after `loop_disarmed`), and a region whose last endpoint was deleted no longer exists, so the next Set A/B creates a fresh one (009 clarify entry; 006 FR-006).
- The track changes while a Section Loop loop is armed: the armed state does not persist across tracks (loop-region "armed" is session/track-scoped per DM-7), the new track's own A/B/cue markers (if any, previously saved for that track identity) are restored before `track_changed` reaches Section Loop, the plugin's overlays are cleared by the host (011 FR-016) and rebuilt by the plugin from `markers.list()`, and its panel/marker list/repeat slider reflect the new track's markers and region.

## Assumptions

- Section Loop ships enabled by default after first run, consistent with the source document's own note at J-2 step 2; first-run onboarding and the enable/disable mechanism themselves are 009's concern and unchanged here.
- The host's pre-existing `I`/`O`/`L` bindings (006) and Section Loop's identical default bindings are expected to collide on a fresh install; 011's already-ratified cross-tier conflict rule (host wins, user resolves) governs this without any change to that mechanism, and Section Loop's panel controls give the musician a fully working path regardless of whether the conflict has been resolved.
- "Nudge A/B earlier/later" (FR-13.1.2) is delivered as two actions operating on whichever marker was most recently touched ("the active marker"), matching J-2's own two-key (`[`/`]`) description rather than four separately-bound keys; the step is a fixed 10 ms because no plugin API reads the host's `[markers] nudge_step_ms`; explicit per-marker nudge mapping and host-step honouring are left to the MIDI wave.
- "A marker list with rename and color" (FR-13.1.3) is delivered as Section Loop's own read-only, seek-on-select marker list (the only contract 011's `marker list` widget supports) plus the host's own already-shipped Markers panel and waveform glyphs, which rename/recolor any marker regardless of owner; this reuses an existing universal capability rather than adding a new widget contract.
- The "Snap to beat" toggle and the declared `analysis.read` permission are inert scaffolding in this slice — the toggle always shows off (011 has no plugin-settable disabled state) beside an explanatory label, never calling any analysis API — reserved so the manifest's permission list will not need to change shape when a later wave implements beat snapping (explicitly out of scope here per FR-13.1.6 and this feature's Scope boundary).
- FR-13.1.1's permission list is read as the capabilities Section Loop *exercises*; `playback.observe` and `markers.read` (both Low risk) are added because the shipped API gates playhead position, `track_changed`, `markers.list()` and the loop/marker events behind them — the source's own J-2 sequence diagram already shows Section Loop receiving `track_changed` and restoring its markers.
- The three additive plugin-API changes (FR-017, v1.3) are the minimum needed for a plugin to drive an incomplete region and a repeat count — both host primitives (DM-7) — without reimplementing marker state in script (Constitution III); they follow 010's additive-minor precedent and require no change to any existing call, event or plugin.
- Section Loop operates only on its own single region per track and never on a host-owned one; the "fresh install" path (host `I`/`O` win the key conflict) therefore produces a host region the plugin's panel does not arm — the plugin's panel controls are the complete, always-working path (Status explains when no plugin region exists).
- Section Loop's overlay-drawn A/B/cue decoration (FR-13.1.4) is additive to, and never a substitute for, the host's own native marker rendering (FR-4.1.3); the latter is what keeps markers visible when the plugin is disabled or suspended.
- Cue-slot "hot cue" hold-to-play behavior (FR-5.3.2, SHOULD) is not part of this slice; only set/jump are implemented, matching the prompt's own action list. Cue jumps, like every plugin seek, need transport focus (010 FR-001) and use the same in-handler `request_focus()` pattern as `toggle_loop`.
